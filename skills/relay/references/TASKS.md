# Доски и задачи: постановка, выполнение и результат

Открывай при выборе доски, постановке и декомпозиции задач, изменении связей и критериев,
исполнении и передаче результата. Методика помогает подготовить работу к самостоятельному
исполнению и делегированию. Общий цикл и история — в [основной инструкции](../SKILL.md);
команды и доступные параметры выбирай через CLI.

## От требований к задачам

Прочитай нужные фичи, сценарии, FI/SI, документы и текущую работу. Сопоставь требуемый
результат с существующим состоянием; переиспользуй подходящие задачи, создай недостающие.
Фича сохраняет постоянную возможность, задача — конкретное изменение для её достижения.
Не превращай каждое предложение или найденный TODO в согласованное обязательство.

Неизвестное, которое мешает постановке, выясни у пользователя или выдели в исследование
с понятным выходом: установленные факты, варианты, открытые вопросы и основание решения.
Результатом исследования не может быть выдуманное согласие на реализацию.

## Полноценная постановка

Заголовок кратко называет работу. В полном Markdown сохрани достаточно для исполнения
без исходного чата; прикреплённые материалы раскрывают общие правила без копирования.

| Часть                    | Что должно быть понятно исполнителю                                                   |
| ------------------------ | ------------------------------------------------------------------------------------- |
| Цель и основания         | Зачем изменение, какой результат нужен, какие требования и решения его обосновывают   |
| Объём и границы          | Что сделать, затрагиваемая область, ограничения, взаимодействия и ожидаемый артефакт  |
| Доска и продуктовые цели | Где находится работа и за готовность какой фичи, сценария или реализации она отвечает |
| Критерии                 | Какие наблюдаемые условия подтвердят выполнение и каким способом их проверить         |
| Связи                    | Родитель, подзадачи, необходимые результаты других задач и тематические отношения     |
| Материалы                | Адреса требований, документов, контрактов и примеров, необходимых для работы          |

Внутренний план исполнителя может уточняться, но цель и границы не должны зависеть
от догадок. Постановку не заменяй итоговым отчётом: фактический результат сохраняется
в комментарии задачи и истории работы.

CLI позволяет создать задачу сразу с критериями, родителем, зависимостями и обычными
связями одной операцией. Когда адреса уже известны, используй этот путь по справке
`task create`, а не собирай каждое поле отдельной записью. Последующие изменения выполняй
предметными действиями по актуальной ревизии задачи.

## Доска и продуктовые цели

Проект создаёт две системные доски; каждое приложение получает собственную при создании:

| Доска            | Размещение работы                                                                    | Допустимые продуктовые цели   |
| ---------------- | ------------------------------------------------------------------------------------ | ----------------------------- |
| Продуктовая      | Общие, базовые и межприложенческие задачи; крупные родительские работы в роли эпиков | Общие фичи и сценарии         |
| Приложения       | Собственная работа конкретного приложения, включая техническую                       | Только FI/SI этого приложения |
| Инфраструктурная | Порученная инфраструктурная работа проекта                                           | Без продуктовых целей         |

«Эпик» — роль обычной родительской задачи, а не отдельный вид или флаг создания.
Продуктовый родитель может объединять подзадачи на досках разных приложений. Прикладную
работу размещай на доске её приложения; слово «техническая» само не делает её инфраструктурной.
Инфраструктурная доска действует, но не означает наличия отдельного готового управления стендами.

Самостоятельного создания и удаления произвольных досок нет. Свойства и каталог читаются
через `board`; имя прикладной доски связано с приложением, `board rename` меняет публичный
ключ, а не префикс задач. Показатели работы по доскам доступны через overview.

Одну задачу можно связать с несколькими реальными обязательствами, если результат нужен каждому.

Цель — участие задачи в расчёте готовности, а не просто тематическая метка. Выбор сценария
не добавляет отдельную цель-фичу. Доска определяет допустимые цели; не связывай прикладную
задачу с реализацией чужого приложения. Для технической работы без продуктовой цели
не создавай фиктивную фичу; при необходимости она становится зависимостью продуктовой задачи.

Прикреплённый документ задаёт материал для чтения, но не делает задачу выполненной.
Адрес задачи в Markdown не создаёт предметную связь. Цели, прикрепления и зависимости
сохраняй соответствующими операциями CLI и проверяй фактические отношения.
Переданный набор продуктовых целей заменяет прежний набор; отсутствие поля при update
сохраняет его. Пустой набор снимает цели, а не назначает задачу всему продукту.

## Декомпозиция и параллельная работа

Разделяй крупный результат до самостоятельных проверяемых задач. Отдельному исполнителю
должны быть понятны входные материалы, область ответственности, результат и приёмка.
Останавливай декомпозицию, когда дальнейшее дробление создаёт передачу контекста без
самостоятельной ценности; количество карточек и размер отдельной функции не являются целью.

Выделяй независимые области и согласуй интерфейсы между ними. Учитывай изменения общих
файлов, схем и ресурсов: одновременный запуск не делает работы независимыми. Укажи,
какой контракт можно использовать заранее и какой результат действительно блокирует
другую задачу. Включи работу по интеграции и сквозной проверке, а не только отдельные части.

Пример для согласованного сценария отправки заявки:

1. Если контракт взаимодействия ещё неизвестен, сначала задача его определить и согласовать.
2. По известному контракту — самостоятельные задачи Web и API с собственными FI/SI,
   границами и критериями. Они могут выполняться параллельно, если нет иных блокеров.
3. Задача интеграции и проверки сценария зависит от результатов обеих частей.
4. Общая родительская задача объединяет требуемый результат и все обязательные подзадачи.

Это пример принципа, а не обязательный набор приложений и задач для каждого проекта.

## Родительство, зависимости и блокеры

- **Подзадача** — обязательная часть результата родителя. Крупная родительская задача
  остаётся обычной задачей, отдельного вида epic нет. Завершение детей не закрывает
  родителя автоматически; его собственные критерии также должны быть проверены.
- **Зависимость** — необходимый результат другой задачи. Если B нужен результат A,
  B зависит от A. Родителю не нужна дублирующая зависимость от собственного ребёнка.
- **Обычная связь** — тематическая близость без блокировки. Не выражай ею обязательный порядок.

Связи возможны между досками одного проекта; не создавай циклов. Блокировка вычисляется,
отдельной колонки для неё нет. При блокере объясни причину и следующий шаг; подготовительная
работа может продолжаться, но невыполненное обязательство мешает завершению.
Отмена ребёнка не равна его выполнению и не снимает обязательство автоматически.
Перед добавлением невыполненного ребёнка к готовому родителю верни родителя из done.
Добавление невыполненной зависимости к готовой задаче также требует её возврата в работу.

## Критерии приёмки

Сохраняй проверяемые условия отдельными критериями задачи, а не только списком внутри
описания. Для каждого сформулируй наблюдаемый результат и нужные условия проверки.
Покрывай согласованный успешный путь и существенные ошибки; не добавляй выдуманные требования.

Например, вместо «форма работает» при соответствующем требовании: «После подтверждённого
сохранения заявки показан её номер; при отказе API введённые данные остаются, доступен повтор».
Отдельные независимые результаты лучше выражать отдельными критериями.

Отмечай критерий после фактической проверки, с основаниями в комментарии или материале
работы. Изменение текста критерия снимает прежнюю отметку. Все отметки сами не закрывают
задачу: для фактического выполнения также нужны её завершение, дети и зависимости.
Критерий принадлежит задаче: изменение защищается ревизией задачи. В done критерии
не редактируются — сначала верни задачу в работу. Критерии можно создать сразу вместе
с задачей либо добавить позднее; методы list/get позволяют отдельно прочитать полные условия.

## Готовность к передаче

Проверь полноту постановки, материалов, целей и отношений. Исполнитель должен понять,
что сделать, от чего зависит начало или завершение и как передать результат. Сформулированную
работу можно поставить в ready; реальную готовность к началу сверяй с блокерами.
Передавая задачу субагенту, укажи её адрес, область ответственности и критерии, а историю
дочерней работы веди по обязательному протоколу основного скилла.

## Как исполнителю выполнить и передать задачу

1. Прочитай полную постановку, критерии, документы, продуктовые цели и актуальные блокеры.
   Уточни недостающие основания до изменений; отметь, если реальный проект расходится с записью.
2. Зарегистрируй участие и намерение в истории. При фактическом начале переведи задачу
   в in-progress. Сохраняй промежуточные результаты на смысловых рубежах.
3. Выполни работу в границах. Новый объём согласуй; принятые требования и решения
   актуализируй у владельца знания. Проверяй условия приёмки и нужный пользовательский путь.
4. **Опубликуй содержательный результат в комментарии задачи от своего имени.** Сообщи,
   что изменилось и где, какие критерии подтверждены, что проверялось фактически,
   какие ограничения остались и что нужно следующему участнику.
5. Отметь подтверждённые критерии. Если требуется приёмка другим участником — передай
   в review; если завершение поручено и обязательства выполнены — явно переведи в done.
   Заверши свою историю с результатом, сохрани адреса сессии и ключевых точек.

Каркас отчёта; каждый раздел заполняй фактами, пустое не добавляй:

```markdown
## Результат

Как достигнута цель; изменённые части и доступные адреса артефактов.

## Проверки и критерии

Какие команды или сценарии выполнены и с каким исходом.
Какие критерии подтверждены; что не проверялось и почему.

## Ограничения и продолжение

Остаток, блокеры, необходимые действия проверяющего или следующего исполнителя.

## Материалы

Адреса документов, изменений и сессии с подробными checkpoints.
```

Комментарий должен быть понятен без полного просмотра истории. Checkpoints содержат ход
работы и промежуточные материалы, комментарий задачи — результат по её постановке,
документы — устойчивые знания. Не заменяй описание задачи отчётом и не копируй всю ленту
checkpoints в комментарий. Ссылка на сессию полезна вместе с кратким содержательным итогом.

`task comment add` сохраняет автора, роль и полный Markdown; для исполнителя выбирай роль
worker, для координирующего агента — orchestrator. Публикация не требует ревизии задачи
и не меняет её колонку, критерии или готовность. Сообщения можно читать, но нельзя изменить
или удалить: исправление публикуется новым сообщением с пояснением. После потери ответа
сначала перечитай обсуждение; повтор с тем же request-id может создать ещё один комментарий.

## Состояния и фактическое выполнение

Колонки фиксированы: inbox — входящая работа, ready — сформулирована к исполнению,
in-progress — выполняется, review — проверяется, done — завершена, cancelled — отменена.
Готовность к началу означает ready без блокеров; невыполненные критерии не запрещают начало.

Фактическое выполнение требует done, всех критериев и выполненных детей/зависимостей
транзитивно. Повторное открытие обязательства может снять готовность, не перемещая зависимую
задачу из done. Отмена не считается успехом. Отметки критериев, результат комментария
и завершение сессии не закрывают задачу автоматически.

## Перенос, удаление и навигация

Перемещение между колонками, изменение порядка и перенос на другую доску доступны через
`task move`. Перенос сохраняет постоянный ID, связи и участие в плане, но меняет ключ;
старый ключ остаётся алиасом. Несовместимые продуктовые цели нужно снять явно до переноса.

Удаление — отдельное действие с `delete-preview`; оно не равно отмене. Дети удаляемой
родительской задачи не удаляются автоматически, их родительская связь снимается. Зависимые
задачи и документы могут потерять ссылки. Участие в плане может запретить удаление;
закрытый план не позволяет снять такую ссылку публичными операциями.

Точки входа: `board`, `task`, `task parent`, `task dependency`, `task criterion`,
`task comment`; полные связи и дети — `task links/children`, причины — `task progress`.
Списки комментариев и критериев компактные, полное содержание читай их адресным get.
