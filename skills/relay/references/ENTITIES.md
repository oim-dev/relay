# Движок основных сущностей

Единый контракт Core, REST, CLI, MCP и Web для одиннадцати видов. Определения задаются в коде,
переносимые схемы находятся в `@relay/contracts/entities`. Все публичные ссылки принимают
ключ либо ID; основное обозначение для человека и агента — ключ.

В [едином формате](STORAGE.md) `resolve` использует адресный индекс и индекс карточек.
ID, алиасы и несколько кандидатов сохраняются независимо от физической принадлежности.

## Виды и идентичность

| Вид            | Назначение                                                | Начальный ключ                          |
| -------------- | --------------------------------------------------------- | --------------------------------------- |
| project        | Настройки выбранного проекта                              | PROJECT                                 |
| product        | Паспорт продукта                                          | PRODUCT                                 |
| feature        | Устойчивая возможность                                    | FEATURE-N                               |
| scenario       | Наблюдаемое поведение внутри фичи                         | SCENARIO-N                              |
| application    | Программная часть продукта                                | Префикс приложения, например WEB        |
| implementation | Вклад приложения в фичу либо сценарий                     | WEB-FI-N / WEB-SI-N                     |
| board          | Организация задач продукта, приложения или инфраструктуры | BOARD-PRODUCT / BOARD-WEB / BOARD-INFRA |
| task           | Конкретная работа                                         | Префикс доски и номер, например WEB-24  |
| document       | Самостоятельный Markdown-материал                         | DOC-N                                   |
| work-plan      | План работ с целью и этапами                              | PLN-N                                   |
| release        | Самостоятельный выпуск выбранных планов                   | REL-N                                   |

Вид (`kind`) определяет контракт; ID — постоянную идентичность; `key` — текущий публичный
адрес. Прежние ключи остаются алиасами и резервируются. Резолвер ищет назначенный адрес
в выбранном проекте, не определяет вид по префиксу. Для уточнения допустим `kind:ID`.
Неоднозначность требует явного вида/ID и не разрешается выбором первой записи.

Смена WEB-24 на TASK-WEB-23 сохраняет ID, содержание, зависимости и продуктовые цели.
Сохранённые ссылки используют ID. Префикс нумерации доски независим от текущего ключа задачи.
Доски создаются при init и вместе с приложением; создание проекта принадлежит регистрации/init.
Продукт адресуем до заполнения паспорта: revision 0, status=uninitialized и пустое содержание.
Явное создание паспорта сохраняет тот же ID; демонстрационные требования не подмешиваются.

## Чтение

Префикс REST — `/api/v1/projects/:project/entities`; в local также `/api/v1/entities`.

| Метод и путь              | Результат                                                                       |
| ------------------------- | ------------------------------------------------------------------------------- |
| GET /types                | Одиннадцать определений с назначением, действиями, фильтрами и политикой ключей |
| GET /type?kind=task       | Определение и JSON Schema данных, создания и изменения                          |
| GET /                     | Страница кратких карточек                                                       |
| GET /get?ref=WEB-24       | Полные типизированные данные одной записи                                       |
| GET /resolve?ref=WEB-24   | Постоянный адрес и краткая карточка                                             |
| GET /keys?ref=WEB-24      | Текущий и прежние ключи                                                         |
| GET /key-spaces?kind=task | Актуальные владельцы нумерации, префиксы и форматы                              |

Карточка: `ref: {kind,id}`, `key`, `title`, `summary`, `revision`, `status`, `active`.
`summary` — обычный многострочный текст. Полная запись добавляет `data` с дискриминатором
kind и `references` — краткие карточки прямых предметных ссылок с актуальными ключами.
Все Markdown-поля данных передаются строками. Технические квитанции не подмешиваются
в полное содержание. Общий автоматический audit и `/entities/history` удалены из контракта.
Комментарии задачи и предметные сведения планирования принадлежат своим владельцам,
а не универсальной сущности истории.

Списки: offset от 0, limit 1–100 (по умолчанию 40), version первой страницы.
Ответ: items/total/nextOffset/version. `nextOffset: null` означает конец выбранной области.
Изменение снимка возвращает ENTITIES_CHANGED; продолжение начинается заново.
Это постраничный ответ, а не обещание адресного физического чтения всего каталога:
нынешние адаптеры собирают согласованный снимок предметных записей.

Общие условия поиска: kind, q, refs (до 100 ключей/ID), sort=key|title. Поиск учитывает
ID, текущие/прежние ключи, название и краткое описание; полный Markdown читается через get.

| Вид            | Дополнительные фильтры                                              |
| -------------- | ------------------------------------------------------------------- |
| feature        | status                                                              |
| scenario       | feature, status                                                     |
| implementation | application, feature, scenario, target, status, active (true/false) |
| board          | application                                                         |
| task           | board, application, target, parent, status                          |
| document       | target                                                              |

Ссылочные фильтры принимают ключи или ID. target проверяет явную предметную связь;
транзитивное окружение читается через граф. При заданном kind неподдерживаемый фильтр
отклоняется. Без kind можно искать подходящие записи разных видов.

## Запись

`work-plan` и `release` имеют `createSchema/updateSchema=null` в общем
движке: их жизненный цикл обслуживают [планы](PLANNING.md) и [релизы](RELEASES.md).
Универсальная запись и rename не обходят эти правила. Прикрепления документов через
`relations` поддерживают все одиннадцать видов. Этап — запись внутри плана с ID,
не самостоятельная сущность, ключ или цель прикрепления документа.

Каждая запись принимает requestId и необязательного actor. Изменение требует ifRevision.
requestId служит корреляции, не гарантирует дедупликацию или исходный ответ. Core
разрешает внешние ссылки под той же блокировкой, что проверка и предметная запись.

| Метод и путь    | Тело                                                                               |
| --------------- | ---------------------------------------------------------------------------------- |
| POST /          | data с kind и типизированными полями, requestId, actor?                            |
| POST /update    | ref, changes с kind и выбранными изменяемыми полями, ifRevision, requestId, actor? |
| POST /rename    | ref, key, ifRevision, requestId, actor?                                            |
| POST /move-task | ref, column, board?, before?, ifRevision, requestId, actor?                        |
| POST /link-task | ref, target, relation, remove?, ifRevision, requestId, actor?                      |

Квитанция: ref/key/revision/requestId/action. Операции обычного содержания не принимают
вычисляемую готовность, ID или произвольные служебные поля. Пропуск поля при update
сохраняет его значение. Пустой targets явно очищает набор.

- Создание задачи: board, title?, description?, targets?, dependencies?, related?, parent?,
  column?. Все ссылки — ключи/ID. Задача, её цели, зависимости и родитель сохраняются атомарно.
- Создание реализации: application, target (фича/сценарий), title, description, status?.
  Сценарный вклад требует существующего активного общего вклада фичи. Добавление не
  переподтверждает соседние реализации. После потери ответа сначала перечитайте состояние.
- Документ: name, summary, body, documentKind, targets?. Цели — продуктовые области.
  Произвольный дополнительный контекст связывается через [граф](GRAPH.md).
- Изменение project меняет имя выбранного проекта. Slug меняется существующей операцией
  настроек, проверяющей уникальность адреса в реестре. Доска меняет читаемый ключ через rename.
- Зависимость задач проверяет циклы и блокирует завершение; `related` — контекст,
  `parent` — декомпозиция. Произвольное графовое ребро не заменяет предметную операцию.

## CLI и MCP

```bash
relay-cli entities types
relay-cli entities type task
relay-cli entities list --kind task --board BOARD-WEB --limit 20
relay-cli entities get WEB-24
relay-cli graph context WEB-24 --depth 4 --format json
relay-cli --actor agent entities create task --board BOARD-WEB \
  --title 'Сделать форму' --targets WEB-SI-8 --dependencies API-15 \
  --description $'## Цель\n\nРеализовать согласованный сценарий.\n\n## Проверка\n\nПроверить основной поток и ошибки.' \
  --request-id form-1
relay-cli --actor agent entities rename WEB-24 TASK-WEB-23 --if-revision 1 --request-id rename-1
```

Ключи и ревизии примеров заменяются реально прочитанными значениями. Продолжение CLI
использует --snapshot-version, машинный режим — --format json. Все команды и поля:
[CLI](CLI-COMMANDS.md), [MCP](MCP.md). MCP предоставляет предметные entity_*_create/update с полями
верхнего уровня и entity_context для обхода. Отдельный вызов resolve перед записью не нужен.

## Хранение, совместимость и ошибки

Новые базы используют [единое ID-хранилище](STORAGE.md): записи находятся в
`entities/<коллекция>/<id>.json`, квитанции и результаты команд не сохраняются. Markdown
кодируется массивами строк; физическая версия базы и версия предметных данных различаются.
Прежние пути продукта, досок и задач являются источниками явного
`storage migrate`. Чтение и reindex не переключают формат. Операции планирования требуют единого формата; для прежних записей
самих планов/релизов принят отдельный [сброс без миграции](STORAGE.md#планы-и-релизы).
Это решение не меняет совместимость общих задач и документов.

Первое чтение продукта закрепляет недостающие ключи, включая PRODUCT и DOC-N, существующим
возобновляемым механизмом продукта. Это техническая операция без изменения ID, Markdown,
ревизий. Переименование — отдельная пользовательская ревизия.
Общий журнал событий не сохраняется и не переносится при миграции; полезные предметные
данные и комментарии сохраняются, квитанции удаляются по [контракту хранения](STORAGE.md).

Ошибки: ENTITY_NOT_FOUND (404), ENTITY_KIND_MISMATCH, AMBIGUOUS_ENTITY_REFERENCE,
ENTITY_KEY_CONFLICT, ENTITIES_CHANGED, REVISION_CONFLICT (409);
UNSUPPORTED_ENTITY_FILTER, UNSUPPORTED_ENTITY_ACTION и VALIDATION_ERROR (400).
Бизнес-отказы сохраняют коды владельца, например TASK_BLOCKED и DEPENDENCY_CYCLE.
