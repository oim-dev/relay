# Стандарт продуктовых материалов

Полное описание — содержательный Markdown для человека, который не видел исходный чат.
Переносы и разделы обязательны для сложных требований. Короткое уточнение может оставаться
коротким; не добавляй пустые разделы ради шаблона.

## Структура по назначению

| Сущность   | Содержание полного описания                                                             |
| ---------- | --------------------------------------------------------------------------------------- |
| Паспорт    | Назначение, пользователи, ценность, границы, ограничения, источники                     |
| Фича       | Цель, границы, поведение и правила, ошибки/ограничения, критерии приёмки                |
| Сценарий   | Участник и цель, предусловия, основной поток, альтернативы/ошибки, результат и проверка |
| Приложение | Ответственность, границы, взаимодействия, ограничения                                   |
| Реализация | Обязательство приложения, поведение, входы/выходы, ошибки, способ проверки              |
| Задача     | Цель, контекст, объём, шаги при необходимости, критерии, проверка                       |
| Решение    | Контекст, выбранное решение, причины, последствия, нерешённые вопросы                   |
| Инструкция | Для кого, предусловия, последовательность, ожидаемый результат, восстановление          |

В публичных операциях ссылки передаются читаемыми ключами или ID; Core сохраняет связи
по постоянным ID. Ключ и название в тексте помогают человеку и агенту ориентироваться.
Не дублируй целую фичу в каждом сценарии: опиши поведение сценария и используй связь.

## Пример сценария

```markdown
## Участник и цель

Владелец публикует объявление об аренде техники.

## Предусловия

- Владелец авторизован.
- Создан черновик объявления.

## Основной поток

1. Владелец указывает условия аренды и комплектность.
2. Добавляет фотографии.
3. Подтверждает публикацию.
4. Система проверяет сведения и показывает объявление в каталоге.

## Ошибки и ограничения

- Неполный черновик остаётся неопубликованным; система перечисляет недостающие сведения.
- Другой пользователь не может редактировать объявление.

## Результат и критерии приёмки

- Полное объявление доступно в каталоге.
- После отказа введённые сведения сохранены, ошибки можно исправить.
```

Плохо: «Пользователь создаёт объявление, всё проверяется, ошибки обработаны».
Плохо: перенести тот же абзац под один заголовок и считать содержание завершённым.
Хорошо: разделить наблюдаемые правила и указать проверяемые исходы без выдуманных деталей.

## Цикл автора

1. Прочитать исходные требования и существующие записи, исключить дублирование.
2. Сначала сформулировать содержание и связи, затем выбрать инструмент записи.
3. Обозначить источники, предположения и вопросы; не выдавать их за принятые решения.
4. Перед серией операций кратко сообщить, какие сущности сохраняются и зачем.
5. Сохранить через предметные CLI/MCP-команды с автором и requestId корреляции.
   При потере ответа сначала прочитать текущее состояние, не повторять мутацию безусловно.
6. Прочитать результат: структура Markdown, связи, полнота и ревизия должны совпадать с замыслом.
7. Сообщить фактический результат и оставшиеся вопросы, а не перечень вызовов инструмента.

`product lint` / `product_lint` дают структурные предупреждения, не исправляют текст
автоматически и не подтверждают бизнес-полноту. `product validate` проверяет целостность.
Приведение существующих описаний к этому стандарту — отдельное содержательное изменение;
оно может сделать прежние подтверждения реализации неактуальными.
