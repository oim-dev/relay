# Терминальное представление Relay CLI

Этот документ помогает читать человеческий вывод и настраивать его для терминала,
pipe и CI. Агент использует то же читаемое представление, которое видит пользователь.
Точный синтаксис команд определён в [справочнике CLI](CLI.md). Документация описывает
текущее дерево исходников, а не обещает совпадение с ранее опубликованным пакетом.

## Выбор формата

```bash
npx @oim-dev/relay-cli task get PRODUCT-1
npx @oim-dev/relay-cli task list \
  --format text
```

Если формат не передан, используется `text`; настройка format в конфигурации
игнорируется. Pipe сам по себе не переключает формат. JSON включается только явно
через `--format json`.

В text предметные команды показывают карточки, компактные списки, содержание и
подсказки следующего действия. JSON возвращает неизменённые машинные поля:
человеческое оформление не меняет DTO, UUID/ID, requestId или details ошибки.
Изменение ширины не меняет данные JSON. Help и версия всегда текстовые.
Команда возвращает карточку, страницу списка, квитанцию действия, прогресс или ошибку.
Квитанция сообщает результат записи, а не заменяет чтение сохранённого содержания.

## Текст без цвета и ширина

CLI — прежде всего инструмент агента: текст всегда выводится без цветного ANSI,
параметр `--color` удалён. TTY, `NO_COLOR`, `FORCE_COLOR` и `TERM` не включают
ANSI-оформление. Это относится также к help, ошибкам и подсказкам. JSON остаётся
без ANSI-оформления. Смысл результата передаётся текстом и структурой, а не цветом.

Ширина берётся из `stdout.columns`, при его отсутствии — из `COLUMNS`.
Корректное положительное целое ограничивается диапазоном 24–160; иначе используется
100 колонок. `COLUMNS` не переопределяет фактическую ширину TTY, если она известна.

```bash
COLUMNS=40 npx @oim-dev/relay-cli task list | less
npx @oim-dev/relay-cli task get PRODUCT-1 | less
```

На узкой ширине представление может переходить от таблиц к карточкам. Выравнивание
учитывает Unicode: число байтов, длина JS-строки и экранная ширина не равны.
Заголовки, summary и обычные метаданные могут переноситься; не используйте пробельные
позиции таблицы как API. Полный Markdown и команды в подсказках не получают жёстких
переносов по ширине. Визуальный перенос самим терминалом не меняет строку ответа.

## Карточки, списки и Markdown

Карточка начинается с ключа и названия в естественном регистре: пользовательский
title не превращается в прописные буквы. Затем идут выровненные по меткам значимые
поля: состояние, ревизия, автор или показатели предметного состава. Пустые
необязательные поля и секции пропускаются, а числовой `0` сохраняется. Отсутствующая
обязательная часть может поясняться явно: например, незаданная цель или пустой состав
плана — полезная причина неготовности, а не пустое поле для скрытия.

Список показывает название выборки, применённые фильтры, ключ/ID и название каждой
записи с краткими предметными деталями. Полные описания каждой записи туда не
копируются: найдите ключ и вызовите адресный `get`. Полное описание в `get` не
усекается. Большие вложенные коллекции читаются отдельными списками с продолжением,
а не бесконечной карточкой. Пустая страница обозначается явно, но не означает ошибку
отсутствующей записи или отказ чтения базы.

Квитанция называет выполненное действие, его адрес и значимый результат, например
новую ревизию, и предлагает перечитать запись. UUID/ID и requestId не дублируются
в каждой карточке или квитанции ради полноты DTO: в text они нужны только для
адресации действия или диагностики. Например, ID этапа нужен вместе с ключом плана;
requestId остаётся корреляцией, а не гарантией безопасного повтора. Подробности ошибки
в text выбираются по смыслу диагностики; полные машинные поля доступны в JSON.

Полное содержание выводится как буквальный Markdown: заголовки, списки, цитаты,
inline-код, ссылки и fenced code сохраняют свои маркеры. Сохраняются в том числе
повторные пустые строки, начальные и конечные пустые строки непустого поля, отступы
и табуляция. Длинные строки Markdown и кода не переносятся принудительно и не
усекаются. Это не HTML-браузер, не исполнение кода и не лексическая подсветка.

Отображение применяет безопасный текст: пользовательские управляющие
последовательности не должны исполняться терминалом. Не считайте text побайтовой
копией исходного поля: служебные заголовки, разделители и обезвреживание управляющих
символов принадлежат представлению. Это не разрешение нормализовать Markdown.
В обычной работе читайте полный текст карточки; побайтовую
проверку содержимого выполняют отдельно при отладке CLI.

## Страницы и полнота

Списки используют `--limit` и `--cursor`. Единственный общий footer из `Result.page`
показывает число выданных элементов, общий размер выборки, если он известен, и конец
либо продолжение; для live отдельно предупреждает о возможном изменении данных
между страницами. Предметные секции не добавляют собственные footer продолжения.
Копируйте предложенную команду целиком: она сохраняет команду, ref, фильтры,
выбранные config/project/server/local. Не переносите курсор в другой проект,
транспорт, команду или выборку и не редактируйте его вручную.

В JSON тот же `Result.page` становится `meta.page`: `count`, необязательный `total`, `limit`,
`nextCursor`, `nextCommand`, `consistency`. `count` — число элементов этой страницы,
а не всего списка; отсутствие `total` не означает ноль. Продолжение определяется
курсором, а не только наличием элементов: пустая страница может иметь продолжение.
Например, `Показано: 0 из 5 подходящих записей` вместе с `Есть продолжение` требует
следующего запроса, а не вывода о пустом составе. `limit` задаёт размер страницы,
но не доказывает ни общий размер, ни полноту ответа.

- `snapshot`: offset-продолжение сохраняет исходную версию и проверяет неизменность
  текущего состояния. Это guard, не доступ к историческому снимку. При конфликте
  начните чтение с первой страницы; CLI не подменяет версию свежей.
- `live`: данные между страницами могут измениться. Курсор не превращает такой
  backend в снимок; перед записью перечитайте целевую карточку.

Workspace project list читает каталог целиком и проверяет его отпечаток на клиенте,
не хранит серверный snapshot. CLI-курсор ленты комментариев сохраняет исходный
native token backend вместе с подключением, ref, фильтрами и размером страницы.
Копируйте meta.page.nextCursor/nextCommand, а не внутренний data.nextCursor:
сырой backend token сохранён для совместимости DTO и напрямую CLI не принимается.
NextCommand может не повторять limit/фильтры — их восстанавливает CLI-wrapper.
У progress и inspect graph list limit действует отдельно на вложенные коллекции,
а count/total суммируют их элементы, не уникальные сущности.

Обзорная сводка `product overview` содержит краткие подборки до пяти элементов.
Их заголовок сообщает полное число: «все N» либо «показано N из M» с отдельной
командой полного чтения. Это не страница и не footer продолжения: общий footer
относится только к карте продуктовых записей, а итоги сводки от `--limit` не зависят.
Полный список показателя работы читается режимом `product overview --metric`: у него
собственный footer и native-курсор, восстанавливающий метрику и блокер.

CLI не ограничивает вывод байтовым бюджетом: параметр `--max-bytes` удалён.
Это не отменяет ограничения ввода, Core, HTTP или MCP. Если ошибку размера вернул
Core или транспорт, следуйте контракту этой операции: уменьшите выборку либо
прочитайте отдельные записи, но не считайте частичный результат полным контекстом.

```bash
npx @oim-dev/relay-cli task list \
  --limit 10
npx @oim-dev/relay-cli task list \
  --limit 10 \
  --format json
```

## Планирование и прогресс

В плане сохранённое состояние «Завершён» и текущие показатели выполнения — разные
факты. После повторного открытия задачи состояние плана сохраняется, хотя
`plan progress` может показывать «Не выполнено» и расхождение с завершением.
Аналогично «Выпущен», автор и дата выпуска релиза не исчезают при потере текущей
готовности. Состав читается из актуальных планов, а не исторического снимка выпуска.
Предметные основания — [планы](../domain/PLANNING.md)
и [релизы](../domain/RELEASES.md).

`plan stage get` показывает полное содержание этапа: краткое описание, Markdown
результата и условий завершения, ID этапа, ревизию плана и число задач в составе.
За актуальными задачами переходите в предложенную `plan stage task list` и читайте
все страницы. JSON карточки сохраняет явные `taskIds`; text не заменяет список задач
перечислением технических ID. Текст условий завершения сам не исполняется как тест.

Прогресс доступен для восьми видов: задачи, реализации, сценария, фичи, приложения,
продукта, плана и релиза. Он разделяет полный предметный итог и видимую часть каждого
вложенного списка, включая причины. Надпись «показано 1 из 3» описывает страницу,
а не долю выполнения. Отсутствие причин на странице не доказывает готовности.
`limit` применяется **к каждому списку отдельно**; общий `count` суммирует видимые
элементы и может превышать `limit`. `total` здесь также сумма размеров списков,
а не уникальных задач. Например, три списка по три элемента дают `count=9` при
`limit=3`. Готовность и уникальные предметные счётчики не пересчитываются по этим
девяти строкам; их смысл задан в [контракте прогресса](../domain/PROGRESS.md).

Например, у завершённого плана после повторного открытия его задачи можно увидеть
следующие строки (это фрагмент ответа, без списков и команды продолжения):

```text
Уникальные задачи состава: 0/1

Состояние: Завершён
Можно начать: нет
Можно завершить: нет
Расхождение с завершением: есть
```

При `limit=1` тот же ответ может содержать одну задачу, один этап и одну из двух
причин: общий footer — `Показано: 3 из 4 подходящих записей` и `Есть продолжение`.
Это не противоречит лимиту и не означает три уникальные задачи.

## Копируемые подсказки

Готовая подсказка адресного чтения, исправления ошибки или продолжения — одна
физическая строка с `npx @oim-dev/relay-cli`. Она сохраняет фактическое подключение:
local и путь выбранного конфига либо сервер и выбранный проект, а не только явно
написанные пользователем флаги. Значения с пробелами и кавычками экранируются;
перевод строки внутри аргумента не превращается в разрыв команды. Копируйте всю
строку и учитывайте указанную оболочку: ANSI-C quoting `$'…'` для таких аргументов
поддерживается Bash/Zsh, но не каждой POSIX-оболочкой.

Не путайте готовую runtime-подсказку с авторским примером help или документации.
Для авторских примеров [COMMAND_STYLE.md](COMMAND_STYLE.md) задаёт многострочное
оформление именованных опций. Эти правила не требуют разбивать готовую подсказку
или opaque cursor на строки.

## Pipe и ошибки

Штатный результат и штатная ошибка идут в stdout; stderr штатного вызова чист.
Ошибка имеет код и понятное сообщение, в text — также визуальную отметку.
Проверяйте код завершения и сообщение результата, а не наличие слова «ошибка» в пользовательском тексте.
Закрытие pipe получателем (`EPIPE`) считается штатным и даёт код 0.

Help группы не требует открытия проекта. Ошибка синтаксиса указывает help команды,
в которой возникла проблема. Потеря ответа после записи не доказывает отсутствие
изменения: сначала перечитайте состояние, не повторяйте вслепую. Скрытых повторов нет.

## Где сопровождается представление

Для разработчика: `src/terminal.ts` вычисляет среду, `src/presentation/` содержит
предметные рендереры. Общий `src/presentation/common.ts` задаёт `cardText`, `listText`
и `receiptText`: единый каркас, но не универсальный обход DTO. Поля и секции выбирает
предметный владелец. `src/presentation/markdown.ts` сохраняет Markdown,
`src/queries/result.ts` сериализует конверт, `src/output.ts` выводит ответ.
Общие сведения `Result.page` должны оформляться централизованно, а не отдельным
footer каждого предметного рендерера.
Готовые команды формируются через `commandInvocation` в `src/command-kit.ts`;
пагинация использует тот же фактический контекст подключения.
Подробности проверки и добавления команды — в [EXTENDING.md](https://github.com/oim-dev/relay/blob/main/apps/cli/docs/EXTENDING.md).
Пути исходников относятся к checkout, а не обещают наличие TypeScript в npm-архиве.
