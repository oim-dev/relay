# Краткое руководство агента по Relay CLI

Relay — рабочая память проекта: требования, документы, задачи и их связи помогают
тебе и человеку продолжать работу с общим пониманием цели и результата. CLI читает
и изменяет эту память; он не выполняет за тебя разработку и проверку продукта.
Запускай пользовательские команды только через `npx @oim-dev/relay-cli`.
Этой страницы достаточно для старта; остальные справочники открывай по задаче.

## Сначала выбери подключение

До записи убедись, что работаешь с нужным **существующим** проектом:

```bash
npx @oim-dev/relay-cli project get
npx @oim-dev/relay-cli config get
```

Сверь имя, идентичность проекта и конфигурацию с поручением. Конфиг ищется вверх
от рабочего каталога; для известного нестандартного пути добавь `--config`.
В workspace для предметных команд явно укажи `--project` с известным селектором;
сохраняй этот выбор во всех следующих чтениях и записях. Не угадывай проект по названию.
Не добавляй `--local` или параметры сервера без необходимости и не переключайся
на локальную базу после HTTP-ошибки. Ошибка подключения не разрешает запускать `init`.
Если проект ещё не подготовлен или нужен сервер, следуй маршруту настройки скилла
или руководству первого запуска из [раздела подключения](CLI.md#вызов-и-подключение).

## Найди сущность, затем действие

Ориентир: `сущность → list/get/create/update/progress`. `list` помогает найти адрес,
`get` — прочитать полное содержание, `create/update` — сохранить изменение,
`progress` — понять текущую готовность и причины. Не каждый вид поддерживает всё.
`project` и `product` — одиночные записи выбранного проекта: `project get`,
`product get` и `product progress` вызываются без ключа записи.

- `feature`, `scenario` — требования.
- `application` — приложения; `implementation` — реализация фичи или сценария в приложении.
- `document` — знания, решения и внешние ссылки; `document section` — разделы библиотеки,
  `document facets` — счётчики каталога, `document materials` — материалы сущности,
  `document bulk` — массовые изменения (exit 1 при частичном отказе).
- `board`, `task` — доски и работа; `task criterion`, `task comment` — приёмка и обсуждение.
- `task parent`, `task dependency` — декомпозиция и обязательные зависимости.
- `plan`, `plan stage`, `plan stage task`, `release` — организация объёма и выпуска.
- `search`, `inspect` — поиск и адресная инспекция; `config`, `workspace project`
  — подключение и реестр, `storage` — отдельное обслуживание, не обычная работа с задачей.

## Пиши команды читаемо: пять правил

1. На первой строке оставляй запуск, путь действия и позиционные аргументы по порядку.
2. Каждый флаг со значением пиши на следующей строке с двумя пробелами отступа.
   Продолжай строку через `\` **вне кавычек**, без пробелов после него; последняя — без `\`.
3. Короткие команды без флагов и вызовы `--help` оставляй одной строкой.
4. Используй читаемые ключи, предметные действия и флаги вместо JSON-ввода
   или прямой записи диагностического графа. Глобальные флаги ставь после действия.
5. Читай обычный текстовый ответ по умолчанию: `--format text` не нужен.
   Добавляй `--format json` только для необходимого машинного разбора.

Примеры рассчитаны на Bash/POSIX shell. Сохраняй настоящие переводы строк, пустые
строки и значимые пробелы Markdown внутри кавычек; не добавляй туда отступы и `\`
ради оформления команды. Для literal-текста предпочитай одинарные кавычки.
При необходимости используй пару `--field` / `--field-file <path|->`, где `field` —
имя поддержанного поля, например `description`, а `-` — stdin. Выбирай один источник
поля и не более одного потребителя stdin. Файл создавать необязательно.
Сложные кавычки и heredoc уточняй адресно в [стиле вызовов](COMMAND_STYLE.md).

## Минимальный рабочий цикл

Полные описания всех сущностей, цели и результаты пиши структурированным Markdown,
а не краткой аннотацией. До первого заполнения прочитай
[правила содержания и примеры](../guides/CONTENT.md)
для нужного вида: фича раскрывает поведение, сценарий — путь и ошибки, FI/SI — конкретные
обязательства приложения, задача — изменение и проверку. `summary` остаётся обычным
кратким текстом. Сохраняй известные требования, неизвестное уточняй или обозначай вопросом.

1. Найди записи через `search` или фильтрованный `list`; до создания проверь дубликаты.
2. Прочитай выбранную запись через `get`, её основания и нужные критерии/связи.
   Возьми реальные ключи, ID и ревизию из ответа, не придумывай их.
3. Выполни только порученную мутацию: задай автора через `--actor` или `RELAY_ACTOR`,
   для изменения передай прочитанную ревизию владельца через `--if-revision`.
   Создание новой записи не требует её ревизии; точные условия задаёт действие.
4. Перечитай сохранённое содержание и затронутые отношения в том же проекте.
   Сравни с намерением и проверь достаточность для работы без чата: квитанция записи
   не подтверждает полноту описания. До постановки задач устрани существенные пробелы требований.

Например, найди задачу по тексту, затем открой выбранный ключ через `task get`:

```bash
npx @oim-dev/relay-cli task list \
  --q 'форма' \
  --limit 20
```

Для `task create` выбирай существующую доску из `board list`/`board get`.
Ключи `BOARD-WEB`, `WEB-10`, `WEB-11`, автор `agent` и ревизия `3` иллюстративны:
**до исполнения замени их реальными адресами, автором и прочитанной ревизией**.
Создание подзадачи для родительской задачи `WEB-10` с одним критерием
(одинаковая метка `saved` связывает поля):

```bash
npx @oim-dev/relay-cli task create \
  --board BOARD-WEB \
  --parent WEB-10 \
  --title 'Проверить сохранение формы' \
  --criterion-title 'saved=Значения сохраняются' \
  --criterion-description 'saved=Открой форму повторно и сравни значения.' \
  --actor agent
```

Родитель требует выполнения ребёнка; дублировать это зависимостью не нужно.
Ниже **WEB-11 зависит от WEB-10**: прочитай обе задачи; ревизия — первой, `WEB-11`:

```bash
npx @oim-dev/relay-cli task dependency add WEB-11 WEB-10 \
  --if-revision 3 \
  --actor agent
```

Существующее родительство задаётся `task parent set`: сначала ребёнок, затем родитель.
Критерии читай через `task criterion list/get`; их изменение и `complete/reopen`
защищаются ревизией задачи, а не отдельной ревизией критерия. Отмечай выполнение
после реальной проверки. Update сохраняет пропущенные поля; переданный набор целей
заменяет весь набор, поэтому не отправляй неполный список как добавление.

## Читай страницы и ошибки

Для небольших выборок начинай с `--limit 20`, продолжай через `--cursor`.
Список — не полные описания и не обязательно весь состав. Копируй готовую команду
продолжения целиком: она сохраняет фактическое подключение, проект, ref и фильтры.
Одна строка готовой команды — исключение из стиля выше.
В JSON бери `meta.page.nextCursor` / `meta.page.nextCommand`, не внутренний
`data.nextCursor`: CLI оборачивает курсор и восстанавливает параметры выборки.
Пустая страница с курсором требует продолжения; неизвестный `total` не равен нулю.
При конфликте snapshot начни чтение заново; live-страницы могут меняться.
Детали вывода и полноты — в [терминальном представлении](TERMINAL.md#страницы-и-полнота).

При ошибке проверь код завершения и сообщение. Для неверного ref уточни адрес
и проект через поиск; для ошибки config — выбранное подключение, не создавай базу.
При конфликте ревизии перечитай запись и согласуй новое изменение: нельзя просто
подставить свежую ревизию к старому телу. После потери ответа сначала прочитай
состояние, комментарии и связи; не повторяй запись вслепую, даже после timeout/5xx.
`requestId` связывает запрос с ответом, но не обеспечивает дедупликацию повторов.

## Уточняй только необходимое и сообщай результат

Если синтаксис неизвестен, один раз открой help группы или действия, например:
`npx @oim-dev/relay-cli task create --help`.
Для установленной версии источник точного синтаксиса — её `--help`; [CLI.md](CLI.md)
даёт подробный контракт. Читай нужное действие и связанный предметный сценарий,
не загружай весь справочник или все документы заранее.
Сохраняй в Relay полезные требования, решения и основания работы, не журнал вызовов.
Различай запись знания, фактическое внешнее выполнение и проверку: текст критерия
не запускает тест, отметка приёмки и прогресс не доказывают его прохождения.
В результате назови сделанное, проверенное, ограничения и следующий необходимый шаг.
