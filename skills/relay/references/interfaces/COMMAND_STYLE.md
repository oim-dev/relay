# Стиль вызовов Relay CLI

Этот документ задаёт принятый стиль команд, которые агент пишет, показывает человеку
и выполняет. По нему оформляются также авторские примеры документации и help.
Цель — сразу видеть действие и его параметры, сохранять текст без искажений
и копировать команду целиком. Синтаксис и условия действий определены в
[справочнике CLI](CLI.md), чтение ответов — в [терминальном представлении](TERMINAL.md).

## Команда и параметры

Всегда вызывайте пользовательский CLI через `npx @oim-dev/relay-cli`, без глобального
бинарника, алиаса или пути к исходникам. Примеры ниже используют Bash/POSIX shell:
правила кавычек и продолжения строк не являются универсальным синтаксисом PowerShell
или cmd.exe. Для другой оболочки требуется соответствующее экранирование.

- Первая строка: `npx @oim-dev/relay-cli`, путь команды (сущность, действие и при
  необходимости вложенные группы), затем позиционные аргументы в их порядке.
- Каждая именованная опция со своим значением — на отдельной следующей строке
  с отступом ровно в два пробела. Несколько значений одной опции остаются вместе.
- В конце каждой продолжающейся строки ставьте `\` вне кавычек, непосредственно
  перед переводом строки. После `\` не должно быть пробелов или комментария.
- Последняя строка команды — без `\`. Не вставляйте пустые строки или пояснения
  между строками продолжения.

Во всех примерах ключи, имена проектов, пути, авторы и ревизии иллюстративны:
они не подтверждают существование записей в вашей базе. До исполнения выберите
свой проект, подставьте реальные адреса и прочитанные ревизии. Не выполняйте
placeholder как будто это уже проверенное значение.

Например, при существующих доске `BOARD-WEB` и родительской задаче `WEB-10`:

```bash
npx @oim-dev/relay-cli task create \
  --board BOARD-WEB \
  --parent WEB-10 \
  --title 'Проверить форму' \
  --actor agent
```

Развёрнутую команду показывайте в fenced-блоке `bash`, не длинным inline-кодом.
Краткие синтаксические ссылки и имена команд можно оставить inline.
Короткие get/list без параметров и вызовы help оставляйте одной строкой:

```bash
npx @oim-dev/relay-cli task get WEB-10
npx @oim-dev/relay-cli task list
npx @oim-dev/relay-cli task create --help
```

## Подключение и формат ответа

Глобальные `--actor`, `--config`, `--project`, `--server-url`, `--local` и `--format`
можно располагать ниже команды на тех же условиях, что и предметные параметры.
Так первая строка объясняет действие, а следующие — его контекст.
Не добавляйте параметры подключения без необходимости.

Для предметных команд workspace предпочитайте явный `--project`. Позиционный
префикс проекта — альтернативный способ; если используете его, он остаётся перед
командой. Не совмещайте префикс и `--project` в одном вызове и не перемешивайте
способы в последовательности примеров без причины. Команды самого реестра
workspace не выбирают отдельный проект; ограничения подключения см. в
[справочнике](CLI.md#вызов-и-подключение).

Пример чтения из выбранного проекта уже настроенного workspace:

```bash
npx @oim-dev/relay-cli task get WEB-10 \
  --config ./relay.workspace.json \
  --project frontend
```

Обычный ответ агент читает в формате `text`; `--format text` избыточен.
Не добавляйте JSON ради самого факта работы агентом. Только если нужен машинный
разбор ответа, укажите его явно:

```bash
npx @oim-dev/relay-cli task list \
  --limit 10 \
  --format json
```

## Предметные флаги, связи и критерии

В обычных сценариях используйте предметные команды, флаги и читаемые ключи,
а не JSON-ввод или прямую запись диагностического графа. JSON-формат **ответа**
не требует JSON-формата **ввода**. Специальные диагностические операции описаны
отдельно в [справочнике](CLI.md#диагностика-и-обслуживание).

Родительство при создании показано выше через `--parent`. Зависимость существующей
задачи задаётся отдельным действием; `REVISION` ниже замените прочитанной ревизией
первой задачи, а ключи — адресами выбранных задач:

```bash
npx @oim-dev/relay-cli task dependency add WEB-11 WEB-10 \
  --if-revision REVISION \
  --actor agent
```

Критерий можно создать вместе с задачей через предметные флаги. Одинаковая метка
`saved` связывает его название и описание:

```bash
npx @oim-dev/relay-cli task create \
  --board BOARD-WEB \
  --title 'Проверить сохранение формы' \
  --criterion-title 'saved=Значения сохраняются' \
  --criterion-description 'saved=Сохраните форму, откройте её повторно и сравните значения.' \
  --actor agent
```

Эти примеры показывают оформление, а не заменяют условия записи. После действия
перечитайте карточку и нужные связи или критерии по
[контракту команд](CLI.md#доски-и-задачи); квитанция не доказывает внешний результат.

## Кавычки и полное содержание

Для literal-текста предпочитайте одинарные кавычки: внутри них `$`, обратные
кавычки и другие shell-конструкции не исполняются. Одинарный апостроф нельзя
экранировать обратной косой чертой внутри одинарных кавычек. Для сложных апострофов
или большого Markdown при желании используйте поддерживаемый файловый ввод
либо stdin. Создавать временный файл только ради стиля не требуется.

Непосредственный многострочный текст тоже допустим. Настоящие переводы строк,
пустые строки и значимые отступы внутри кавычек — часть сохраняемых данных:
не добавляйте туда `\` или два пробела ради оформления команды.

```bash
npx @oim-dev/relay-cli document create \
  --name 'Правила проверки' \
  --document-kind rules \
  --body '## Проверка

1. Открыть карточку.
2. Сравнить сохранённое содержание.' \
  --actor agent
```

Для уже подготовленного UTF-8 файла можно выбрать `--body-file ./rules.md` вместо
`--body`. Альтернатива без файла — stdin с quoted heredoc: кавычки у `MARKDOWN`
защищают содержание от shell-интерполяции. Ограничитель закрытия ставится отдельной
строкой без отступа; это синтаксис ввода, не ещё один параметр команды.

```bash
npx @oim-dev/relay-cli document create \
  --name 'Памятка' \
  --actor agent \
  --body-file - <<'MARKDOWN'
## Проверка

Сохраните строку `user's choice` и буквальное значение `$HOME`.
MARKDOWN
```

Для одного поля выбирайте один источник; не передавайте одновременно `--body`
и `--body-file`. Какие поля принимают файл/stdin и какие ограничения действуют,
см. в [правилах ввода](CLI.md#ввод-запись-и-восстановление).

## Пояснения и проверка копирования

Поясняйте назначение и заменяемые значения перед блоком или после него, не внутри
исполняемой команды. Короткий `#`-комментарий допустим на отдельной строке перед
командой; не ставьте его после `\` или между продолжающимися строками.

```bash
# Прочитать задачу перед изменением
npx @oim-dev/relay-cli task get WEB-10
```

Перед исполнением проверьте адрес проекта, ключи и значения. Для проверки только
shell-синтаксиса используйте `bash -n`, не исполняя примеры с placeholder и операции
над рабочей базой. Такая проверка не подтверждает существование записей, актуальность
ревизии или выполнение предметного действия.

## Готовая команда продолжения

Стиль выше относится к **написанию** команд агентом и авторских примеров help/docs.
Генерируемый `meta.page.nextCommand` сейчас остаётся одной копируемой физической
строкой. Копируйте его целиком; это допустимое исключение, не требование менять
runtime-формат продолжения. Не переносите или редактируйте курсор ради стиля.
Правила продолжения и полноты ответа — в [TERMINAL.md](TERMINAL.md#страницы-и-полнота).
