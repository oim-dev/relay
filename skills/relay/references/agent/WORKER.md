# Работа исполнителя

[Главная инструкция](../../SKILL.md).

Проверь выданное подключение и идентичность проекта. В worktree используй общую базу
по поручению, не инициализируй независимую копию. Основной интерфейс — CLI через npx.
Прочитай задачу через `npx @oim-dev/relay-cli task get <ключ-или-ID>`,
полные требования, критерии и необходимые документы; связи — по необходимости.
Уточни недостающий контекст до содержательной записи. Соблюдай выданные границы.

Если родитель передал pending-ветку, прочитай её поручение через `session get` и
исходное намерение через `checkpoint get`, затем выполни `session attach` с актуальной
ревизией ребёнка. Не создавай вместо неё независимый корень и не используй run родителя.
Сохрани свой постоянный `run.id`: `--run` принимает именно его, не читаемый ключ участия.
`--if-revision` во всех дальнейших операциях относится к твоей **ветке**, не к checkpoint.
Сверь контекст человека-оператора: без явного переопределения attach наследует человека
создавшего ветку родительского участия. Не заменяй его случайным Git-пользователем сервера.

Если поручено продолжение, сначала прочитай отдельный список `session intents` нужной
ветки (при необходимости с `--include-children`), затем context/history страницами и детей.
Не теряй старые незакрытые intent среди новых закрытых. Проверь реальные файлы,
проверки и процессы. Для paused
используй явный resume, для смены агента в open — takeover с причиной по поручению.
Это не захват всех незавершённых работ; дети не передаются вместе с родителем.
Старый run после передачи не вправе писать, даже если узнает свежую ревизию.

До работ открой собственный intent через `checkpoint open <session-ref>` с полным
Markdown намерения. На смысловых границах сохраняй progress через `checkpoint save <intent-ref>`.
Раскрой сделанное, остаток, следующий шаг и фактические проверки; title/summary — только
краткие подписи. Используй `--body` или `--body-file` и предусмотренные парные Markdown-поля,
не сворачивай многострочное содержание в одну строку. Не сохраняй лог каждого инструмента.
Название точки должно объяснять событие; summary для подсказки необязательна, body
по-прежнему содержит полное намерение или результат. Веб-граф не меняет CLI-протокол
и не заменяет `session intents`: старое открытое намерение может быть вне его страницы.

Выполни работу внешними инструментами, проверь результат и сохрани в Markdown:

- что изменено и где находится результат;
- фактические команды/сценарии проверок и их исход;
- состояние кода, ограничения и незавершённая работа;
- ближайший конкретный шаг для продолжения.

Закрой intent отдельной точкой result или cancel, затем заверши ветку с итогом либо
явно приостанови её с причиной и следующим действием. Не объявляй completed при
незакрытых намерениях, открытых детях или непринятых результатах. Если тебе разрешены
свои субагенты, следуй [протоколу родителя](ORCHESTRATOR.md): fork до запуска, attach
ребёнка, собственные checkpoints и явное принятие результата.
Твой completed — передача результата родителю, не его принятие. Передай адреса ветки
и итоговых точек, результаты проверок, ограничения и оставшиеся ресурсы.

Для изменения используй прочитанный `--if-revision` и `--actor`; `--request-id` — корреляция.
Сохрани нужное прежнее
описание и цели; после записи перечитай результат. При конфликте не затирай чужую работу.
Не заменяй постановку задачи отчётом: существенные проверки сохраняй в комментарии,
устойчивые знания — у их владельца. Перед паузой следующий агент должен понять продолжение.
Изменяй статус задачи только согласно поручению. Готовность продуктовой цели
рассчитывается автоматически, включая каскад через активные имплементации приложений.

Полные правила: [история работы](../domain/WORK_HISTORY.md). При потере ответа сначала
перечитай состояние: [восстановление](../guides/RECOVERY.md). Покрытие интерфейсов —
в [матрице](../CAPABILITIES.md); точный синтаксис всегда сверяй с установленным `--help`.
