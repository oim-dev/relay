# Обсуждения задач

[Канбан](KANBAN.md) · [CLI](CLI-COMMANDS.md#task-comment-publish) · [MCP](MCP.md#обсуждения-и-история)

Полные сообщения сохраняются в файле задачи. Общая автоматическая история изменений
и её REST, CLI и MCP-операции удалены из контракта; URL и имена операций комментариев
сохраняются. Это не перенос всего прежнего журнала внутрь задачи.

## REST

Корень — `/api/v1/projects/:project/board-tasks/:reference`; local также допускает
`/api/v1/board-tasks/:reference`. Reference — постоянный ID, текущий или прежний ключ.
Ответ — обычный `{ok:true,data:...}`.

| Метод | Путь                 | Результат                                      |
| ----- | -------------------- | ---------------------------------------------- |
| POST  | `/comments`          | Публикация сообщения, первоначальная квитанция |
| GET   | `/comments`          | Компактная страница сообщений                  |
| GET   | `/comments/:entryId` | Сообщение с полным Markdown                    |

POST принимает обязательные `title`, `description`, `actor`, `actorRole`, `requestId`.
Title — однострочный непустой текст до 1024 байт; description — непустой Markdown до
256 КиБ UTF-8. Роли: `operator`, `orchestrator`, `worker`. Web передаёт «Оператор»/operator,
агент задаёт собственное имя. Атрибуция не является аутентификацией.

Квитанция: `{id,commentId,action:"comment-publish",revision,requestId}`. Revision — номер
сообщения, а не ревизия содержания задачи. `ifRevision` не нужен; запись не меняет статус,
критерии, updatedAt и ревизию карточки. Публикация допустима в done/cancelled.
Повтор с тем же автором/requestId и содержимым возвращает исходную квитанцию, включая
после переноса задачи. Область повторов общая с операциями канбана: автор + проект.
Правка и удаление сообщений в первой версии отсутствуют.

## Страницы и полные записи

Параметры списка: `limit` (20 по умолчанию, 1–100), `cursor`, `after` (номер,
после которого нужны сообщения), `actor` (точное имя), `action` (совместимый фильтр,
только `comment-publish`).
Ответ `{items,nextCursor,snapshot}` упорядочен от новых к старым.
Курсор привязан к проекту, задаче, фильтрам и верхней границе снимка;
новые сообщения не сдвигают страницы. Для новых сообщений передайте `after: snapshot` без курсора.
Пустая страница с nextCursor означает продолжение, а не конец ленты.

Список содержит `id`, `taskId`, `sequence`, `at`, `actor`, `actorRole?`, `action`,
`title`, `operationId`, `revision`, `legacy`, `fields`; полное сообщение добавляет
`description` в Markdown и `changes`. Совместимые `fields` и `changes` пусты:
комментарий не содержит audit-изменений. Revision сообщения — ревизия содержания
задачи при публикации, в отличие от sequence в квитанции публикации.
ID — строковый номер в обсуждении конкретной задачи, не ID самостоятельной сущности.
Время задаётся в UTC, sequence определяет порядок; пропуски прежних номеров допустимы.
Список содержит компактные сведения о сообщении, авторе и времени; полный Markdown
читается через `/comments/:entryId`. ID сообщения сохраняется при миграции;
неизвестные старые факты не восстанавливаются вымышленными событиями.
После публикации перечитайте сообщение и проверьте точное содержание. Публикация сама
по себе не подтверждает выполнение задачи или критерия.

Ошибки: `VALIDATION_ERROR` — неверные поля/курсор; `NOT_FOUND` — задача/сообщение не найдены;
`IDEMPOTENCY_CONFLICT` — ключ использован с другим содержимым;
`INVALID_DATA` — повреждённое хранилище; `RESPONSE_TOO_LARGE` — превышен лимит ответа.

## Хранение и восстановление

В формате `relay-entities` версии 3 файл задачи содержит `comments`, `commentSequence`
и встроенные `receipts`. Markdown сообщения хранится массивом строк без потерь.
Автоматические `events`, снимки исходного состояния и общий audit не добавляются.
Отдельные `.relay/history` и `.relay/task-activity` не являются новым источником данных.
Общий WAL согласует публикацию файла владельца, связанных записей и производных индексов.

Явный `storage migrate` сначала восстанавливает WAL, затем переносит из legacy/v1/v2
полные комментарии, их идентичность, авторство и квитанции. Общий аудит не переносится;
известные старые журналы удаляются после согласованной публикации. Чтение и reindex
не выполняют миграцию. Потеря исходных комментариев не считается пустым обсуждением.

Квитанции бессрочны и сохраняют первоначальный результат, в том числе при повторе после
удаления задачи; повтор не создаёт её заново. Общий аудит не заменяется новым глобальным
журналом квитанций. Сохраняемые комментарии и квитанции могут увеличивать файл владельца:
новый предел 16 МиБ и retention этим решением не вводятся.
[Точный контракт хранения и перехода](STORAGE.md).

SSE служит сигналом перечитать данные через REST, а не источником истории.
Ручное редактирование JSON вне Core не обеспечивает согласованность квитанций и индексов.
