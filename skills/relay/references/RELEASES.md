# Постоянные релизы

Самостоятельные релизы используют общие правила Core через Web, REST, [CLI](CLI-COMMANDS.md)
и [MCP](MCP.md). Состав выбирается из [планов работ](PLANNING.md).

`release` — самостоятельная сущность с ключом `REL-<номер>`, ревизией, обозначением версии,
описаниями, плановой датой и `planIds`. Собственных этапов и задач нет.
Один релиз включает от 1 до 200 планов целиком; повтор ID запрещён. План может участвовать
в разных релизах, обозначение версии не является уникальным адресом.

## Состояния

`planned` допускает незавершённые планы. `cancelled` может быть явно перепланирован.
`released` фиксируется участником и требует завершённых, фактически готовых планов.
Новые включения отменённых планов запрещены; прежнее отменённое включение отображает
неготовность и требует пересмотра состава. Статусы планов и колонки задач не меняются.
Готовность до сохранения формы также читается серверной операцией preview.

Выпущенный релиз доступен для чтения. Он сохраняет выбранные ID планов, дату и автора;
история операций и первоначальные ответы не сохраняются. Фиксация информации не
запускает публикацию, Git или CI/CD.

## Хранение и чтение состава

У релиза один файл `entities/releases/<id>.json`, дисковая версия данных — `dataVersion=2`.
Технических видов `release-snapshot` и `release-snapshot-entry`, поля `snapshotId`
и операций чтения снимка нет. Физическая версия базы не меняется; совместимость и
границы согласованного сброса описаны в [контракте хранения](STORAGE.md#планы-и-релизы).

Состав всегда читается из актуальных планов по `planIds`, с обычной версией
продолжения и порциями по 12 записей по умолчанию, максимум 100. Изменение задач может
изменить текущую готовность плана и релиза, но не отменяет сохранённый факт выпуска. Интерфейсы явно показывают
актуальные данные, а не обещают архивное содержание.

`readiness.total/ready/missing/percent` относятся к текущему составу. В чтении
сохранённого релиза `canRelease=true` возможно только для `planned` с готовыми планами;
у `released` это поле false даже при полной готовности. `release_progress` также
читает текущие планы: его результат не восстанавливает состояние на дату выпуска.

После продуктовой записи владелец явно согласует группу `release-composition`:
релиз → проект (`part-of`), релиз → выбранный план (`includes`). Продуктовые линки
и связи публикуются общей восстанавливаемой операцией.
`planningEvents`, квитанции и результаты команд не сохраняются ни в релизе, ни отдельно.
`requestId` служит корреляции. После потери ответа прочитайте текущий релиз и его связи,
а не повторяйте мутацию безусловно; WAL удаляется после успеха.
