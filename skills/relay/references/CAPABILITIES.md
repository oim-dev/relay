# Возможности Relay

Каталог описывает **статически подтверждённые возможности и их подключение в текущем
дереве исходного кода**. Это не отчёт об исполнении пользовательских сценариев, прохождении
тестов или составе выпущенной версии. Он предназначен для людей и агентов, выбирающих
способ работы с проектом. Каталог также отмечает принятые, но пока отсутствующие
возможности: их целевая модель указана отдельно и не означает доступности действия.

## Как читать каталог

- **Есть** — действие реализовано в Core или подключено в указанном интерфейсе, в том числе
  через **общие операции сущностей** (generic). Отсутствие отдельной предметной команды не
  означает отсутствие возможности.
- **Частично** — доступна только часть действия или ограниченный пользовательский путь;
  ограничение указано в последнем столбце.
- **Нет** — соответствующего действия слой или интерфейс не предоставляет.
  Для принятой целевой возможности это пробел реализации, если так указано в границах.
- **—** — действие не применимо к этому слою.

Таблицы по областям составляют **единый реестр покрытия Core / REST / Web / CLI / MCP**.
Web-покрытие отражает пользовательские пути, а не просто наличие метода SDK. Для REST,
CLI и MCP учитываются зарегистрированные обработчики и их подключение к Backend.
Читаемый вид сущности не обязательно поддерживает создание или изменение через общие
операции. Диагностические рёбра графа не заменяют предметные операции над связями задач.

Точки входа под таблицами — ориентир, а не полный справочник API. CLI-команды подразумевают
префикс `npx @oim-dev/relay-cli`; REST-пути — `/api/v1`, а для выбранного проекта также
`/api/v1/projects/:project`. Семейство `entity_<kind>_create` регистрируется по схемам
поддерживаемых видов, а не для любого произвольного `kind`.

Точные команды и аргументы находятся в [справочнике CLI](interfaces/CLI.md),
[справочнике MCP](interfaces/MCP.md) и [REST API](interfaces/API.md).
Пути человека описаны в [руководстве Web](interfaces/WEB.md),
выбор базы и подключения — в [конфигурации](interfaces/CONFIGURATION.md).

## Проект и подключения

MCP поддерживает Streamable HTTP и управляемый клиентом stdio-процесс (`--transport stdio`).
В обоих режимах данные доступны только через Relay Server. Проектное подключение клиентов
описано в [руководстве MCP](interfaces/MCP-CLIENTS.md); discovery stdio не доказывает доступности API.

Разделы меняются через общую операцию изменения проекта, а не через settings PUT.
В CLI `document link/unlink` без `--legacy` меняют одну связь, `--next-relation`
меняет её тип; прежние области задаются `--targets` либо `--legacy`. `document section`
сохраняет массив разделов read-modify-write под исходной ревизией PROJECT, не повторяя
запись при конфликте.

Новые операции каталога требуют Server с возможностью `relay-document-materials-v1`;
со старым Server клиенты получают `SERVER_INCOMPATIBLE`. После записи новой версией
прежние сборки базу не читают — см. [совместимость версий](domain/STORAGE.md#совместимость-версий).
Работа новых MCP-инструментов в реальном агентском клиенте не подтверждена.

## Существенные ограничения

- **Удаление учитывает ссылки всех планов.** Ссылки на удаляемые сущности в `taskIds` или
  `scope` любого плана, включая закрытый, блокируют удаление с
  `PLANNING_REFERENCE_IN_USE`. Закрытый план неизменяем; штатной операции удаления таких
  ссылок из него нет. Наличие удаления вида не означает, что любой его экземпляр можно удалить.
- **Вычисляемый прогресс отличается от сохранённого состояния.** Текущая готовность задачи,
  плана и релиза может отличаться от сохранённых статусов. Совместимые ручные отметки
  контрактов не переопределяют вычисляемую готовность.
- **Условия этапа — текст.** `completionConditions` не являются исполняемой проверкой.
  Пустой этап не блокирует завершение всего плана, если общий состав задач непуст и все
  задачи выполнены.
- **Не вся пагинация закреплена за снимком.** Старые backend-операции `product list` и `product entities` возвращают
  версию состояния, но не принимают её для контроля продолжения: строгие схемы запросов не
  содержат `version`. Согласованность нескольких страниц одним снимком не гарантируется;
  подробнее — в [документе о хранилище](domain/STORAGE.md). Эти команды больше не
  зарегистрированы в CLI: каталоги используют предметные list и search.
  CLI `--cursor` с consistency=snapshot проверяет неизменность текущей версии,
  не открывает исторический снимок; `workspace project list` проверяет отпечаток каталога на клиенте.
  Полный контракт `meta.page` — в [CLI](interfaces/CLI.md#правила-продолжения).
- **Сохраняется текущее состояние, не история запросов.** Единое хранилище использует формат
  4 и конверт сущности версии 3. Постоянных квитанций результатов и истории содержания нет;
  `requestId` служит только корреляции. Комментарии, алиасы и уведомления имеют собственное
  назначение и не являются историческими ревизиями.

Проект адресуется постоянным `projectId`, который не обязан быть UUID. Устройство local/HTTP,
подключение CLI/MCP и ответственность Server описаны в [архитектуре](ARCHITECTURE.md).
Автоматических повторов мутаций в подключении CLI/MCP → Backend → REST нет. После потери
ответа нужно перечитать состояние, а не автоматически отправлять прежнее тело со свежей
ревизией; правила сохранения — в [документе о хранилище](domain/STORAGE.md),
порядок действий при потере ответа — в [руководстве по восстановлению](guides/RECOVERY.md).
