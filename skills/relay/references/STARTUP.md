# Подключение к Relay и выбор проекта

[Основное руководство](../SKILL.md) · [Точные настройки](CONFIGURATION.md) · [Восстановление](RECOVERY.md)

Открой этот материал, когда подключение ещё не определено, создаётся новый проект или работник находится в отдельной рабочей копии.

## 1. Что должно быть известно до записи

- Роль и выданное поручение.
- Проект: его конфиг либо ключ/UUID на сервере.
- Транспорт: MCP или CLI; для HTTP — адрес Relay Server.
- Автор `actor` и, для работника, ID задачи и каталог кода.

Путь установки скилла — место инструкций. Конфиг `.relay/config.json` относится к сопровождаемому проекту. Команды выполняются в каталоге этого проекта либо с явным подключением.

## 2. Подключённый MCP

1. Проверь список инструментов клиента. Нужны `projects_list`, `entity_get`, `entity_context` и операции задач досок.
2. Вызови `projects_list({})`, при необходимости дочитай страницы.
3. Сверь режим, доступность и идентичность выданного проекта. В workspace передавай `project` в каждом вызове; выбор не сохраняется глобально.
4. Оркестратор читает `product_context` и `project_config`; работник — `board_task_get` и `entity_context` своей задачи.

Если нужного инструмента нет, сначала проверь подключённую версию. Скилл не устанавливает и не обновляет Relay. Команды и схемы установленного сервера должны поддерживать описанный жизненный цикл.

## 3. CLI для существующего проекта

`relay-cli` в примерах — установленная команда. Без установки используй `npx @oim-dev/relay-cli` с теми же аргументами.

Local из каталога проекта:

```bash
relay-cli config get --format json
relay-cli product context --format json
```

Явный конфиг, например из другого каталога:

```bash
relay-cli --config /work/app/.relay/config.json product context --format json
```

Workspace с работающим сервером:

```bash
relay-cli --config /work/relay.workspace.json projects list --format json
relay-cli --config /work/relay.workspace.json app product context --format json
```

Только по HTTP, без локальных конфигов:

```bash
relay-cli --server-url http://127.0.0.1:4700 --project app task get PRODUCT-1 --format json
```

Адрес и имя `app` — примеры. Возьми реальные значения из поручения и списка проектов. Сервер принимает ключ регистрации или ID проекта. Вызов с `--server-url` проверяет контекст сервера и закрепляет выбранную базу по её идентификатору.

### Как выбираются режим и транспорт

- `--config` имеет приоритет над `RELAY_CONFIG` и поиском вверх от cwd.
- В ближайшем каталоге `relay.workspace.json` имеет приоритет над `.relay/config.json`.
- В local наличие URL выбирает HTTP; без URL CLI работает через Core напрямую.
- Workspace всегда использует сервер и явный проект, даже если регистрация одна.
- `--local` предназначен для прямого доступа к конкретному проектному конфигу.
- Отказ HTTP не переключает запись в локальную копию.

Чтение конфигурации помогает определить фактический путь базы. Один `server.port` задаёт запуск сервера, а `server.url` — подключение клиентов.

## 4. Новый проект

Оркестратор сначала убеждается, что проект ещё не инициализирован и ему поручено его создать. В каталоге проекта:

```bash
npx @oim-dev/relay-cli init
npx @oim-dev/relay-cli config get --format json
```

Для Web и общего доступа запусти отдельный процесс:

```bash
npx @oim-dev/relay-server --open
```

Затем при необходимости отдельный процесс MCP:

```bash
npx @oim-dev/relay-mcp --server-url http://127.0.0.1:4700
```

Подключи MCP-клиент к `http://127.0.0.1:4710/mcp`. Relay Server, MCP и долгоживущие работники требуют реального процесса среды; сохранение результата в Relay не запускает их.

Сверь фактические адреса запуска. При занятом порте выясни, относится ли слушающий процесс к нужному Relay. Используй существующий подходящий сервер либо согласованный другой порт. Останавливай только процесс, которым уполномочен управлять.

После подготовки создай паспорт продукта по фактам. Отсутствующий паспорт — нормальное начальное состояние; пустые значения не являются подтверждёнными требованиями.

## 5. Несколько проектов

Каждый проект сначала инициализируется отдельно. В общем каталоге:

```bash
relay-cli projects init
relay-server
```

После запуска, в другом терминале того же каталога:

```bash
relay-cli projects add api ./api
relay-cli projects add web ./web
relay-cli projects list --format json
relay-cli api product context --format json
```

Реестр хранит регистрации. Продукт, доски, задачи и связи каждого проекта находятся в его собственной базе. Одинаковые ключи между проектами допустимы. Зависимости задач и ссылки документов задаются внутри выбранного проекта.

## 6. Работник в worktree

Оркестратор передаёт:

```text
Подключение: общий MCP или URL Relay Server
Проект: точный ключ/ID
Задача: ID из ответа создания
Автор: имя, совпадающее с назначением
Код: путь рабочей копии и исходное состояние
Поручение: результат, границы, критерии и нужные документы
Проверка: наблюдаемый результат, способ проверки и допустимые действия записи
```

Для задач используй общий сервер, для кода — выданную рабочую копию. Ближайшая `.relay` в worktree может быть независимой копией; проверь подключение перед первой записью. Если информации недостаточно, запроси её у оркестратора, а не создавай новую базу.

## 7. Проверка связи

Успешный вызов возвращает `ok: true`; в MCP это находится в `structuredContent`. Для CLI дополнительно проверяй код процесса `0`. `actor` не выбирает проект и не задаёт адрес подключения.

Для проверки подключения достаточно чтения существующей задачи:

```bash
relay-cli --server-url http://127.0.0.1:4700 --project app task get PRODUCT-1 --format json
```

Замени URL, проект и ключ реальными значениями из поручения. Проверка связи выполняется
без служебной записи о начале работы. После разрешённой работы сохрани существенный результат
в задаче или связанном документе по [инструкции исполнителя](WORKER.md), с явным автором,
актуальной ревизией и стабильным requestId. Перечитай сохранённые данные.
Для неизвестных опций используй [справочник команд](CLI-COMMANDS.md) и `--help`;
для MCP — [каталог инструментов](MCP.md) и фактические схемы клиента.
