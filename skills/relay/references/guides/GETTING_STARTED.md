# Первый запуск Relay

Команды выполняются из корня пользовательского проекта. Нужны Node.js 22+, npm/npx
и доступ к npm registry либо подготовленный кеш. `npx` запускает опубликованные пакеты,
не исходники checkout. Глобальные команды Relay не предполагаются.

## 1. Скилл и проверка окружения

Если скилл ещё не установлен, выполните `npx skills add oim-dev/relay` и выберите своего
агента. Уже загруженный скилл повторно не устанавливайте.

Агент начинает с диагностического скрипта поставляемого скилла:

```sh
node "<каталог скилла>/scripts/diagnose.mjs" --root "<каталог проекта>"
```

Основной инструмент агента — CLI через npx с обычным читаемым выводом. MCP подключают
только по явному запросу пользователя; для работы CLI он не требуется.

Скрипт только читает настройки и API: не устанавливает, не запускает процессы и не исправляет
данные. `--client claude-code|codex|opencode` указывает среду, `--config`, `--project`
и `--server-url` уточняют подключение, `--offline` исключает HTTP. Каталог скилла
не является корнем сопровождаемого проекта. Отчёт с exit 0 не означает готовность:
проверьте отдельные состояния, ограничения проверки и `next`. Клиентские поля и
рекомендации MCP применяются только к запрошенной MCP-ветке.

Проверьте `.relay/config.json`, workspace, явное подключение и родительские конфиги.
Ошибка, частичная `.relay` и недоступный сервер не означают пустую базу. Правила —
в [конфигурации](../interfaces/CONFIGURATION.md).
Готовое HTTP-подключение может работать без местных файлов: сначала проверьте его.

Если Relay отсутствует, предложите инициализацию, проверку CLI и запуск Server,
дождитесь согласия, если подготовка ещё не поручена. Если всё готово, подтвердите проект,
передайте ссылку на Web UI и продолжайте [работу](WORKFLOW.md).

## 2. Инициализируйте проект

```sh
npx @oim-dev/relay-cli init
npx @oim-dev/relay-cli config get
npx @oim-dev/relay-cli board list
```

Результат: `.relay/config.json`, хранилище и системные доски `product`/`infrastructure`.
Init не заменяет данные. Для проверки не создавайте служебную задачу: чтений достаточно.
Пустой паспорт — нормальное начальное состояние.

## 3. Проверьте CLI-доступ

Для local-конфига без URL CLI обращается к базе напрямую; URL из параметра, среды или
конфигурации включает HTTP. Workspace всегда использует Server и явный выбор проекта.
Проверьте конфигурацию и доски командами выше, сопоставьте проект и фактические пути.
Для HTTP сначала обеспечьте работающий Server по следующему разделу, затем повторите чтения.
Успешная команда и содержимое карточки подтверждают чтение; диагностического отчёта недостаточно.
По умолчанию CLI использует text независимо от output.format в конфиге;
JSON выбирается явно через `--format json`. Полный текст карточки не обрезается
байтовым лимитом CLI; страницы списков продолжаются по `--cursor` из подсказки.
Точный синтаксис — в [CLI](../interfaces/CLI.md).

## 4. Запустите Server и передайте URL

```sh
npx @oim-dev/relay-server --open
```

Server должен работать, чтобы человек видел происходящее в Web UI, в том числе при
прямом local-доступе CLI. Сначала проверьте существующий подходящий процесс; при его
отсутствии запустите свой. Не завершайте чужие процессы.
Server живёт в долгоживущей сессии среды либо отдельном терминале; `Ctrl+C`/SIGTERM
останавливает его. Сам он не перезапускается. Сообщите пользователю фактический URL
(обычно `http://127.0.0.1:4700/`) кликабельной ссылкой и способ поддержания процесса.
Если используете уже работающий Server, также передайте ссылку на него. Если браузер не открылся,
используйте ссылку вручную. [Параметры Server](../interfaces/SERVER.md).

Повторите диагностику: health проверяет API, `/server` и проектный `/context` — базу.
При другом порте обновите URL HTTP-клиента. Занятый порт не подтверждает нужный проект.
Если запуск не удался, сообщите блокер и следующий шаг: работающий local-CLI не заменяет Web UI.

## 5. Продолжение и необязательный MCP

CLI читает нужную базу, Server доступен, пользователь получил ссылку на UI — окружение
готово. Новый проект — [ТЗ и цикл](WORKFLOW.md), существующий — [внедрение](ADOPT_EXISTING.md).
Для обычного CLI перезапуск агентского клиента не нужен.

Только при явном запросе пользователя на MCP определите клиент и откройте
[подключение клиентов](../interfaces/MCP-CLIENTS.md). Подготовьте один проектный конфиг,
сохраняя остальные настройки; домашние конфиги не меняйте. MCP запускает клиент,
но Relay Server продолжает работать отдельно. Проверьте совместимость опубликованного пакета.
После настройки предложите нужный перезапуск (для OpenCode — обязательно), проверьте
инструменты и чтение нужного проекта. До проверки сообщайте «конфиг подготовлен».
Новая сессия повторяет проверку, а не init. MCP не является обязательным этапом CLI-маршрута.

## Несколько проектов и специальные подключения

Workspace регистрирует независимые базы. Каждый проект сначала инициализируется отдельно.
Из общего каталога создайте реестр через `npx @oim-dev/relay-cli workspace project init`,
запустите Server, затем зарегистрируйте существующие базы:

```sh
npx @oim-dev/relay-cli workspace project add alpha ./alpha
npx @oim-dev/relay-cli workspace project add beta ./beta
npx @oim-dev/relay-cli workspace project list
npx @oim-dev/relay-cli config get \
  --project alpha
```

В workspace все предметные CLI-команды требуют `--project`, даже при одной регистрации.
Команда CLI `workspace project list` не является универсальной проверкой local-проекта.
Она читает регистрации через сервер, принимает `--limit`/`--cursor`, но не `--project`
или `--local`. Курсор проверяет отпечаток текущего каталога, не хранит серверный снимок.
Local CLI без URL
обращается напрямую к базе, HTTP CLI и MCP — через Server. Ошибка HTTP не разрешает
переключение базы. Подробности: [проекты](../domain/PROJECTS.md),
[конфигурация](../interfaces/CONFIGURATION.md), [восстановление](RECOVERY.md).
