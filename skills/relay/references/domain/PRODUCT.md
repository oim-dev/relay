# Продукт, требования и реализации

Продукт описывает, для кого и зачем создаётся система, какие возможности она обещает
и какие приложения их реализуют. Начните с паспорта, затем опишите фичи и сценарии,
после этого спроектируйте и создайте нужные приложения, выберите их участие и опишите
собственные обязательства FI/SI. Одновременно сохраняйте исходное ТЗ, пояснения
и материалы реализации в [библиотеке документов](DOCUMENTS.md). Содержание этих
сущностей и документов — знания, на основании которых создают [задачи](TASKS.md).
Это рекомендуемый путь, а не блокировка создания задач до заполнения паспорта.

## Паспорт и требования

В каждом [проекте](PROJECTS.md) ровно один продукт. Паспорт содержит название,
краткое описание и полное Markdown-содержание о назначении, пользователях и границах.
Незаполненный паспорт не означает отсутствия сущности продукта.

Фича — постоянная возможность продукта. Сценарий — конкретное действие и ожидаемый
результат внутри одной фичи. Иерархия имеет ровно два уровня: фича → сценарий.
Подфичи и подсценарии не вводятся; каждый сценарий принадлежит ровно одной фиче.
Перенос существующего сценария между фичами не поддерживается.
Задача не становится сценарием от совпадения названия.

Общий контракт хранится у требования, а не копируется в каждое приложение.
Название — одна строка без разметки, краткое описание — обычный многострочный текст,
полное описание и требования — Markdown. Правила содержательной записи —
в [руководстве по содержанию](../guides/CONTENT.md).

## Приложения и участие

Приложение — логическая программная часть продукта, не отдельная регистрация проекта.
Оно имеет собственное назначение и доску задач. Выбранные реализации образуют его состав.
Slug приложения и префикс его доски после создания неизменяемы; переименование
читаемого ключа их не меняет.

- FI — реализация фичи определённым приложением.
- SI — реализация сценария определённым приложением.
- SI требует FI той же фичи в том же приложении.
- Для пары приложение/фича существует один активный FI; участие не дублируют копиями.
- Выбор FI не выбирает все SI: нужные сценарии выбираются явно.
- Допустимы FI без выбранных SI и приложение без состава.
- Текст реализации описывает вклад приложения, не заменяя общий контракт требования.

Изменение общих требований не переписывает текст реализации приложения автоматически.
Для понимания работы читайте оба уровня: что требуется продукту и за что отвечает приложение.

## Изменение состава без потери адресов

Сохранение состава одного приложения применяет выбранный набор согласованно.
Неизвестная цель, невалидное участие или конфликт версии не должны оставлять часть
нового состава вперемешку с прежним.

Чтобы снять FI, нужно исключить из выбранного состава и её SI. Оставить активные SI
без активной FI нельзя. Снятие последнего SI само по себе не снимает FI.
Снятие участия — не удаление: адрес, тексты и существующие ссылки сохраняются.
Повторное включение через состав приложения по той же цели `featureId` и, для SI,
`scenarioId` возвращает прежние ID и ключ с `active: true`. Удалённая реализация
таким способом не восстанавливается.

Снятая реализация не участвует в активном расчёте готовности. Существующие ссылки
на неё остаются разрешимыми, но новая цель задачи или прикрепление к снятой реализации
не допускаются. Само снятие не означает общего запрета Core на редактирование её текста.
Удаление с каскадом — отдельное действие
с [предпросмотром последствий](STORAGE.md).

## Работа и готовность

Продуктовая доска связывает задачи с общими фичами и сценариями. Доска приложения
связывает задачи с реализациями своего приложения. Технической работе не нужна
искусственная фича: задача без продуктовой цели может быть обязательной зависимостью
продуктовой задачи. Инфраструктурная доска существует, но в базовом рабочем цикле
пока не используется; будущий [раздел инфраструктуры](../PRODUCT.md#будущий-раздел-инфраструктуры)
не следует считать готовым по наличию доски.

Готовность вычисляется по полному предметному составу: задачам, активным реализациям
и обязательным сценариям. Прямые продуктовые задачи образуют дополнительную ветку,
а не заменяют работы приложений. Правила расчёта принадлежат [прогрессу](PROGRESS.md).

Изменение текста требования или реализации само по себе не сбрасывает готовность.
Если появился новый объём работы, выразите его новой задачей либо возвратом существующей
в работу. Не используйте редактирование описания как скрытую команду смены состояния.
Вычисляемая готовность не доказывает внешнюю проверку или поставку результата.
Сохранённые совместимые поля `status`/`basis` не управляют вычисляемой готовностью.

## Обзор состояния продукта

Обзор отвечает на вопрос «что это за продукт и что в нём происходит сейчас» одним
чтением. Это точка входа для человека и агента, начинающих работу с проектом, а не
замена полного содержания записей, каталогов и расчёта [прогресса](PROGRESS.md).
Core формирует его одним чтением под общей блокировкой рабочего пространства, без записи
предметных данных; Web и CLI используют этот же расчёт, а не собственные подсчёты.

Состав среза:

- проект (ID, имя, slug) и паспорт в одном из состояний: не создан; заполнен с краткой
  summary; создан без summary — тогда показывается начало полного описания
  (обрезанные края, не более 600 символов, признак обрезки); сохранённый паспорт не меняется;
- знания: фичи и сценарии по вычисляемой готовности, приложения по назначению,
  реализации FI и SI — все, действующие, снятые и готовность только действующих;
- задачи: общее число, все шесть колонок (включая нулевые), фактически выполненные,
  находящиеся в `done` при невыполненных критериях или обязательствах, готовые к началу
  (`ready` без блокеров), заблокированные (невыполненные прямые зависимости или подзадачи
  в любой колонке) и критерии приёмки задач вне `cancelled`;
- «требует внимания»: задачи в `in-progress`, в `review` и заблокированные — с доской,
  прогрессом критериев и причинами блокировки;
- доски с числом всех и открытых задач, документы по состоянию публикации, закреплённые
  и разделы библиотеки, планы и релизы по собственным статусам.

Показатели задач пересекаются и не складываются: выполненная задача остаётся в своей колонке,
а заблокированной может быть задача любой колонки. Колонка `done` не доказывает
выполнения — фактическое выполнение требует также критериев и обязательств.
Собственный статус плана или релиза показывается отдельно от фактической готовности состава:
для планов дополнительно считаются завершённые по статусу, но фактически не выполненные;
у релиза готовность состава вычисляется по его планам. Релиз относится к проекту,
а не к отдельному приложению. Обзор не назначает приоритеты и сроки и не решает,
какую задачу начинать или завершать.

Перечни в обзоре — краткие подборки не более чем из 5 элементов. Каждая сообщает полное
число и признак продолжения; полные итоги не зависят от ограничения подборки.
Порядок детерминирован: задачи в работе и на проверке, активные планы и закреплённые
действующие документы — по последнему изменению; заблокированные — по колонке
(`in-progress`, `review`, `ready`, `inbox`, `done`, `cancelled`), затем по изменению;
запланированные релизы — по ближайшей плановой дате, затем без даты; выпущенные —
последние первыми; доски — в порядке каталога. Полные данные читаются каталогами
задач, планов, релизов, документов и досок.

### Показатели оператора

Блок `snapshot.operator` помогает решить, что проверить, что мешает работе, какая работа
вне планирования и что подготовлено к выпуску. Это чтение существующих данных: оно не
меняет статусы, не назначает приоритеты и не оценивает трудозатраты или людей.
Обозначения: `C(t)` — действующее [выполнение задачи](PROGRESS.md) с обязательствами;
**незавершённая работа U** — задачи вне `cancelled`, фактически не выполненные (включая
`done` с открытыми обязательствами); **исполняемая работа W** — колонки `in-progress` и
`review`; **открытый план** — `draft` или `active`, его состав — явно включённые в этапы ID
задач без автоматического добавления детей и зависимостей.

- **Очередь проверки (M-01).** Все задачи `review` делятся на «обязательства выполнены»
  (`C(t).canComplete`) и «остались обязательства»; сумма групп равна числу задач `review`.
  У второй группы указаны причины: невыполненный критерий, прямая зависимость, подзадача.
  Пустой список критериев завершению не мешает. Готовность обязательств позволяет
  рассмотреть завершение, но не доказывает внешнюю проверку и не закрывает задачу.
- **Влияние прямых блокеров (M-02).** Для каждого прямого невыполненного блокера —
  число различных задач U, которые он задерживает. Ребёнок, указанный ещё и зависимостью,
  считается один раз; `related` не учитывается. Это не критический путь и не транзитивное
  влияние: в цепочке A → B → C задача C влияет только на B. Отменённая задача остаётся
  блокером со своей колонкой; отменённая заблокированная задача в U не входит.
- **Работа вне открытых планов (M-03).** W минус объединение составов открытых планов,
  с разбиением по колонкам. Участие только в завершённом или отменённом плане не исключает
  задачу; перенос на другую доску включение не меняет. Это сигнал, а не ошибка:
  самостоятельная работа допускается.
- **Распределение по доскам (M-04).** Для каждой доски, включая пустые: все задачи,
  шесть колонок, фактически выполненные, `remaining` (задачи U), `blockedRemaining`
  (задачи U с блокерами) и готовые к началу. `remaining` отличается от прежнего `open`,
  который исключает колонки `done` и `cancelled`. Суммы по доскам равны проектным итогам.
- **Открытые планы с выполненным составом (M-05).** Планы `draft`/`active` с непустым
  фактически выполненным составом по [правилам планирования](PLANNING.md). Пустой план
  не готов. Это не готовность к операции `complete`: она дополнительно требует итог.
- **Подготовка выпуска (M-06).** Запланированные релизы, чей состав готов к явному выпуску
  (не подтверждение CI или публикации), и завершённые фактически готовые планы, которые
  не входят ни в один релиз `planned` или `released`. Участие только в отменённом релизе
  не исключает план; повторно открытая задача убирает план и релиз из групп, сохраняя
  их собственные статусы.

Показатели пересекаются и не складываются. Каждая группа имеет полный счётчик, подборку
не более чем из 5 элементов и полную постраничную детализацию той же классификацией:
очередь проверки и работа вне планов — по последнему изменению, затем ID; блокеры — по
числу затронутых задач, затем ID, их затронутые задачи — по изменению; доски — по
`remaining`, затем ID; планы — по изменению; релизы — по плановой дате, без даты в конце.
Продолжение детализации действительно только для той же метрики, проекта, блокера и
неизменного `snapshotVersion`; иначе чтение начинают заново (`VERSION_CONFLICT`).
Временные показатели, история переходов, загрузка исполнителей и общий балл состояния
не входят в обзор.

Ответ содержит также прежнюю карту продуктовых записей `items` с готовностью фич и
сценариев. Две версии имеют разный смысл:

- `version` — версия продуктового состава для замены участия; задачи, планы и релизы
  её не меняют;
- `snapshotVersion` — отпечаток всех данных среза: настроек проекта, паспорта и записей
  продукта, задач с критериями, досок, документов и разделов, реализаций, планов с этапами
  и релизов. Повторное чтение неизменного состояния даёт ту же версию; время формирования
  `generatedAt` в неё не входит.

`snapshotVersion` проверяет неизменность текущего состояния и не открывает доступ
к историческому снимку. Ошибка чтения любого источника прерывает обзор целиком:
интерфейсы не показывают вместо неё нули или пустой проект. Отсутствие паспорта,
задач или планов — нормальное пустое состояние, а не ошибка.

Интерфейсы: экран «Обзор» в [Web](../interfaces/WEB.md#обзор-проекта),
[`product overview` в CLI](../interfaces/CLI.md#product-overview),
[`GET /product/overview`](../interfaces/API.md#продукт-реализации-и-документы).
MCP-инструмент `product_overview` возвращает только прежнюю карту и готовность — см.
[матрицу возможностей](../CAPABILITIES.md#продукт-и-реализации).

## Проверка данных продукта

Чтение состояния продукта проверяет структурные инварианты и ссылки, затем вычисляет
готовность. `product validate` проверяет эти правила, а не только доступность данных.
`lintProduct` даёт рекомендации по тексту и структуре содержания; такие рекомендации
не заменяют проверку целостности и не доказывают выполнение требований.

## Материалы и следующий шаг

Прикрепляйте основания и пояснения через [документы](DOCUMENTS.md) по мере анализа,
а не только после описания всех сущностей. Один материал
может относиться к нескольким целям, не расширяя обязательный состав каждой из них.
Если требуется выяснить связи, используйте [контекст](CONTEXT.md); знания читайте
в полном содержании выбранных записей.
Для ближайшего изменения создайте задачи и объедините явный объём в [план](PLANNING.md).
