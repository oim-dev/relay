# История агентской работы

История сохраняет поручение, намерения, промежуточные материалы и результаты так,
чтобы человек или следующий агент мог продолжить работу без исходного чата.
Это предметная память работы, **не аудит всех команд**, не запись переписки и
не исторические снимки кода или других сущностей Relay.

Ниже — **предметный контракт**. Core, REST и CLI поддерживают чтение и запись истории;
Web предоставляет граф времени проекта только для чтения, без фильтров.
Графовая проекция отмечается отдельно; новых MCP-действий нет. Границы конкретного действия —
в [матрице возможностей](../CAPABILITIES.md#история-агентской-работы), синтаксис
установленной версии — в [CLI](../interfaces/CLI.md#история-агентской-работы)
и `--help`. Подключение интерфейса не означает публикации версии или браузерной приёмки.
Практический маршрут — [рабочий цикл](../guides/WORKFLOW.md#история-работы-агента-и-субагентов),
продолжение после обрыва — [восстановление](../guides/RECOVERY.md#незавершённая-ветка-или-смена-агента).

## Ветка, участие и точка работы

| Запись                           | Назначение                                                                                     | Собственный адрес |
| -------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------- |
| Рабочая сессия (`work-session`)  | Логическая ветка поручения, живущая дольше одного участия агента                               | `S-<token>`       |
| Участие (`agent-run`)            | Один период ответственности агента за ветку: автор, клиент, внешняя сессия, начало и окончание | `RUN-<token>`     |
| Точка работы (`work-checkpoint`) | Неизменяемое намерение или содержательный материал его исполнения                              | `CP-<token>`      |

Ветка Relay не является Git-веткой, процессом или сессией внешнего клиента.
`sourceSessionId` обозначает внешнюю сессию; он не заменяет ID ветки или участия Relay.
Автор — сохранённое авторство, не аутентификация и не подтверждение присутствия в сети.
История имеет собственные адреса; её не следует создавать или изменять через
универсальные операции продуктовых сущностей.

У открытой ветки ровно один `currentRunId`. Разные независимые ветки могут работать
параллельно. Каждый checkpoint сохраняет собственные `runId` и автора: смена агента
не переписывает прежнее авторство. Постоянные ID используются для владения и ссылок;
читаемые ключи помогают человеку найти запись.

Новые ID и ключи истории используют случайный 128-битный token — 32 шестнадцатеричных
символа, не общий последовательный счётчик. `<token>` здесь — условное обозначение:
передавайте фактический адрес из ответа, не вычисляйте его самостоятельно.
Это позволяет двум людям независимо создавать разные сессии в отдельных
Git-ветках или копиях проекта и затем объединять их файлы. Внутренний `sequence`
упорядочивает хронологию одной рабочей ветки, но не выделяет глобальные адреса.

## Человек, агент и Git-контекст

Участие различает агента (`actor`, клиент, внешняя сессия) и человека-оператора.
`operator` — nullable-снимок `{name, email, source}`; имя и email также могут быть null.
Источник — `explicit`, `environment`, `git` или `inherited`. Если человека нет,
интерфейс показывает «пользователь не указан», не выводит его из имени агента.
Это происхождение записи, **не аутентификация или проверенная личность**.

Снимок сохраняется при start, attach, resume и takeover. CLI выбирает пару по приоритету:
`--user-name`/`--user-email` → `RELAY_USER_NAME`/`RELAY_USER_EMAIL` →
`git config user.name`/`user.email` в текущем каталоге CLI внутри репозитория.
Если выбранный источник задаёт лишь одно поле пары, второе остаётся null: нельзя
домешивать другого человека из источника ниже. Не используются Git-конфигурация Server
или автор последнего коммита. При HTTP-подключении контекст по-прежнему собирает клиент.

Attach ребёнка без explicit/environment-переопределения наследует operator родительского
участия, создавшего эту ветку: CLI оставляет поле operator непереданным, а не подставляет
Git-пользователя исполнителя. Контекст человека передают в поручении субагенту.
При намеренном takeover новый участник получает новый снимок оператора; старое участие
и его человек сохраняются. Передача корня не переписывает операторов детей.

Отдельный nullable-снимок `git` содержит nullable-поля `branch` и `commit` текущей копии.
Detached HEAD или ещё не созданный первый коммит допустимы: неизвестное остаётся null.
Эти метаданные помогают найти исходное состояние, но не доказывают чистоту рабочей копии,
не сохраняют diff и не превращают checkpoint в снимок кода.

## Жизненный цикл ветки

| Действие                | Исходное состояние             | Результат                                                                        |
| ----------------------- | ------------------------------ | -------------------------------------------------------------------------------- |
| Начать (`start`)        | Новая корневая работа          | `open` и первое участие создаются атомарно                                       |
| Ответвить (`fork`)      | Открытое намерение родителя    | Новый ребёнок `pending`, без участия                                             |
| Подключиться (`attach`) | `pending`                      | `open`, первое участие ребёнка                                                   |
| Приостановить (`pause`) | `open`                         | `paused`, участие окончено с `paused`; намерения остаются открытыми              |
| Возобновить (`resume`)  | `paused`                       | `open`, новое участие со ссылкой на предыдущее                                   |
| Передать (`takeover`)   | `open`                         | Та же ветка и её история; старое участие окончено с `transferred`, создано новое |
| Завершить (`complete`)  | `open`                         | `completed` и итог, текущее участие окончено с `completed`                       |
| Отменить (`cancel`)     | `pending`, `open` или `paused` | `cancelled` и причина; текущее участие, если есть, окончено с `cancelled`        |

`completed` и `cancelled` — неизменяемые терминальные состояния. Для дальнейшей новой
работы создают новую ветку, а не переоткрывают завершённую. Пауза — явное действие,
не результат долгого отсутствия записей. Отмена не означает выполненный результат.

Relay не использует heartbeat, online-индикатор или таймаут «устаревшего агента».
Незавершённая ветка означает только `pending`, `open` или `paused` — она могла остаться
после обрыва клиента. Человек выбирает нужную работу и поручает другому агенту изучить
историю и реальный проект, затем довести её до завершения. Возраст последней точки
не даёт права автоматически захватить ветку.

`takeover` действует только на выбранную ветку. Передача корня **не передаёт его детей**:
для каждой дочерней ветки отдельно выясняют состояние и согласуют продолжение.
Relay сохраняет передачу ответственности, но не завершает внешний процесс прежнего агента.

## Намерения и неизменяемые материалы

До содержательной работы агент открывает `intent`: что и зачем он собирается делать,
границы, основания и способ проверки. На смысловых границах сохраняет `progress`:
вывод исследования, законченную часть, проверку, блокер или изменение следующего шага.
Не требуется точка на каждый инструмент, чтение файла или команду терминала.

Каждая точка неизменяема. `progress`, `result` и `cancel` указывают `intentId` исходного
намерения той же ветки. `result` или `cancel` — **отдельная терминальная запись**,
а не обновление исходного `intent`. Состояние намерения определяется наличием такой
закрывающей записи. После закрытия нельзя дописывать к нему progress или повторно
закрывать; новая работа требует нового намерения.

Полное содержание — Markdown: заголовки, списки, код, пустые строки, отступы и переводы
строк сохраняются без потерь. `title` называет точку одной строкой, `summary` служит
краткой аннотацией. Они не заменяют обязательный содержательный `body` намерения,
прогресса или результата. Дополнительные `done`, `remaining`, `nextStep`, `checks`
позволяют отдельно раскрыть сделанное, остаток, следующий шаг и фактические проверки.
Пустые разделы ради формального заполнения не нужны.

Название точки должно понятно называть событие и его предмет: например, «Проверено
сохранение многострочного Markdown», а не только «Результат». Необязательная summary
помогает узнать материал в краткой подсказке; её отсутствие не разрешает выдумывать
аннотацию или брать скрыто обрезанный body. Подробные основания и результат остаются
в полном Markdown, даже когда граф показывает только аватар и короткую подпись.

Ссылки на задачи, документы и другие предметные записи сохраняют постоянный адрес
и подпись на момент записи. Это не снимок полного содержания цели и не отношение
общего графа. Требования и устойчивые решения остаются у своего предметного владельца;
история объясняет работу над ними, а не заводит конкурирующую библиотеку знаний.

## Дочерняя работа и принятие результата

Родитель создаёт дочернюю ветку **до запуска субагента** от своего открытого `intent`.
Сохраняются родитель, исходное намерение и участие, сделавшее fork. Связь неизменяема.
Глубина вложенности произвольная: субагент при разрешённом делегировании действует
как родитель собственных детей, а не создаёт несвязанные корневые работы.

Внешняя агентская среда запускает исполнителя. Родитель передаёт ему выбранный проект,
конфигурацию и транспорт, адрес pending-ветки, исходного намерения, предметные основания,
назначение, границы и критерии. Субагент проверяет подключение, выполняет `attach`, получает
собственный run и открывает собственные намерения. Передавать ему run родителя для записи
в родительскую ветку нельзя. Relay не запускает и не отслеживает процессы субагентов.

Дочерняя ветка `completed` означает, что исполнитель сохранил свой результат,
**но не что родитель его принял**. Родитель читает полный результат, проверяет основания
и сохраняет явное принятие через `acceptedSessionIds` в своём `progress`, `result`
или `cancel`, связанном с исходным intent. Принимаются постоянные ID завершённых
прямых детей именно этого намерения, не ключи `S-<token>` и не весь подграф автоматически.
Пустой список ничего не принимает; ранее записанное принятие сохраняется в истории.

Завершить или отменить намерение нельзя, пока его дети незавершены или результаты
завершённых детей не приняты. Закрытие ветки также требует закрытых собственных
намерений, отсутствия незавершённых детей и непринятых результатов. Отменённый ребёнок
не становится выполненным и не принимается как успешный результат; причина должна
оставаться видимой. Если результат не принят, родитель описывает проблему и организует
доработку; завершённую ветку не переписывают ради изменения вывода.

## Владение, ревизии и потеря ответа

Мутация проверяет `ifRevision` **ветки**, даже когда адресует намерение. Операция
текущего владельца также передаёт постоянный `runId`, равный `currentRunId` ветки.
Это две независимые защиты: CAS от параллельной записи и run fencing от записи
прежнего участника после передачи. В CLI `--run` принимает `run.id`, не `RUN-<token>`.
Для fork ревизия и run принадлежат родителю; для attach — ревизия pending-ребёнка.

После передачи старый run не вправе сохранять новые точки даже со свежей ревизией.
При конфликте перечитайте ветку, текущее участие и историю и согласуйте продолжение;
не подменяйте ревизию или run в старой команде автоматически. Отсутствие current run
у paused/pending не разрешает владельческие записи: сначала соответствующее явное
подключение или возобновление.

`requestId` — корреляция, не ключ идемпотентности. После потери ответа проверьте ветку,
участие, детей и точки: повтор start, fork или checkpoint может создать дубликат.
Наличие предметной истории не означает постоянного сохранения квитанций запросов.

## Чтение без ложной полноты

Предметные чтения CLI/REST сохраняются независимо от устройства Web. Все фильтры
CLI остаются доступны: отсутствие фильтров на графическом экране не меняет команды
`session list`, `session intents`, `session history` и остальные чтения.

- Список веток и дерево — компактные карточки без полного поручения и итога.
  Каждая карточка содержит счётчики своей ветки, последнее участие `latestRun`
  (агент, человек и Git-контекст) и `acceptance` — ссылку на явную точку принятия
  родителем. Полное содержание ветки и отдельной точки читают адресно через `get`.
  Полная карточка тоже сохраняет latestRun и acceptance, даже если у completed/paused
  уже нет currentRun. Completed-ребёнок без acceptance **ожидает принятия**;
  null у корня или незавершённой ветки не означает ту же ситуацию.
- Открытые намерения находят **отдельным постраничным чтением**, в CLI — `session intents`
  для выбранной ветки, при необходимости с потомками. Старый intent не должен теряться
  за последними закрытыми работами: просмотр первой страницы history не заменяет
  этот список. Из него открывайте полные точки адресно.
- История — объединённая хронология веток, участий и checkpoints, производная от
  этих записей. Отдельного event-store нет. Точки жизненного цикла показывают текущую
  карточку ветки или участия, не прежнюю ревизию этой карточки.
- `context` содержит полную карточку выбранной ветки и страницу последних материалов
  самой ветки, **не все материалы и не всё поддерево**. Историю потомков выбирают явно.
- Полные счётчики ветки или поддерева не равны числу элементов страницы. Следуйте
  явному продолжению; отсутствие ребёнка на странице не делает его корневой веткой.
  `projectTotals` списка описывает **весь проект**, независимо от фильтров и страницы;
  `total` — число подходящих под фильтры веток. Не вычисляйте эти показатели по странице.
- Версия страниц защищает чтение текущего состава от смешения состояний, но не открывает
  исторический снимок. После конфликта начните чтение заново.

Для продолжения достаточно сначала выбрать нужную незавершённую ветку, затем прочитать
её поручение, отдельный список открытых намерений, последние материалы, детей и необходимые предыдущие
страницы. Не выгружайте всю историю проекта перед каждым действием. Последняя точка —
утверждение участника: перед изменением проверьте реальные файлы, тесты и внешние ресурсы.

## Граф времени проекта

Это **принятая модель чтения Web**. Доступность её реализации и транспорта указана
в [матрице возможностей](../CAPABILITIES.md#история-агентской-работы), устройство
пользовательского экрана — в [руководстве Web](../interfaces/WEB.md).
Граф является проекцией существующей истории, а не новым журналом, набором записываемых
рёбер или отдельным писателем. Он не меняет правила участия и принятия результатов.

### Ось, ветки и смысл соединений

Главная ось — **время всего проекта с датами**, не линия одного агента. Корневые
рабочие ветки выходят из этой оси. Дочерняя ветка визуально ответвляется **от линии
родителя в момент создания ребёнка**, а не от даты прежнего intent. Сохранённый
`originCheckpointId` остаётся основанием делегирования и контекстом; автор создания
по-прежнему определяется через `createdByRunId`. Смена участия и автора продолжается
на той же рабочей ветке: handoff не создаёт новую ветку и не переписывает прежние точки.

Любая закрытая работа — **completed и cancelled** — сразу визуально сливается с
родительской линией в момент закрытия (`branch-end`), а корневая — с осью проекта
(`root-end`). Статусы различаются в содержании и оформлении точки: возврат cancelled
не означает успешного выполнения. Невлитыми остаются только незавершённые ветки
`pending`, `open`, `paused`. Наличие точки закрытия и конец загруженной страницы —
разные вещи.

**Визуальное слияние не равно предметному принятию результата.** Завершённый ребёнок
может уже вернуться к родительской линии и всё ещё ожидать явного принятия в checkpoint
родителя. `acceptedSessionIds` сохраняет прежний предметный смысл и условия закрытия
родителя, но не управляет геометрией возврата. Отдельного графового ребра `acceptance`
нет. UI не принимает ребёнка и не закрывает родителя автоматически.

Соединения вычисляет Core из сохранённых записей: `sequence` связывает реальные точки
одной ветки, `fork` — линию родителя с точкой создания ребёнка, `branch-end` — точку
закрытия ребёнка с линией родителя, `root-start`/`root-end` — корень с осью проекта.
Присоединение к линии не создаёт фиктивный checkpoint родителя или новую дату события.
Граф не угадывает родство и закрытие по близости точек, одинаковому имени агента или
таймауту бездействия. В нём нет online/heartbeat/stale-эвристик.

Ветки имеют вертикальные стволы, а split/join — короткие соединения в полосе строки
создания/закрытия. Длинные кривые от старого intent через несколько дат не используются.
Подписи размещаются справа в отдельной текстовой полосе и не перекрывают линии.

Текущая раскладка может переиспользовать колонку для новой работы, не пересекающейся
по времени с её прежним владельцем. Уже показанные ветки сохраняют свои колонки при
обновлении и продолжении страниц. **Динамическое уплотнение существующих линий после
освобождения колонки не реализовано**: закрытие работы не обещает сдвинуть соседние ветки.

### Краткая точка и полное содержание

В пункте «История» с иконкой первоначальная страница показывает **только граф времени
проекта**. В Web нет фильтров, прежнего каталога веток, набора карточек, отдельного
списка открытых намерений или текстовой хронологии на основной странице. Это не
удаляет соответствующие предметные чтения из CLI/REST.

Точка checkpoint показывает аватар и короткое понятное название. Наведение открывает
локальную краткую карточку: название, вид, сохранённую дату, человека, агента и summary,
если она задана. Первичная страница не передаёт body и остальные большие Markdown-поля;
для подсказки не выполняют полное чтение и не синтезируют отсутствующее содержание.

Нажатие открывает **центральное модальное окно** и отдельно читает полное содержание
выбранной точки. Для checkpoint это все его Markdown-поля и ссылки. Точки жизненного
цикла также могут открывать подробности: поручение/итог ветки и материалы участия,
если оно есть. Жизненному циклу не создают фиктивный checkpoint. Полная карточка
ветки в таком ответе остаётся текущей, не прежней ревизией её содержания.

### Авторство точки и аватар

Исторический автор определяется сохранённым участием, а не `currentRun` или `latestRun`:

- создание корня — **первый run** корневой ветки;
- создание ребёнка — `createdByRunId`, то есть создавший его run родителя;
- checkpoint — его собственный `runId`;
- начало/окончание участия — соответствующий run; закрытие ветки — связанное участие
  либо явное отсутствие автора, если участия не было.

Человек берётся из `AgentRun.operator` этого авторского run, агент — из его `actor`.
Передача работы не заменяет человека на старых точках. Для Gravatar используется
SHA-256 от сохранённого email после удаления краевых пробелов и приведения к нижнему
регистру. Без email или доступного аватара показывают инициалы, если известны,
либо нейтральное изображение; отсутствующего человека не выдумывают.

Аватар — внешний визуальный ориентир, **не аутентификация и не исторический снимок
лица**. Изображение профиля может измениться независимо от истории. Сохранёнными
остаются сведения operator; URL Gravatar и координаты рисунка в базу не записываются.

### Страницы, границы и адресные подробности

Граф читает ограниченную страницу компактных точек и связанные с ней данные, а не
всю историю с Markdown. ID точки производен от существующей записи и вида:
`<session.id>:created/closed`, `<run.id>:started/ended`, `<checkpoint.id>:checkpoint`.
Это адрес проекции, не новая постоянная запись; fork представлен связью, а не вторым
событием создания ребёнка. Публичные S-/RUN-/CP-адреса и три коллекции не меняются.

Если узловой конец соединения вне страницы, он явно представлен в `boundaryNodes`:
до страницы, после неё или вне выбранной области. Граница не превращается в настоящий
корень или завершение ветки. Непоказанный родитель сохраняет свою роль: для fork/join
передаётся его линия через `branches`, а не выдуманная родительская точка.
Сохраняются и sequence-линии, **пересекающие окно страницы**, когда оба конца вне `items`:
их концы явно передаются как границы before/after. Отсутствие обоих концов среди точек
страницы не разрешает потерять проходящую между ними ветку. Узлы переданных соединений
должны быть явно адресованы реальными точками или границами, родительские линии — ветками;
рисовать оборванное соединение как законченный результат нельзя.

Чтобы старая незавершённая работа не исчезала за новыми событиями других веток,
`openEnds` содержит последние **реальные компактные точки всех незавершённых веток
выбранной области** (`pending`, `open`, `paused`), независимо от возраста и попадания
в `items`. Это не отдельный список-фильтр Web, не новые события «сейчас» и не журнал.
UI обозначает незавершённость самим невлитым концом или пунктирным продолжением
внутри графа, **без верхних карточек openEnds** и без новой даты события;
дату последней реальной точки раскрывает при наведении. Такой конец не подтверждает
присутствие агента в сети и не переносит старое событие на текущую дату.

`total` считает все точки выбранной области, не количество загруженных элементов,
границ или вспомогательных веток. Передача реальных точек через `openEnds` не добавляет
новых событий к `total` и не увеличивает число элементов `items`. `branches` и `runs` — необходимый контекст страницы,
не полный каталог проекта. Состояние открытого intent вычисляется по сохранённым
terminal-точкам всей области, а не по видимой части графа. Версия продолжения защищает
от смешения состояний, но не открывает исторический снимок. При конфликте перечитайте
проекцию; для полной точки используйте её адрес, даже если она вне текущей страницы.

Проекция имеет отдельный read-only контракт `relay-work-history-graph-v2` и два
HTTP-чтения: `/work-history/graph` и `/work-history/graph/points/:ref`. Их наличие не
создаёт команды CLI, MCP-инструменты или мутации графа. Параметры области HTTP-чтения
не означают наличие Web-фильтров. Граф не требует нового профиля хранения: остаётся
профиль 3. После объединения Git-копий действуют прежние явные reindex и проверка.
Версия графовой capability относится к lane-based fork/branch-end и визуальному
возврату обоих терминальных состояний; она не меняет `relay-work-history-v1`,
предметное принятие результатов или мутации CLI.

## Сохранение и совместимость

Хранение использует три коллекции: `entities/work-sessions`,
`entities/agent-runs`, `entities/work-checkpoints`. Это технические владельцы хранения
с собственными публичными адресами, не новые редактируемые продуктовые виды.
API передаёт Markdown строками, диск использует массивы строк через `markdownCodec`.
Индексы компактны и восстанавливаются из постоянных записей; полные тексты в них
не дублируются. Согласованность мутаций обеспечивает существующая атомарная WAL-публикация.

Физический формат — **4**; текущий профиль совместимости — **3**.
Профиль 2 переносится явно в профиль 3 с пустой историей: прошлые команды, переписка
и изменения сущностей не реконструируются как намерения и результаты. Обычное открытие
не мигрирует базу. Правила резервирования и восстановления — в
[контракте хранения](STORAGE.md#совместимость-версий-и-миграция), технические версии —
у [владельца хранения](https://github.com/oim-dev/relay/blob/main/packages/core/docs/FORMAT.md#версии-и-корень-базы).

### Объединение независимых Git-копий

Разные сессии, участия и checkpoints лежат в независимых файлах со случайными адресами.
Индексы производны: после merge сохраните резерв, остановите писателей выбранной базы,
явно выполните `storage reindex`, затем `doctor check` и перечитайте объединённую историю.
Автоматической пересборки при открытии или обещания бесконфликтного merge всей базы нет.

Если обе копии меняли одну и ту же рабочую сессию, CAS каждой копии не защищает от
расхождения между ними. Конфликт постоянных файлов и same-session divergence требуют
явного разбора и согласования; reindex восстанавливает индекс, **не выбирает верную
историю** и не разрешает смысловой конфликт. Не удаляйте чужие точки и не подставляйте
максимальную ревизию ради формально успешной проверки.
