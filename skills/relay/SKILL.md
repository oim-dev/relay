# Relay — рабочая память проекта

Relay хранит требования, работу и основания результата. Человек через Web и агент через
CLI/MCP используют одни данные. Действующие области: **Продукт**, **Доски и задачи**,
**Планы**, **Релизы**, **Связи**. Обзор Web находится в разработке. У карточки задачи есть
собственные обсуждения; общий аудит и прежние операции числовой доски удалены.

## Подключение

Сначала вызови `projects_list` или `relay-cli projects list --format json` и установи
нужный проект. Workspace — реестр независимых баз; в каждом вызове указывай project.
В local проект выбирается автоматически. MCP работает через Server, CLI — через HTTP
или напрямую с Core. Не переключайся на локальную копию после отказа HTTP.
[Запуск и режимы](references/STARTUP.md), [конфигурация](references/CONFIGURATION.md).

## Контекст и модель

`entity_types` / `entities types` объясняет одиннадцать видов: project, product, feature,
scenario, application, implementation, board, task, document, work-plan, release. `entity_type_get` /
`entities type <kind>` возвращает контракт вида. Ищи через `entities_list`, читай
полное содержание через `entity_get`. Ключи удобны для работы; ID постоянны, прежние
ключи сохраняются как алиасы. Не определяй вид только по префиксу.

`entity_context({ref})` или `graph context <ref>` одним вызовом возвращает весь достижимый
граф в обоих направлениях: root/version/nodes/edges/complete. Проверяй complete=true;
циклы и параллельные рёбра сохраняются. Глубина и страницы не ограничивают этот вызов.
При ошибке бюджета можно явно увеличить maxBytes / --max-bytes; частичного успешного
графа нет. Полные тексты читай адресно, краткие карточки их не заменяют.

Контекст читает только сохранённые связи Core. В едином формате предметная операция
сохраняет линки и явно изменяет свои группы связей в одной транзакции. Прежние базы
переносятся через локальный `storage migrate`; не выполняй перенос или массовый ремонт
без поручения. Для диагностической ограниченной выборки остаётся `graph list`: у неё
есть depth, nextOffset/version, boundary и depthLimited.
История операций запрещена: общий и inline audit, events/planningEvents,
receipts/requests и результаты команд не сохраняются, в том числе bounded/TTL,
sidecar или runtime. Сохраняются текущие предметные данные и отношения, полные
пользовательские комментарии, необходимые алиасы, резервы адресов, надгробия,
текущие состав/статус планов и ревизии. Незавершённый WAL удаляется после успеха.
[Модель](references/DATA-MODEL.md), [контракты сущностей](references/ENTITIES.md),
[граф](references/GRAPH.md).

## Запись

- Заголовок — одна строка; summary — многострочный обычный текст; описание и инструкция —
  структурированный Markdown. Передавай его напрямую, хранилище само кодирует массивы строк.
- Предпочитай предметные `entity_<kind>_create/update` и `product_*_save`.
  Параметры доступны на верхнем уровне. Прочитай исходную запись перед изменением.
- Каждая запись подписана actor и имеет стабильный requestId. Изменение требует
  прочитанной ifRevision; состав продукта и граф также проверяют версию снимка.
- `requestId` — корреляция, не гарантия дедупликации или исходного ответа. После потери
  ответа перечитай текущее состояние, комментарии и отношения, затем реши, нужно ли
  ещё изменение. Не повторяй мутацию безусловно. При конфликте согласуй поля с новой
  записью, не подставляй новую ревизию к устаревшему содержимому.
- Перед серией записей объясни цель; после перечитай содержимое и связи.
  `product_lint` проверяет структуру, но не доказывает полноту требований.

## Работа на досках

`boards_list`, `board_tasks_list`, `board_task_get/create/update/move/link/links`;
CLI: `boards`, `task list|get|create|update|move|link|links`. Задача получает постоянный
ID и ключ вроде PRODUCT-1; перенос меняет ключ, сохраняя ID и связи.
Колонки: inbox, ready, in-progress, review, done, cancelled. Выполнение требует done,
отмеченных критериев и фактического выполнения всех подзадач и зависимостей.
Родительство задаёт декомпозицию, зависимости — порядок. `readiness=ready` выбирает
работу без блокеров; `completion=unfinished` исключает готовые/отменённые до пагинации.
На продуктовой доске цели — фичи и сценарии продукта; на доске приложения — только
его объявленные реализации; на инфраструктурной доске целей реализации нет.
Несовместимые цели перед переносом снимаются явно. Фича, сценарий и реализация приложения
получают готовность каскадно: задача → активная реализация → её проектная цель.
Если работа есть хотя бы в одной ветке, цель как минимум partial; все активные
реализации и существующие прямые задачи должны быть готовы для done. Без задач — none.
FI приложения включает выбранные SI той же фичи и приложения; проектная фича также
требует готовности всех своих сценариев. Не считай FI выполненной только по её прямым задачам.
Проверку фактического результата выполняет участник до завершения задачи. [Канбан](references/KANBAN.md).

При постановке задачи задавай проверяемые acceptanceCriteria (title, summary,
description) через `board_task_create` или `entity_task_create`. Для существующей
задачи используй `task_criteria_list`, `task_criterion_get/add/update/complete/remove`;
CLI — `task criterion list|get|add|update|complete|reopen|remove`.
Полный Markdown читается адресно. Отмечай completed=true только после фактической
проверки: сохраняются автор и время. Изменение текста снимает отметку. Критерии
не мешают начать работу, но все должны быть выполнены перед done; задача закрывается явно.

## Планы и выпуски

План организует существующие задачи по этапам. Используй `plans_list`, `plan_get`,
`plan_stages_list`, `plan_tasks_list`, `plan_task_candidates`; создавай через `plan_create`
и `plan_stage_create`, включай задачи через `plan_tasks_include`. Параметры предметные,
тексты Markdown передаются напрямую. `plan_update` меняет только переданные поля.
У плана нет релизного типа; задача сохраняет доску, колонку, критерии и родителя.

Этап хранится внутри плана и имеет только локальный ID; его нет в каталоге сущностей,
графе и целях документов. Создание/изменение/перестановка этапов и состава требуют
`ifRevision` плана. `plan_stages_list` возвращает `planRevision`, а квитанция создания —
`stageId` и новую ревизию плана. Подбор `plan_task_candidates` с `stage` требует `plan`.
Включай только выбранные задачи: дети и зависимости не дописываются в `taskIds` автоматически.
`plan_stage_update` изменяет только заданные поля; пропуск сохраняет значение, пустая строка
очищает необязательный текст. После потери ответа сначала перечитай план и этап.

У задачи одно текущее участие в черновом/начатом плане. `task_plan_memberships` раскрывает
текущий состав планов, не журнал прежних включений. Перенос — `plan_task_transfer` с `targetPlan`,
локальным `targetStage`, причиной и ревизиями `ifRevision`/`targetRevision` обоих планов;
исключение — `plan_tasks_exclude`. Не меняй граф вручную вместо состава.
После продуктовой записи бекенд явно согласует отдельную связь задача → `part-of` → план
в одной восстанавливаемой операции; клиент выполняет одно действие.

`plan_start` необязателен; `plan_complete` доступен и без него, требует фактического выполнения всего
состава и содержательного итога; `plan_cancel` сохраняет причину. Проверяй `work_plan_progress`:
пустота и отмена не означают успеха. Состав закрытого плана остаётся его текущими данными,
без журнала прежних включений; повторное открытие обязательства показывает расхождение,
не переписывая сохранённый статус плана.
Действия плана не перемещают задачи между колонками; операции канбана доступны независимо от начала плана.

Релиз самостоятельно выбирает планы целиком. `release_preview` проверяет выбор,
`release_create` планирует выпуск с `planIds`; незавершённые планы допустимы.
`release_publish` явно фиксирует состоявшийся выпуск, проверяет весь состав и сохраняет
статус, автора и дату. Сначала проверь реальный результат внешней поставки: Relay сам
не запускает CI/CD. `release_plans_list` читает актуальные планы страницами, а
`release_progress` — их текущую готовность даже после выпуска. Изменение задач может
снизить готовность, сохраняя статус «Выпущен». Выпущенная запись неизменяема;
снимка и отдельной операции его чтения нет.

CLI: `plan list|get|create|update|stages|tasks|include|exclude|transfer|start|complete|cancel`,
`plan stage create|update|remove|move`, `release list|get|create|update|plans|preview|plan|cancel|publish`.
Параметры страниц — `--offset`, `--limit`, `--snapshot-version`; записи — `--request-id`,
`--if-revision`, автор. При переносе обязательны `--target-plan` и `--target-revision`.
Операции требуют единого хранилища и актуального формата записей. Прежние отдельные
этапы и снимки автоматически не переносятся; порядок согласованного перехода —
в [хранении](references/STORAGE.md#планы-и-релизы).
[Планирование](references/PLANNING.md), [релизы](references/RELEASES.md).

## Проверка и достоверность

Для актуального выполнения вызывай `task_progress`, `implementation_progress`,
`scenario_progress`, `feature_progress`, `application_progress`, `product_progress`;
CLI — `progress <вид> <ref>` (для продукта без ref). Не выводи готовность только из колонки.
Невыполненная инфраструктурная зависимость снимает выполнение по всей цепочке, не перемещая
карточки. Раскрывай source причин адресным запросом. Списки по 20, максимум 100;
для продолжения сохраняй version и limit. [Контракт прогресса](references/PROGRESS.md).

Обсуждение задачи: `task_comment_publish` принимает reference, обязательные title и
description (Markdown), собственное имя actor, actorRole (orchestrator/worker) и requestId.
CLI: `--actor <имя> task comment publish <задача> --role worker --title <тема> --description <Markdown>`.
Публикация не требует ifRevision, не завершает задачу и не подтверждает критерии автоматически.
Сообщения человека из Web подписаны «Оператор».

Читайте `task_comments_list` / `task_comment_get`; CLI — `task comment list|get`.
Общие entity/graph/task history API и команды отсутствуют; не пытайтесь читать audit
или заменять его собственным универсальным журналом событий.
Списки по 20, nextCursor означает продолжение даже у пустой страницы. Snapshot используйте
как after для новых записей. Полное содержание читайте адресно и проверяйте после публикации.
Не выдумывайте прежние значения и результаты отсутствовавших проверок.

Оркестратор уточняет цель, организует задачи, выдаёт поручения и проверяет общий результат.
Работник выполняет конкретное поручение и сохраняет фактические проверки, ограничения
и следующий шаг в Markdown задачи или связанного документа. Запуск процессов, Git,
тесты и поставка выполняются внешней средой в рамках поручения; Relay их не запускает.
Не выдумывай результаты и не объявляй прежнюю проверку свежей.
