# Relay — рабочая память проекта

Relay сохраняет общее понимание продукта и работы над ним для человека и агентов.
По его записям должно быть понятно, что требуется, кто работал, что сделано и проверено,
где находятся результаты и как продолжить без исходного чата.

Основной инструмент агента — CLI: `npx @oim-dev/relay-cli`. Человек читает знания,
наблюдает историю и проверяет результаты в Web. Код, тесты и поставку выполняй внешними
инструментами; сохраняй в Relay их фактические результаты и основания.

**Основной цикл: знания о продукте → декомпозиция задач → согласование планов →
выполнение и приёмка → состав релиза.** Библиотека знаний и история сопровождают весь цикл.

**Ведение истории — обязательная часть поручения. До содержательной работы зарегистрируй
участие и сохрани намерение; по ходу сохраняй промежуточные материалы; перед завершением
или передачей сохрани итог либо контекст продолжения. Ответ в чате этого не заменяет.**
Это относится к исследованию, планированию, реализации, ревью, проверкам и документации,
в том числе к работе без изменений кода. Для простого объяснения возможностей Relay
без выполнения проектного поручения регистрация работы не требуется.

## Как устроена память

| Что нужно выразить                                           | Где сохранять                                     |
| ------------------------------------------------------------ | ------------------------------------------------- |
| Назначение продукта, пользователи и границы                  | Паспорт продукта                                  |
| Ожидаемое поведение и пользовательские пути                  | Фичи и сценарии                                   |
| Ответственность программной части за требования              | Приложение и его реализации фич/сценариев — FI/SI |
| Устойчивое решение, исследование, инструкция или исходное ТЗ | Документ, прикреплённый к соответствующим записям |
| Конкретное изменение и условия его приёмки                   | Задача, критерии, подзадачи и зависимости         |
| Цель, этапы и состав работы                                  | План из существующих задач                        |
| Состав и сведения о выпуске                                  | Релиз                                             |
| Поручение, исполнители, промежуточные материалы и результат  | Сессия, участия и checkpoints                     |

Фича описывает возможность продукта, задача — работу над ней. Реализация описывает вклад
конкретного приложения. История объясняет ход работы; устойчивые требования и решения
актуализируй у их предметных владельцев, чтобы их можно было найти вне хронологии.

## Как находить действия в CLI

Точный синтаксис узнавай из справки установленной версии. При первом использовании
открой корневую справку, выбери группу по предмету работы, затем раскрой нужное действие:

```bash
npx @oim-dev/relay-cli --help
npx @oim-dev/relay-cli overview --help
npx @oim-dev/relay-cli task --help
npx @oim-dev/relay-cli task create --help
```

Справка работает без проекта. Она объясняет аргументы, ограничения, примеры и связанные
действия. Читай её адресно при новом действии или неизвестном параметре; уже изученную
справку повторяй по необходимости. При смене версии уточняй изменившийся синтаксис.

Используй читаемый текстовый вывод по умолчанию: человек должен видеть понятные команды
и результаты. JSON предназначен для отладки и передачи данных скриптам, а не обычной
работы агента. Короткие вызовы оставляй одной строкой, длинные оформляй с переносами флагов.

Для общей картины используй `overview`, для недостающих деталей — предметные действия.
Обычно `list` помогает выбрать запись, `get` читает её целиком, `progress` объясняет
готовность. `search` ищет проектные сущности; сессии ищи средствами группы `session`.
Продолжай нужную выборку по команде с курсором из ответа.

## Подключись к нужному проекту

Определи корень проекта и выданное подключение. В workspace явно выбирай проект.
В настроенном подключении начинай чтение с `overview` и сверь показанный проект с поручением.
Если адрес базы или её идентичность требуют уточнения, используй `config get` и `project get`
по необходимости. Сохраняй выбранные проект, конфигурацию и транспорт во всех вызовах.
Ошибка подключения не означает отсутствия базы и не разрешает повторную инициализацию
или переключение на другую базу. Для действительно нового проекта подготовь `init`,
если создание поручено; иначе сначала согласуй его с пользователем.

Обеспечь работающий Relay Server для Web, в том числе при прямом local-доступе CLI.
Используй подходящий существующий процесс либо запусти `npx @oim-dev/relay-server`,
уточнив запуск через его `--help`. Передай человеку фактическую ссылку на Web и способ
поддержания процесса. MCP используй только по явному запросу и при проверенном подключении.

## Начинай чтение проекта с overview

`overview` даёт согласованный срез проекта: назначение продукта, состояние задач и критериев,
блокеры, планы и релизы, продуктовые знания, последнюю и незавершённые сессии. Используй
его как точку входа и выбирай следующее чтение по увиденному и цели поручения.

- **Знакомство с проектом или восстановление общей картины:** начни сразу с
  `npx @oim-dev/relay-cli overview --view full`. Он раскрывает подборки задач и причины
  блокировок, планы, релизы, документы, карту продукта и последние события сессий.
- **Быстро проверить состояние знакомого проекта:** используй
  `npx @oim-dev/relay-cli overview` — компактную сводку с показателями и сессиями.

Выбирай один подходящий режим; compact и full не являются обязательной парой.
По обзору найди относящуюся к поручению сессию, задачу, план или знание и раскрой нужный
материал. Не собирай ту же общую картину заново цепочкой `product get`, `board list`,
`task list`, `plan list`, `release list` и `session list`. Уже известное конкретное поручение
читай адресно; перед каждым действием повторять обзор не требуется.

Итоги обзора относятся ко всему выбранному проекту, а подборки ограничены. Если нужная
запись не показана, используй соответствующий список, поиск или детализацию `overview`
из справки. Курсор обзора листает карту продукта, а не все задачи и сессии; для полного
списка незавершённых сессий предназначен `session list --unfinished`. Полные требования,
документы и материалы работы читай адресно, когда они нужны для решения или изменения.

Обзор и чтение нужной прежней сессии составляют вход в поручение. Затем зарегистрируй
участие и намерение: исследование кода и анализ требований уже должны оставлять историю.

## Основной цикл работы над проектом

Проходи цикл в пределах поручения: в новом проекте сформируй основу, в существующем
прочитай и уточни относящиеся к работе знания, задачи и планы. Начинай с нужного этапа;
локальное изменение не требует заново описывать весь продукт. На каждом этапе соблюдай
обязательный протокол истории ниже.

### 1. Собери знания и опиши продукт

Получи ТЗ, документы и пояснения пользователя: что нужно, для кого, какие есть ограничения
и тонкости. Сохраняй источники и уточнения в библиотеку по мере анализа. На их основании
заполни паспорт → определи фичи и сценарии → согласуй и создай приложения → выбери их FI/SI
и полно опиши обязательства каждой реализации. Общие требования и вклад приложения различаются.
Неизвестное уточняй; код описывает текущее устройство, но не заменяет требования.

**Библиотека обязательна к использованию:** перед постановкой и выполнением задачи читай
относящиеся к ней документы и правила; если прямых прикреплений нет, найди материалы.
Группируй документы по разделам, прикрепляй к требованиям и работе, актуализируй принятые
решения. Устойчивое знание должно быть доступно вне чата и истории сессии.

**Результат:** понятны требования, ответственность приложений, основания и открытые вопросы;
существенные пробелы ближайшей работы выяснены либо выделены в исследование.
Методики: [знания и библиотека](references/KNOWLEDGE.md),
[фичи и сценарии](references/FEATURES.md), [приложения и FI/SI](references/APPLICATIONS.md).

### 2. Декомпозируй работу и создай полноценные задачи

Найди существующую работу и создай недостающую на основании знаний. Декомпозируй до задач,
которые можно независимо поручить и проверить. Для каждой задай цель, объём и границы,
документы-основания, доску, подходящие продуктовые цели, отдельные критерии приёмки,
родителя/подзадачи и реальные зависимости. Цель задачи участвует в расчёте готовности;
технической работе не нужна фиктивная фича.

Выдели параллельные участки по согласованным контрактам, учитывая общие ресурсы и блокеры.
Включи интеграцию и сквозную проверку; количество карточек само по себе не цель.
**Результат:** задачи можно передать исполнителям без догадок по исходному чату.
Методика: [постановка, связи и декомпозиция задач](references/TASKS.md).

### 3. Согласуй итерации и составь планы

Предложи, что войдёт в первую итерацию, что позже и какой результат даст каждая.
**Согласуй границы и приоритеты с пользователем до выполнения**, если они ещё не заданы.
Собери планы с целями и этапами из существующих задач; явно выбери состав каждого этапа.
Самостоятельные цели удобно разделять планами, шаги одной цели — этапами.
**Результат:** согласованные объём, последовательность, параллельные участки и условия приёмки.
Методика: [планирование работ](references/PLANNING.md).

### 4. Выполни планы и проверь общий результат

Перед работой прочитай полную задачу, требования, документы, критерии и блокеры. Выполняй
согласованный объём самостоятельно или через разрешённое делегирование. Сохраняй прогресс,
проверяй критерии и общий сценарий, отражай итог в задачах и истории. Новые знания переноси
к их владельцам; изменения объёма и итераций согласовывай с пользователем.
**Результат:** фактически проверенная работа, обозначенные ограничения, актуальные знания,
явно завершённые задачи и отдельный итог плана. Отчёты частей не заменяют их интеграцию.
Методики: [результат задачи](references/TASKS.md#как-исполнителю-выполнить-и-передать-задачу)
и [приёмка плана](references/PLANNING.md#выполнение-и-приёмка).

### 5. Определи релиз и его состав

С пользователем выбери планы выпуска целиком, опиши изменения, версию и ограничения.
Плановый состав можно определить заранее; для фиксации выпуска планы должны быть завершены
и фактически готовы. Если поручено только определить релиз, остановись на составе и описании.
**Результат:** понятно, что войдёт в выпуск и является ли он плановым или состоявшимся.
Фиксация в Relay не запускает CI/CD. Методика: [релизы](references/RELEASES.md).

## Обязательный протокол истории

**Сессия** — логическая ветка поручения, которая может пережить смену чата или агента.
**Участие** — один период ответственности исполнителя за неё. **Checkpoint** — неизменяемое
намерение, промежуточный материал или итог в Markdown. Подробный порядок переходов,
авторства и делегирования прочитай в [HISTORY.md](references/HISTORY.md) до первой записи.

1. **До работы** зарегистрируй новую сессию или явно продолжи порученную; сохрани полное
   поручение и собственное участие. Открой намерение с целью, основаниями, границами и проверкой;
   при продолжении используй подходящее незакрытое намерение и сохрани уточнения.
2. **По ходу работы** сохраняй checkpoints после содержательных рубежей, до следующего:
   исследование, законченная часть, проверка, блокер, изменение плана. Перед переключением,
   передачей или ожидаемым сокращением контекста обязательно сохрани продолжение.
   Длительные этапы дели на подшаги; не откладывай историю до финального отчёта.
3. **В полном Markdown** раскрывай выводы и основания, сделанное, артефакты, фактические
   проверки, остаток и следующий шаг. «Работа идёт» недостаточно. Сохраняй полезное содержание,
   а не только путь к временному файлу. Точка нужна на смысловой границе, не после каждого инструмента.
4. **При разрешённом делегировании** создай дочернюю сессию до запуска исполнителя.
   Каждый работает со своим участием и намерениями. Прочитай и проверь результат ребёнка,
   затем явно прими его в истории родителя: completed ребёнка само не означает приёмку.
5. **В конце** закрой намерения и затем сессию с итогом. При остановке сохрани остаток,
   блокеры, следующий шаг и явно поставь сессию на паузу. Сохранение истории не заменяет
   итог в задаче и актуализацию знаний.

Для продолжения начни с сессии в overview и её `session context`: карточка и полные материалы
страницы приходят вместе. Для общей хронологии есть `session history`, для старых открытых
намерений — отдельный `session intents`; его обязательно проверь перед возобновлением.
Прочитанные материалы сопоставь с реальным проектом. Не забирай чужую работу по давности записи.

**Поручение нельзя объявлять полностью завершённым, пока его история не сохранена.**
При ошибке записи сообщи препятствие, сохрани Markdown в доступный пользователю файл
и укажи, что в Relay он пока не записан. Ответ в чате не заменяет сохранённого материала.

## Правила записи и результата

- До создания ищи существующую запись; до изменения читай содержание и ревизию владельца.
  Сохраняй актуальные адреса и ревизии из ответов CLI, не вычисляй их самостоятельно.
- Используй предметные операции. Ссылка в Markdown не создаёт зависимость, продуктовую
  цель или участие в плане. Файлы базы напрямую не редактируй.
- При конфликте перечитай состояние и согласуй изменение с ним. Не подставляй свежую
  ревизию в старое тело автоматически. Проверяй сохранённое содержание и значимые связи.
- В финальном ответе назови результат, фактические проверки, ограничения и адрес сессии
  с ключевыми точками. При остановке укажи состояние и следующий шаг. Человек и следующий
  агент должны найти материал в Relay и понять продолжение без обращения к этому чату.
