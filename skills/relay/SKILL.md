# Relay — рабочая память проекта

Relay сохраняет общее понимание продукта и работы над ним для человека и AI-агентов.
В нём живут требования, документы, решения, задачи, планы и результаты. Эти знания
позволяют продолжать проект после смены сессии или исполнителя без исходного чата.

Твоя задача — понимать продукт вместе с пользователем, сохранять знания и на их
основании организовывать работу. Основной процесс всегда один:

**Собрать знания о продукте → распределить задачи → построить план и выполнить работы → сформировать релиз.**

Новый и существующий проект проходят эту последовательность. В новом проекте источниками
служат идея, ТЗ и ответы пользователя; в существующем — также сохранённая память,
документация и код. Существующие записи сначала прочитай и актуализируй. Наличие кода
не заменяет выяснение требований: различай текущее поведение и то, что должно работать.

## Что можно хранить и делать в Relay

| Возможность                 | Для чего использовать                                                                                                                    |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **Паспорт продукта**        | Описать назначение, пользователей, цели, границы и ограничения продукта.                                                                 |
| **Фичи и сценарии**         | Сохранить постоянные возможности и конкретные пользовательские пути с ожидаемым результатом. Сценарий принадлежит одной фиче.            |
| **Приложения и реализации** | Определить программные части продукта и вклад каждой в общие требования: FI — реализация фичи, SI — реализация сценария.                 |
| **Документы**               | Сохранять ТЗ, пояснения, инструкции, исследования, предложения и решения; организовывать библиотеку и прикреплять материалы к сущностям. |
| **Доски и задачи**          | Распределять конкретную работу, задавать критерии приёмки, подзадачи и зависимости, обсуждать результаты.                                |
| **Планы и этапы**           | Объединять существующие задачи целью изменения, последовательностью этапов и общим итогом.                                               |
| **Релизы**                  | Выбирать выполненные планы целиком и фиксировать состав и сведения о выпуске.                                                            |
| **Прогресс**                | Узнавать фактическую готовность задач, реализаций, требований, приложений, продукта, планов и релизов; разбирать причины неготовности.   |
| **Связи и контекст**        | Находить связанные требования, работу и материалы. Содержание сущностей и документов остаётся источником знаний.                         |
| **Проекты**                 | Вести одну локальную базу либо подключать несколько независимых баз через workspace с явным выбором проекта.                             |

## Инструменты: чем пользоваться

| Инструмент | Роль                                                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CLI**    | Основной инструмент агента. Читает и изменяет данные через локальный Core или HTTP. Запускай через `npx @oim-dev/relay-cli`, используй обычный читаемый вывод.                         |
| **Server** | Предоставляет API и раздаёт Web. Запускается через `npx @oim-dev/relay-server`. Нужен для Web и MCP, а также HTTP-подключения CLI.                                                     |
| **Web**    | Интерфейс человека: читать знания, наблюдать работу, редактировать записи и проверять результаты. При работе с данными обеспечь работающий Server и передай фактическую ссылку на Web. |
| **MCP**    | Дополнительный интерфейс агента по явному запросу пользователя. Требует работающего Server и проверенного подключения инструментов в агентской среде.                                  |

Предметные правила едины и принадлежат Core. Доступность действий в интерфейсах различается.
Relay хранит знания и состояние работы; разработку, тестирование и поставку выполняй
внешними инструментами. Установленный скилл сам по себе не создаёт базу и не подключает MCP.

## Как заполнять содержание сущностей

Название — одна строка; `summary`, где предусмотрено, — краткая аннотация обычным текстом.
Полные описания, требования, цели, результаты и документы пиши **содержательным Markdown**:
используй смысловые разделы, списки, шаги и примеры. Одна общая фраза, пересказ названия
или аннотация не заменяют полного описания; добавление `##` само по себе не раскрывает смысл.

| Запись               | Что раскрыть в полном содержании                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------- |
| Паспорт / приложение | Назначение, пользователи / ответственность, границы, ограничения и взаимодействия.                       |
| Фича                 | Для кого и зачем возможность, поведение и правила, границы и проверяемые результаты.                     |
| Сценарий             | Участник, предусловия, основной путь, альтернативы, ошибки и наблюдаемый результат.                      |
| FI/SI                | Требования к вкладу именно этого приложения: поведение, входы/выходы, взаимодействия, ошибки и проверка. |
| Задача               | Цель изменения, основания, конкретная работа, границы, ограничения и способ проверки.                    |
| План / этап / релиз  | Цель и ожидаемый результат / условия завершения / содержание выпуска; фактический итог и ограничения.    |

Перед первым заполнением прочитай [правила содержания и примеры](references/guides/CONTENT.md)
для нужного вида. Пиши достаточно подробно для исполнения и проверки без исходного чата.
Общие правила адресно связывай с владельцем; в FI/SI раскрывай собственные обязательства,
а не только «приложение реализует фичу». Известное сохраняй, неизвестное уточняй или обозначай
вопросом; не выдумывай требования ради объёма и не добавляй пустые разделы.
После сохранения перечитай полный текст: понятны ли поведение, условия, ответственность
и проверка? До перехода к задачам устрани существенные пробелы требований ближайшего объёма.

## Единый рабочий процесс

Проходи этапы последовательно в пределах поручения. Если пользователь попросил только
собрать знания или подготовить план, результатом будет соответствующий этап.
При продолжении работы сначала прочитай относящиеся к поручению знания и проверь их
актуальность, затем используй существующие задачи и планы и продолжай незавершённую работу.
Масштаб изучения соразмерен изменению: конкретный баг не требует заново описывать весь продукт.

### 1. Собери и сохрани знания о продукте

Это основа дальнейшей работы. Не торопись создавать задачи, пока не понятно,
какое поведение требуется и зачем.

1. Прочитай исходные материалы и существующие записи. Выясни назначение продукта,
   пользователей, ожидаемый результат и границы поручения. Уточняй существенное неизвестное
   у пользователя; собственные варианты сохраняй как предложения, а не принятые требования.
2. Заполни или актуализируй **паспорт продукта**.
3. Выдели **фичи** и их **сценарии**. Опиши поведение, предусловия, нормальный путь,
   существенные ошибки и наблюдаемый результат. Фича — возможность продукта, задача — работа
   по её созданию или изменению; это разные записи.
4. Определи **приложения** и ответственность каждого. Существующую структуру изучи,
   новую согласуй. Frontend и backend — возможное разделение, а не обязательный набор.
5. Выбери реализации **FI/SI** в составе приложений и опиши их собственные обязательства.
   SI требует FI той же фичи в том же приложении; выбор FI не включает все SI автоматически.
   Общие требования остаются у фичи и сценария, вклад приложения — у реализации.
6. На протяжении анализа сохраняй **документы**: исходное ТЗ, пояснения, решения и материалы.
   Прикрепляй их к соответствующим записям. Различай требования, проверенные факты,
   предложения и открытые вопросы.

**Результат:** для выбранного объёма понятны продукт, требуемое поведение и вклад приложений;
знания, основания и нерешённые вопросы сохранены и понятны без исходной беседы.

### 2. Распредели задачи на основании знаний

1. Найди существующие задачи и сопоставь их с требуемым результатом. Создай недостающие,
   уточни актуальные; выполненную работу учитывай по подтверждённым основаниям.
2. Общую продуктовую работу размести на **продуктовой доске**, работу приложения —
   на **его доске**. Инфраструктурная доска уже существует, но в базовом цикле не используется.
3. Опиши цель, границы и проверяемые **критерии приёмки**. Прикрепи документы-основания.
4. Укажи продуктовые цели: фичу или сценарий на продуктовой доске, FI/SI своего приложения —
   на доске приложения. Цель включает задачу в расчёт готовности, а не просто обозначает тему.
   Техническая задача может быть без цели; создавать фиктивную фичу для неё не нужно.
5. Организуй декомпозицию обычными родительскими задачами и подзадачами; отдельного типа
   epic нет. Для обязательного результата другой задачи задай зависимость `depends-on`,
   для тематической связи — `related`. Родителю не нужна дублирующая зависимость от ребёнка.

**Результат:** работа распределена по доскам, связана с основаниями и имеет понятные
условия завершения, подзадачи и необходимые зависимости.

### 3. Построй план, выполни работы и проверь результат

1. Собери один или несколько **планов** из существующих задач. Опиши цель, границы
   и ожидаемый результат, создай этапы и явно выбери их задачи. План может содержать одну
   задачу. Включение родителя не включает автоматически подзадачи и зависимости.
2. Перед выполнением прочитай задачу, требования, материалы, критерии и блокеры.
   При фактическом начале переведи задачу в `in-progress`. Порядок этапов сам по себе
   не блокирует работу: обязательный порядок выражается зависимостями задач.
3. Выполни работу внешними средствами. Новые требования и решения сохраняй у владельца
   знания, затем уточняй затронутые задачи и план. Расширение поручения согласуй с пользователем.
4. Проверь результат по критериям. В комментарии задачи сохрани сделанное, фактические
   проверки, их основания, ограничения и необходимый следующий шаг.
5. Отметь подтверждённые критерии, передай в `review`, если нужна следующая проверка,
   и явно заверши задачу в `done`, когда обязательства выполнены. Проверь прогресс:
   учитываются критерии, дети и обязательные зависимости транзитивно.
6. По завершении всего состава **отдельно заверши план с содержательным итогом**.
   Нужны непустой состав и фактическое выполнение всех его задач. Выполнение задач
   автоматически не переводит план в `completed`.

**Результат:** работа выполнена и проверена, основания и ограничения сохранены,
план явно завершён с итогом. Непроверенное обозначено как непроверенное.

### 4. Сформируй релиз из выполненных планов

1. Выбери вошедшие в выпуск планы **целиком**, опиши выпуск и обозначение версии.
2. Проверь состав: все выбранные планы должны иметь статус `completed` и сохранять
   фактическую готовность. Повторно открытая задача может препятствовать выпуску.
3. Выполни порученные внешние действия поставки и проверь их результат. Сохрани основания
   и явно зафиксируй выпуск в Relay. Само действие выпуска не запускает CI/CD.
4. Перечитай релиз, его состояние и состав; сообщи пользователю результат и ограничения.

**Результат:** сохранены состав и сведения о состоявшемся выпуске.
Целевая модель — релиз приложения; сейчас Relay поддерживает проектный релиз с `planIds`,
без `applicationId`. Выпущенная запись неизменяема, исторический снимок состава не создаётся.

## Как начать работу с данными

Для объяснения возможностей Relay достаточно этой инструкции. Перед первым обращением
к проектным данным определи корень сопровождаемого проекта и проверь окружение:

```bash
node "<каталог скилла>/scripts/diagnose.mjs" --root "<корень проекта>"
```

Подставь реальные абсолютные пути. Прочитай состояния и рекомендации отчёта:
exit 0 означает успешную диагностику, а не готовность всех компонентов.
Проверь существующее подключение, выбранный проект и доступность Server.
Workspace требует явного `--project`; при нестандартном пути используй `--config`.
Ошибка подключения или отсутствие локального конфига не означают отсутствия базы.

Если Relay действительно ещё не настроен, согласуй инициализацию, если она не была
уже поручена, и выполни из корня проекта `npx @oim-dev/relay-cli init`.
Подтверди подключение чтением:

```bash
npx @oim-dev/relay-cli config get
npx @oim-dev/relay-cli project get
```

Используй подходящий работающий Server либо запусти `npx @oim-dev/relay-server --open`.
Передай человеку фактическую кликабельную ссылку на Web и объясни, как поддерживается
процесс. Для нового, удалённого или workspace-подключения уточняй порядок в
[руководстве первого запуска](references/guides/GETTING_STARTED.md).

### Как найти и выполнить действие через CLI

Ориентир: `сущность → list/get/create/update/progress`. Не каждый вид поддерживает все действия.
Группы соответствуют модели: `product`, `feature`, `scenario`, `application`,
`implementation`, `document`, `board`, `task`, `plan`, `release`.
Для критериев, комментариев и этапов есть подгруппы: `task criterion`, `task comment`, `plan stage`.

Начни с `product overview` — среза состояния проекта с командами полного чтения, затем открывай записи через `get`.
`list` и `search` помогают найти ключ; полное содержание читай отдельно.
`product get` и `project get` вызываются без ключа. Например:

```bash
npx @oim-dev/relay-cli product overview
npx @oim-dev/relay-cli product get
npx @oim-dev/relay-cli feature list
npx @oim-dev/relay-cli task create --help
```

Точный синтаксис установленной версии узнавай через `<команда> --help`.
При первом использовании CLI открой нужные разделы
[краткого руководства](references/interfaces/AGENT_GUIDE.md); параметры отдельного
действия — в [каталоге команд](references/interfaces/CLI-COMMANDS.md).
Команды компонентов запускай через `npx`, без глобальной установки. Используй читаемый
текстовый вывод; JSON нужен при машинном разборе. Если запрошен MCP, прочитай
[подключение клиентов](references/interfaces/MCP-CLIENTS.md) и проверь доступные
инструменты по [справочнику MCP](references/interfaces/MCP.md).

## Правила, которые действуют на всех этапах

- **Сохраняй смысл.** Название называет предмет, описание объясняет его, критерий задаёт
  наблюдаемый результат. Markdown передавай строкой. Сохраняй полезные знания и результаты,
  а не журнал каждого вызова инструмента.
- **Читай перед записью.** Проверь выбранный проект, полное содержание и актуальную ревизию.
  До создания ищи существующую запись. Для записи укажи `--actor`, для изменения —
  `--if-revision`, где он требуется. Переданный набор целей или состава может заменять весь набор.
- **Проверяй сохранённое.** После изменения перечитай содержание и значимые отношения.
  При конфликте согласуй изменение с актуальными данными. После потери ответа сначала
  выясни состояние: `requestId` не обеспечивает дедупликацию.
- **Различай статус и результат.** `done` не доказывает внешнюю проверку. Отмена не равна
  выполнению. Открытие зависимости может снять готовность, сохранив колонку задачи.
  Закрытые планы и выпущенные релизы сохраняют статус, даже если текущая готовность утрачена.
- **Используй предметные операции.** Они согласуют данные и связи внутри Core.
  Markdown-ссылка и диагностическое ребро не заменяют цель задачи, зависимость,
  прикрепление документа или включение в план. Файлы базы напрямую не редактируй.
- **Учитывай полноту чтения.** Продолжай нужные списки по курсору или готовой команде
  продолжения. Контекст используй для выяснения связей; полный текст требований читай
  адресно. Ограниченный обзор графа не является полным контекстом.

## Где уточнять подробности

Эта инструкция задаёт весь процесс. Перед новым видом действия прочитай соответствующий
предметный контракт; затем уточни синтаксис инструмента. Загружай материалы для ближайшего
шага, не всю библиотеку сразу.

| Когда нужно уточнение                                           | Материал                                                                                         |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Описываешь паспорт, фичи, сценарии, приложения и FI/SI          | [Продуктовая модель](references/domain/PRODUCT.md)                                               |
| Пишешь требования, документы или результаты                     | [Полезное содержание](references/guides/CONTENT.md), [документы](references/domain/DOCUMENTS.md) |
| Создаёшь задачи, критерии, подзадачи и зависимости              | [Задачи](references/domain/TASKS.md)                                                             |
