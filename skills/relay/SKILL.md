# Relay — рабочая память проекта

Relay сохраняет требования, документы, решения, работу и основания результата.
Человек читает их в Web, **основной инструмент агента — CLI через `npx @oim-dev/relay-cli`**.
CLI работает напрямую с local-базой или через Server; Server предоставляет Web и API.
При работе с проектом обеспечь работающий Server и дай человеку ссылку на Web UI,
даже если CLI обращается к local-базе напрямую. Подходящий работающий Server используй повторно.
MCP используй только по явному запросу пользователя и при настроенном, проверенном окружении.
Его отсутствие не блокирует CLI. Relay не исполняет код, тесты или CI/CD.
Читай обычный человекочитаемый вывод CLI: пользователь должен видеть команды, содержание
и результаты действий агента. Текст — формат по умолчанию независимо от конфигурации.
Установленный скилл — инструкции, **не установленная база и не подключённый MCP**.
Все команды компонентов запускай только через `npx`, без глобальной установки.

## Обязательное обучение CLI при загрузке

Первым делом, до диагностики и предметной работы, **полностью прочитай только
[краткое руководство агента](references/interfaces/AGENT_GUIDE.md)**.
Если инструмент вернул часть файла, дочитай его до конца. Это обязательная стартовая
база: подключение, поиск действия, краткий стиль команд, запись, страницы и ошибки.
Изучение примеров не требует их выполнения. Не загружай заранее CLI.md, CLI-COMMANDS.md,
COMMAND_STYLE.md или все предметные контракты: открывай нужный раздел по текущей задаче.
Полный [стиль вызовов](references/interfaces/COMMAND_STYLE.md) нужен при уточнении
оформления, кавычек и передачи Markdown. Синтаксис установленной версии проверяй через
`npx @oim-dev/relay-cli <команда> --help`.

Затем **сначала запусти диагностику из раздела 1**, прочитай её результаты и установи
состояние окружения. Только после этого выбирай сценарий по поручению и найденным данным
из карты раздела 5. Подготовку из разделов 2–4 выполняй по результатам проверки.
Если обнаружен workspace или границы проектов неясны, прочитай его маршрут и уточни
целевую базу до инициализации. Ошибка диагностики — блокер проверки, а не признак пустого проекта.

## 1. Сначала проверь окружение

Определи корень сопровождаемого проекта, не каталог скилла. Запусти поставляемый скрипт:

```sh
node "<каталог установленного скилла>/scripts/diagnose.mjs" --root "<корень проекта>"
```

Подставь реальные абсолютные пути. Можно добавить `--client opencode` (или `claude-code`,
`codex`), явные `--config`, `--project`, `--server-url`; `--offline` исключает HTTP-проверку.
Скрипт не устанавливает пакеты, не запускает процессы и не открывает Core для записи.
Он проверяет Node/npx, конфиги, адрес API, идентичность базы и наличие клиентских файлов.
`--offline` проверяет только локальную часть и не подтверждает доступность Web UI.
Поля `client` и рекомендации проверки MCP относятся только к запрошенной пользователем MCP-ветке.
Результат — JSON `schemaVersion: 1`; ненулевой exit означает ошибку самой диагностики.
Отчёт с exit 0 **не означает готовность**: прочитай отдельные состояния и `next`.
Проверка конфигурации структурная; JSONC/TOML и фактическую загрузку проверяет клиент.

| Наблюдение                                                              | Действие                                                                                 |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Нет Node/npx или скрипт не запускается                                  | Сообщи конкретный блокер, предложи подготовить окружение; не объявляй базу отсутствующей |
| `configuration.state=missing`, нет следов данных/известного подключения | Предложи настройку по разделу 2                                                          |
| Есть `.relay` без конфига, invalid-конфиг или нет маркера базы          | Выясни состояние; не вызывай init поверх данных                                          |
| Найден workspace или родительский конфиг                                | Проверь, относится ли он к проекту; выбери регистрацию явно                              |
| Server недоступен                                                       | Проверь процесс/адрес; запусти нужный Server для Web UI, не создавай вторую базу         |
| `server.identity=mismatch` или `unverified`                             | Подтверди проект до записи; не выбирай первый доступный                                  |
| Клиентский MCP-файл есть                                                | Не переключай интерфейс автоматически; для CLI это не условие готовности                 |
| CLI читает нужный проект, Server доступен                               | Передай ссылку на UI и перейди к сценарию, не повторяй установку                         |

Проверь известный URL и настройки среды: удалённая база может быть доступна без местного
конфига; его отсутствие не даёт права создавать другую базу. Подтверждай готовность
чтением через выбранный CLI-путь, а не только диагностическим отчётом.

## 2. Если Relay ещё не настроен

До предметной работы сообщи: «Relay в этом проекте ещё не настроен. Предлагаю
инициализировать память, проверить CLI и запустить Server, чтобы вы видели работу в Web UI.
Подготовить окружение?»
Дождись согласия; если оно уже явно дано поручением, повторный вопрос не нужен.
Не устанавливай скилл повторно — он уже загружен. После согласия, из корня проекта:

```bash
npx @oim-dev/relay-cli init
npx @oim-dev/relay-cli config get
npx @oim-dev/relay-cli board list
```

Init создаёт `.relay/config.json`, хранилище и системные доски. Чтение подтверждает пути.
Для уже выбранного HTTP сначала установи состояние существующей базы, не обходи ошибку init.
Обработай запросы npm при подготовке. Опубликованную версию проверяй через CLI `--help`;
отсутствующая команда — блокер совместимости, а не повод угадывать другой синтаксис.
Не добавляй по умолчанию глобальную установку, `--yes`, фиксированную версию или dev-команды.

## 3. Выбери CLI-подключение и проверь готовность

Local-конфиг без URL даёт прямой доступ к Core. Явный URL, переменная `RELAY_SERVER_URL`
или `server.url` включают HTTP; workspace работает через Server с явным `--project`.
Не выбирай `--local` для обхода ошибки HTTP. Настройки и база должны соответствовать поручению.

```bash
npx @oim-dev/relay-cli config get
npx @oim-dev/relay-cli board list
```

В workspace сначала прочитай реестр, затем выбранный проект; `alpha` замени реальным ключом:

```bash
npx @oim-dev/relay-cli workspace project list
npx @oim-dev/relay-cli config get \
  --project alpha
npx @oim-dev/relay-cli board list \
  --project alpha
```

`workspace project list` не является проверкой обычного local-проекта. При нестандартном расположении
используй явный `--config`, при удалённом доступе — согласованный `--server-url`.
Проверь успешное завершение, проект и фактические пути; одинаковые имена не доказывают идентичность.
Для прямого local-CLI не нужен перезапуск агентского клиента.

## 4. Server, Web и необязательный MCP

Server должен работать в каждом рабочем сценарии: человек наблюдает знания, задачи и
результаты в Web UI. Это обязательно и при прямом local-CLI. Из корня проекта либо workspace:

```sh
npx @oim-dev/relay-server --open
```

Сначала проверь существующий процесс: не запускай второй и не останавливай чужой.
При занятом порте выбери согласованный свободный и обнови URL HTTP-подключения.
Повтори диагностику с фактическим адресом: health не доказывает принадлежность базы.
Сообщи пользователю URL Web из запуска, как поддерживается процесс и как его остановить.
Передай кликабельную ссылку с фактическим адресом: «Наблюдать за работой в Relay: <URL>».
Если Server уже работал, проверь нужный проект и всё равно дай ссылку, а не только статус процесса.
Если среда не удерживает процесс, объясни необходимость отдельного терминала с этой командой.
Если запуск не удался, сообщи конкретный блокер и следующий шаг; не объявляй подготовку
завершённой только потому, что local-CLI уже читает данные.

**Только если пользователь запросил MCP:** открой справочники MCP и MCP-клиентов из
раздела 10. При ненастроенном окружении предложи проектную настройку выбранного клиента,
сохраняя другие поля; домашние конфиги не меняй. Наличие файла не подтверждает подключение.
После настройки предложи необходимый перезапуск клиента (для OpenCode — обязательно),
проверь доступность инструментов и чтение нужного проекта. До этого сообщай только
о подготовленном конфиге. В сценариях и примерах используй CLI-команды; соответствующие
MCP-действия при запрошенном переходе сверяй со справочником, не угадывай их имена.

## 5. Карта сценариев и выбор следующих шагов

К этому шагу краткое руководство агента прочитано, диагностика выполнена и её результат разобран.
Сопоставь цель поручения с результатом диагностики, состоянием кода и памяти, выбранным
проектом и готовностью подключения. Отсутствие локального конфига не означает новый продукт. Выбирай **один
основной маршрут по ближайшей цели**, а не все подходящие по словам. Workspace и совместная
работа дополняют его; при ошибке временно переходи к восстановлению. Если выбор влияет
на границы работы и его нельзя сделать из доступных сведений, задай адресный вопрос.

Открой выбранную инструкцию из `scenarios/`, кратко объясни пользователю, что обнаружено,
предложи ближайшие шаги и ожидаемый результат. Выполняй уже порученное без повторного
согласования; уточняй недостающее решение или расширение области. Фраза «используй Relay»
задаёт способ ведения памяти, но сама не задаёт требования к продукту или объём разработки.

| Ситуация / ближайшая цель                                 | Инструкция                                      | Результат маршрута                               |
| --------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------ |

Каждый маршрут указывает, что читать **сейчас**, а что — только перед соответствующим
действием из карты раздела 10. Не загружай все маршруты и справочники заранее. После
достижения результата маршрута выбери следующий по поручению; переход не разрешает
автоматически начинать разработку, делегирование или выпуск.

## 6. Чтение знаний выбранного проекта

Начни с цели пользователя и поиска существующих знаний:

```bash
npx @oim-dev/relay-cli product overview
npx @oim-dev/relay-cli document list
```

Полную запись читай у её владельца, например `npx @oim-dev/relay-cli document get <ключ-или-ID>`,
задачу — через `npx @oim-dev/relay-cli task get <ключ-или-ID>`.
Угловые скобки обозначают подстановку. Добавляй параметры выбранного подключения.
Точный синтаксис проверяй через `npx @oim-dev/relay-cli <команда> --help` и каталог команд.
Полные тексты читай отдельно от карточек. Дочитывай нужные страницы по контракту операции.
Связи и `npx @oim-dev/relay-cli inspect graph context <ключ-или-ID>` используй по необходимости; граф не заменяет
чтение знаний и не является обязательным первым шагом. Не создавай дубли существующего.
Если CLI не предоставляет нужного действия, сверь покрытие и согласуй доступный интерфейс
для той же базы. Это не автоматическое переключение на MCP. Ошибка HTTP не разрешает local fallback.

## 7. Общая модель работы

Знания и документы → задачи → при необходимости планы → работа и проверка → выпуск.
Паспорт описывает продукт, фича — возможность, сценарий — путь внутри фичи, приложение —
программную часть. FI/SI описывают вклад приложения в фичу/сценарий; SI требует FI той же
фичи и приложения. Продуктовые задачи относятся к общим целям, задачи приложения — к его
реализациям. Задача может быть без продуктовой цели; отдельного вида Epic нет.
Сохраняй документы по мере анализа. Различай требования, проверенные факты, предложения
и вопросы. Для существующей памяти уточняй записи вместо повторного создания.

## 8. Рабочий цикл и результат

Перед изменением прочитай требования и задачу. Уточнения сохраняй у владельца знания.
План задаёт цель, этапы и явно выбранные существующие задачи, включая при необходимости
одну задачу. Дети и зависимости не включаются в состав автоматически. Работа без плана допустима.
Выполни работу внешними средствами, проверь реальный результат, сохрани основания,
ограничения и следующий шаг. Отмечай критерии после проверок, завершай задачу явно.
`done` недостаточно без критериев, детей и зависимостей; проверяй предметный прогресс.
План завершается отдельно с итогом. Релиз фиксирует внешнюю поставку выбранных планов;
он сейчас проектный, без `applicationId` и исторического снимка. Не выдумывай поля и проверки.
Поручения другим агентам допустимы только по полномочиям среды и пользователя.

## 9. Чтение и безопасная запись

Для записей указывай `--actor`, для изменений — прочитанный `--if-revision`, где он требуется.
Читай содержание карточек, сообщения результата, код завершения и подсказки продолжения.
Читай до изменения; используй актуальные ревизии и версии. При конфликте согласуй содержание,
не подставляй новую ревизию к старому телу. После записи перечитай текст и значимые отношения.
`--request-id` — корреляция, не дедупликация: после потери ответа сначала проверь состояние.
Полный Markdown передавай строкой. Предметная операция сама согласует связи, второй запрос
графа не нужен. Сохраняй знания и существенный результат, не журнал каждого вызова.
Ошибка чтения не означает пустоту; полнота графа подтверждается `complete:true`.
