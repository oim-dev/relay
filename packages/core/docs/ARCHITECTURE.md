# Устройство и расширение Core

Core реализует предметный контракт, общий для local и Server. Начните с
[предметной области](../../../docs/domain/README.md), затем найдите её прикладной сервис
по карте ниже. Общие границы пакетов описаны в [архитектуре Relay](../../../docs/ARCHITECTURE.md).

## Слои и владельцы

Пути в таблице относительны `packages/core/src`.

| Область                                           | Назначение                                                                                                                                                                                  |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `domain/`                                         | Доменные функции, валидация и совместимые фасады переносимых схем Contracts                                                                                                                 |
| `application/entities/`                           | `EntityEngine`, каталог, резолвер, обработчики общих операций, каскадное удаление и проекция карточек                                                                                       |
| `application/product/`                            | Паспорт, фичи, сценарии, приложения, реализации; мутации, подборки и продуктовые проверки                                                                                                   |
| `application/documents/`                          | Библиотека, разделы и workflow прикреплений документов                                                                                                                                      |
| `application/boards/`, `application/board-tasks/` | Доски, задачи, порядок, критерии, комментарии и предметные ограничения канбана                                                                                                              |
| `application/planning/`, `application/releases/`  | Операции планов и релизов, проверка состава, собственные группы отношений                                                                                                                   |
| `application/progress/`                           | Расчёт предметных показателей и причин неготовности                                                                                                                                         |

| `application/project-settings/`                   | Изменение настроек проекта                                                                                                                                                                  |
| `application/work-history/`                       | Логические ветки агентской работы, участия, неизменяемые материалы и производная хронология                                                                                                 |
| `application/storage/`, `application/validate.ts` | Явное обслуживание, API status/dry-run/migrate и проверка согласованности                                                                                                                   |
| `storage/`                                        | Репозитории, общий Workspace, совместимые адаптеры, кодеки, блокировка, индексы и WAL; `storage/data-model/` — профили, реестр переходов, исторические схемы, backup и исполнитель миграции |

Contracts не зависит от Core. Core зависит от Contracts, Zod и средств Node.js для
хранения, но не от NestJS, React или приложений. REST-контроллеры и local-адаптер
выбирают проект, передают аргументы и оформляют ответ, не реализуют второй вариант
предметной проверки.

## Подключение и public exports

Публичная карта задаётся `packages/core/package.json`: `./*` отображается на
`src/*.ts` при условии `tasks-source`, на `dist/*.d.ts` для типов и `dist/*.js`
при обычном исполнении. Корневого `@relay/core` нет.

```ts
import { EntityEngine } from "@relay/core/application/entities/service";
import { Workspace } from "@relay/core/storage/workspace";
import type { EntityRef } from "@relay/contracts/entities";
```

Импорт через export не требует пути `packages/core/src` и не связывает потребителя
с расположением собранных файлов. Wildcard технически открывает много модулей;
для предметного действия используйте сервис, а не низкоуровневую запись JSON.
Сборка и запуск исходников — в [разработке](DEVELOPMENT.md).

## Путь операции

```text
local project-runtime или Server runtime
  → прикладной сервис / EntityEngine
  → parse переносимой схемы, определение автора
  → Workspace.mutate → общий замок и StorageSession
  → разрешение адресов и проверка целей/ревизий/инвариантов
  → предметный репозиторий → unified-adapter → EntityStore
  → явное согласование owned relations
  → актуализация карточек → индексы и WAL → результат
```

Не все действия обязаны проходить через универсальный `EntityEngine`: планирование,
выпуск и специализированные действия имеют собственные сервисы. `EntityEngine`
предоставляет общую адресацию и зарегистрированные операции; `handlers.ts` направляет
изменения к предметным владельцам. Это не произвольный CRUD поверх дисковой оболочки.

`catalog.ts` и `resolver.ts` связывают публичные ключи/ID с постоянным адресом `{kind,id}`.
`Workspace.mutate` объединяет вложенные обращения в одну сессию. Адреса целей должны
разрешаться под тем же замком, что защищает запись; предварительная клиентская проверка
не устраняет гонку. Ошибки Core (`AppError`, `invariant`) содержат код и предметное
объяснение; HTTP-статус и конверт назначает транспорт.

После записи продуктовых полей сервис явно вызывает согласование отношений в той же
сессии. Поля и граф — разные постоянные данные. Например, план владеет своей группой
включений, даже если направление ребра идёт от задачи к плану. Подробности механизма —
в [физическом хранении](FORMAT.md); смысл линков — в
[предметном контракте контекста](../../../docs/domain/CONTEXT.md).

## Чтение и границы агрегатов

`EntityEngine.get` читает PROJECT в текущем едином формате адресно: разрешение через
индекс и чтение записи настроек выполняются в одной `Workspace.locked`/`StorageSession`.
Полный `EntityDetail`, включая порядок и пустой массив `documentSections`, строится
той же проекцией `entities/project.ts`, что и строка полного каталога. Чтение не
обходит продукт, доски, задачи, планы, релизы или отношения; карточка индекса не
заменяет проверку содержимого и версии записи. Текущий ключ, алиасы и ID работают
с видом и без него; slug остаётся селектором только при явном `kind: project`.
Доски, документы и продуктовые виды имеют адресные пути текущего чтения; legacy-reader
и операции записи сохраняют строгий каталог. Проверки совместимости и recovery остаются
у Workspace, полная диагностика базы — у `validateWorkspace`.

`BoardsService.list` читает полные небольшие записи досок и их `keyspaces`, а для приложений —
компактные `records/cards/selectors`: имя и slug владельца достаточны для `BoardView` и проверки
соответствия доски приложению. Проверяются обе системные доски и наличие доски у каждого
приложения. Сортировка product → приложения по `createdAt`/ID → infrastructure и версия
SHA-256 от прежнего полного массива `BoardView` сохранены. Малый `limit` не сокращает этот
снимок: остаются два обхода общего компактного `records` и один `selectors`, но полные тексты
продукта, задач и планов не открываются.

`BoardsService.get` и `EntityEngine.get` доски читают только выбранную запись, её пространство
ключей и связанное приложение. Общая карточка остаётся `EntityDetail`, включая текущую ссылку
на владельца из канонической карточки приложения; специализированная — полным `BoardView`
с автором и датой создания. Ключи/ID/алиасы и slug разрешаются индексно. Для префикса в прежних
индексах, где он отсутствует в `selectors`, обходятся только компактные selectors владельцев
slug и карточки досок — без общего реестра задач/документов/планов. Записи проверяются кодеками,
принадлежность — по slug/ID приложения, ключи/ревизии/имя сверяются с карточками. Изменённая
сессия и legacy сохраняют прежнее логическое чтение, без раннего обновления индексов.
Каталоговая проекция не является полной проверкой содержимого файлов приложений: внешние
изменения обслуживаются через отметку stale и `reindex`, полную диагностику выполняет doctor.
Формат, профиль и проектор миграции `workspace-cards@2` не изменяются.

`EntityEngine.keys` разрешает ключи, алиасы и постоянные адреса через компактные
индексы `addresses/records/cards`, сохраняя правила резолвера каталога. При выборе
доски по selector читаются карточки досок, не тела задач. Статические `keySpaces`
строятся из определений; динамические — из карточек владельцев и их постоянных
компактных файлов `keyspaces` (префикс приложения не хранится в карточке). Изменение
публичного ключа не меняет префикс. Обе операции сохраняют прежнюю версию — отпечаток
упорядоченного списка результатов — и проверяют продолжение в одной `Workspace.locked`.
В изменённой общей сессии `keys` и динамические `keySpaces` читают логический каталог:
канонические названия и selectors карточек ещё могут быть не готовы. Чтение не запускает
раннюю проекцию или публикацию; после завершения мутации используется индексный путь.

`EntityEngine.list` фильтрует и сортирует каталог до пагинации; продолжение использует
`offset`, `nextOffset`, `version`, при смене снимка — `ENTITIES_CHANGED`.
В неизменённой current-сессии `indexed-list.ts` отбирает компактные карточки по kind/refs
и применимым типовым фильтрам, затем читает нужные записи-кандидаты и прямые адреса целей.
Поиск использует явные поля `query.ts`, включая полное содержание, не JSON.stringify
агрегата: комментарии, критерии и этапы не входят. Сортировка updated берёт собственную
предметную дату, у FI/SI — дату реализации; неизвестные даты идут последними.
Guard общего пути — `entities-v2:` плюс отпечаток корней: старое продолжение требуется
начать заново. Это консервативная проверка текущих индексов, не история и не полный doctor.
Отбор не обещает O(limit): все подходящие кандидаты проверяются до сортировки и страницы.
Общий mixed-поиск может читать тела всех видов-кандидатов и при limit=1, и при limit=20;
повторный вызов заново выполняет этот отбор, не использует сохранённый результат поиска.
Узкий refs-путь разрешает выбранные карточки через адресные индексы, без перечисления
общего records; необходимые собственные записи и прямые цели всё равно читаются.
Это граница логических чтений, не утверждение о числе физических дисковых операций.
Запись и dirty/legacy-сессия не используют частичный read-only каталог.

`entitySearchMatch` в `query.ts` выбирает одно реальное совпадение из тех же полей,
что используются при отборе: сначала текущий ключ и название, затем остальные поля.
`matchFragment` возвращает до 240 единиц UTF-16 вокруг совпадения без добавленной
разметки; обычные границы сохраняют графемы, патологически длинная графема может
разделяться по Unicode scalar, но не внутри surrogate pair. Lowercase-индекс
сопоставляется с исходным текстом. Проекция не меняет summary или полные Markdown-поля.
Общий, документный и dirty/legacy-пути используют один helper; прежний document.excerpt
сохраняется. Это объяснение выдачи, не отдельный полнотекстовый индекс.
Это не универсальный формат всех выборок. Комментарии/ленты задач используют собственный
cursor/snapshot; продуктовые `list`/`entities` возвращают версию, но не принимают её
для фиксации продолжения. Нельзя обещать им единый снимок нескольких offset-страниц.

Документы в неизменённой current-сессии имеют отдельный путь чтения:

- `EntityEngine.get` разрешает адрес через индексы, проверяет и читает одну запись
  документа и получает только карточки её прямых целей. Общая с каталогом проекция
  сохраняет точный Markdown, сырой `sectionId` и эффективный раздел. Optional
  `EntityDetail.metadata` содержит четыре сохранённых значения создания/изменения
  той же записи и ревизии; метаданные не попадают в `EntitySummary`, storageCard или
  хеш каталога. Полный каталог передаёт их отдельно, без повторного чтения продукта.
- `EntityEngine.list({kind: "document"})` обходит компактный `records`, читая карточки
  только документов. Фильтры и библиотечные счётчики используют эти карточки; непустой
  `q` и фильтр `target` требуют полных записей документов-кандидатов, но не чужих тел.
  `q` ищет body и возвращает его поисковый фрагмент. Общий межвидовой поиск использует
  отдельный индексный путь `indexed-list.ts`, сохраняя документные фрагменты.
- Версия текущего документного списка — `documents-v1:` плюс SHA-256 от отсортированных
  по имени пар корней индексов. Это новый непрозрачный guard, не прежний хеш полных
  entries: старый курсор отклоняется `ENTITIES_CHANGED`. Guard консервативный — изменение
  других индексируемых данных также может потребовать начать чтение заново. Он не
  обнаруживает произвольную внешнюю правку неоткрытого файла до stale/reindex и не
  является полным doctor. Dirty/legacy сохраняют логический каталог и его прежнюю версию.
- `DocumentLibraryService.links` читает только выбранный документ, выделяет страницу
  `relations`, затем `links`, и получает карточки только целей этой страницы. Ответ
  не содержит body, аннотаций целей или пояснений вне страницы. Физически весь JSON
  документа всё равно читается: тело и отношения находятся в одном файле.
  `sections` адресно читает один PROJECT, сохраняя порядок разделов и его текущий ключ.
  Обе страницы используют исходный guard `<ID владельца>:<ревизия>` и `VERSION_CONFLICT`;
  он не фиксирует отдельные ревизии названий целей.

`DocumentLibraryService.changeRelation/changeSection` переносят read-modify-write
из клиента в одну `Workspace.mutate`: строгий каталог, исходный CAS, разрешение цели
или преобразование массива и существующий `EntityEngine.update`. Запись сохраняет
полные проверки каталога, owned relations и общий WAL; индексный read не ослабляет
writer. Непереданное пояснение сохраняется, пустая строка очищает, modern/legacy не
конвертируются друг в друга. Успешный no-op по-прежнему увеличивает ревизию. Удаление
раздела меняет PROJECT и эффективные карточки, не тела и ревизии документов.
Все записи и dirty/legacy-чтения остаются широкими; сокращение клиентских запросов
не означает O(1) стоимость мутации.

`GraphService.context` и `FullContextReader` читают полную компоненту в обоих направлениях.
`GraphService.read` — другая операция с глубиной, направлением, страницами и границей;
её `nextOffset` не отменяет `depthLimited`. Предметная подборка продукта также не является
полным графовым контекстом. Полные тексты читаются адресно, карточка их не заменяет.

В текущем формате `GraphService.read` строит каталог из сохранённых карточек и реестра
адресов, а соседство — из компактных индексов рёбер и смежности. Полное содержание
отношений открывается только для рёбер страницы; продуктовые записи и задачи не
читаются. Готовность в карточках обновляется канонической проекцией до публикации
предметной мутации; вложенная запись до этой проекции сохраняет логический каталог.
Версия графа по-прежнему является отпечатком корней `cards/edges/adjacency`, общим
с полным контекстом. Сверяются наличие карточек, концы рёбер и согласованность
смежности; потеря индекса не заменяется пустым результатом. Это не полная диагностика
предметных файлов: её выполняет `validateWorkspace`. При пустом индексе рёбер дополнительно
проверяются известные индексу файлов наборы отношений: непустой набор означает потерю
индекса, а не пустой граф. Малый `limit` ограничивает выдачу
и чтение пояснений, но не полный обход компактных индексов для состава и сортировки.

`GraphService.mutate` по умолчанию использует отдельный строгий `projectGraphCatalog`:
до изменения отношений читает и проверяет весь прежний предметный каталог, включая
несвязанные с выбранными концами сущности. Ошибка схемы сохраняет `INVALID_DATA` и
адресные details и прерывает запись; индексное чтение не является разрешением мутации.
Переданный `GraphCatalogProvider` по-прежнему используется и для чтения, и для записи,
вместе с исходной политикой `validateMutation`; его не заменяет каталог проекта.

Обзор продукта (`ProductQueries.overview`) — владелец общего среза для REST, CLI и Web.
[overview.ts](../src/application/product/overview.ts) разделён на чтение источников и
чистый расчёт: `readOverviewSources` читает записи продукта, задачи, доски, планы и релизы
внутри одной сессии `workspace.locked` без записи, `buildProductOverview` считает показатели.
В том же чтении `WorkHistoryReader.projectOverview` получает последнюю сессию и до пяти
незавершённых с полным total. Он использует общую с history производную хронологию и только
компактные индексы истории, не открывая Markdown. Guard обзора учитывает отпечаток всех
карточек сессий, участий и checkpoints, включая невидимые в подборке.
Выполнение задач и блокеры берутся из действующей модели обязательств, готовность
требований — из `productState`, готовность планов и релизов — из расчёта планирования;
второй набор правил здесь не заводится. `snapshotVersion` — sha256 нормализованных
по ID источников без времени ответа; прежняя `version` остаётся версией продуктового
состава. Ошибка любого источника прерывает обзор. Смысл показателей —
в [контракте продукта](../../../docs/domain/PRODUCT.md#обзор-состояния-продукта).

Показатели оператора считает [operator.ts](../src/application/product/operator.ts):
`operatorIndex` за один проход по задачам строит полные отсортированные списки всех
метрик и обратный индекс прямых блокеров. `buildProductOverview` берёт из него подборки
`snapshot.operator`, `ProductQueries.overviewMetric` — страницы тех же списков в собственном
`workspace.locked`; второй классификации нет. Выполнение задач считается один раз на чтение:
`overviewCompletion` берёт расчёт из снимка планирования (без планирования — считает сам),
и тот же результат передаётся в `productState` для готовности требований. Сводка каждого плана
запоминается на время чтения (`memoizedPlanning`). Продолжение детализации — непрозрачный
курсор `shared/cursor.ts`: scope связывает проект, метрику и ID блокера, позиция хранит
смещение и `snapshotVersion`; несовпадение версии — `VERSION_CONFLICT`. Версия сверяется
до разрешения блокера: продолжение после удаления блокера даёт `VERSION_CONFLICT`,
`NOT_FOUND` возможен только без курсора и версии. Хранимого кеша,
истории и фоновых записей для метрик нет.

У `ProductQueries` есть отдельные ограниченные проекции, не замена прежних full DTO:

- `validate()` возвращает только результат структурной проверки; внутри сохраняет
  чтение `state()`, а не обещает дешёвую проверку одних индексов.
- `lint()` выполняет рекомендации внутри Core и возвращает страницу с публичными
  адресами, включая адресный FI/SI. `readProductSelection` использует единый снимок
  продуктовых записей и реализаций; задачи для lint не читаются.
- `overviewMap()` использует те же источники и `snapshotVersion`, что обзор, но не
  строит его операторские подборки и не передаёт всю сводку. Это уменьшение проекции,
  не O(limit) дискового I/O: источники и готовность по-прежнему читаются и рассчитываются.
- `participation()` возвращает компактную страницу состава с целями, собственными
  ревизиями реализаций и раздельными вычисленным/сохранённым статусами. Guard учитывает
  продукт и задачи; версия для замены состава остаётся продуктовой.
- `implementation()` возвращает полное содержание выбранного вклада с `savedStatus`,
  не меняя прежний `entity()` ради новой проекции.

`replaceParticipation()` разрешает прежние реализации и новые цели, проверяет CAS
состава/продукта и вызывает существующую границу записи в одной `Workspace.mutate`.
Нет промежуточных create и клиентского N разрешений; новый FI и его SI допустимы
в одном выборе. Возврат существующего вклада без изменения содержания сохраняет
его basis, а не подтверждает заново изменившееся требование. `updateImplementation`
редактирует снятый вклад по собственной ревизии независимо от передачи нового ключа.
Переносимые формы и guards — в [Contracts](../../contracts/docs/API.md#продуктовые-чтения-и-замена-состава).

Этап плана находится внутри записи плана и защищается её ревизией, отдельного агрегата
этапа нет. Текущая схема релиза хранит `planIds`; принятая принадлежность приложению
ещё не реализована — см. [правила релизов](../../../docs/domain/RELEASES.md).
Не добавляйте эту принадлежность как вычисляемый факт из названия или графа.

`PlanningService.listCompact` и `ReleasesService.listCompact/compositionCompact/previewCompact`
добавляют явную проекцию без больших Markdown-полей, сохраняя полные итоги и прежние
default DTO. `ReleasesService.createByRefs/updateByRefs` разрешают plans под замком
одного сохранения; update остаётся полным сохранением, не patch.
Задачные list/links и плановые задачи/кандидаты используют общий расчёт выполнения
в пределах чтения вместо расчёта для каждой карточки. `ProgressService.release`
использует один PlanningState. `taskDependencies` читает и проверяет задачи без
всего продукта/планирования и возвращает отдельную страницу с собственным guard.
Это устранение повторных вычислений и лишних проекций, не SLA и не O(limit) чтения.

`entities/deletion.ts` строит полный каскад и проверяет версию подтверждения.
При расширении каскада учитывайте ссылки `stages.taskIds` и `scope` всех планов:
`PLANNING_REFERENCE_IN_USE` касается и закрытых. Сообщение об исправлении не должно
обещать снять ссылку закрытого плана — публичной операции для этого сейчас нет.
Полные правила удаления не дублируются здесь: их владелец —
[контракт сохранения](../../../docs/domain/STORAGE.md).

## История агентской работы

`WorkHistoryService` в `application/work-history/service.ts` реализует переносимый
`WorkHistoryServiceContract`: семь чтений и двенадцать мутаций. Предметные правила —
в [истории работы](../../../docs/domain/WORK_HISTORY.md); транспорт не вычисляет
переходы, принятие детей или владение участием. `storage/work-history.ts` использует
существующую `StorageSession`: разрешение адресов, CAS ветки, проверка текущего run,
сохранение материалов и индексов находятся в одной `Workspace.mutate`/WAL. Повторов
по `requestId` и постоянных квитанций нет.

ID — 128 случайных бит, ключи `S-<ID>`, `RUN-<ID>`, `CP-<ID>` не используют общий
счётчик. Независимые Git-копии создают отдельные файлы; после объединения нужен явный
`StorageService.reindex` и doctor. Это не разрешение расхождения одной и той же ветки.
`operator` и `git` сохраняются из входа каждого подключения; Core не читает Git
сервера. Только attach без поля operator наследует снимок из неизменного
`createdByRunId` ребёнка, помечая источник `inherited`; явный null не наследуется.

Владелец каждой новой точки — текущий `runId`, `createdBy` берётся из его actor.
Старая точка не переписывается при закрытии intent или принятии результата ребёнка.
Участие сохраняет начальную `reason` отдельно от `endSummary`. Собственный sequence
ветки выделяется для создания, подключения, окончания, fork и checkpoint; номера
fork и run lifecycle сохранены явно. Производная хронология не угадывает прежнее
событие по текущему `updatedAt`. Закрытие ветки выделяет последний sequence;
терминальная ветка больше не изменяется.

`read.ts` читает компактные `work-history-sessions/runs/checkpoints`; адреса разрешает
`work-history-addresses`, не общий продуктовый каталог. Полные тела открываются
только для выбранной записи или страницы истории. Исключение — поиск по поручению:
он читает description подходящих по остальным фильтрам кандидатов. Полные счётчики
считаются до страницы, дерево обходится явным стеком без рекурсивного лимита глубины.
Guard связывает проект, выбранные записи, фильтры и направление. `context` возвращает
полную карточку и ограниченную историю с total/nextOffset, а не полный снимок работы.
`openIntents` отбирает незакрытые намерения по индексам и открывает только Markdown
страницы, независимо от числа последующих закрытых материалов. Обзоры list/tree
добавляют собственные counts, последнее участие без Markdown и первое явное принятие
ребёнка. Эти данные вычисляются одним проходом индексов, не записываются в ребёнка;
list.projectTotals считает весь проект независимо от фильтра и страницы.

Подписи внешних ссылок разрешаются под тем же замком через компактные карточки,
сохраняют ID/key/title и не становятся рёбрами графа. Мутации истории не меняют
содержание задач, планов или их прогресс. Общая финализация Workspace по-прежнему
может запускать продуктовый projector после записи `entities/`; индексные чтения
истории этого обхода не требуют.

`validateWorkHistory` подключён к read-only doctor через `issues.check("work-history")`.
Он читает все постоянные записи и проверяет смысловую согласованность: единственное
закрытие intent, владение и цепочки run, принадлежность fork/checkpoint, циклы родителей,
уникальность sequence и явное принятие детей до закрытия. Два результата независимых
копий остаются ошибкой `WORK_HISTORY_INVALID` даже после корректного reindex: индексы
не выбирают победителя и doctor не исправляет историю. Проверка циклов итеративная.

### Граф истории и адресные материалы

`WorkHistoryGraphService` в `application/work-history/graph.ts` реализует отдельный
[переносимый контракт графа](../../contracts/src/work-history-graph.ts): `graph` и `point`.
Существующие операции истории, дисковый профиль и индексы не меняются. Чтение проходит
в одной `Workspace.locked`, используя guards состава `WorkHistoryRepository` и компактный
снимок `WorkHistoryReader`. Все точки и связи производны; event-store и геометрии в Core нет.

Проектная ось соединяется с созданием настоящего корня и с его закрытием в completed
или cancelled. `fork` соединяет линию родителя с точкой создания ребёнка ровно на
`child.createdAt`, а `branch-end` возвращает закрытого ребёнка на линию родителя ровно
на `child.closedAt`. Это визуальное закрытие работы, не предметное принятие результата:
completed-ребёнок уже возвращён на линию, даже когда родитель ещё обязан явно принять его.
Принятие остаётся checkpoint без отдельной acceptance-линии. Исходный intent сохраняется
как `originCheckpointId`, но не становится концом длинной связи к более позднему fork.
Автор создания корня — первый run, ребёнка — `createdByRunId` родителя, материала — его run.
Закрытие без связанного закрывающего участия возвращает runId=null, а не последнего автора.
Атомарные дубли первого root run-started, terminal run-ended и transferred перед следующим
run-started исключаются из графа; pause, attach, resume и takeover остаются значимыми точками.
Скрытые lifecycle-дубли доступны адресно через `point` по прежнему derived ID.

Страница содержит соседство видимых точек и sequence-связи, пересекающие её окно между
before/after. Fork и branch-end выдаются только при видимой точке создания/закрытия ребёнка;
для parent lane передаётся ID ветки, а не фиктивный node. Все узловые концы передаются
в items или boundaryNodes, родительские линии — в branches. Выбранный ребёнок не становится
корнем, даже если родитель вне scope. Таблицы branches/runs содержат только необходимый
контекст: владельцев точек и границ, родительские линии,
авторские участия с непосредственными предшественниками и цепочки предков. Sequence-связи
идут по сохранённому номеру ветки; порядок страницы — по времени, ID ветки, sequence и ID.

`openEnds` сохраняет последнюю отображаемую реальную точку каждой pending/open/paused-ветки
выбранной области независимо от страницы. Нового события «сейчас» и фиктивной точки fork
для этого нет; openEnds не увеличивает total. Чтобы один ID имел одинаковую сохранённую
summary в items/openEnds/point, Core адресно читает checkpoint-файлы объединения
`items ∪ openEnds`, один раз на ID. Остальная история не открывается. Summary находится
в монолитном JSON вместе с Markdown: компактный сетевой DTO не означает отдельного дешёвого
чтения поля и не обещает O(limit) обхода компактных индексов. Полный материал возвращает
только `point`, включая точный Markdown выбранного checkpoint, ветки и авторского run.

Версия графа связывает модель проекции, проект, область, направление и все корни индексов,
включая file-hashes для summary; продолжение прежней edge-модели отклоняется. Guard
консервативен: другая индексируемая правка этого проекта тоже может вызвать
VERSION_CONFLICT. Бюджеты ответа: до 500 openEnds, до 5000 суммарных строк items/openEnds/
edges/boundaryNodes/branches/runs и до 4 МиБ JSON UTF-8. Превышение — CONTEXT_TOO_LARGE,
не успешное усечение. Это предел проекции, а не новый формат хранения или миграция.

## Добавить поле, вид или действие

1. Определите пользователя, результат и владельца инварианта. Измените канонический
   предметный контракт, если меняется поведение; не выводите правило из удобства DTO.
2. В Contracts задайте переносимую схему ввода/вывода и описания полей, включая вложенные.
   Для нового вида согласуйте `entityKinds`, `entityDataSchemas`, определения,
   фильтры и схемы зарегистрированных действий в `src/entities.ts`.
   [Правила схем](../../contracts/docs/API.md) объясняют input/output и defaults.
3. Реализуйте действие в сервисе владельца; при общей адресации подключите обработчик
   `entities/handlers.ts`, каталог и резолвер. Не рекламируйте действие в определении
   вида до появления обработчика. Для специализированного сценария сохраните отдельный
   сервис вместо обхода инвариантов общим `update`.
4. Согласуйте хранение: кодек, коллекцию, `dataVersion`, Markdown-пути, карточку и индексы,
   репозиторий и `unified-adapter`. Изменённый дисковый формат требует нового профиля,
   исторической схемы, перехода и фикстуры по [порядку миграции](DEVELOPMENT.md#следующая-миграция-данных);
   новая Zod-схема сама данные не мигрирует.
5. Определите необходимые отношения, владельца и `slot`. После предметной записи
   вызовите согласование в общей сессии. Если поле не создаёт отношения, не добавляйте
   искусственное ребро только ради присутствия в контексте.
6. Проверьте обратное чтение, удаление, снятие ссылок, резервы адресов, прогресс и
   обслуживание. Новый вид в реестре хранения не становится автоматически публичным
   видом каталога или удаляемым видом. Не добавляйте аудит/квитанции для повтора.
7. Проверьте инвариант, конфликт ревизии, повторное исполнение, сбой после предметного
   шага и recovery, сохранность чужих групп и точного текста. Выбор наборов —
   в [разработке](DEVELOPMENT.md).
8. Подключите потребителей отдельно: REST/OpenAPI, SDK, local, CLI, MCP, Web.
   Их наличие отмечается только в [общей матрице](../../../docs/CAPABILITIES.md),
   а не следует из существования схемы Core.
