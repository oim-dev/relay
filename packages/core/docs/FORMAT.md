# Физическое хранение Core

Эта страница объясняет устройство файлов и безопасное сопровождение хранилища.
Наблюдаемые гарантии находятся в [предметном контракте](../../../docs/domain/STORAGE.md),
пользовательское восстановление — в [руководстве](../../../docs/guides/RECOVERY.md).
Файлы базы не являются альтернативным публичным API записи.

## Версии и корень базы

Текущий маркер `storage.json` содержит `format: "relay-entities"`, `schemaVersion: 4`,
`dataModelVersion: 2` и необязательный `productId` для совместимости прежнего продуктового
агрегата. Проверяются разные уровни версии; ни один не заменяет другие, и semver
приложения в планирование миграции не входит:

| Уровень                                                         | Текущее значение                | Назначение                                   |
| --------------------------------------------------------------- | ------------------------------- | -------------------------------------------- |
| Физический формат `storage.json.schemaVersion`                  | 4                               | Физическая организация хранения              |
| Профиль модели данных `storage.json.dataModelVersion`           | 2                               | Целевые версии всех постоянных владельцев    |
| Оболочка live-записи и надгробия                                | 3                               | Общие поля текущей записи                    |
| `dataVersion` плана, релиза и записи совместимости `plan-stage` | 2                               | Предметные данные этих видов                 |
| `dataVersion` остальных встроенных и технических видов          | 1                               | Предметные данные соответствующего владельца |
| Keyspace, набор отношений, состояние индексов, конфигурация     | 1                               | Формы служебных файлов                       |
| `revision`                                                      | Изменяется предметной операцией | Compare-and-swap содержимого агрегата        |
| `.indexes/state.json.version`                                   | Непрозрачная строка             | Локальный снимок производных индексов        |
| `transactions/pending.json` `schemaVersion`                     | 1 или 2                         | WAL обычной операции (1) или миграции (2)    |

Профиль — замороженный дескриптор в `storage/data-model/profiles.ts`, а не значение,
вычисляемое из текущих кодеков. Профиль 1 — состояние Relay 0.9.2: manifest формата 4
без поля `dataModelVersion`; его распознаёт только исторический reader обслуживания.
Профиль 2 добавляет к владельцам профиля 1 `plan-stage` 2, `release-snapshot` 1 и
`release-snapshot-entry` 1. Профиль повышается при несовместимом изменении любого
постоянного владельца, в том числе одного `dataVersion`; физический формат — только
при реальном изменении его контракта.

Обычное открытие (`EntityStore.open/locked/underLock`, `Workspace`, `readWorkspaceConfig`)
разбирает manifest через `data-model/manifest.ts` после проверки вида WAL и до предметной
работы, без обхода записей:

| Manifest                      | Результат                                                            |
| ----------------------------- | -------------------------------------------------------------------- |
| Формат 1/2/3                  | `STORAGE_MIGRATION_REQUIRED`, `details.reason: physical`             |
| Формат 4 без профиля или ниже | `STORAGE_MIGRATION_REQUIRED`, `details.reason: profile`              |
| Формат или профиль новее      | `STORAGE_VERSION_UNSUPPORTED`                                        |
| Неизвестная структура         | `STORAGE_FORMAT_UNKNOWN`; некорректный JSON — `STORAGE_DATA_CORRUPT` |
| Текущий профиль               | Работа продолжается; записи сохраняют свои проверки версий           |

Запись с чужим `dataVersion` при чтении по-прежнему даёт `STORAGE_DATA_MIGRATION_REQUIRED`:
маркер не разрешает пропустить шаг. Расхождение manifest и записей ищут только
`storage status` и `--dry-run`. Долгоживущий процесс перепроверяет manifest при каждом
захвате замка и сбрасывает кеши при его смене. Строгий parser 0.9.2 отвергает manifest
с `dataModelVersion` до записи данных, поэтому прежний writer на новой базе безопасно отказывает.
Любой recovery (обычное открытие, `storage migrate`) проверяет маркер на диске и маркер,
публикуемый самим WAL, до первого изменения: маркер обязан разобраться как совместимый.
При повреждённом маркере (`STORAGE_DATA_CORRUPT`), неизвестной структуре или формате
(`STORAGE_FORMAT_UNKNOWN`) и формате или профиле новее поддерживаемого
(`STORAGE_VERSION_UNSUPPORTED`) незавершённый WAL не исполняется, база и `pending.json`
сохраняются; `storage status` и `--dry-run` дают `invalid` или `unsupported`, а не
`recovery-required`, `migrate` отказывает до резервной копии. Отсутствие маркера допустимо,
только если сам WAL публикует совместимый маркер (инициализация); иначе — `STORAGE_FORMAT_MISSING`
до записи на всех входах, `pending.json` сохраняется.

В едином формате корень данных — реальный каталог, содержащий конфигурацию проекта
и маркер, а не прежнее значение `storageDir`. `Workspace.withEntityStorage` использует
`realpath` и блокировку этого каталога: symlink не должен давать отдельный замок.
Выбор проекта и размещение конфигурации описывает
[Project runtime](../../project-runtime/docs/CONFIGURATION.md).

## Постоянные и служебные файлы

Все пути ниже относительны корню выбранной базы.

```text
config.json
storage.json
entities/<collection>/<id>.json
keyspaces/<id>.json
relations/<collection>/<owner-id>.json
relations/<collection>/<owner-id>/<hash-prefix>.json  # только сегментированные наборы
.indexes/state.json
.indexes/segments/<первые-2-символа-хеша>/<sha256>.json
.indexes/product-catalog.json                      # производный кеш продукта
transactions/pending.json                          # только незавершённый WAL
runtime/                                           # замок и временные файлы
```

Имя конфигурационного файла может задаваться явно; `config.json` выше — обычный вариант.
`runtime/index-stale.json` отмечает обнаруженное внешнее изменение. Служебные каталоги
`runtime`, `transactions`, `.indexes` создаются с `.gitignore`; это не разрешение
удалять незавершённый WAL.

`entity-store/codecs.ts` выводит коллекции из реестра схем:
`projects`, `products`, `features`, `scenarios`, `applications`, `implementations`,
`boards`, `tasks`, `documents`, `work-plans`, `releases`.
`workspaceStorageRegistry` в `storage/unified-adapter.ts` добавляет технические коллекции:

- `scopes` — состав приложения с ID и ревизией, без публичного ключа и карточки;
- `plan-stages` — записи совместимости прежних адресов этапов (`plan-stage` v2,
  `data: { planId }`), см. [ниже](#перенос-планирования-v1);
- `release-snapshots`, `release-snapshot-entries` — исторические снимки выпуска v1,
  данные в дисковой форме замороженной схемы, без публичного адреса и DTO.

Публичных операций над этими тремя видами нет; запись `plan-stage` сессия разрешает
только исполнителю миграции, иначе отвечает `ENTITY_RELOCATED` или `ENTITY_DELETED`.
Новый проект создаётся сразу в формате 4 с текущим профилем, без промежуточных
legacy-каталогов.

Нет постоянных автоматических `history`, `audit`, `events`, `receipts`, `requests`
или результатов команд. Имена совместимых методов и полей старых адаптеров не означают,
что их прежнее содержимое сохраняется в формате 4. Ответ операции может содержать
квитанцию, но она не записывается для будущего повтора.

## Записи и кодеки

Переносимые оболочки определены в `packages/contracts/src/storage.ts`.
Live-запись содержит `kind`, `id`, `key`, `aliases`, `revision`, `dataVersion`,
`data`, даты и авторов создания/изменения. Для технического владельца `key: null`.
Задача может содержать `comments` и `commentSequence`; комментарий — полное
пользовательское содержание, а не автоматическое событие изменения.
Номер последовательности может иметь пропуски после переноса прежней смешанной ленты.

Надгробие сохраняет идентичность и резервы адресов с фактом удаления `deleted`,
но не полное предметное содержание удалённой записи. Перенесённые резервы без
сохранившегося владельца могут находиться в `reservedKeys` записи проекта.
`keyspaces` сохраняет владельца, вид и префикс нумерации; следующий номер производен.

`EntityStorageRegistry` проверяет уникальность вида и коллекции, ID-путь, оболочку,
версию данных, публичность ключа и схему после декодирования. Запись адаптера может
принимать прежнюю версию оболочки в памяти, но `encode` всегда пишет оболочку 3.

`markdownCodec` преобразует только явно перечисленные поля:

- задача: описание и описания критериев;
- документ: тело и описания отношений;
- план: цель, обоснование, границы, ожидаемый/итоговый результат,
  результаты и условия завершения этапов;
- остальные текстовые владельцы: `description`; проект и доска не имеют такого преобразования.

Преобразование — `split("\n")` / `join("\n")`: сохраняются CRLF, пустые строки,
завершающий перевод строки и пробелы. Например, `"a\r\n\n"` кодируется как
`["a\r", "", ""]`. Краткий обычный текст остаётся строкой.
Комментарии и описания рёбер кодируются своими адаптерами по тому же принципу.
Нельзя добавлять `trim` или нормализацию текста в техническое чтение/перенос.

## Сохраняемые группы отношений

`entity-store/relations.ts` хранит набор по владельцу; каждая запись набора имеет
`slot` и ребро. Владелец не обязан совпадать с `from`. Набор до 256 записей и менее
1 МиБ хранится inline; больший делится по префиксу SHA-256 ID ребра. Манифест владельца
содержит контрольные суммы сегментов. Это постоянные данные, не производные индексы.

`replaceOwnedRelations(session, owner, slot, desired, actor)` сопоставляет существующие
рёбра по типу и концам, сохраняет ID неизменённых, обновляет описание и отзывает
исчезнувшие из выбранной группы. Чужие `slot` не заменяются. Отозванное ребро хранится
с `active: false`; метаданные его текущего состояния не являются лентой событий.
Тип и концы существующего ID неизменяемы: смена цели требует другого ребра.

Прикладные вызовы синхронизации расположены в `application/entities/owned-relations.ts`,
`application/planning/relations.ts`, `application/releases/relations.ts` и документном
workflow. Чтение и `reindex` используют сохранённые наборы, а не выводят рёбра из полей.
Публичная диагностика не может перезаписать управляемые группы (`RELATION_MANAGED`).

## Индексы и чтение

`HashIndex` — неизменяемое дерево JSON-сегментов: SHA-256 содержимого задаёт путь,
SHA-256 ключа — ветвление. Лист ограничен 1024 записями и 1 МиБ. Общий кеш процесса
ограничен 64 МиБ / 4096 сегментами; ключ кеша включает реальный путь базы.
`.indexes/state.json` публикует корни и версию снимка.

Индексы содержат адреса/алиасы и резервы, карточки, селекторы, нумерацию, записи,
рёбра и смежность, настройки проекта и контрольные суммы постоянных файлов.
`application/entities/storage-projection.ts` актуализирует карточки перед публикацией.
Обычное открытие не выполняет полный обход базы и не перестраивает индексы.

Полный контекст читает карточки и индекс смежности из одного заблокированного снимка,
а не открывает каждый предметный файл на каждом переходе. Бюджет `FullContextReader`:
250 000 узлов, 500 000 рёбер и 128 МиБ JSON; превышение — `CONTEXT_TOO_LARGE`.
Это предел алгоритма, не обещание производительности или предел heap процесса.
Контракт полного контекста и отличие от диагностики — в
[предметной странице](../../../docs/domain/CONTEXT.md).

## Сессия, конкуренция и WAL

1. `Workspace.locked` берёт общий замок и восстанавливает уже начатый WAL обычной
   операции; WAL миграции он не исполняет (см. [ниже](#исполнение-и-wal-миграции)).
2. `Workspace.mutate` исполняет действие в общей `StorageSession` через
   `AsyncLocalStorage`. Вложенные репозитории видят подготовленные изменения,
   но не публикуют независимые части операции.
3. Прикладной сервис разрешает адреса, проверяет ревизии и цели, сохраняет данные,
   явно согласует отношения. Все эти шаги находятся под тем же замком.
4. `StorageSession.prepare` готовит файлы и индексы. `StorageTransaction.publish`
   проверяет исходные отпечатки, затем долговечно сохраняет `transactions/pending.json`.
5. Recovery сначала проверяет весь пакет: текущее содержимое каждого пути должно
   совпадать с исходным или уже целевым. Далее публикуются данные, отношения, индексы,
   состояние индексов и маркер. После успеха WAL удаляется с синхронизацией каталога.

Читатели держат тот же замок; атомарная замена одного файла не обеспечивает
атомарность всего предметного действия. Проверка владения замком сопровождает запись.
При несовместимой внешней правке возникает `STORAGE_WRITE_CONFLICT` или
`STORAGE_RECOVERY_CONFLICT`; оставшийся WAL нельзя стирать или заменять кешем.

Бюджет предметных данных записи — 16 МиБ, пакета WAL — 128 МиБ.
В оболочке 3 массив комментариев исключён из этих предметных бюджетов; его ограничения
задаёт сценарий комментариев. Поэтому эти числа не являются универсальным максимумом
размера файла с комментариями.

`requestId` — только корреляция. `StorageSession.execute` и `EntityStore.run` не ищут
сохранённый результат: повтор выполняется заново. После потери ответа проверяют состояние;
после `REVISION_CONFLICT` перечитывают запись и согласуют ввод, а не подставляют новую
ревизию в устаревший полный объект.

## Миграция и обслуживание

Обслуживание открытой базы принадлежит `application/storage/service.ts` (`StorageService`),
миграция модели данных — `application/storage/maintenance.ts` и `storage/data-model/`.

| Действие                                     | Что делает                                                               | Чего не делает                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| `StorageService.initialize`                  | Создаёт новый проект сразу в формате 4 с текущим профилем                | Не перезаписывает существующую базу                              |
| `inspectStorage` (`storage status`)          | Полная диагностика минимальным reader под замком обслуживания            | Не выполняет recovery, reindex, миграцию, mkdir постоянных путей |
| `planStorageMigration` (`migrate --dry-run`) | Диагностика и подготовка всех шагов в памяти, бюджеты, `planFingerprint` | Не создаёт backup, WAL, индексы и иные файлы                     |
| `migrateStorage` (`storage migrate`)         | Перенос до текущего профиля одной публикацией WAL с проверенным backup   | Не запускается автоматически при чтении, старте или установке    |
| `StorageService.migrate`                     | Тонкая обёртка над `migrateStorage` для открытого Workspace              | Не имеет собственных правил переноса                             |
| `StorageService.reindex`                     | Проверяет текущие постоянные файлы и перестраивает производные индексы   | Не мигрирует данные и не создаёт предметные связи                |
| `StorageService.reconcileRelations`          | Явно согласует управляемые группы по текущим предметным полям            | Не меняет ревизии сущностей и не заменяет диагностические группы |

API обслуживания принимает путь файла конфигурации любого имени и не применяет текущую
схему проекта; поиск конфигурации и выбор проекта выполняет
[Project runtime](../../project-runtime/docs/CONFIGURATION.md#доступ-к-обслуживанию-старой-базы).
CLI и runner `scripts/migrate-storage.mts` вызывают одну реализацию. Опции — строгий
объект `{ backupDir?, ifPlan? }`; результаты — схемы `@relay/contracts/storage-maintenance`.
`product migrate` и `graph migrate` в формате 4 — совместимые no-op, вне его требуют
общего переноса.

### Реестр переходов

`data-model/transitions/index.ts` — единственный список определений поставки;
`productionTransitionRegistry()` проверяет его до работы с базой. Виды определений:

- `record` — локальный переход одной записи владельца `N → N+1`: чистая функция над
  дисковыми данными, вход и выход проверяются замороженными схемами своих версий,
  оболочка (ID, ключи, ревизия, даты) не меняется, надгробие получает только новую `dataVersion`;
- `snapshot` — переход над согласованным снимком проекта для объединения, разделения
  видов и переноса отношений. Он получает только чтение (`SnapshotView`) и возвращает
  набор изменений (`ChangeSet`); доступа к файлам и публикации у него нет;
- `physical` — составной перенос исходной раскладки (`legacy`, `unified-1/2/3`) в формат 4;
  записи выходят в оболочке 3 с исходными `dataVersion`, дальше работают предметные цепочки.

Обход строится из реестра хранения и каталога исторических видов
(`data-model/history/catalog.ts`), а не из списка в движке: коллекция без вида даёт
`UNKNOWN_ENTITY_KIND`, версия без входа перехода — `STORAGE_TRANSITION_MISSING`,
версия выше целевой — `STORAGE_VERSION_UNSUPPORTED`. Порядок предметных шагов строит
реестр; движок и planner не ветвятся по видам и semver.

Ошибки определения — `STORAGE_REGISTRY_INVALID` с `details.reason`: повтор или недопустимый
ID, шаг не `N → N+1`, немонотонный выход, цикл, два перехода из одной версии, разрыв
цепочки до цели, неизвестная зависимость или вид, профиль, не совпадающий с владельцами
`workspaceStorageRegistry`, выход шага, не совпадающий по JSON Schema со входом следующего
шага или с дисковой схемой текущего кодека. `registryDigest` — SHA-256 канонического
описания профилей, видов и переходов (ID, версия, вход/выход как JSON Schema); он входит
в отпечаток плана и в WAL миграции.

Исторические схемы лежат в `data-model/history/`: строгие дисковые формы без defaults,
transform и импорта изменяемых текущих схем, с заголовком происхождения (SHA, команда
`git show`, фикстура). Номер релиза Relay коммиту без тега не приписывается.

### Диагностика и план

Reader `data-model/source/reader.ts` читает сырую конфигурацию и manifest, обходит базу
через `lstat` без перехода по symlink, считает размер и SHA-256 каждого файла, проверяет
JSON и UTF-8 и классифицирует пути. Файлы обрабатываются по одному: байты не удерживаются
после разбора; в памяти остаются только метаданные, разобранные страницы индекса и WAL. Внутри управляемой области (конфигурация, маркер,
`entities`, `relations`, `keyspaces`, `.indexes`, `transactions`, `runtime`, каталоги
legacy-раскладки) неизвестный файл, symlink или повреждение — блокер; посторонний объект
вне неё — предупреждение `STORAGE_FOREIGN_FILE`, он сохраняется. Отметка
`runtime/index-stale.json` и расхождение индекса с файлами — предупреждения: миграция
строит индексы заново. Потеря ожидаемой индексом записи — блокер, не удаление.
Проверяются деревья страниц всех корней `.indexes/state.json` по правилу `HashIndex`:
каждая страница занимает ровно одну позицию (префикс хеша ключа) и проверяется один раз,
поэтому обход ограничен числом страниц на диске; ключи листа уникальны и принадлежат
префиксу ветви. Повторная ссылка на страницу или чужой префикс — нарушение структуры.
Отсутствие `state.json` или корня, который построитель обязан создать для имеющихся данных,
равносильно потере страницы: `records`, `file-hashes` — при записях, `addresses` —
при адресуемых, `cards` — при действующих адресуемых, `edges` — при любом ребре,
`adjacency` — только при активном (`edgeIndexRoots`), `configuration` — при действующем
проекте и кодеке с индексами; пустой корректный индекс потерей не считается. Потерянная или повреждённая
страница рабочего индекса (`cards`, адреса, рёбра и др.) при целых записях у базы без шагов —
блокер `STORAGE_INDEX_STALE` со следующим действием `storage reindex` (`invalid`, no-op
отказывает, скрытой пересборки нет); перенос, который и так строит индексы заново,
получает предупреждение. Повреждение дерева `file-hashes` остаётся `STORAGE_DATA_CORRUPT`:
без него потерю записей проверить нельзя.
В формате 4 явные `status`, `dry-run` и `migrate` проверяют весь постоянный набор: каждую
запись схемой её версии, а наборы отношений (манифест владельца, сегменты, их отпечатки,
повторы ID рёбер) и пространства ключей — строгими замороженными схемами
(`source/unified-sets.ts`, те же, что у физических переходов). Неизвестное поле или объект —
блокер до пересборки, а не молчаливое удаление. Затем выполняется та же полная проверка
согласованности, что у подготовки переноса (`plan/integrity.ts`): уникальность ключей
и алиасов, комментарии, предметные ссылки (см. ниже), владельцы пространств ключей, концы
активных рёбер (действующие адресуемые записи), глобальная уникальность ID рёбер и
`config.projectId` (по умолчанию `project`) — действующая запись проекта; конфигурация
единого хранилища проверяется текущей схемой. Повреждённая база текущего профиля получает
`invalid` (`STORAGE_ADDRESS_COLLISION`, `STORAGE_REFERENCE_BROKEN` с путём), а не no-op.
Для раскладок до формата 4 явный `status` читает весь набор физическим шагом его
замороженными историческими схемами (чистое чтение, преобразования не исполняются),
поэтому повреждение исторической записи даёт `invalid`, а не `migration-required`.
Обычное открытие этот обход не выполняет.

Статусы: `current`, `migration-required`, `recovery-required` (любой незавершённый WAL),
`unsupported` (новее поддерживаемого, разрыв цепочки, неизвестный вид или формат) и
`invalid` (повреждение, потеря файла, коллизии адресов и комментариев, разорванные ссылки).
Блокеры содержат код, шаг, владельца, безопасный относительный путь или ID и действие;
пользовательский текст и секреты конфигурации в них не попадают.

Замок обслуживания (`source/maintenance-lock.ts`) использует те же lockfile, что writers:
`<realpath корня>/runtime/write.lock`, для legacy сначала замок каталога данных. Два пути
к одной базе получают один замок. Отсутствующий `runtime/` создаётся без `.gitignore`
и удаляется после освобождения, если остался пустым. Если замок нельзя взять без изменения
постоянных данных, возвращается `STORAGE_BUSY` или `STORAGE_UNSAFE_PATH`, чтения без замка нет.

`planFingerprint` — SHA-256 канонического JSON: версия алгоритма, `registryDigest`,
исходные раскладка, физический формат и профиль, целевой профиль, все постоянные пути
обеих областей с SHA-256 (каталоги — `dir`) и упорядоченные шаги `id@version`.
Абсолютных путей, времени и UUID в нём нет. Правка, добавление или удаление файла
и изменение реестра меняют отпечаток; runtime и замки в него не входят.

`plan/prepare.ts` применяет шаги в памяти: физический шаг, затем предметные с проверкой
входа и выхода каждого шага; полная проверка текущими кодеками и общая проверка
`plan/integrity.ts` итогового набора (та же, что у `status` текущей базы): уникальность ключей
и алиасов, комментарии, концы активных связей и ID рёбер, идентичность проекта
в итоговой конфигурации; предметные ссылки по ID в данных
записей и владелец каждого пространства ключей должны указывать на существующую запись вида
или её надгробие, иначе `STORAGE_REFERENCE_BROKEN` с путём независимо от наличия ребра.
Правила ссылок регистрирует владелец вида в кодеке (`EntityCodec.references`, встроенные —
`entity-store/references.ts`, этапы и составы — `unified-adapter.ts`); движок
(`plan/references.ts`) только обходит зарегистрированное, поэтому новый владелец со ссылками
объявляет их вместе с кодеком своей версии. Правило может требовать взаимности
(`inverse`: поле действующей цели обязано ссылаться обратно), так описана принадлежность
части целому. Встроенные правила: доска, родитель, зависимости
и связанные задачи, продуктовые цели, приложение, фича и сценарий, состав приложения, цели
документа, проект, задачи этапов, области плана (включая продукт и проект), планы релиза,
план прежнего этапа. Итоговая конфигурация проверяется схемой целевого профиля
(`config` реестра — текущая `configSchema`): иначе `STORAGE_DATA_CORRUPT` с её путём, так
как результат должен открываться обычным `Workspace`. Отдельного перехода конфигурации нет:
по `git log -p` схем конфигурации (`src/domain/config.ts` с 1efc794,
`packages/core/src/domain/config.ts`, настройки проекта) схема только расширялась
необязательными полями и значениями по умолчанию, а встроенный аудит настроек проекта
`projectSettings.requests/events` (bf95518…1afe138) текущая схема принимает; поля `history`
в конфигурации не было ни в одной версии; построение индексов заново
в отдельной сессии; бюджеты. Dry-run и исполнение используют один путь подготовки;
dry-run legacy-раскладки читает её только через чистые readers. Legacy-вход разбирается
замороженными схемами `history/legacy-readers-4321233.ts` (последнее объявление поддержки
legacy); прежние значения по умолчанию переход применяет явно. Критерии приёмки задач
версий 1–3, если они есть в файле, сохраняются, а не заменяются пустым списком.

База формата 4 с профилем ниже целевого получает явный шаг `profile.<из>-to-<в>` типа
`profile` («только маркер»): он виден в плане и результате, входит в отпечаток и WAL,
предметные данные не меняет и учитывает проверенные записи.

Счётчики результата `counts`:

- `checked` — записи (live и надгробия), наборы отношений и keyspaces, прошедшие полную
  проверку текущими схемами;
- `changed` — файлы постоянного набора (без `runtime/`), созданные, изменённые или удалённые
  публикацией, включая `.indexes/state.json`, страницы индекса и служебные
  `.indexes/.gitignore`, `transactions/.gitignore`, создаваемые сразу после публикации
  (категория `service` в `changes.files`); сумма
  `counts.owners[категория].changed` равна `changed`;
- `removedByRule` — удалённые распознанные исторические структуры: файлы и вложенные
  счётчики физического шага.

В плане `changes.files[категория]` содержит количества `create`/`update`/`delete`.

### Исполнение и WAL миграции

`migrateStorage` выполняет шаги под одним непрерывным замком:

1. Определить реальный корень, проверить вид WAL, прочитать полный набор источников.
2. Построить план; при `ifPlan`, не равном отпечатку, — `STORAGE_PLAN_STALE` до изменений.
   Текущий профиль без шагов — no-op `migrated: false` без backup и изменения файлов.
   Изменяющий план без `backupDir` — `STORAGE_BACKUP_REQUIRED`.
3. Подготовить результат и проверить свободное место корня базы.
4. Создать и проверить резервную копию.
5. Повторно прочитать источники: отпечаток, включая состав каталогов, должен совпасть,
   иначе `STORAGE_PLAN_STALE` (копия сохраняется); проверить владение замком.
6. Подготовить новые неизменяемые страницы индекса во временной области
   `runtime/migration-pages/`, записать WAL `schemaVersion: 2` (в intent — только SHA-256
   страниц, поле `pages`), перенести страницы в `.indexes/segments` и опубликовать фазами: `entities` и прочие записи (keyspaces, конфигурация, удаления
   исходников) → `relations` → прежние журналы → `.indexes` → `.indexes/state.json` →
   `storage.json`. Маркер с целевым `dataModelVersion` публикуется последним и означает
   завершённый профиль. После публикации WAL удаляется, затем вне WAL создаются служебные
   `.gitignore` каталогов `runtime`, `transactions`, `.indexes` и удаляются производные
   runtime-следы и опустевшие прежние каталоги.

До записи intent постоянный набор не меняется: сбой оставляет исходную базу и, возможно,
следы в `runtime/` (`runtime/<uuid>.json`, `runtime/migration-pages/`); их удаляет под
замком следующий `migrate` или продолжение. WAL v2 дополнительно хранит `migration`: ID,
`registryDigest`, `planFingerprint`, источник и цель, упорядоченные `id@version`, путь и
SHA-256 manifest резервной копии, итог плана `report` (шаги, счётчики, число сущностей —
продолжение возвращает его без пересчёта), SHA-256 страниц индекса `pages`, отпечатки
`unchanged` (путь и SHA-256 байтов каждого принятого постоянного файла управляемой области
корня, который публикация не меняет, включая конфигурацию любого допустимого имени, в том
числе Unicode; пути изменений WAL v2 и физического reader источника допускают такое же
безопасное имя, без `..`, абсолютной части и symlink) и, если перед планированием был восстановлен
обычный WAL, его SHA-256. WAL v2 без `report` (предварительная
сборка) продолжить нельзя: `storage status` даёт `unsupported`, `migrate` —
`STORAGE_VERSION_UNSUPPORTED`; следующий шаг — восстановление резервной копии.
Строгий parser 0.9.2 принимает только WAL `schemaVersion: 1` и отвергает v2 до записи.

Обычный recovery (`Workspace`, watcher, любой запрос) завершает только WAL v1;
при WAL v2 он ничего не публикует и отвечает `STORAGE_RECOVERY_REQUIRED`
(`details.reason: migration`); для WAL v2 без `report` — `STORAGE_VERSION_UNSUPPORTED` с тем же
следующим шагом, что у `storage status`. Повторный `migrateStorage` продолжает WAL v2 без
`backupDir`: проверяет известность переходов и профиля, наличие manifest копии с тем же
SHA-256, её завершённость и SHA-256 каждого файла, затем допубликовывает подготовленный
результат без повторных преобразований (`resumed: true`). Пропавшая или изменённая копия —
`STORAGE_BACKUP_MISSING` (`details.reason`, например `file-hash`), WAL сохраняется. Если копия
испорчена до записи WAL, ответ тот же, но база не изменена, и следующий шаг — новый запуск
с `--backup-dir`. Посторонняя правка пути из WAL,
удаление или правка файла из `unchanged` и новый файл в `entities/`, `relations/` или
`keyspaces/` вне плана — `STORAGE_RECOVERY_CONFLICT` с этим путём до публикации; WAL и копия
сохраняются. После продолжения опубликованная база проверяется полностью: блокеры дают
ошибку с машинной причиной, а не успешный результат. WAL неизвестной или
будущей версии блокирует любую запись (`STORAGE_VERSION_UNSUPPORTED`/`STORAGE_DATA_CORRUPT`).

Если перед миграцией остался WAL обычной операции или журнал legacy-репозитория, нужен
`backupDir`: копия создаётся вместе с этим WAL, затем под тем же замком выполняется
существующий recovery и план строится заново. С `ifPlan` такой запуск сразу отвечает
`STORAGE_PLAN_STALE` без копии и recovery: запустите без `--if-plan`.

### Резервная копия

`data-model/backup.ts` создаёт под `backupDir` новый каталог
`relay-backup-<projectId>-<UTC-время>-<8 hex>` (без перезаписи существующих). Реальный путь
`backupDir` не может находиться внутри корня базы, каталога legacy-данных или Git-рабочей
копии, содержащей базу (`STORAGE_UNSAFE_PATH`); отсутствующий `backupDir` создаётся по
одному каталогу. Каждое новое имя — недостающие предки `backupDir` и сам каталог копии —
закрепляется fsync родителя до копирования; ошибка fsync останавливает миграцию до intent.
До копирования проверяется свободное место: объём копии × 1,05 + 1 МиБ.

Раскладка: `files/config-root/<путь>` и, для legacy с отдельным каталогом данных,
`files/storage-root/<путь>`; `RESTORE.md` с русской инструкцией и `backup-manifest.json`
(формат `relay-storage-backup`, проект, исходные раскладка/формат/профиль, целевой профиль,
`planFingerprint`, признак WAL обычной операции, каталоги, файлы с размером и SHA-256,
итоги, `complete: true`). Копируется весь прочитанный постоянный набор: конфигурация
любого имени, маркер, записи, отношения, индексы, незавершённый WAL, посторонние файлы
и каталоги (рекурсивно; они входят и в отпечаток плана) и пустые каталоги.
Резервная копия не включает `runtime/`: замок процесса `write.lock`, временные копии
атомарной записи `<uuid>.json`, временные страницы индекса миграции `migration-pages/`
и прочие следы процессов — это не данные базы, а скопированный замок мешал бы открыть
восстановленную копию; исключение — `runtime/index-stale.json`, он копируется. Пустой
`runtime/` создаётся при первом открытии. Байты каждого файла сверяются с чтением плана,
пишутся `wx` с fsync файла и каталогов и перечитываются; SHA-256 каждого файла копии
повторно сверяется перед первой публикацией и при продолжении. Manifest пишется последним и тоже
перечитывается. Ошибка записи, fsync или места — `STORAGE_BACKUP_FAILED` или
`STORAGE_INSUFFICIENT_SPACE`: база не изменена, неполный каталог без manifest остаётся.
Копия автоматически не удаляется.

### Физические переходы и удаление по правилу

| Переход                   | Источник                                                                                                 | Происхождение формы |
| ------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------- |
| `physical.legacy-to-4`    | Репозитории `product/`, `boards/`, `task-activity/`, `relations/`, `entity-deletions/`, `relations.json` | c1c353f … 5c7265b   |
| `physical.unified-1-to-4` | Формат 1: оболочка 1, журнал `operations/`                                                               | 90d7b26             |
| `physical.unified-2-to-4` | Формат 2: оболочка 1, журнал `history/<stream>/`                                                         | 68124da … ec4a2cc   |
| `physical.unified-3-to-4` | Формат 3: оболочка 2 с `receipts` и `planningEvents`                                                     | 3875aee             |

Физические переходы читают только через `PhysicalSourceIo`, не пишут, не обращаются
к часам и случайным ID. Комментарии и номера ленты задач из журналов и legacy-ленты
становятся `comments`/`commentSequence`; резервы адресов прежнего индекса — `reservedKeys`
проекта. Разные комментарии с одним ID блокируют перенос. Лента без задачи в legacy —
блокер; комментарии задачи, ставшей надгробием, сохраняются в надгробии вместе с
`commentSequence`, как при текущем удалении задачи.

Удаление разрешено только для распознанных структур; поле не очищается по имени,
лишнее поле — блокер. Категории в `removedByRule` плана и результата:

- файлы: `operation-journal`, `history-journal`, `journal-writer-state`,
  `task-activity-journal`, `graph-history`, `legacy-receipts`, `derived-index`;
  `converted-source` — исходный файл, содержание которого перенесено в записи или отношения;
- вложенные структуры: `record-receipts`, `planning-events` (оболочка 2), `journal-events`
  (журналы 1/2), `legacy-record-events`, `legacy-record-requests`,
  `task-activity-events`, `graph-events` (legacy).

Время технических фактов legacy берётся из данных: проект без событий настроек и созданный
паспорт получают самое раннее `createdAt` прежних записей, синхронизированное управляемое
ребро — `updatedAt` записи-владельца с автором `relay`. Существующие рёбра графа и привязок
сохраняют ID.

### Перенос планирования v1

`planning-v1-to-v2` (snapshot) переносит план v1, отдельные этапы `plan-stage` v1 и релиз v1
из баз до `1afe138` (последний такой коммит — `43d683b`, тегов нет). Входные схемы —
`history/planning-v1.ts`, выход — `history/planning-v2.ts`, сверенный с текущими кодеками.

- Этапы группируются по `planId`. Блокеры: этап без плана или со ссылкой на удалённый план,
  этап v1 у плана v2, чужой проект, задача вне live-задач, повтор задачи в этапах одного
  плана или в двух открытых планах, более 200 этапов.
- `stages` плана: `title`, `summary`, `outcome`, `completionConditions`, `id`, `taskIds`
  без декодирования. Порядок — `rank`, затем `Intl.Collator("en")` с параметрами по
  умолчанию `localeCompare`, затем сравнение кодовых точек. Это фиксирует прежнее правило
  `a.rank - b.rank || a.id.localeCompare(b.id)` независимо от локали процесса.
  `projectId` и `rank` этапа не хранятся. Оболочка и даты плана не меняются.
- Этап становится записью совместимости `plan-stage` v2 с той же оболочкой (ID, ключ
  `STG-N`, алиасы, ревизия, авторы, даты) и `data: { planId }`. Надгробия плана, этапа
  и релиза получают только `dataVersion: 2`. Кодек задаёт `relocation`: индекс сохраняет
  адреса и нумерацию `STG`, карточка технической записи — `status: "relocated"`, `active: false`;
  разрешение адреса без ожидания `plan-stage` даёт `ENTITY_RELOCATED` с `details.from`,
  `to`, `stageId`, `key`. Каталоги, поиск и прогресс такие записи не перечисляют.
- Отношения: в наборе этапа все активные рёбра слота `planning-membership` получают
  `active: false` без изменения ID, ревизии и авторских `updatedAt`/`updatedBy`. В набор плана
  для каждой задачи этапа добавляется `task part-of work-plan` в том же слоте, если
  активного такого ребра ещё нет: детерминированный ID, `revision: 1`, описание, авторы
  и даты — от прежнего ребра `task part-of plan-stage`, при его отсутствии — от
  `updatedAt`/`updatedBy` этапа. Остальные слоты и рёбра с концом `plan-stage`, включая
  диагностические, не меняются. Документ сохраняет `relations[].target.kind: "plan-stage"`
  только для чтения; новое прикрепление к этапу сервис отклоняет `INVALID_REFERENCE`.
- Релиз v2 — данные v1 без `snapshotId`. Снимки `release-snapshot` и записи
  `release-snapshot-entry` v1 сохраняются без изменений. Перенос требует однозначной связи:
  ссылка релиза на существующий снимок, `releaseId` снимка на релиз с этой ссылкой или
  на надгробие релиза, каждая запись перечислена ровно в одном снимке, признак плана записи
  совпадает с `planEntryIds`, у снимков и записей нет наборов отношений и надгробий.
  Иначе — блокер с ID. После переноса те же ссылки объявлены кодеками технических видов
  и проверяются в любом профиле: снимок → релиз (запись или надгробие) и записи `entryIds`,
  запись → снимок `snapshotId`, принадлежность взаимна. Инварианты внутри снимка —
  `entryIds` и `planEntryIds` без повторов, `planEntryIds` входят в `entryIds` — проверяет схема
  кодека `release-snapshot` при каждой проверке записи, независимо от перехода планирования.
  Признак `plan` записи и её присутствие в `planEntryIds` снимка — взаимные ссылки кодеков,
  `plan` допустим только у записи о плане (`item.kind: work-plan`).

### Детерминизм и пределы

Переходы не используют часы, сеть и случайные ID. Новый технический ID —
`deterministicId(transitionId, seed)`: UUID v8 из SHA-256 строки
`relay:migration:<transitionId>:<seed>`; коллизия с существующим или подготовленным ID —
`STORAGE_ADDRESS_COLLISION`. Одинаковые данные и реестр дают одинаковые план, отпечаток
и предметный результат; служебные UUID WAL и `.indexes/state.json.version` в сравнение
не входят.

Бюджеты не ослабляются: предметные данные одной записи до 16 МиБ, пакет WAL до 128 МиБ
(без страниц индекса, которые готовятся в `runtime/migration-pages/`; массив комментариев задачи в бюджет записи
не входит). Физический шаг, как и обычное чтение Core, не ограничивает файл записи целиком:
предел 16 МиБ применяется к записи без `comments`. Planner считает их до изменений, превышение — `STORAGE_LIMIT_EXCEEDED`.
Бюджет WAL (`budgets.walBytes`) — размер того же intent, что запишет публикация (общий
построитель `migrationIntentOf` и `intentBytes`), без массивов комментариев; неизвестные
до исполнения UUID, путь копии (берётся предельная длина 4096) и отпечаток восстановленного
WAL учитываются с запасом. Отдельно считается фактический объём корня `space.rootRequired`:
новые файлы, страницы индекса дважды (временная область и постоянные пути) и WAL целиком
с комментариями. Если каталог копии на той же файловой системе, проверка свободного места
корня добавляет и требуемый объём копии.
Подготовленный результат целиком находится в памяти процесса; пакетной публикации
для больших баз нет.

### Индексы и симптомы

При `reindex` новые неизменяемые страницы подготавливаются отдельно, WAL публикует
корни, затем под замком удаляются неиспользуемые сегменты. Если прежний индекс доступен,
проверяется наличие ожидаемых постоянных файлов: потерянная запись не считается удалением.

| Симптом                                                                       | Следующий шаг                                                                                                                       |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `STORAGE_MIGRATION_REQUIRED`                                                  | Остановить клиентов, выполнить `storage status` и `storage migrate --dry-run`, затем перенос с `--backup-dir`                       |
| `STORAGE_DATA_MIGRATION_REQUIRED`                                             | Запись имеет чужую `dataVersion` при текущем маркере: выполнить `storage status`; не сбрасывать данные                              |
| `STORAGE_VERSION_UNSUPPORTED`                                                 | Открыть базу версией Relay, которая её создала, или новее; не править номера версий вручную                                         |
| `STORAGE_TRANSITION_MISSING`, `UNKNOWN_ENTITY_KIND`, `STORAGE_FORMAT_UNKNOWN` | Поставка не умеет перенести эту структуру; сохранить базу и диагностику, не удалять файл                                            |
| `STORAGE_REGISTRY_INVALID`, `STORAGE_TRANSITION_OUTPUT_INVALID`               | Дефект поставки Relay: реестр или результат перехода неверен; база не изменена                                                      |
| `STORAGE_PLAN_STALE`                                                          | Повторить `--dry-run` и использовать новый отпечаток; после восстановления операции — запуск без `--if-plan`                        |
| `STORAGE_BACKUP_REQUIRED`, `STORAGE_UNSAFE_PATH`                              | Передать `--backup-dir` вне базы и Git-рабочей копии                                                                                |
| `STORAGE_BACKUP_FAILED`, `STORAGE_INSUFFICIENT_SPACE`                         | Освободить место или выбрать другой каталог; база не изменена, неполная копия не удаляется сама                                     |
| `STORAGE_BACKUP_MISSING`                                                      | Вернуть копию по пути из WAL, не удаляя `transactions/pending.json`, и повторить `storage migrate`                                  |
| `STORAGE_RECOVERY_REQUIRED`                                                   | Для `details.reason: migration` повторить `storage migrate`; иначе — локальное обслуживание с копией                                |
| `STORAGE_FORMAT_MISSING`                                                      | Восстановить достоверный маркер; не инициализировать «пустую» базу поверх записей                                                   |
| `STORAGE_INDEX_CORRUPT`                                                       | Различить потерю производного индекса и постоянного файла; первый восстанавливается `reindex`, второй требует восстановления данных |
| `STORAGE_INDEX_STALE`                                                         | Проверить внешнюю правку, выполнить явный `reindex` для согласованных данных и перечитать записи                                    |
| `STORAGE_RECOVERY_CONFLICT`                                                   | Сохранить WAL и копию, выяснить конфликтующий путь и восстановить согласованное исходное/целевое состояние                          |
| `ENTITY_RELOCATED`                                                            | Использовать адрес плана из `details.to` и этап `details.stageId`                                                                   |

Файловый наблюдатель передаёт изменённые пути в `checkExternalChanges`; тот сравнивает
их с индексом отпечатков и ставит `runtime/index-stale.json`. Это не постоянный полный
сканер всех внешних изменений при каждом чтении. Проверки механизмов — в
[разработке Core](DEVELOPMENT.md).
