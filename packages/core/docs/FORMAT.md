# Физическое хранение Core

Эта страница объясняет устройство файлов и безопасное сопровождение хранилища.
Наблюдаемые гарантии находятся в [предметном контракте](../../../docs/domain/STORAGE.md),
пользовательское восстановление — в [руководстве](../../../docs/guides/RECOVERY.md).
Файлы базы не являются альтернативным публичным API записи.

## Версии и корень базы

Текущий маркер `storage.json` содержит `format: "relay-entities"`, `schemaVersion: 4`
и необязательный `productId` для совместимости прежнего продуктового агрегата.
Проверяются разные уровни версии:

| Уровень                                                         | Текущее значение                | Назначение                                   |
| --------------------------------------------------------------- | ------------------------------- | -------------------------------------------- |
| Маркер базы                                                     | 4                               | Физическая организация хранения              |
| Оболочка live-записи и надгробия                                | 3                               | Общие поля текущей записи                    |
| `dataVersion` плана и релиза                                    | 2                               | Предметные данные этих видов                 |
| `dataVersion` остальных встроенных видов и технического `scope` | 1                               | Предметные данные соответствующего владельца |
| `revision`                                                      | Изменяется предметной операцией | Compare-and-swap содержимого агрегата        |
| `.indexes/state.json.version`                                   | Непрозрачная строка             | Локальный снимок производных индексов        |

В едином формате корень данных — реальный каталог, содержащий конфигурацию проекта
и маркер, а не прежнее значение `storageDir`. `Workspace.withEntityStorage` использует
`realpath` и блокировку этого каталога: symlink не должен давать отдельный замок.
Выбор проекта и размещение конфигурации описывает
[Project runtime](../../project-runtime/docs/CONFIGURATION.md).

## Постоянные и служебные файлы

Все пути ниже относительны корню выбранной базы.

```text
config.json
storage.json
entities/<collection>/<id>.json
keyspaces/<id>.json
relations/<collection>/<owner-id>.json
relations/<collection>/<owner-id>/<hash-prefix>.json  # только сегментированные наборы
.indexes/state.json
.indexes/segments/<первые-2-символа-хеша>/<sha256>.json
.indexes/product-catalog.json                      # производный кеш продукта
transactions/pending.json                          # только незавершённый WAL
runtime/                                           # замок и временные файлы
```

Имя конфигурационного файла может задаваться явно; `config.json` выше — обычный вариант.
`runtime/index-stale.json` отмечает обнаруженное внешнее изменение. Служебные каталоги
`runtime`, `transactions`, `.indexes` создаются с `.gitignore`; это не разрешение
удалять незавершённый WAL.

`entity-store/codecs.ts` выводит коллекции из реестра схем:
`projects`, `products`, `features`, `scenarios`, `applications`, `implementations`,
`boards`, `tasks`, `documents`, `work-plans`, `releases`.
`workspaceStorageRegistry` в `storage/unified-adapter.ts` добавляет техническую
коллекцию `scopes`: состав приложения с ID и ревизией, без публичного ключа и карточки.
Новый проект создаётся сразу в формате 4, без промежуточных legacy-каталогов.

Нет постоянных автоматических `history`, `audit`, `events`, `receipts`, `requests`
или результатов команд. Имена совместимых методов и полей старых адаптеров не означают,
что их прежнее содержимое сохраняется в формате 4. Ответ операции может содержать
квитанцию, но она не записывается для будущего повтора.

## Записи и кодеки

Переносимые оболочки определены в `packages/contracts/src/storage.ts`.
Live-запись содержит `kind`, `id`, `key`, `aliases`, `revision`, `dataVersion`,
`data`, даты и авторов создания/изменения. Для технического владельца `key: null`.
Задача может содержать `comments` и `commentSequence`; комментарий — полное
пользовательское содержание, а не автоматическое событие изменения.
Номер последовательности может иметь пропуски после переноса прежней смешанной ленты.

Надгробие сохраняет идентичность и резервы адресов с фактом удаления `deleted`,
но не полное предметное содержание удалённой записи. Перенесённые резервы без
сохранившегося владельца могут находиться в `reservedKeys` записи проекта.
`keyspaces` сохраняет владельца, вид и префикс нумерации; следующий номер производен.

`EntityStorageRegistry` проверяет уникальность вида и коллекции, ID-путь, оболочку,
версию данных, публичность ключа и схему после декодирования. Запись адаптера может
принимать прежнюю версию оболочки в памяти, но `encode` всегда пишет оболочку 3.

`markdownCodec` преобразует только явно перечисленные поля:

- задача: описание и описания критериев;
- документ: тело и описания отношений;
- план: цель, обоснование, границы, ожидаемый/итоговый результат,
  результаты и условия завершения этапов;
- остальные текстовые владельцы: `description`; проект и доска не имеют такого преобразования.

Преобразование — `split("\n")` / `join("\n")`: сохраняются CRLF, пустые строки,
завершающий перевод строки и пробелы. Например, `"a\r\n\n"` кодируется как
`["a\r", "", ""]`. Краткий обычный текст остаётся строкой.
Комментарии и описания рёбер кодируются своими адаптерами по тому же принципу.
Нельзя добавлять `trim` или нормализацию текста в техническое чтение/перенос.

## Сохраняемые группы отношений

`entity-store/relations.ts` хранит набор по владельцу; каждая запись набора имеет
`slot` и ребро. Владелец не обязан совпадать с `from`. Набор до 256 записей и менее
1 МиБ хранится inline; больший делится по префиксу SHA-256 ID ребра. Манифест владельца
содержит контрольные суммы сегментов. Это постоянные данные, не производные индексы.

`replaceOwnedRelations(session, owner, slot, desired, actor)` сопоставляет существующие
рёбра по типу и концам, сохраняет ID неизменённых, обновляет описание и отзывает
исчезнувшие из выбранной группы. Чужие `slot` не заменяются. Отозванное ребро хранится
с `active: false`; метаданные его текущего состояния не являются лентой событий.
Тип и концы существующего ID неизменяемы: смена цели требует другого ребра.

Прикладные вызовы синхронизации расположены в `application/entities/owned-relations.ts`,
`application/planning/relations.ts`, `application/releases/relations.ts` и документном
workflow. Чтение и `reindex` используют сохранённые наборы, а не выводят рёбра из полей.
Публичная диагностика не может перезаписать управляемые группы (`RELATION_MANAGED`).

## Индексы и чтение

`HashIndex` — неизменяемое дерево JSON-сегментов: SHA-256 содержимого задаёт путь,
SHA-256 ключа — ветвление. Лист ограничен 1024 записями и 1 МиБ. Общий кеш процесса
ограничен 64 МиБ / 4096 сегментами; ключ кеша включает реальный путь базы.
`.indexes/state.json` публикует корни и версию снимка.

Индексы содержат адреса/алиасы и резервы, карточки, селекторы, нумерацию, записи,
рёбра и смежность, настройки проекта и контрольные суммы постоянных файлов.
`application/entities/storage-projection.ts` актуализирует карточки перед публикацией.
Обычное открытие не выполняет полный обход базы и не перестраивает индексы.

Полный контекст читает карточки и индекс смежности из одного заблокированного снимка,
а не открывает каждый предметный файл на каждом переходе. Бюджет `FullContextReader`:
250 000 узлов, 500 000 рёбер и 128 МиБ JSON; превышение — `CONTEXT_TOO_LARGE`.
Это предел алгоритма, не обещание производительности или предел heap процесса.
Контракт полного контекста и отличие от диагностики — в
[предметной странице](../../../docs/domain/CONTEXT.md).

## Сессия, конкуренция и WAL

1. `Workspace.locked` берёт общий замок и восстанавливает уже начатый WAL.
2. `Workspace.mutate` исполняет действие в общей `StorageSession` через
   `AsyncLocalStorage`. Вложенные репозитории видят подготовленные изменения,
   но не публикуют независимые части операции.
3. Прикладной сервис разрешает адреса, проверяет ревизии и цели, сохраняет данные,
   явно согласует отношения. Все эти шаги находятся под тем же замком.
4. `StorageSession.prepare` готовит файлы и индексы. `StorageTransaction.publish`
   проверяет исходные отпечатки, затем долговечно сохраняет `transactions/pending.json`.
5. Recovery сначала проверяет весь пакет: текущее содержимое каждого пути должно
   совпадать с исходным или уже целевым. Далее публикуются данные, отношения, индексы,
   состояние индексов и маркер. После успеха WAL удаляется с синхронизацией каталога.

Читатели держат тот же замок; атомарная замена одного файла не обеспечивает
атомарность всего предметного действия. Проверка владения замком сопровождает запись.
При несовместимой внешней правке возникает `STORAGE_WRITE_CONFLICT` или
`STORAGE_RECOVERY_CONFLICT`; оставшийся WAL нельзя стирать или заменять кешем.

Бюджет предметных данных записи — 16 МиБ, пакета WAL — 128 МиБ.
В оболочке 3 массив комментариев исключён из этих предметных бюджетов; его ограничения
задаёт сценарий комментариев. Поэтому эти числа не являются универсальным максимумом
размера файла с комментариями.

`requestId` — только корреляция. `StorageSession.execute` и `EntityStore.run` не ищут
сохранённый результат: повтор выполняется заново. После потери ответа проверяют состояние;
после `REVISION_CONFLICT` перечитывают запись и согласуют ввод, а не подставляют новую
ревизию в устаревший полный объект.

## Миграция и обслуживание

Владелец сценариев — `application/storage/service.ts` (`StorageService`).

| Действие             | Что делает                                                             | Чего не делает                                                   |
| -------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `initialize`         | Создаёт новый проект сразу в формате 4                                 | Не перезаписывает существующую базу                              |
| `migrate`            | Переносит поддерживаемые legacy-базы и единые версии 1/2/3 в 4         | Не запускается автоматически при чтении                          |
| `reindex`            | Проверяет текущие постоянные файлы и перестраивает производные индексы | Не мигрирует данные и не создаёт предметные связи                |
| `reconcileRelations` | Явно согласует управляемые группы по текущим предметным полям          | Не меняет ревизии сущностей и не заменяет диагностические группы |

Реальный перенос выполняет `storage migrate`; `product migrate` и `graph migrate`
в формате 4 — совместимые no-op, вне его требуют общего переноса.
Опции `StorageMigrationOptions` сейчас — строгий пустой объект.
Для актуального формата перенос возвращает `migrated: false`.

Перенос сохраняет текущие данные, ID, ревизии, авторство, комментарии, алиасы,
резервы адресов и отношения; прежние автоматические события и квитанции не переносятся
как история. Исходники и контрольные суммы проверяются до публикации. Неизвестная
коллекция или нераспознанный файл не дают права удалить его как предполагаемый аудит.
Неподдерживаемая предметная версия плана/релиза отклоняется: общий переход физического
формата не реализует миграцию их старого состава. Нельзя подменять его пустым.

При `reindex` новые неизменяемые страницы подготавливаются отдельно, WAL публикует
корни, затем под замком удаляются неиспользуемые сегменты. Если прежний индекс доступен,
проверяется наличие ожидаемых постоянных файлов: потерянная запись не считается удалением.

| Симптом                           | Следующий шаг                                                                                                                       |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `STORAGE_MIGRATION_REQUIRED`      | На отдельной копии проверить применимость явного переноса                                                                           |
| `STORAGE_DATA_MIGRATION_REQUIRED` | Проверить версию вида и наличие зарегистрированного перехода; не сбрасывать данные                                                  |
| `STORAGE_FORMAT_MISSING`          | Восстановить достоверный маркер; не инициализировать «пустую» базу поверх записей                                                   |
| `STORAGE_INDEX_CORRUPT`           | Различить потерю производного индекса и постоянного файла; первый восстанавливается `reindex`, второй требует восстановления данных |
| `STORAGE_INDEX_STALE`             | Проверить внешнюю правку, выполнить явный `reindex` для согласованных данных и перечитать записи                                    |
| `STORAGE_RECOVERY_CONFLICT`       | Сохранить WAL, выяснить конфликтующий путь и восстановить согласованное исходное/целевое состояние                                  |

Файловый наблюдатель передаёт изменённые пути в `checkExternalChanges`; тот сравнивает
их с индексом отпечатков и ставит `runtime/index-stale.json`. Это не постоянный полный
сканер всех внешних изменений при каждом чтении. Проверки механизмов — в
[разработке Core](DEVELOPMENT.md).
