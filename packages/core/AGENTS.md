# Работа в Core

Инструкция для любого исполнителя, включая QA, в `packages/core`.
Общие правила — в [корневом AGENTS.md](../../AGENTS.md).
Здесь принадлежат предметные сервисы и хранение; изменения других владельцев
согласуйте с оркестратором, не переносите их ответственность в Core.

## Перед изменением

- Начните с [README](README.md) и [архитектуры Core](docs/ARCHITECTURE.md).
- Если назначение Relay и границы неизвестны, прочитайте [PRODUCT](../../docs/PRODUCT.md)
  и [ARCHITECTURE](../../docs/ARCHITECTURE.md). Далее выбирайте только затронутую
  [возможность](../../docs/CAPABILITIES.md) и её [предметный контракт](../../docs/domain/README.md),
  а не весь общий комплект документов. Контракт прочитайте до изменения реализации.
- Для записи, удаления и recovery обязательны [STORAGE](../../docs/domain/STORAGE.md)
  и затронутый раздел [FORMAT](docs/FORMAT.md); актуальные версии берите оттуда.
  Для отношений дополнительно прочитайте [CONTEXT](../../docs/domain/CONTEXT.md).
- При изменении схем используйте [контракт Contracts](../contracts/docs/API.md).

## Границы реализации

- Выполняйте предметный сценарий через сервис владельца и общую запись Workspace;
  не создавайте обход инвариантов низкоуровневым CRUD или бизнес-логику у клиента.
- Разрешение целей, проверка ревизий, запись данных и явное согласование отношений
  должны оставаться в общей сессии. Проекция при чтении не доказывает запись связи.
- Сохраняйте внешний Markdown строкой; дисковый кодек не должен терять содержание.
  Не переносите в новое поведение старые ожидания history, квитанций и дедупликации:
  действующий источник гарантий — STORAGE. Автоматический повтор мутации недопустим.
- Core не оформляет HTTP, терминал или MCP. Подключение нового действия к интерфейсам
  согласуйте отдельно; одна схема не означает готовность всех потребителей.

## Проверка и знания

- Выберите наборы по механизму из [DEVELOPMENT](docs/DEVELOPMENT.md):
  `pnpm --filter @relay/core run typecheck` и адресные тесты, при необходимости
  `pnpm run test:core`. Собственного lint нет; все проверки репозитория не обязательны.
- Для общей записи проверяйте конфликт, сбой между шагами, recovery и обратное чтение
  содержания и отношений; работайте с фикстурами, не с рабочей базой.
- Обновляйте знание у канонического владельца по [DOCUMENTATION](../../docs/DOCUMENTATION.md).
  Проверка документации — адресные Prettier, ссылки и `git diff --check`;
  результат сценария отличайте от успешной типизации.
