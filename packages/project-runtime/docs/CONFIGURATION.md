# Конфигурация и подключение Relay

Этот справочник определяет выбор local/workspace, пути, адреса и идентичность проекта.
Для первого запуска используйте [начало работы](../../../docs/guides/GETTING_STARTED.md),
для команды Server — [USAGE](../../../apps/server/docs/USAGE.md).
Предметная граница базы описана в [проектах](../../../docs/domain/PROJECTS.md).

## Поиск и режим

Приложение выбирает `--config`, затем `RELAY_CONFIG`, затем ищет вверх от текущего
каталога. В каждом каталоге сначала проверяется `relay.workspace.json`, затем
`.relay/config.json`; найденный ближайший файл останавливает поиск.
Ошибка чтения найденного файла не разрешает выбирать другой или создавать пустую базу.
Обычное чтение конфигурации не инициализирует хранилище.

Если конфиг не найден, CLI и Server проверяют возможность подключения внешней Git-базы
по правилам ниже. Явный HTTP-вызов CLI и MCP не запускают локальную установку.

### Внешняя Git-база

Для этого режима нужен Git 2.36+; файловый режим вне Git сохраняет прежние требования.
Git-объекты и ссылки синхронизируются на диск с `core.fsync=all`, `core.fsyncMethod=fsync`.
Эти параметры действуют только в запущенных Relay процессах Git и не меняют Git-конфиг пользователя.

Git-репозиторий без явного/найденного конфига использует настоящий linked worktree
ветки `relay-data` в `~/.relay/{repo-name}-{hash}`. Origin и первый коммит кода для init
не обязательны. Hash — первые 32 hex-символа SHA-256 идентичности канонического
`git-common-dir`. Основной checkout и его worktree разделяют одну базу; независимые
клоны имеют собственные локальные базы и синхронизируются через origin.
Имя берётся из origin, а до его появления — из каталога основного checkout.
Регистрация в общем Git-хранилище сохраняет адрес базы при появлении/смене origin.
`RELAY_HOME` меняет корень при первой установке. Другой RELAY_HOME у уже зарегистрированного
worktree отклоняется, а не создаёт вторую базу того же Git-хранилища.

Для github.com/gitlab.com/bitbucket.org стандартные HTTPS и SSH с пользователем git
сводятся к host/path без суффикса `.git`. Регистр host нормализуется, пути сохраняется.
У прочих hosts схема, SSH-пользователь и нестандартный порт сохраняют различия: алиасы
и разные endpoints не отождествляются догадкой. Вложенные группы входят в идентичность.
Локальные remotes используют абсолютный реальный путь. Credentials не входят в адрес
состояния Relay; для доступа используйте Git credential helper/SSH. Это идентичность
удалённого подключения, а не ключ локального каталога базы.

Первый коммит `relay-data` не имеет родителей: код и его история не входят в ветку.
Индекс worktree отдельный; HEAD, индекс и рабочие файлы кода не меняются. Файл `.git`
внешнего каталога указывает на метаданные worktree внутри общего Git-хранилища.
Origin общий с исходным репозиторием и перечитывается при синхронизации. Конфигурация —
`config.json` в корне базы; `.gitignore` присутствует и в коммите, и в рабочем каталоге.
Удаление исходной `.git` делает worktree неработоспособным: файлы базы сохраняются,
а операции отказывают с `SYNC_GIT_OWNER_MISSING`. Восстановите исходный Git-репозиторий
и связь worktree; приложение не подменяет владельца другой копией.

При отсутствии базы используется существующая локальная ветка `relay-data`, иначе
загружается только эта ветка origin, без тегов и веток кода. Получается вся история
базы, не shallow-копия. Отдельные fetch/push допускают до одного часа; служебные локальные
Git-команды и проверка наличия ветки — до 30 секунд. После передачи данные проверяются
Core, создаются worktree и индексы. Одновременные установки сериализуются замком в общей
`.git`; незавершённая установка сохраняет проверяемое намерение для продолжения.
Если ветки точно нет, возвращается
`RELAY_NOT_INITIALIZED` с предложением `npx @oim-dev/relay-cli init`. Ошибка сети или
доступа — `SYNC_NETWORK_UNAVAILABLE`, а не разрешение создать новую базу.

`init` явно создаёт orphan-ветку и worktree; при наличии origin публикует базу.
Без origin записи сохраняются локально, worker фиксирует их в локальной ветке.
После добавления origin следующее обращение запускает синхронизацию прежних данных;
нового init или пути к config не требуется. Смена origin также сохраняет каталог,
projectId и локальные записи. Новая удалённая ветка создаётся без force-push; существующая
ветка с другим projectId или несвязанной историей останавливает отправку, сохраняя
локальную работу и обе базы. Ошибка сети не считается отсутствием ветки.
Для файловой инициализации используйте явный `--config`; вне Git сохраняется файловый режим.
Существующая `.relay`, workspace и явные конфигурации сохраняют прежний приоритет до
явного переноса. Help/version не устанавливают базу и не обращаются к сети.

`sync migrate --from-config <path>` из каталога исходного Git-проекта переносит
согласованный снимок прежней файловой или самостоятельной Git-базы в worktree.
ProjectId, записи, отношения и неопубликованные изменения сохраняются; у прежней
Git-базы сохраняется также история. Исходная база остаётся резервной копией.
На время перехода остановите её писателей и после него переключите Server на выданный
новый config. Обычный CLI выбирает зарегистрированный worktree вместо перенесённой
`.relay`; явный `--config` позволяет открыть сохранённую исходную копию.
Существующий worktree другой базы и чужая relay-data на origin не заменяются.
Обнаружение неперенесённой или изменённой после переноса прежней внешней копии
даёт `SYNC_WORKTREE_MIGRATION_REQUIRED` с путём исходного конфига. Сохранённая неизменная
резервная копия не мешает независимым клонам подключать ветку origin.

Если удалён только внешний каталог базы, регистрация в `RELAY_HOME/.runtime`
восстанавливает его из локальной ветки в сохранившейся `.git` владельца. Это сохраняет
и локальные коммиты, ещё не отправленные в origin; удалённые незакоммиченные записи
без резерва восстановить нельзя. Утраченные файлы внутри существующего каталога
не исправляются заменой всей базы.

Предметные операции работают с локальной базой без проверки origin перед мутацией.
После WAL отмечается поколение изменений; запуск worker не превращает успешную запись
в сетевую ошибку. Чтения не накапливают отдельные запросы Git. Локальные коммиты
группируются: 2 секунды тишины, максимум 15 секунд накопления. Отдельный сетевой цикл
может ожидать fetch/push, пока тот же worker продолжает локальные коммиты. Server не нужен.
Сетевая ошибка сохраняет очередь и повторяется с backoff 2…60 секунд; локальная работа
не ограничивается. Worker остаётся активным до отправки очереди, без origin или при
разрешаемом вручную конфликте завершается после локального сохранения. Пустая база
проверяется в фоне при обращениях не чаще 30 секунд. Явный запрос сбрасывает backoff.

`relay-local-lock` сериализует локальные Git-публикации отдельно от `relay-sync-lock`
сети. Merge проверяет исходные HEAD и отпечаток постоянных данных перед WAL. Локальный
checkpoint меняет Git ref/index, но не подменяет текущие файлы базы старым снимком.
Поколение `committedGeneration` отдельно от подтверждения origin: поздняя запись остаётся
ожидающей. При запуске worker сверяет базу с HEAD, в том числе после падения между WAL
и уведомлением доставки. Новые поля локального sync-state имеют совместимые defaults;
формат предметной базы не меняется.

Статус доступен через `sync status`, метаданные `overview`, REST `/context/sync` и Web.
`queuedCommits` считает локальные коммиты относительно последнего проверенного origin,
`null` обозначает неизвестное удалённое состояние. Отдельно показываются изменения вне
коммитов, последняя успешная синхронизация, ошибка и следующая попытка. Git-конфликт
приостанавливает только доставку. Полный контракт —
[STORAGE](../../../docs/domain/STORAGE.md#внешняя-git-база).

Для выбора источника перед CLI `init` используется отдельный
`readInitializationConfiguration`: тот же поиск, классификация local/workspace и
схемы конфигурации, но только метаданные самого файла. Он не читает проекцию PROJECT,
manifest или WAL, не открывает Store и не выполняет recovery. Это позволяет проверить
HTTP-намерение и выбрать путь регистрации без изменения существующей базы, даже
если рядом с конфигом осталась незавершённая операция. Ошибочный ближайший конфиг
по-прежнему останавливает поиск; метаданные не подтверждают готовность базы.
Обычный `readConfiguration` сохраняет чтение актуальных проектных настроек через Core
и его штатное восстановление обычного WAL перед чтением. Эта возможность не используется
для preflight инициализации.

| Файл                   | Режим     | Доступ к данным                                               |
| ---------------------- | --------- | ------------------------------------------------------------- |
| `.relay/config.json`   | local     | Одна база; CLI напрямую через Core или по HTTP                |
| `relay.workspace.json` | workspace | Регистрации независимых баз; предметные операции через Server |

Workspace остаётся workspace при одной регистрации и требует выбора проекта.
Он не объединяет базы. MCP всегда подключается к отдельно запущенному Server;
ни MCP, ни project-runtime не запускают API автоматически.

### Создание из шаблона

`init --template` создаёт новую независимую базу из полного снимка Git-репозитория.
Синтаксис и параметры — в [CLI](../../../apps/cli/docs/CLI.md#init), состав копии и
правила смены идентичности — в [контракте хранения](../../../docs/domain/STORAGE.md#создание-проекта-из-шаблона).
Нужен Git-проект без найденной конфигурации Relay; явный config, выбор регистрации
workspace и `--storage` с этим режимом несовместимы. Origin и первый коммит кода
не обязательны. Существующие регистрации, каталоги базы, локальная или удалённая
`relay-data` останавливают установку без замены данных.
Ветка кода не должна называться `relay-data`, включая ещё не имеющую коммита ветку:
`TEMPLATE_BRANCH_IN_USE` требует сначала выбрать другое имя ветки кода.

Источник может быть HTTPS/SSH Git-репозиторием или локальным путём. Авторизацию
обеспечивают штатные Git credential helper/SSH. Ветка по умолчанию — `relay-data`;
можно выбрать ветку, тег или полный SHA коммита. При совпадении имени ветки и тега
нужен явный `refs/heads/...` либо `refs/tags/...`. Выбранный коммит должен содержать
базу в корне дерева (`config.json`, `storage.json`, постоянные коллекции), а не код
приложения. Получение произвольного SHA зависит от доступности объекта на Git-сервере.

Источник загружается в отдельный временный репозиторий. Фактический SHA определяется
после fetch и остаётся неизменным для установки. Core проверяет исходный снимок,
создаёт новую идентичность и проверяет результат с пересобранными индексами. Новый
коммит создаётся в Git-хранилище целевого проекта без родителей; refs, remote и история
шаблона туда не импортируются. Worktree и его регистрация используют штатную идентичность
`git-common-dir`, поэтому все checkout целевого репозитория разделяют эту базу.

Имя без `--name` берётся из нового репозитория, slug создаётся заново. `server` получает
локальные defaults без URL источника, порт MCP — штатное значение, `storageDir` — `tasks`.
Предметные настройки, включая разделы документов, сохраняются. Имя паспорта продукта
и исторические подписи не переименовываются вместе с проектом.

До публикации ref сохраняется проверяемое намерение установки с новым коммитом, ID,
именем, slug и происхождением шаблона. После прерывания повтор той же команды продолжает
этот снимок без повторного скачивания; другой шаблон или явно отличающиеся настройки
дают `TEMPLATE_INSTALL_MISMATCH`. Внешняя правка создаваемой базы даёт
`SYNC_RECOVERY_CONFLICT` и сохраняет данные. Обычное подключение также может завершить
штатное восстановление установки. Повтор после её завершения — `ALREADY_INITIALIZED`.

Готовая база синхронизируется только с origin целевого проекта. Ошибка публикации
сохраняет готовую локальную базу и возвращает `synchronization.status: pending` с причиной;
после исправления подключения выполните `sync now`. Без origin статус — `local`, при
успешной публикации — `synchronized`. Ответ установки сообщает новый ID, пути, фактический
SHA шаблона и результат проверки целостности. Добавление origin позже не требует нового init.

## Проектная конфигурация

Файл создаётся инициализацией CLI. Ниже — поля конфигурации и совместимого представления,
возвращаемого при чтении; это не перечень независимых постоянных данных в `config.json`:

| Поле                                         | Назначение                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------------- |
| `version`                                    | Версия конфигурации, `1`; не физическая версия базы                               |
| `mode`                                       | `local`, если не указан                                                           |
| `projectId`                                  | Постоянная идентичность проекта; не редактировать для переименования              |
| `projectSettings`                            | Проекция предметных настроек проекта в совместимом представлении конфигурации     |
| `storageDir`                                 | Совместимый путь прежнего хранения относительно каталога конфигурации             |
| `server.port`                                | Порт запуска REST, по умолчанию `4700`                                            |
| `server.url`                                 | Необязательный адрес подключения клиентов, не адрес listener                      |
| `mcp.port`                                   | Порт отдельного MCP, по умолчанию `4710`                                          |
| `output`                                     | Настройки вывода: `format`, `defaultLimit`, `maxBytes`                            |
| `defaultStatus`, `readyStatuses`, `statuses` | Совместимые поля конфигурации статусов; не настройка фиксированных колонок Kanban |

У `output` defaults: `text`, `20`, `16384` соответственно. Эти поля не устанавливают
общую форму REST-пагинации. Колонки актуальных задач определяет
[контракт задач](../../../docs/domain/TASKS.md).

В текущем едином формате постоянные настройки проекта принадлежат записи
`entities/projects` внутри базы. При чтении конфигурации Core подставляет их проекцию
в `projectSettings`; её показывают API и `config get`. Сырой `config.json` не является
вторым авторитетным источником имени, slug и ревизии. В legacy-конфигурации эти настройки
могли храниться непосредственно в `projectSettings`; совместимость чтения не меняет
владельца текущих данных. Изменяйте настройки предметными операциями, а не правкой проекции.

В текущем едином формате база с `storage.json` находится в каталоге **выбранного конфига**.
Для стандартного `.relay/config.json` это `.relay`; при явном выборе конфигурации каталог
может быть другим. `storageDir` не переносит единую базу. Для прежнего хранения относительный
`storageDir` считается от каталога выбранного конфига, не от рабочего каталога процесса.
Фактический путь сообщает поле `storagePath` ответа `GET /context`. Если нужен другой
конфиг, задаётся его путь; ручная правка предметных настроек и данных не заменяет операции Core.

## Workspace-реестр

Пример `relay.workspace.json` с обычными defaults без повторения портов:

```json
{
  "version": 1,
  "projects": {
    "shop": { "path": "../shop" },
    "portal": { "config": "../portal/.relay/config.json" }
  }
}
```

`mode` по умолчанию равен `workspace`. Дополнительно допустимы `server` и `mcp`
с теми же назначениями портов. В записи нужен `path` или `config`:

- `path` — каталог проекта; без `config` выбирается `.relay/config.json` внутри него;
- `config` — путь к проектной конфигурации;
- если заданы оба, относительный `config` считается от `path`;
- относительный `path`, а при его отсутствии `config`, считается от каталога реестра.

Ключ регистрации содержит 1–64 буквы/цифры, `_` или `-`, начинается с буквы/цифры.
Регистрация подключает существующий локальный проект, не создаёт базу и не указывает
на другой workspace. Замена требует явного `replace`; удаление регистрации сохраняет
файлы базы. Изменения реестра сериализуются отдельной межпроцессной блокировкой.

Каталог доступен без клиентской копии реестра: CLI `workspace project list` с явным
URL или `RELAY_SERVER_URL` читает как workspace-, так и local-сервер без выбора проекта.
Add/remove требуют workspace на стороне Server. Передаваемые `path` и `config`
разрешаются в файловой системе Server относительно **его** реестра, не cwd клиента.
После изменения перечитайте каталог; `available: false` требует исправления причины
на стороне сервера, а не инициализации новой клиентской базы.

Server с `relay-project-catalog-v1` предоставляет отдельно discovery без чтения баз,
страницу каталога с серверным guard и адресные квитанции регистрации/удаления.
Проверка возможности не требует выбора проекта: `/server/capabilities` отличается
от проектного `/context`. Страница сохраняет сведения о режиме и серверном конфиге;
её версия охватывает весь каталог, включая недоступные регистрации. При конфликте
начните чтение заново, не склеивайте страницы разных состояний.
Квитанция регистрации подтверждает сохранённый path/config, но не доступность базы:
после неё прочитайте каталог или подключитесь к выбранному проекту. Старые полные
ответы сохраняются отдельными маршрутами. Точные формы и пути —
[в REST-контракте](../../server-runtime/docs/API.md#серверные-страницы-и-адресные-квитанции);
доступность конкретного CLI-режима проверяйте в его справочнике.

## Имя, ID, ключ регистрации и slug

| Значение                            | Роль                                                               |
| ----------------------------------- | ------------------------------------------------------------------ |
| `projectId` / `id` в ответе сервера | Постоянная идентичность базы, закрепляемая HTTP-клиентом           |
| `projectSettings.name` / `name`     | Отображаемое имя; не селектор регистрации                          |
| Ключ `projects.shop` / `key`        | Имя регистрации workspace, которое можно переназначить другой базе |
| `projectSettings.slug` / `slug`     | Человекочитаемый Web-адрес проекта; не ID и не ключ регистрации    |

Название продукта также не является ни одним из этих адресов. Смена slug не оставляет
автоматического алиаса. REST принимает ключ регистрации, ID или slug; local также
принимает `local`. В workspace разрешение ищет ключ регистрации, затем ID, затем slug.
Коллизии slug требуют исправления настроек; разные базы с одинаковым ID отклоняются.
Отображаемое имя не следует посылать вместо селектора.

При HTTP ключ, ID или slug разрешает Server независимо от содержимого клиентского
workspace-конфига. Клиентский реестр выбирает подключение, но не ограничивает набор
серверных селекторов своими регистрациями. Отсутствующий/повреждённый явно выбранный
config по-прежнему является ошибкой, не разрешением игнорировать его или перейти на local.

Для длительного подключения используйте ID, полученный от сервера, и не предполагайте
формат UUID: есть короткие ID, а для прежнего конфига без `projectId` сервер вычисляет
совместимый ID из пути. Такой fallback не обещает сохранения ID после переноса конфига.
В `/server` недоступная регистрация помечается `available: false`; её поле `id` не нужно
принимать за подтверждённую идентичность базы.

## Порты, URL и env

| Настройка           | Приоритет                                                   |
| ------------------- | ----------------------------------------------------------- |
| Конфиг приложений   | `--config` → `RELAY_CONFIG` → поиск вверх                   |
| Порт Server         | `--port` → `RELAY_PORT` → `server.port` → `4700`            |
| Автор Server        | `--actor` → `RELAY_ACTOR` → `human`                         |
| URL клиента CLI/MCP | `--server-url` → `RELAY_SERVER_URL` → адрес из конфигурации |
| Порт MCP            | его `--port` → `RELAY_MCP_PORT` → `mcp.port` → `4710`       |

Env разбирают приложения, а не библиотека конфигурации. `RELAY_WEB_PORT` относится
к dev-origin Web (обычно `5173`), не заменяет REST-порт и не требуется обычному запуску.

Порт — целое от `0` до `65535`. Ноль при запуске поручает выбор ОС. `server.url` —
HTTP(S) origin без `/api/v1`, credentials, query и hash, например `http://127.0.0.1:4700`.
Он задаёт подключение, а не меняет порт/host запущенного Server. При отсутствии URL
workspace и MCP получают `http://127.0.0.1:<server.port>`; для `server.port=0` нужен
фактический URL, иначе `SERVER_URL_REQUIRED`. Порт отдельного MCP не является адресом REST.

## Прямой local и local по HTTP

Local — режим проекта, а не обязательный прямой доступ к файлам:

- CLI с проектным конфигом и без URL вызывает Core напрямую. Наличие только
  `server.port` не включает HTTP для CLI.
- URL из флага, env или `server.url` включает HTTP. Явный `--local` у CLI выбирает
  прямой доступ, в том числе для обслуживания; в workspace он отклоняется.
- Workspace CLI использует Server и явный выбор регистрации; один проект не выбирается молча.
- MCP использует HTTP даже с проектным конфигом и берёт адрес из `server.url` либо порта.
- Явный URL позволяет подключиться без найденного локального конфига. Это не разрешение
  игнорировать повреждённый найденный конфиг в обычном поиске CLI.

### Доступ к обслуживанию старой базы

`storage status` и `storage migrate` находят базу через `locateMaintenanceTarget`
(`@relay/project-runtime/maintenance`), а не через обычное чтение конфигурации. Поиск
тот же: вверх от cwd или `--config` с файлом любого имени либо каталогом корня; найдена
и база без конфига, если есть `storage.json` или `transactions/pending.json`. Текущая
схема проекта не применяется, recovery, создание каталогов и запись не выполняются —
старую базу диагностирует reader Core. В workspace обслуживается один проект реестра,
выбранный `--local --project KEY`; реестр только читается. HTTP-режим (URL из флага,
env, `server.url` или реестр без `--local`) даёт `LOCAL_REQUIRED` до любого сетевого
запроса; гард `requireLocalMaintenance` приложение вызывает до подключения.

`storage reindex` и `storage reconcile-relations` требуют прямой проектный config,
не файл workspace. При явном local-вызове с выбранной регистрацией CLI возвращает
`LOCAL_CONFIG_REQUIRED` (exit 2) и `details.configPath`/`details.next` с прямым
`--local --config` выбранной базы. Подсказка не исполняет обслуживание и не обращается
к Server: остановите писателей, сохраните резерв и явно запустите указанное действие.
Это выбор локального пути из реестра, не fallback после HTTP-ошибки.

Обычный Server запускается без дополнительных flags:

```bash
npx @oim-dev/relay-server --open
```

Выбор проекта и особые режимы CLI/MCP описаны в их [README CLI](../../../apps/cli/README.md)
и [README MCP](../../../apps/mcp/README.md). HTTP-ошибка не переключает клиента на local.

## HTTP-адаптер и восстановление подключения

`createHttpBackend` читает `/context`, проверяет capability `relay-projects-v1` и
закрепляет клиент за возвращённым `projectId`. Возможности отдельных операций
проверяются до их вызова: `relay-full-context-v1` — полный контекст графа,
`relay-overview-metrics-v1` — детализация метрик обзора `product.overviewMetric`,
`relay-document-library-v1` — страницы прикреплений/разделов и адресные изменения
`documents.links/sections/changeRelation/changeSection`;
`relay-product-queries-v1` — validate/lint/overviewMap, participation/replaceParticipation
и адресная implementation; `relay-work-read-models-v1` — compact-чтения планов/релизов
и taskDependencies; `relay-release-refs-v1` — createByRefs/updateByRefs релиза;
`relay-entity-search-v2` — новая семантика entities.list при implementationTarget,
при переданном q или sort=updated вне явного kind=document, а также при active/section
без kind;
без них вызов даёт `SERVER_INCOMPATIBLE`, а не 404 маршрута. Переназначение ключа регистрации не
должно переносить существующий клиент на другую базу; исчезновение выбранной регистрации
даёт ошибку. Runtime проверяет конверт и предметные ответы схемами, а не доверяет только
типам SDK.

Отдельное семейство `workHistory` требует `relay-work-history-v1`. Его отсутствие
даёт `UNSUPPORTED` (exit 5), а не общий `SERVER_INCOMPATIBLE`: ни local fallback,
ни запрос старого маршрута не выполняется. Все методы сохраняют закреплённый ID
проекта; мутации передают actor тела либо defaultActor вызова и исходную ревизию
ветки без скрытого перечитывания. Ввод и полные результаты проверяются каноническими
схемами, мутации не повторяются. Параметры истории и продолжение страниц — в
[REST API](../../server-runtime/docs/API.md#история-работы-агентов).

Текущий Server объявляет перечисленные предметные capabilities через выбранный
`/context`. `relay-project-catalog-v1` также объявляется там, но его независимый
discovery доступен через `/server/capabilities` без открытия проекта. Объявление
возможности и наличие схемы не подтверждают актуальность установленного SDK клиента.

Операции библиотеки не обходят отсутствие capability через `entities.get` или локальную
перезапись полных массивов. `entities.get` принимает необязательные сохранённые метаданные
записи: прежний ответ без `metadata` остаётся допустимым, частичный блок — ошибка контракта.
Старый строгий клиент без этого поля может отклонить ответ нового Server: обновляйте
Server и потребителей согласованно, а не полагайтесь на двустороннюю совместимость.

Timeout адаптера — 15 секунд, перенаправления запрещены (`redirect: error`). Для чтений
при транспортном отказе/5xx допускаются не более двух повторов после первой попытки.
`POST /releases/preview` и `/releases/preview/compact` относятся к чтениям.
Записи не повторяются автоматически;
ошибки валидации и конфликты 409 также не запускают retry. Отдельный клиент реестра
`createServerApi` использует timeout/redirect, но не имеет этой петли повторов чтений.

`createServerApi` предоставляет прежние полные операции и новые серверные страницы/
компактные квитанции через generated SDK. До `getProjectCatalogPage`,
`registerProjectCompact` и `unregisterProjectCompact` выполняется лёгкий
`getServerCapabilities`; отсутствие `relay-project-catalog-v1` или 404 discovery даёт
`SERVER_INCOMPATIBLE` (exit 5) до предметного запроса. Полный каталог и local не используются
как скрытый fallback. Успешная capability кешируется только внутри экземпляра клиента;
после ошибки следующий явный вызов может повторить discovery, но текущий не повторяется.
Каталог между запросами не кешируется. Прежние полные операции остаются явным выбором.

Ввод проверяется generated-операциями SDK, ответы — runtime-схемой соответствующего
маршрута и HTTP-метода: полного каталога, capability, страницы или адресной квитанции.
`getProjectCatalogPage` дополнительно проверяет число элементов, согласованность
total/nextOffset и исходной version. Корректного HTTP-статуса недостаточно: неверный JSON,
DTO или несогласованная страница дают `INVALID_SERVER_RESPONSE`, не пустую базу.
После такого ответа на add/remove или потери соединения запись могла завершиться:
сначала перечитайте реестр, не отправляйте изменение автоматически снова. Мутации
не повторяются. Поля прежних результатов сохраняются; compact — отдельные операции.

CLI list использует серверную страницу с прежней формой data и
`meta.paginationSource: server-catalog-fingerprint`. Для add/remove text по умолчанию
выбирает compact, JSON — полный прежний ответ; `--projection compact|full` задаёт выбор
явно. Ошибка capability не переключает проекцию автоматически. Точный синтаксис и
восстановление продолжения — в [CLI](../../../apps/cli/docs/CLI.md#workspace-project-list).

`requestId` — корреляция, не идемпотентность. После потери ответа запись могла завершиться:
перечитайте данные и отношения, а перед повторной публикацией — комментарии.
Нельзя обещать сохранённый первоначальный ответ или автоматически отправлять запись снова.
`SERVER_UNAVAILABLE`, `SERVER_INCOMPATIBLE`, `INVALID_SERVER_RESPONSE` и предметный
конфликт различаются. Например, ответ `GET /product/overview` сервера прежней версии
без `snapshotVersion` и `snapshot` или без `snapshot.operator` даёт `SERVER_INCOMPATIBLE`, а не
`INVALID_SERVER_RESPONSE`: клиент и Server выпускаются одной версией, и Server нужно
обновить и перезапустить. Дальнейшие действия — в [восстановлении](../../../docs/guides/RECOVERY.md).
