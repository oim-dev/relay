# Workspace и границы нескольких проектов

[Карта сценариев](../skill.md). Это дополнительный маршрут: выбери рабочую область,
затем выполняй основной сценарий отдельно в нужном проекте.

## Определи исходную ситуацию

Проверь доступный сервер, реестр, конфигурации и поручение. Выясни, это несколько
программных частей одного продукта или независимые продукты. Не выводи границы Relay
только из числа каталогов, репозиториев, сервисов или worktree.

- Один продукт с frontend/backend может быть одним проектом с несколькими приложениями.
- Workspace — реестр независимых баз; в каждом проекте свой продукт и свои записи.
- Разные worktree одного проекта по поручению могут использовать одну общую базу.
- Отношения, планы и зависимости задач не пересекают границу проекта.

## Что предложить пользователю

Если границы не определены, покажи найденные продукты и программные части и предложи
размещение: один проект с приложениями либо несколько независимых проектов в workspace.
Объясни последствия для общих требований и зависимостей. Уточни спорную границу до init.
Если пользователь уже указал проект, подтверди его по данным без повторного выбора.

## Как действовать

1. Прочитай список регистраций и идентичность нужных баз. Зафиксируй для работы
   соответствие «каталог кода → проект Relay → ключ регистрации / projectId».
2. Для готового workspace выбери существующую регистрацию. Если базы ещё нет,
   инициализируй её отдельно после согласования подготовки; затем добавь регистрацию.
   Регистрация существующей базы сама не создаёт проектные данные.
3. Для нового workspace используй путь первого запуска: реестр, отдельные базы,
   регистрации, Server и проверка CLI через HTTP. Не дублируй уже работающий сервер.
   Передай пользователю фактическую ссылку на Web UI и поясни, какой проект выбрать.
4. В каждой проектной CLI-команде передавай `--project`, даже при одной регистрации.
   Сохраняй выбор при пагинации, чтении связанных записей и проверке результата записи.
5. При переключении заново читай сущность в целевой базе. Одинаковые ключи задач
   в разных проектах не взаимозаменяемы; старые ревизии и выборы не переноси.

## Развилки

- **Поручение касается нескольких проектов:** разложи работу по их границам, предложи
  порядок внешней координации. Общие интерфейсные договорённости можно описать документами
  с адресами внешних источников; они не создают межпроектную связь или автоматический блокер.
- **Проект недоступен:** останови обращения к нему и установи причину. Другая доступная
  база не является заменой. Независимую порученную работу в других проектах можно продолжать.
- **Удаление регистрации:** объясни, что данные базы сохраняются; это не удаление продукта.

Для существующего workspace прочитай реестр, затем выбранную базу. `alpha` замени
проверенным ключом регистрации; при необходимости добавь `--config` и `--server-url`:

```sh
npx @oim-dev/relay-cli projects list
npx @oim-dev/relay-cli --project alpha config get
npx @oim-dev/relay-cli --project alpha boards
```

## Когда этап закончен

Для каждого порученного действия однозначно известна база, она проверена, пользователь
понимает границы. Далее: [новый проект](NEW_PROJECT.md), [внедрение](ADOPT_EXISTING.md)
или [продолжение](RESUME.md). Условия workspace сохраняются на всём основном маршруте.
