# Отдельная задача, баг и техническая работа

[Карта сценариев](../skill.md). Выбирай для конкретного ограниченного изменения,
которому не требуется заново проектировать весь продукт. Размер задачи не определяется
количеством файлов; важны ясность цели, границы и проверяемый результат.

## Определи исходную ситуацию

Найди существующую задачу и относящиеся к ней знания. Для бага различи ожидаемое
и фактическое поведение, собери условия воспроизведения. Для технической работы
выясни полезный результат и ограничения. Если ожидаемое поведение меняется, используй
[изменение продукта](CHANGE.md); если оно неизвестно — [исследование](RESEARCH.md).

## Что предложить пользователю

Объясни ближайшие действия: «Уточню основание, оформлю или дополню задачу, выполню
изменение и проверю такой результат». Для бага начни с воспроизведения.
Спрашивай о неизвестном продуктовом решении, а не о технических сведениях, которые
можно получить из доступных источников. Не превращай небольшое поручение в обследование
всего проекта. Если попросили только диагностику, ограничься ею.

## Как действовать

1. Подтверди проект и прочитай задачу полностью. Перед созданием проверь смысловые дубли.
2. Выбери доску: общая работа — продуктовая, работа приложения — его доска.
   Продуктовую цель указывай только при реальном обязательстве перед фичей, сценарием
   или реализацией. Задача без цели допустима; фиктивные фича и приложение не нужны.
3. Опиши цель, объём, ограничения, основания и наблюдаемые критерии. Для бага сохрани
   воспроизведение, ожидаемый исход и фактическое наблюдение, включая его условия.
4. Проверь необходимые зависимости. Родительство используй для декомпозиции, `related` —
   для темы, `depends-on` — для обязательного результата, без дублирования отношений.
5. Выбери соразмерную организацию. Задача может выполняться сама; план полезен для
   явных этапов, общего итога или состава будущего релиза и может включать одну задачу.
6. Перейди к выполнению, если оно поручено. По ходу устойчивые знания сохраняй у их
   владельца, результат проверки — в комментарии; постановку не заменяй отчётом.

## Развилки

- **Баг не воспроизводится:** сохрани условия и ограничения, запроси недостающие данные;
  не утверждай отсутствие проблемы и не закрывай её как исправленную.
- **Работа оказалась шире:** объясни найденную причину, предложи декомпозицию или уточнение
  границ до расширения. Независимую согласованную часть можно продолжать.
- **Нет продуктовых знаний, но техническая цель ясна:** оформи достаточные основания
  для задачи; паспорт и полная карта фич не являются предварительным условием Core.
- **Запрос только на объяснение:** ответь по источникам; новая задача нужна для порученной
  работы, а не для регистрации каждого вопроса.

## Когда этап закончен

Есть однозначная задача с границами и способом проверки либо обоснованный результат
диагностики. Далее: [выполнение](EXECUTION.md), при необходимости [планирование](PLANNING.md).
