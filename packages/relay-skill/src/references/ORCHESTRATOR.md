# Работа оркестратора

[Главная инструкция](../skill.md).

1. Проверь подключение по главной инструкции, установи проект и цель поручения.
   Используй подходящий работающий Server и передай человеку фактическую ссылку на Web.
   Проверь незавершённые ветки, отдельно прочитай `session intents <session-ref>`
   (при необходимости с `--include-children`), затем нужное context/history страницами.
   Старый открытый intent не ищи только среди последних закрытых работ. Полные счётчики
   проекта, ветки и поддерева не вычисляй из страницы; projectTotals не зависит от фильтров.
   Сопоставь историю с реальным проектом: последняя запись не доказывает состояние кода.
   Начни корневую ветку или явно продолжи выбранную по поручению; не захватывай все ветки.
   Для человека принят Web-граф в пункте «История» без фильтров; доступность смотри в матрице.
   Не ищи в нём весь остаток вместо CLI: фильтры и отдельный session intents сохраняются.
   Найди и прочитай полные знания нужной области; граф используй для выяснения связей.
   Для пустой памяти начни с ТЗ, паспорта, фич/сценариев, приложений и FI/SI;
   документы сохраняй по мере анализа. Не начинай с произвольного набора задач.
2. Сверь требования с кодом и основаниями; неизвестное сохрани как вопрос в Markdown.
   До содержательных работ открой намерение. Сохраняй progress на смысловых границах:
   исследование, законченная часть, проверка, блокер; не после каждого вызова инструмента.
   Называй точку понятно по событию и предмету. Summary необязательна и нужна для краткой
   подсказки; полноценный Markdown body обязателен, его не заменяют аватар и подпись графа.
3. Создай задачи с описанием, критериями и реальными зависимостями. Продуктовая цель
   необязательна; не создавай искусственную фичу для технической работы.
4. Организуй существующие задачи в план и этапы через CLI: `npx @oim-dev/relay-cli plan --help`
   уточняет команды и параметры. Изменения этапов и состава используй с актуальной ревизией плана;
   включение родителя не добавляет детей автоматически. Передай исполнителю проект,
   ключ/ID задачи, план и локальный ID этапа, автора, подключение, границы и критерии.
5. Запускай исполнителей средствами внешней среды только при явном разрешении пользователя
   или применимых инструкций. Relay не запускает агентов; один агент может выполнить работу сам.
   **До запуска** создай pending-ветку через `session fork <intent CP-ref>` от открытого
   намерения родителя. Используй `--run` с постоянным `run.id` родителя и его ревизию
   ветки в `--if-revision`. Полученный ребёнок ещё не имеет участия.
   В prompt передай config/транспорт и выбранный проект, адрес дочерней ветки,
   исходного intent, предметные основания, назначение, границы и проверяемый результат,
   а также контекст человека-оператора. Для независимых Git-копий укажи их реальные пути:
   не подменяй локальный снимок человека серверной Git-конфигурацией.
   Потребуй attach и собственные checkpoints ребёнка; run родителя ему для записи не выдавай.
   То же правило действует для делегирования следующего уровня.
6. Перечитай результат и подтверждения, проверь общий сценарий. Измени статус задачи
   по фактическому результату. Готовность фичи, сценария или реализации вычисляется
   каскадно: задачи → активные реализации → их проектные цели. Прямые задачи
   учитываются дополнительно; пустая активная реализация удерживает начатый состав в partial.
   У FI обязательны все выбранные SI своего приложения; у проектной фичи — все её
   проектные сценарии. Проверяй полный состав, а не только задачи родительской записи.
   Новую работу выражай задачей или возвратом задачи в работу, а не ручной отметкой контракта.
   Отдельно прочитай полный результат дочерней ветки и фактические проверки. После приёмки
   запиши постоянный ID ребёнка в `acceptedSessionIds` progress/result/cancel исходного
   намерения. Его completed само по себе не подтверждает принятие. Не принимай по одной
   аннотации и не подменяй ID ключом ветки: в CLI передай `--accept <session.id>`.
   В карточке ребёнка проверь acceptance — точку родительского принятия, а не только
   completed. LatestRun показывает последнего агента и человека даже после закрытия.
   Слитая линия Web-графа означает completed/cancelled, не принятие: оно по-прежнему
   требует твоего явного checkpoint и проверки результата.
7. Закрой собственные намерения отдельными result/cancel, затем ветку с содержательным
   итогом. Открытые дети и непринятые результаты препятствуют закрытию. Перед паузой
   сохрани выполненное, проверки, ограничения и следующий шаг, затем явно выполни pause.
   Resume создаёт новое участие; takeover открытой ветки требует явного поручения и причины.
   Передача корня не передаёт дочерние ветки. Завершённые ветки и точки не редактируются.

Полные многострочные Markdown сохраняй через предусмотренные `--body`/`--body-file`,
`--description`/`--description-file`, `--result`/`--result-file`, `--reason`/`--reason-file`
и другие парные поля установленной команды. Списки краткие, полные материалы читай
через get. Счётчики контекста и дерева не означают, что дочитаны все страницы.
Перед мутацией сверяй актуальную ревизию **ветки** и её currentRunId; прежний run после
takeover не может писать. Потеря ответа требует чтения состояния, не повтора вслепую.
Правила и границы поставки: [история работы](domain/WORK_HISTORY.md),
[восстановление](guides/RECOVERY.md), [матрица](CAPABILITIES.md).

После проверки состава заверши план с итогом; отдельное начало плана необязательно.
Для состоявшейся внешней поставки явно зафиксируй релиз из выбранных планов и перечитай
его статус, автора и дату через `npx @oim-dev/relay-cli release get <ключ-или-ID>`,
состав — через `npx @oim-dev/relay-cli release plans <ключ-или-ID>`.
`npx @oim-dev/relay-cli plan progress <ключ-или-ID>` объясняет текущие обязательства,
`npx @oim-dev/relay-cli release progress <ключ-или-ID>` читает актуальную
готовность планов даже после выпуска. Снижение готовности не отменяет сохранённый факт
выпуска. Основной интерфейс агента — CLI через npx; MCP допустим только по запросу
пользователя при проверенном окружении. У релиза пока нет принадлежности приложению:
не передавай `applicationId`.
Подробности: [планы](domain/PLANNING.md), [релизы](domain/RELEASES.md).
