# История работы: сессии, участия и Markdown-материалы

Открывай перед первой регистрацией работы, продолжением чужого поручения, делегированием
или разбором прежних результатов. История обязательна для исследования, планирования,
реализации, проверок и документации по [основному скиллу](../skill.md).
Результат — другой участник понимает работу и может продолжить её без исходного чата.

## Модель

| Запись        | Что сохраняет                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| Сессия        | Логическое поручение: название, полное описание, состояние, родитель и итог                                           |
| Участие — run | Один период ответственности агента: автор, клиент, внешняя сессия, человек-оператор, Git-контекст, начало и окончание |
| Checkpoint    | Неизменяемое намерение или материал: intent, progress, result, cancel; Markdown, авторство, ссылки                    |

Сессия переживает смену чата или агента. Она не является Git-веткой, процессом или внешней
сессией клиента. У открытой сессии ровно одно текущее участие; независимые сессии могут
работать параллельно. Checkpoint не делает снимок кода и не является записью каждого инструмента.

Случайные адреса S-/RUN-/CP- бери из ответов. Для владения нужен постоянный run.id,
а не читаемый RUN-ключ. Внешний ID чата помогает сопоставлению, но не заменяет адрес Relay.

## Сначала восстанови достаточный контекст

Начни с overview: он показывает последнюю и незавершённые сессии. Последняя определяется
по сохранённому событию, а не присутствию агента online. Если нужной работы нет в подборке,
найди её через `session list`; учитывай и уже завершённые сессии.

| Вопрос                                             | Чтение                                                                                           |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Что делали и где остановились?                     | `session context`: полное поручение, состояние, участия и страница полных материалов самой ветки |
| Что происходило в проекте?                         | `session history` без адреса: хронология всего проекта, включая закрытые работы                  |
| Как развивалось поручение?                         | History выбранной сессии; потомков включай явно                                                  |
| Какие поручения делегированы?                      | `session tree`: иерархия и счётчики поддерева                                                    |
| Что осталось открытым?                             | `session intents`: отдельный список незакрытых намерений, при необходимости с потомками          |
| Нужен один полный артефакт?                        | `checkpoint get`                                                                                 |
| Нужны только состояние, поручение, итог и участие? | `session get`                                                                                    |

Выбирай чтение по вопросу. Context уже содержит полную карточку: не запрашивай следом get
или каждую точку, полный текст которой уже получен. History показывает события для выбора;
Markdown раскрывается через context или checkpoint get. Context не включает всю историю потомков.

Перед продолжением обязательно найди открытые намерения через intents: старый intent
может отсутствовать на последних страницах. Читай нужные страницы, а не всю историю проекта.
Общие счётчики не равны числу показанных записей; projectTotals списка относится ко всему
проекту даже при фильтрах. При изменении версии страницы начни выборку заново.

## Начало и переходы сессии

| Ситуация                              | Действие и результат                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| Новое самостоятельное поручение       | start создаёт корень open и первое участие                               |
| Родитель готовит делегирование        | fork от открытого intent создаёт pending-ребёнка без участия             |
| Исполнитель получил pending           | attach создаёт первое собственное участие, сессия становится open        |
| Нужно остановиться с продолжением     | pause завершает участие; сессия paused, намерения остаются открытыми     |
| Поручено продолжить paused            | resume создаёт новое участие той же сессии                               |
| Поручено передать open другому агенту | takeover с причиной завершает прежнее участие и создаёт новое            |
| Работа выполнена                      | complete закрывает сессию и участие с итогом после закрытия обязательств |
| Поручение отменено                    | cancel сохраняет причину; это не выполненный результат                   |

Перед стартом сохрани полное поручение: что сделать, зачем, границы и критерии результата.
При продолжении сначала прочитай прежние материалы и проверь реальное состояние файлов,
проверок и ресурсов. Затем зарегистрируй нужный переход и сохрани уточнение следующего шага.
Наличие open или давность последней точки не дают разрешения захватить работу автоматически.

Передача корня не передаёт дочерние сессии. Takeover также не останавливает внешний процесс
предыдущего агента. Согласуй продолжение каждого нужного поручения отдельно.
Completed и cancelled неизменяемы: новая работа требует новой сессии, а не переоткрытия.

## Авторство и контекст

Укажи агента, фактический клиент и известный внешний ID сессии. Человек-оператор сохраняется
отдельно. CLI выбирает его из явных пользовательских полей, окружения или Git клиента;
источники пары имя/email не смешиваются. При attach без явного/env-переопределения ребёнок
наследует оператора создавшего поручение участия, а не случайного пользователя другой копии.

Автор checkpoint принадлежит его сохранённому run. Смена текущего агента не переписывает
старые точки. Git-контекст снимается при подключении участия, не при каждом checkpoint:
он помогает ориентироваться, но не сохраняет diff и не доказывает чистоту файлов.
Атрибуция не является аутентификацией или online-индикатором; неизвестное не выдумывай.

## Намерение, прогресс и результат

До содержательных действий открой intent с ожидаемым результатом, границами, основаниями
и способом проверки. Для продолжения используй подходящий открытый intent, сохрани уточнения.
Progress, result и cancel адресуют исходный intent, а не последнюю progress-точку.

**Сохраняй progress после содержательного рубежа до следующего действия:** вывод исследования,
завершённая часть, проверка, блокер, изменение плана. Перед передачей, остановкой или ожидаемым
сокращением контекста обязательно сохрани продолжение. Длительную работу дели на законченные
подшаги; не откладывай историю до общего финального отчёта и не веди лог каждого инструмента.

Название называет событие и предмет; summary помогает выбрать запись. Обязательный полный
body раскрывает содержание. Дополнительные done, remaining, nextStep, checks помогают
отдельно указать сделанное, остаток, следующий шаг и проверки; пустые разделы не нужны.

Полезный материал отвечает: что выяснено или сделано, на каких основаниях, где артефакты,
что проверено фактически, что осталось и с какого действия продолжать. Сохраняй выводы
и проверяемые основания, а не переписку или внутренние рассуждения агента.

Учебный пример progress, а не отчёт о реальной работе:

```markdown
## Вывод

Пустой ответ поиска и отказ API сейчас отображаются одинаково.
Проверено на запросе без совпадений и на воспроизведённом отказе сервера.

## Сделано и остаток

Причина локализована в обработке ответа формы. Исправление ещё не внесено.

## Продолжение

Разделить состояния, затем проверить совпадения, пустую выдачу, ошибку и повтор запроса.
```

Сохраняй сам полезный текст промежуточного артефакта. Для внешнего результата укажи
доступный адрес, существенное содержание и при необходимости версию; один путь к временному
файлу не обеспечивает продолжение. Предметные ссылки checkpoint сохраняют адрес и подпись
цели, но не снимок её содержания и не отношение общего графа. Устойчивые знания обновляй
в документах и требованиях, итог по задаче — в её комментарии.

Result или cancel — новая неизменяемая точка, закрывающая intent. После неё нельзя дописывать
progress к этому намерению; самостоятельная новая работа требует нового intent.

## Делегирование и принятие результата

1. Когда делегирование разрешено, родитель создаёт fork от своего открытого intent
   **до запуска** исполнителя внешней средой.
2. Передай проект, конфигурацию/транспорт, адрес pending-сессии и исходного намерения,
   задачу и документы-основания, границы, критерии и контекст человека-оператора.
3. Ребёнок читает поручение, делает attach, получает собственный run и ведёт свои intent
   и checkpoints. Run родителя для записи ему не выдаётся. Это действует на любом уровне вложенности.
4. Исполнитель сохраняет итог, проверки, ограничения, адреса материалов и закрывает свою
   сессию. Completed означает передачу результата, а не его принятие родителем.
5. Родитель читает полный результат и проверяет основания. Затем явно принимает постоянный
   session.id ребёнка через свой progress/result/cancel исходного intent. Для CLI это `--accept`;
   читаемый S-ключ не заменяет постоянный ID.

Принимаются только completed-прямые дети именно этого намерения. Отменённый ребёнок
не принимается как успешный результат. Пустой набор ничего не принимает; прежнее принятие
остаётся в истории. При доработке сохрани причину и организуй новую работу: завершённую
ветку ребёнка переписать нельзя. Acceptance в карточке ребёнка показывает точку принятия.

## Закрытие, пауза и ошибки

Перед complete/cancel намерения закрой его детей и прими завершённые результаты. Перед
закрытием всей сессии также закрой собственные intent. Отмена не обходит эти условия.
При паузе заранее сохрани сделанное, проверки, блокеры и конкретный следующий шаг.
Если paused-сессия имеет открытые intent, для их записи сначала требуется resume.

Все изменения существующей сессии проверяют её ревизию; операции checkpoint тоже используют
ревизию владеющей сессии. Владельческая запись дополнительно требует текущий постоянный run.id.
Старый run после передачи не может писать даже со свежей ревизией. После конфликта перечитай
состояние и согласуй продолжение, не подставляй новые guard-значения в старую команду автоматически.

После потери ответа start/fork/checkpoint сначала найди фактическую запись: requestId
не предотвращает дубликаты. Если история недоступна, сообщи препятствие, сохрани подготовленный
Markdown в доступный файл и укажи, что в Relay он пока не записан. Работа не объявляется
полностью завершённой без сохранённой истории.

Для человека Web показывает историю графом и открывает полные материалы из точек.
Визуальное возвращение закрытой ветки к родителю означает завершение или отмену, не приёмку.
Для адресного поиска и продолжения агент использует CLI. Действия и параметры раскрывай
через `session --help`, `checkpoint --help` и справку выбранной команды.
