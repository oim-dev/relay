# Миграция данных после обновления Relay

[Главная инструкция](../skill.md). Порядок для человека и восстановление из копии —
в [руководстве](guides/RECOVERY.md#явная-миграция-и-резервная-копия), правила
сохранности — в [контракте хранения](domain/STORAGE.md#совместимость-версий-и-миграция),
синтаксис — в [справочнике CLI](interfaces/CLI.md#storage-status).

## Когда нужна миграция

Новая версия Relay не открывает базу старого формата и никогда не переносит её сама.
Данные при этом не потеряны. Признак — ошибка совместимости хранилища в ответе любого
интерфейса: CLI, MCP или REST (HTTP 409), а в Web — причина вместо данных проекта.

| Код                                                    | Что означает и что делать                                                                                            |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `STORAGE_MIGRATION_REQUIRED`                           | Устаревший формат или профиль данных: выполнить перенос по шагам ниже.                                               |
| `STORAGE_DATA_MIGRATION_REQUIRED`                      | Запись с чужой версией данных: начать с `storage status`, данные не сбрасывать.                                      |
| `STORAGE_RECOVERY_REQUIRED`                            | Прерванная миграция или операция: см. «Сбой и продолжение».                                                          |
| `STORAGE_VERSION_UNSUPPORTED`                          | Обычно база новее этой версии Relay: не мигрировать, открыть её создавшей или более новой версией; следовать `next`. |
| `STORAGE_FORMAT_UNKNOWN`, `STORAGE_TRANSITION_MISSING` | Поставка не умеет перенести структуру: сохранить базу и диагностику, передать пользователю.                          |

Ответ различается по источнику:

- **Ошибка обычного вызова** Core (CLI, MCP, REST) несёт `details` с причиной; `details.next` —
  следующее действие. Оно может включать команду обслуживания, а может быть текстовым
  указанием: обновить Relay, вернуть копию, восстановить названный файл. Команда в ответах
  MCP и HTTP имеет вид `npx @oim-dev/relay-cli --local --config <config> storage …`: замени
  `<config>` проверенным путём к конфигурации этой базы — `.relay/config.json` local-проекта
  или `relay.workspace.json` вместе с `--project <имя>`. Локальный CLI в text-режиме
  подставляет фактический путь сам.
- **Ненулевой `storage status` или неприменимый `--dry-run`** возвращает в `error.details`
  полный диагностический отчёт: статус, блокеры с их путями и действиями, а незавершённую
  транзакцию — в `pending` (`pending.kind`: `migration`, `operation`, `legacy` или `unknown`).
  Верхнеуровневых `reason` и `next` в таком отчёте нет; решение принимай по нему.

## Чего не делать

- Не повторяй запрос и мутацию: запись с такой ошибкой не выполнена, повтор её не выполнит.
- Не обходи ошибку другим интерфейсом, другим проектом, `init` или новой базой.
- Не правь и не удаляй файлы `.relay`, номера версий и `transactions/pending.json` вручную.
- Миграцию выполняет только локальный CLI с `--local` на машине, где лежит база.
  MCP, REST и Web её не исполняют; в HTTP-режиме команды `storage` отвечают
  `LOCAL_REQUIRED` и ничего не меняют.

## Порядок переноса

Перенос изменяет данные пользователя, поэтому каждый изменяющий шаг согласуй.
Каждая база переносится отдельно. В примерах — local-база `alpha`; для проекта
реестра используй `--local --config ./relay.workspace.json --project alpha`.

1. **Сообщи пользователю** код ошибки, базу и предстоящие шаги; получи согласие на перенос.
2. **Останови процессы Relay**, работающие с этой базой: Server, MCP, сеансы записи
   в Web и других агентов. Согласуй остановку процессов, которые запускал не ты;
   занятая база даёт `STORAGE_BUSY`. Совместимый Server технически подхватывает базу
   после внешнего обслуживания без перезапуска; эта возможность не отменяет безопасный
   порядок остановки клиентов.
3. **Проверь состояние** без изменений:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage status
   ```

   `current` — переносить нечего; `migration-required` — переходи к плану.
   `recovery-required`, `unsupported`, `invalid` завершаются ненулевым кодом с блокерами
   и следующим действием: покажи их пользователю, не исправляй файлы ради статуса.

4. **Построй план** — перенос в памяти, без изменения базы и без копии:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage migrate --dry-run
   ```

   Покажи пользователю шаги, изменения, удаляемые по правилу исторические структуры,
   предупреждения, требуемое место и блокеры. Сохрани `planFingerprint`
   (в JSON — `data.planFingerprint`). При блокерах перенос не начинай.

5. **Согласуй каталог резервной копии** вне базы и вне Git-рабочей копии, например
   `/backups/relay-alpha`. Копия создаётся в новом подкаталоге `relay-backup-…`
   и автоматически не удаляется.
6. **Выполни перенос** по проверенному плану; второго подтверждения команда не просит:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage migrate \
     --backup-dir /backups/relay-alpha --if-plan PLAN_FINGERPRINT
   ```

   `STORAGE_PLAN_STALE` означает, что база или поставка изменились после плана:
   вернись к шагу 4. Сообщи пользователю путь копии из `backup.path` результата.

7. **Проверь результат:** `storage status` должен показать `current`, затем выполни
   `doctor check` и прочитай важные записи, комментарии, планы и связи через локальный CLI
   (`--local --config …`), пока Server остановлен.

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage status
   npx @oim-dev/relay-cli doctor check --local --config ./alpha/.relay/config.json
   ```

   Только после этого запусти Server и другие клиенты и передай пользователю ссылку на Web.

Если ответ команды потерян, выполни `storage status`: он покажет фактическое состояние.
Повтор `storage migrate` после успеха ничего не меняет и копию не создаёт.

## Сбой и продолжение

- **Прерванная миграция:** ошибка обычного вызова `STORAGE_RECOVERY_REQUIRED` с
  `details.reason: migration` или отчёт `storage status` с `pending.kind: migration`.
  Повтори `storage migrate` с тем же `--config` без `--backup-dir`: он продолжит записанную
  транзакцию с исходной копией, результат помечен `resumed: true`. Если запуск с `--if-plan`
  ответил `STORAGE_PLAN_STALE` с `details.reason: wal`, записанная миграция относится
  к другому плану: новый `--dry-run` здесь неприменим. Подтверди незавершённую миграцию
  через `storage status` и с согласия пользователя продолжи её тем же запуском без `--if-plan`.
- **Незавершённая обычная или legacy-операция** (`pending.kind: operation` или `legacy`
  в отчёте; `migrate` с `--if-plan` отвечает `STORAGE_PLAN_STALE` с `details.reason: pending`
  и ничего не меняет). Запуск `storage migrate --backup-dir DIR` без `--if-plan` выполнит
  две записи подряд без промежуточного подтверждения: сначала сделает копию и **завершит
  прежнюю операцию** (recovery), затем построит **новый план** и сразу исполнит миграцию
  по нему. Объясни пользователю обе записи, покажи найденный путь журнала и получи согласие
  именно на это. Исключение действует только при подтверждённой такой операции.
- **Обычное устаревание плана** — `STORAGE_PLAN_STALE` с `details.reason: fingerprint`:
  база или поставка изменились после проверки, изменений нет. Построй новый `--dry-run`,
  покажи план пользователю и используй новый отпечаток.
- **`STORAGE_BACKUP_MISSING`** — различай по сообщению и `next`:
  - копия повреждена **до начала публикации миграции** («перенос не начат», `next`
    предлагает новый `--backup-dir`) — сама миграция не начата. Но если перед ней была
    незавершённая обычная или legacy-операция, она могла быть уже завершена. До миграции
    предметное чтение недоступно (`STORAGE_MIGRATION_REQUIRED`): ограничься диагностикой
    `storage status` и не повторяй прежнюю мутацию. Согласуй новый каталог копии и запусти
    перенос заново, начиная с `--dry-run`; результат прежней операции проверь чтением
    через локальный CLI после успешной миграции, на шаге 7;
  - копия **незавершённой миграции** пропала или изменилась (`next` требует вернуть копию
    по пути из WAL) — остановись. Продолжение возможно только с исходной проверенной копией:
    покажи пользователю путь и `next`, новой копией её не заменяй.
- **`STORAGE_RECOVERY_CONFLICT`** — файл базы изменён посторонним процессом после прерывания.
  Остановись, покажи пользователю код, названный путь и `next`; чужое содержимое
  не перезаписывай.

В случаях незавершённой транзакции не удаляй журнал `transactions/pending.json` и каталог копии.

## Откат из резервной копии

Автоматического восстановления поверх действующей базы и обратной миграции нет;
старые файлы поверх перенесённой базы не копируй. Копию разворачивают в отдельный
каталог по `RESTORE.md` и `backup-manifest.json` внутри неё и открывают совместимой
старой версией Relay. Предложи это пользователю и следуй
[порядку восстановления](guides/RECOVERY.md#восстановление-из-резервной-копии).
