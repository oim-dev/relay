# Восстановление после ошибки

[Главная инструкция](../skill.md), [подключение](STARTUP.md).

- SERVER_UNAVAILABLE: проверь URL и процесс Server; не переключай запись на другую базу.
- PROJECT_REQUIRED / PROJECT_NOT_FOUND: перечитай projects_list, проверь выбранный проект.
- REVISION_CONFLICT: перечитай запись и согласуй изменение с новой версией.
- GRAPH_CHANGED / BOARD_CHANGED: начни выборку заново, сохраняя проект и фильтры.
- IDEMPOTENCY_CONFLICT: ключ уже использован с другим содержимым; восстанови исходный запрос.
- RESPONSE_TOO_LARGE: используй компактный список, сузь выборку или увеличь maxBytes.
- INVALID_DATA: проверь конкретную причину; не заменяй повреждённые данные пустыми.
- STORAGE_MIGRATION_REQUIRED: для прежней базы останови старые версии клиентов и выполни
  явный локальный `storage migrate`. Формат 2 группирует историю в сегменты; текущие тексты,
  комментарии и квитанции сохраняются. Полные технические снимки удаляются, прежние
  Markdown-правки отмечаются фактом изменения. `history` — постоянные данные, не кеш.
- RELATION_MANAGED: связь обслуживает предметный сценарий; измени линк через его владельца.
  Для согласования уже единой базы после обновления используй явный локальный
  `storage reconcile-relations --request-id <id>` с автором. Он сохраняет независимые
  диагностические рёбра и ревизии сущностей. Старую базу сначала перенеси через `storage migrate`.

После неизвестного исхода записи повторяй неизменный requestId. Продукт и граф имеют
собственные [миграции](PRODUCT.md) и [восстановление индексов](GRAPH.md).
Для продолжения после паузы перечитай задачу и документы, затем сверь реальные код,
процессы и проверки. Исторический отчёт не доказывает текущее состояние.
