# Приложения и реализации FI/SI

Открывай при определении программных частей продукта, создании приложения, выборе его
состава и заполнении реализаций. Результат — явная ответственность каждого приложения
за общие требования. Общий цикл — в [основном скилле](../skill.md).

## Что является приложением

Приложение — логическая программная часть продукта с собственным назначением и доской.
Это не отдельный проект Relay и не папка для группировки случайных задач. Разделение
на Web, API, внутренний сервис или другое приложение должно соответствовать ответственности.
Не навязывай раздельные frontend/backend, если продукт реализуется одним приложением.

Перед созданием прочитай требования и существующую архитектуру, согласуй недостающие части.
В полном описании раскрой назначение, границы, взаимодействия, входы/выходы и ограничения.
Выбери тип по ответственности из вариантов справки CLI; название и тип не заменяют описания.

Создание приложения создаёт его доску. Выбирай slug и префикс задач внимательно: после
создания они неизменяемы. Отображаемое имя и публичный ключ можно менять соответствующими
действиями; изменение ключа не меняет slug или префикс. Самостоятельных `board create/delete` нет.

## FI и SI

| Запись | Ответственность                               |
| ------ | --------------------------------------------- |
| FI     | Вклад одного приложения в общую фичу          |
| SI     | Вклад одного приложения в конкретный сценарий |

SI требует FI той же фичи в том же приложении. Выбор FI не включает все SI автоматически:
выбери действительно реализуемые сценарии. FI без SI допустима. Для одной пары приложение/цель
переиспользуй существующую реализацию; новое имя не делает тот же вклад независимым.

Общее требование определяет, что нужно продукту; FI/SI — что обеспечивает именно это
приложение. Реализация хранит требования к вкладу, а не факт завершения кода и не копию фичи.

## Как создать и описать состав

1. Найди и прочитай приложение, общие фичи/сценарии, правила и уже объявленные реализации.
2. Выбери необходимые FI, затем SI. Для новой части можно создать отдельную реализацию
   через `implementation create`; полный состав приложения меняется через `participation`.
3. Каждой FI/SI дай понятное название и полный Markdown. Раскрой основания, своё поведение,
   данные, контракты взаимодействия, ошибки, границы и способ проверки. Аннотации вида
   «форма и сохранение» недостаточно для реализации без чата.
4. Прикрепи материалы именно к тем вкладам, которым они нужны: API-контракт, правила UI,
   ограничения хранения, согласованные решения. Один документ можно использовать для нескольких.
5. Перечитай состав и полное содержание новых или изменённых реализаций. Затем ставь задачи
   на доске приложения с целями на соответствующие FI/SI.

## Как выглядит полезное описание

Ниже учебный вклад Web в сценарий поиска инструкций; правила должны быть подтверждены
требованиями реального проекта, а не перенесены из примера автоматически.

```markdown
## Ответственность и основания

Web обеспечивает ввод запроса и открытие результата по сценарию поиска.
Отбор и хранение инструкций принадлежат API; контракт запроса приложен к реализации.

## Поведение

Передать введённый запрос в API. Показать названия найденных инструкций и переходы
к полному тексту. Сохранить запрос при открытии результата.

## Состояния и ошибки

Различать ожидание, пустую выдачу и отказ API. При отказе сохранить запрос
и предложить повтор; не показывать «ничего не найдено» вместо ошибки.

## Проверка

Проверить совпадения, пустой ответ и отказ API. После открытия инструкции запрос сохранён.
```

SI в API для того же сценария должна описывать собственный контракт, правила отбора,
результат и ошибки. FI объясняет общий вклад приложения и отношения выбранных SI.
Для полного пути нужны согласованные вклады всех участвующих приложений.

## Замена, снятие и возвращение участия

`application participation replace` сохраняет **весь выбранный активный состав**.
Перед записью прочитай весь нужный состав, его ревизию и версию продукта. Не передавай
только добавляемую реализацию как будто это точечное добавление: пропущенные вклады снимаются.
Версия состава продукта для записи и snapshot обзора имеют разный смысл; бери значения
из чтения participation и сверяй условия через help.

Существующий вклад выбирай как существующий: сохраняются адрес и содержание. Новые FI/SI
можно включить в одну согласованную замену. Если пара уже есть, включая снятое участие,
переиспользуй её вместо создания новой. Пустой состав снимает всё участие.

Чтобы снять FI, исключи и её SI. Снятие последнего SI само не снимает FI. Снятие участия
сохраняет ID, тексты и прежние ссылки; реализация доступна для чтения и изменения своего
содержания. Новые задачи не должны назначаться на снятый вклад. Для возвращения выбери
существующую реализацию в составе; удалённую запись этим способом не восстановить.

Отдельный `implementation create` для снятой пары также может вернуть прежний ID, но
заменит её название, описание и совместимую отметку переданными значениями. Для возврата
с сохранением прежнего содержания выбирай существующий вклад через participation.

Изменение текста отдельной реализации защищается её собственной ревизией. После общего
пересмотра требований самостоятельно уточни затронутые FI/SI: автоматического переписывания нет.

## Готовность и изменение объёма

Готовность вычисляется по текущим обязательствам: собственным задачам реализации,
а у FI также по её активным SI в этом приложении. Снятые вклады исключены из активного расчёта.
SI без задач не готова; FI может завершиться по выбранным SI без отдельной прямой задачи,
но существующие незавершённые задачи FI продолжают влиять на результат.

Сохранённая совместимая ручная отметка статуса не заменяет вычисляемую готовность.
Для причин используй `implementation progress` или `application progress`. Все задачи
доски и обязательства объявленного состава приложения — разные выборки. Новую работу
отрази задачами, а не попыткой вручную выставить процент или статус требования.

## Удаление и навигация

Если цель — временно исключить вклад, используй снятие участия. Удаление FI включает
её SI того же приложения; удаление приложения включает реализации, доску и задачи доски.
Внешние документы и задачи могут потерять связи; ссылки планов могут запретить удаление.
Сначала прочитай `delete-preview`, затем используй исходную версию этого предпросмотра.

Точки входа в CLI: `application`, `application participation`, `implementation`, их
`list/get/create/update/progress` и help ближайшего действия. Не заменяй полное содержание
каталогом или компактным составом: они помогают выбрать запись, но не объясняют весь вклад.
