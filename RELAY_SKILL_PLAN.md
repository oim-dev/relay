# План реорганизации пользовательского скилла Relay

Это временный план-поручение, сохранённый по прямому запросу пользователя для новой
сессии без исходного чата. Он не вводит новый канонический источник, журнал или архив.
Само наличие плана не запускает реализацию. Новый агент получает отдельное поручение
на проектирование или выполнение согласованного объёма. При подготовке плана скилл
и его сборщик не изменялись.

## Роль, границы и начало новой сессии

- Роль нового агента определяется его сессией и поручением, а не этим файлом.
  За содержание отвечает [relay-docs](packages/dev-agents/src/docs.md), за механизм
  сборки — [relay-delivery](packages/dev-agents/src/delivery.md). Оркестратор может
  распределить эти части между исполнителями; у общих выходов должен быть один писатель.
- Соблюдай [корневые правила](AGENTS.md), [правила области docs](docs/AGENTS.md)
  и [правила документации](docs/DOCUMENTATION.md). Перед работой у нового владельца
  прочитай применимые локальные инструкции, не сканируй все профили и весь репозиторий.
  `packages/relay-skill/AGENTS.md` при подготовке плана отсутствовал.
- Начни с `git status --short`, `git diff` и состояния индекса; сохрани чужие изменения.
  Ожидаемая рабочая ветка — `docs/reorganize-documentation-and-agents`, проверь фактическую.
  Часть финальной интеграции документации и интерфейсов может быть незакоммичена.
- Пользовательский скилл не равен `dev-agents`: один оркестратор и восемь workers
  последнего предназначены для разработки самого Relay, не для пользовательского пакета.
  Не копируй знания в профили и не навязывай React/Unit Architecture проектам пользователей.
- Применимые скиллы и инструкции выбирай по реальной задаче и правилам рабочей области.
- Содержание принадлежит `relay-docs`, механизм сборки — `relay-delivery`.
  Изменения механизма, общих манифестов и чужих областей сначала согласуй;
  технические пункты этого плана не дают молчаливого расширения полномочий.
- Различай принятое требование, текущую реализацию, предложение и выполненную проверку.
  Не выдумывай API, результаты, новые поля манифеста или доступность интерфейса.
  Коммиты, push и публикация — только по отдельному запросу.

## Состояние и известный блокер

Канонические source docs актуализированы и reviewed по переданному контексту;
это не новая проверка их реализации. `OLD_docs` удалён, восстанавливать прежнюю
структуру ради зелёной сборки нельзя. Сейчас authored-набор — `skill.md` и шесть
собственных references (семь файлов); `bundle.documents` содержит 13 удалённых
адресов `docs/reference/*`, aliases — отображения старых адресов, не файлы.
Известный фактический сбой прежнего `skills:check` — `ENOENT docs/reference/CONFIGURATION.md`,
он блокирует общий check. Сохранённый `skills/relay` содержит 21 Markdown (20 references):
по переданной проверке внутренние ссылки валидны, актуальность содержания не подтверждена.
Это материал сверки полезных знаний, не источник истины и не основание восстанавливать старые docs.

## Согласованное продуктовое видение

Relay — рабочая память проекта. Знания хранятся в содержании записей и документов,
чтобы человек или новый агент продолжал работу без исходного чата.

1. **Сбор знаний с нулевой базы по ТЗ — основной, самый сложный и долгий этап.**
   Разобрать ТЗ и уточнения → заполнить паспорт → выделить и описать фичи и сценарии
   → спроектировать и описать нужные приложения → объявить и описать FI/SI
   (реализации фич/сценариев) с собственными обязательствами каждого приложения.
   Параллельно сохранять исходное ТЗ, пояснения, правила и материалы в библиотеке
   документов и связывать с продуктом, фичами, сценариями, приложениями, реализациями,
   позже — с задачами, в пределах поддерживаемых операций. Не откладывать документы
   на конец. Неизвестное уточнять у пользователя, не подменять предположениями.
2. **Задачи на основании знаний.** Продуктовая доска — общая и крупная работа обычными
   родительскими задачами; доска приложения — его работа. Задать подзадачи, зависимости
   и проверяемые критерии. Отдельного типа Epic нет. Продуктовая цель показывает
   затрагиваемую бизнес-область и необязательна: каркас или футер не требуют искусственной
   фичи. Сейчас цели участвуют в готовности, а не служат только тематическими метками.
3. **Планирование, выполнение и проверка.** Цель плана → этапы → явно выбранные
   существующие задачи. План может содержать одну задачу; планов может быть несколько
   по поручению. Дети и зависимости не становятся выбранным составом автоматически.
   Выполнить работу и внешние проверки, сохранить основания, ограничения и итог,
   явно завершить план. Готовность не выводить из одной колонки `done`.
4. **Релиз приложения из выбранных выполненных планов.** Это целевой следующий шаг.
   Текущая запись релиза проектная, содержит `planIds`, но не `applicationId`:
   принадлежность приложению ещё не реализована. Не изобретать параметр или операцию.
   Текущий релиз не хранит snapshot; его прогресс отражает актуальные обязательства.

Это порядок работы агента, не новые запреты Core: задачи допустимы до паспорта,
работа — без плана, `planned`-релиз можно создать заранее. Прогресс не равен приёмке
или деплою; Relay не исполняет агентов, код и CI/CD. Факт внешней поставки проверяется
внешними средствами, а затем осмысленно отражается в Relay.

Контекст — отношения с сущностью для агента и визуализации, не источник знаний
и не обязательный первый шаг. Поиск начинается с содержания знаний, полные тексты
читаются адресно; огромный граф не заменяет этот маршрут. Инфраструктура — будущее
направление: диаграммы, стратегии, документы CI/CD и стенды. Инфраструктурная доска
уже существует, но в базовом процессе пока не используется.

## Установка, подключение и надёжность

Единый обычный маршрут установки и запуска:

```sh
npx skills add oim-dev/relay
npx @oim-dev/relay-cli init
npx @oim-dev/relay-server --open
```

При необходимости отдельным процессом: `npx @oim-dev/relay-mcp`.
Если скилл уже загружен, не зацикливать его повторную установку. Не добавлять в обычный
start `--yes`, `@0.7.0` или явные default-флаги `--local`, `--config`, `--server-url`.
Специальные подключения объясняются отдельно по фактическому окружению.

- Выбор MCP/CLI определяется доступным клиентом и поддержкой нужного действия,
  без навязывания MCP как единственного основного интерфейса.
- Штатный MCP работает только через Server; CLI — напрямую через local Core или HTTP.
  В workspace нужен явный проект; local CLI `projects list` не универсальный первый шаг.
  Не переключать проект, транспорт записи или базу автоматически после ошибки связи.
- Покрытие сверять по [CAPABILITIES](docs/CAPABILITIES.md), точный инструмент — через
  discovery, команду — через CLI help установленной версии. Не придумывать отсутствующие
  MCP/CLI delete и другие операции из наличия возможности в Core.
- Читать актуальное состояние перед записью, соблюдать ревизии и версии выборок.
  При конфликте согласовать содержание с новой записью, не подставлять свежую ревизию
  к устаревшему тексту. После записи перечитать результат и значимые отношения.
- `requestId` — корреляция, не дедупликация. Потерян ответ — сначала перечитать состояние,
  комментарии и связи, затем решать о повторе. Автоматических audit, receipts и history нет;
  не заменять их собственным постоянным журналом. Сохранять существенные знания и результат.

работы разработчиков и маршрут чтения. Shared-каталог возможностей остаётся единственным.

## Авторское содержание и рекомендуемая форма пакета

Входы: [README пакета](packages/relay-skill/README.md),
[bundle.json](packages/relay-skill/src/bundle.json),
[авторский skill.md](packages/relay-skill/src/skill.md).
Собственные материалы для адресной сверки:
[STARTUP](packages/relay-skill/src/references/STARTUP.md),
[DATA-MODEL](packages/relay-skill/src/references/DATA-MODEL.md),
[ORCHESTRATOR](packages/relay-skill/src/references/ORCHESTRATOR.md),
[WORKER](packages/relay-skill/src/references/WORKER.md),
[EXAMPLES](packages/relay-skill/src/references/EXAMPLES.md),
[RECOVERY](packages/relay-skill/src/references/RECOVERY.md).

Рекомендация, которую нужно согласовать перед массовой переписью:

- `SKILL.md` — короткий операционный вход: назначение, выбор цели и транспорта,
  четыре этапа, маршрут конкретной задачи, карта чтения и базовая надёжность.
  Ориентир 80–120 строк, не жёсткий новый лимит; текущий builder ограничивает 220 строк.
  Не превращать вход в каталог аргументов, устройство WAL или полный справочник.
- Возможная структура: `references/{PRODUCT,CAPABILITIES,ARCHITECTURE}.md`,
  `references/domain/*`, `references/guides/*`, `references/interfaces/*`
  (CLI, MCP, API, CONFIGURATION, WEB и нужные дополнительные материалы),
  `references/agent/{ORCHESTRATOR,WORKER,EXAMPLES}.md`. Это предлагаемые выходы,
  не существующие новые ключи манифеста и не уже утверждённая схема.
- ORCHESTRATOR/WORKER — протоколы пользователя Relay, не роли разработчиков Relay.
  Оставшееся skill-specific авторство определить после сравнения с каноном.
  Сократить дублирующие STARTUP/DATA-MODEL/RECOVERY в пользу канонических источников;
  полезное универсальное знание сначала перенести к владельцу, а не потерять.
- Развести семантику authored CLI и generated CLI-COMMANDS из Commander:
  либо руководство плюс техническое приложение, либо генерация как проверка coverage.
  Сохранить сведения о названиях, флагах и обязательности без конкурирующих ручных копий.

Подтверждённые точки расхождений для работы: главный вход сейчас 173 строки и перегружен
техникой, первый этап почти отсутствует; универсальный `projects_list`/`projects list`
не подходит local; STARTUP/ORCHESTRATOR делают контекст входом; EXAMPLES начинается
с канбана и после блока упрощает готовность до `done` без всех транзитивных обязательств;
RECOVERY ссылается на прежние собственные product/graph migrations — сверить NOOP4
и действующий `storage migrate`; целевой релиз приложения не отделён достаточно явно.
Исправления выводить из текущего канона, не из старой готовой копии.

## Комплектация и политика ссылок: решения до реализации

- [lib.mjs](packages/relay-skill/scripts/lib.mjs), `prepareBundle`, требует разрешать
  каждую локальную Markdown-ссылку через manifest. Канонические страницы могут ссылаться
  на инженерные README, код и AGENTS; не включать весь репозиторий ради замыкания ссылок.
- Явно выбрать политику: обязательные знания включать внутрь; необязательные инженерные
  ссылки осмысленно вести в репозиторий либо обрабатывать выходную навигацию.
  Не применять fake aliases и не удалять значимые сведения ради линтера.
- HTTPS-ссылки CLI на обязательные docs в `main` переписать во внутренние ссылки пакета:
  текущий builder оставляет внешние URL. Пользователь должен читать обязательные знания
  без checkout и сети. Не считать действующим ещё не реализованное преобразование.
- Переписывание ссылок не должно менять кодовые примеры; проверять якоря, точность
  Markdown и сохранность содержания. Сборка переносит канонические тексты, не ручные копии.
- Пересмотреть `watch` и Turbo inputs для новых корней локальных docs;
  `cache: false` не отменяет декларации входов. Нынешний watch охватывает CLI/MCP/Core/схемы.

## Последовательность будущей работы

1. **Инвентаризация и карта пробелов.** Сопоставить источники таблицы, шесть authored refs
   и полезные материалы старого bundle. Определить владельца каждого знания, пропуски,
   дубли и обязательную автономную навигацию. Не повторять глубокий аудит всей кодовой базы.
2. **Дизайн входа и маршрутов чтения.** Предложить главный entry и форму references,
   политику ссылок и роль generated CLI. Согласовать до массовой переписи.
3. **Актуализация содержания.** Обновить agent-specific инструкции и исполняемые примеры,
   отразить первый этап, продолжение без чата, current/target. Новое предметное правило
   требует уточнения пользователя и канонического владельца, а не изобретения в скилле.
4. **Манифест и механизм сборки.** После согласования области обновить включения,
   замыкание ссылок, watch и Turbo inputs. Сохранить единственный авторский источник.
5. **Сборка и приёмка.** Проверить build/check/test, автономность пакета и полный цикл
   пользователя. Отдельно указать проверенное поведение, ограничения и оставшиеся пробелы.

## Проверки и безопасное применение

Перед реализацией прочитать [инструменты репозитория](scripts/README.md),
[package.json пакета](packages/relay-skill/package.json),
[Turbo пакета](packages/relay-skill/turbo.json), [генерацию](packages/relay-skill/scripts/generate.mjs),
[build](packages/relay-skill/scripts/build.mjs), [check](packages/relay-skill/scripts/check.mjs),
[тесты bundle](packages/relay-skill/scripts/bundle.test.mjs)
и [тесты примеров](packages/relay-skill/scripts/examples.test.mjs).
`src/skill.md` — авторский; `skills/relay/SKILL.md` — generated, вручную не править.
Build использует корневой `.artifacts` для staging и обновляет **оба** выхода:
`skills/relay` и `apps/playground/.agents/skills/relay`. Check вычисляет пакет без записи.

Будущие команды: `pnpm run skills:build`, `pnpm run skills:check`, `pnpm run skills:test`;
по области — `pnpm run docs:check`, `pnpm run agents:check`, `pnpm run format:check`.
Аргументы корневым scripts передавать без дополнительного `--`. Общий `pnpm run check`
уместен после устранения известного блокера и готовности связанных изменений.
До build учитывать drift и diff выходов, чтобы генерация не скрыла чужие изменения.

Fixtures создавать изолированно: в прежнем окружении `/tmp/opencode` оказался root-owned
с правами 0755 и недоступен `gromov`. Проверить доступность; при такой ситуации использовать
собственный уникальный временный каталог в `.artifacts` и `TMPDIR`. Не менять глобальные
права, не использовать пользовательские базы; очистить только свои fixtures и процессы.

Канонические сценарии приёмки:

- Пустой проект + ТЗ → весь набор знаний и связи документов → задачи с целями и без цели
  → план из одной задачи и несколько планов → фактические проверки и завершение плана
  → релиз только с текущими полями, без выдуманного `applicationId`.
- Исполнитель выполняет существенную задачу; новый агент продолжает по сохранённым
  знаниям, ограничениям и следующему шагу без исходного чата.
- Потеря ответа, конфликт ревизии, страницы списков и адресное чтение полных текстов;
  готовность учитывает критерии, детей, зависимости и обязательства FI/SI.
- Покрытие CLI и MCP с явными ограничениями. Внешние результаты кода, проверок и поставки
  в fixtures обозначены как фикстурные: Relay сам их не выполняет.
- Изучить маркеры исполняемых примеров в `EXAMPLES.md` и их обработку в `examples.test.mjs`;
  изменять примеры и проверки согласованно. Проверка только структуры пакета не доказывает
  выполнение пользовательского цикла.
- Изолированный пакет читается без checkout/сети: все обязательные знания внутри,
  ссылки и якоря корректны, Markdown и кодовые блоки сохранены точно.

## Критерии завершения и отчёт

Готовность: самодостаточный entry и весь необходимый состав знаний; нет пропущенных
references, устаревших утверждений и выдуманных API; current/target видны; один источник
каждого факта; автономность и сценарии подтверждены фактическими проверками.
Нет изменений native agent config, постоянных журналов или очистки пользовательских данных.
Итог будущего исполнителя: файлы, проверки и их исход, gaps/блокеры, следующий шаг,
оставшиеся свои ресурсы — без хроники этапов и без коммита, если он не поручен.
