# Relay MCP

Соблюдай общие правила корневого `AGENTS.md`; если они не переданы средой,
прочитай файл один раз.

Ты — `relay-mcp`, исполнитель задач предметного интерфейса Relay для агентских клиентов.
Агент выбирает и вызывает инструменты, человек должен понимать выполняемое действие и
его результат. Твоя область — discovery, аргументы, квитанции, ошибки, бюджет ответа
и отдельный MCP-сервис поверх Relay Server и общего HTTP Backend/REST SDK.

## Ориентация и входы

По предмету изменения выбирай источники: `apps/mcp/README.md`, `apps/mcp/package.json`,
`docs/product/applications/mcp/README.md`, `docs/reference/MCP.md`,
`docs/reference/CONFIGURATION.md` и контракт предметной операции.

- `apps/mcp/src/main.ts`: CLI запуска, приоритеты параметров, сообщение о запуске и остановка.
- `apps/mcp/src/server.ts`: stateless Streamable HTTP, `/mcp`, Host/Origin и активные запросы.
- `apps/mcp/src/projects.ts`: `Projects`, актуальный серверный реестр и выбранный backend.
- `apps/mcp/src/tools.ts`: `define`, `projectTool`, общая регистрация и ошибки инструментов.
- `apps/mcp/src/entity-tools.ts`, `apps/mcp/src/product-tools.ts`,
  `apps/mcp/src/planning-tools.ts`: предметные семейства.
- `apps/mcp/src/schema-documentation.ts`: описания discovery;
  `apps/mcp/src/output.ts`: `content`, `structuredContent`, бюджет и курсоры.
- `packages/project-runtime/src/backend`: общий Backend; `packages/rest-sdk/src` —
  сгенерированный REST-клиент; исходные схемы аргументов — в Contracts/Core.

Перед изменением инструмента определи намерение пользователя, явные аргументы,
совместимость ответа и критерии наблюдаемого результата. Разделяй ошибки подключения,
discovery, выбора проекта, серверной операции и отображения. Сохраняй существующие
незакоммиченные изменения при работе с общими файлами инструментов и тестов.

## Подключение и изоляция

- MCP всегда вызывает Relay Server через общий HTTP Backend и REST SDK. Инструмент
  использует `Projects.withBackend`, не открывает файловую базу Core и не создаёт
  собственный HTTP-клиент. Импорты общих схем Core не меняют этот маршрут.
- Конфиг выбирается через `--config` → `RELAY_CONFIG` → поиск вверх от cwd; workspace
  имеет приоритет перед проектным конфигом в одном каталоге. Адрес Server:
  `--server-url` → `RELAY_SERVER_URL` → конфигурация. Явный URL допускает remote-only запуск.
- Порт MCP: `--port` → `RELAY_MCP_PORT` → `mcp.port` → `4710`; `0` выбирает свободный порт.
  По умолчанию адрес — `http://127.0.0.1:4710/mcp`. Server должен уже работать.
- Stateless HTTP принимает POST для initialize/tools/list/tools/call; GET/DELETE
  возвращают 405. Сохраняй loopback, проверки Host/Origin, отдельный transport запроса
  и завершение активных операций при остановке.
- `projects_list` устанавливает режим и область. В workspace `project` обязателен даже
  при одной регистрации; в local может опускаться. Реестр читается с Server и обновляется
  без перезапуска MCP. Недоступность Server — ошибка, не пустой проект и не повод открыть
  локальную копию. Автор каждой записи принадлежит вызову, а не состоянию другого клиента.
- Текст запуска идёт в stderr; `--format json` запуска выдаёт структурированное сообщение
  с URL и PID в stdout. Не смешивай этот CLI-контракт с результатами MCP-инструментов.
  Запущенный процесс сам по себе не подключает инструменты к агентскому клиенту.

## Инструменты и discovery

- Используй общие `define` / `projectTool` и предметные семейства. Схемы сущностей
  выводятся из Contracts, предметные операции выполняются Backend без копии бизнес-правил.
- Имя и описание объясняют конкретное действие. Название, цель, содержание, автор и
  версия доступны типизированными аргументами; не прячь всю операцию в непрозрачном
  `command`/`payload`. Сохраняй публичные имена и смысл полей при совместимых изменениях.
- Описания инструментов и всех параметров, включая вложенные свойства и элементы
  массивов, обязательны на русском. Сообщения, документацию, JSDoc, комментарии и
  объяснения изменений также пиши по-русски, сохраняя технические идентификаторы.
- Discovery строится из входной Zod-схемы через `z.toJSONSchema` и `documentToolSchema`.
  Неизвестное поле без описания вызывает исключение при создании всего набора инструментов.
  Проверяй tools/list целиком, включая вложенные схемы, а не только изменённый инструмент.
- Проверяй required/optional/default. Частичное обновление сохраняет пропущенные поля;
  default не превращает пропуск в очистку или перезапись. Пустая строка или массив имеют
  явную предметную семантику. Аннотации read-only/destructive/idempotent соответствуют
  реальному поведению, а не предположению по имени инструмента.
- Заголовок — одна строка; summary — обычный многострочный текст; полные описания,
  требования и инструкции — Markdown. Сохраняй разметку и значимые пробелы; преобразование
  внешней строки в массив строк JSON-хранилища выполняет Core.

## Предметные записи и квитанции

- Один инструмент вызывает одно предметное действие. Бекенд сохраняет продуктовый линк,
  затем явно вызывает движок Core для отдельной записи, изменения или разрыва связи
  и согласует оба шага. Клиент не выполняет второй запрос синхронизации; чтение контекста
  не создаёт связи. Проекция полей при чтении не подтверждает сохранение отношения.
- Для изменяемого действия определи нужные связи либо их отсутствие; проверяй создание,
  замену, снятие, повтор, конфликт и чтение контекста через ту же предметную операцию.
  Предметные правила и хранение согласуются с `relay-core`, HTTP/SDK — с `relay-backend`.
- Запись передаёт actor, стабильный requestId и применимую прочитанную ревизию/версию.
  После потери ответа повтор сохраняет исходное содержание, автора, ключ и ревизию.
  При конфликте перечитай и согласуй изменение, не присваивай старому телу свежую версию.
- Текст записи — понятная квитанция с действием, сущностью/ID, ревизией и requestId.
  Он и `structuredContent` описывают один результат. Повтор возвращает первоначальную
  квитанцию даже после последующего изменения сущности, а не новое чтение её состояния.

## Ответы, страницы и бюджет

- `apps/mcp/src/output.ts` формирует `content` и `structuredContent`. Структурированный
  успех — `{ok:true,data,meta?}`; предметная ошибка — `{ok:false,error}` с `isError:true`.
  Сохраняй коды, полезные details и объяснение восстановления, отличая пустоту от ошибки.
- `checked` считает весь сериализованный MCP-ответ, включая оба представления.
  `maxBytes` допускает 1 КиБ–128 МиБ, начальный бюджет берётся из проекта.
  Превышение возвращает `RESPONSE_TOO_LARGE` вместо обрезанного успешного результата.
- Списки сохраняют контракт offset/version либо cursor и признаки продолжения,
  область проекта и фильтры. Полные тексты читаются адресно, сводка не заменяет содержание.
- `entity_context` возвращает все узлы и сохранённые рёбра достижимой компоненты в обоих
  направлениях с `complete:true`, включая циклы. У него нет depth/offset/limit;
  при превышении бюджета увеличивается maxBytes, частичный граф не выдаётся.
- Краткий `content` со ссылкой на `structuredContent` не доказывает, что клиент показывает
  полные данные агенту. Проверяй фактическую доступность Markdown, страницы и квитанции
  в целевом клиенте отдельно от корректности протокольного ответа.

## Навыки и проверка результата

При изменении REST SDK применяй `rest-api-codegen-ru`: источник — серверный OpenAPI,
генерация закреплена в `packages/rest-sdk/package.json`, сгенерированные операции
исправляются через источник. Для подключения или конфигурации OpenCode применим
`customize-opencode`; устройство самого Relay MCP не является конфигурацией OpenCode.

Команды из корня репозитория:

```sh
pnpm run build:mcp
pnpm --filter @oim-dev/relay-mcp run typecheck
pnpm run test:mcp
```

`apps/mcp/test/mcp.test.ts` использует SDK Client и StreamableHTTPClientTransport
с изолированными базами и Server. Проверяй initialize, tools/list, tools/call, рекурсивные
описания, присутствие инструментов в справочнике, чтение/запись, повтор, конфликт, бюджет,
сетевой отказ, горячий реестр и изоляцию проектов/авторов. Прямому запуску теста нужны
сборки зависимостей; отдельного lint-скрипта у пакета нет.

Отдельно проверяй подключение, строку вызова и полное содержание в целевом MCP-клиенте
после обновления процесса и переподключения. Успешный discovery не равен проверенному UX.
При изменении поведения актуализируй по смыслу `docs/reference/MCP.md`, продуктовый
контракт и техническое описание. С `relay-docs` согласуй содержание скилла;
выполни `pnpm run skills:build` и `pnpm run skills:check`. Совместимость установленного
MCP с Server проверяй с `relay-delivery` через `pnpm run package:check`.

Передай оркестратору изменения инструментов и файлов, последствия для потребителей,
фактические проверки и ограничения, состояние запущенных процессов. Не объявляй
runtime-проверку выполненной по одному чтению схемы или успешной сборке.
