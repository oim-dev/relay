# ТЗ: интеграция планов и релизов с бекендом

**Цель:** общие постоянные планы и релизы во всех интерфейсах Relay. Первоначальное
подключение Web выполнено; текущий этап — упрощение хранения по решению пользователя
25 сентября 2026 с сохранением предметных владельцев и сценариев.

Предметные правила: [планы работ](../entities/plans/README.md), [самостоятельные релизы](../entities/releases/README.md),
[прогресс](../PROGRESS.md). Этот документ задаёт границы интеграции и сквозной приёмки;
точные DTO, хранение и операции описываются только в справочниках владельцев ниже.

Текущая реализация задания — в [технической библиотеке](../../engineering/implementation/README.md).
Точные действующие интерфейсы: [планы](../../reference/PLANNING.md), [релизы](../../reference/RELEASES.md).

## 1. Модель и хранение

- В планировании остаются две сущности — план работ и релиз. Этапы — вложенные записи
  плана, изменения которых защищает его ревизия. Их локальные ID не становятся ключами
  сущностей или самостоятельными адресами графа и документов.
- Этап содержит только явно выбранные ссылки на существующие задачи;
  релиз — ссылки на планы целиком. Дети выбранной задачи не дописываются автоматически.
  Релиз не является типом плана и не имеет собственных этапов/задач.
- Сохранить поля готового UI. Заголовки — одна строка, краткие описания — обычный текст,
  полные описания и итоги — Markdown; в JSON Markdown хранится массивом строк.
- Версии предметных данных и решение о сбросе прежних записей без миграции определены
  в [контракте хранения](../../reference/STORAGE.md#планы-и-релизы). Физическая версия базы,
  общие задачи и документы сохраняются. Демоданные браузера не импортируются автоматически.

## 2. Предметные операции

- **Планы:** список, чтение, создание, редактирование, управление этапами и их порядком,
  включение/исключение задач, начало, завершение с итогом, отмена.
  Web показывает `draft` как «Запланирован»; отдельное начало не требуется для завершения.
- **Релизы:** список, чтение, создание с выбором планов, изменение состава и реквизитов,
  планирование, отмена и явная фиксация выпуска. Статусы: «Запланирован», «Выпущен», «Отменён».
  Незавершённые планы можно включить в запланированный релиз; выпуск требует готовности
  всего состава и сохраняет статус, автора и фактическую дату. Чтение состава и готовности
  остаётся актуальным после выпуска. API и технических видов снимка нет.
- Готовность рассчитывать в Core через предметные обработчики прогресса, а не по загруженным
  карточкам или одному полю `done`. Переходы повторно проверять под блокировкой.
  Действия плана и релиза не должны автоматически менять колонки задач.

До включения обязательного основания начала работы уточнить переход старых задач
и повторного открытия; не вводить ограничения молча из UI-проверок. Перенос уже имеет
явные целевые план/этап и ревизии обоих планов в [контракте](../../reference/PLANNING.md).

## 3. Связи и надёжность

Продуктовые сервисы сохраняют линки, затем **явно вызывают Core для записи/снятия связей**:
план → проект, явно выбранная задача → план (`part-of`), план → область (`affects`),
релиз → проект (`part-of`), релиз → выбранный план (`includes`). Материалы подключать
через существующие операции документов. Контекст читает сохранённый граф.

Одна предметная операция согласует данные, связи, предметные сведения планирования и квитанцию; клиент не синхронизирует
рёбра отдельным запросом. Нужны проверка ревизии, безопасный повтор по requestId и
восстановление после отказа между шагами. Удаление/снятие состава не оставляет висячих связей.

## 4. API и подключение Web

- Поддерживать согласованные REST-операции в server-runtime, OpenAPI и сгенерированный SDK.
  Бизнес-правила общие в Core; CLI/MCP используют те же операции. Точные DTO и URL —
  в [справочнике API](../../reference/API.md#планирование-и-релизы).
- Серверные домены `planning` и `releases` предоставляют данные композициям Web. Планы,
  задачи выбора, релизы и прогресс читать с сервера; sessionStorage оставить для черновиков.
- Сохранить SSE-обновления, состояния загрузки/ошибки, конфликты ревизий и повтор сохранения.
  Фоновое обновление не затирает ввод; выбор не теряется при поиске и смене страницы.
- Каталоги и вложенные списки имеют пагинацию, полное количество и продолжение.
  Полный прогресс не зависит от числа загруженных строк. Изоляция по проекту обязательна.

## 5. Приёмка

План из реальных задач создаётся, изменяется и сохраняется после перезапуска сервера.
Релиз планируется из этих планов; после готовности явно выпускается. Повторное открытие
задачи меняет текущую готовность, сохраняя факт выпуска. Приёмка должна подтвердить
две предметные сущности, вложенные этапы, отсутствие автоматических включений детей,
независимость статусов, граф и обратные связи, конфликты, повтор запросов,
отказ/восстановление, пагинацию и два изолированных проекта.
Web, REST, CLI и MCP работают с одними данными; черновики и адаптивность сохраняются.
Исполнитель передаёт оркестратору фактические результаты, границы разрешённой очистки
и непроверенное. Наличие этого ТЗ не подтверждает выполнение. Ветки и дерево
задач Web — отдельные следующие этапы, требующие самостоятельного поручения.
