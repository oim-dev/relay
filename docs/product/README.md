# Relay: концепция продукта

[Библиотека знаний](../README.md) → Продукт

**Relay — рабочая память и система сопровождения жизненного цикла проекта для агентов.**
Он связывает понимание создаваемого продукта с планированием, выполнением, проверкой
результатов и продолжением работы между сессиями. Человек задаёт направление и видит,
что происходит; агент получает сохранённый контекст вместо восстановления прежнего разговора.

Этот раздел описывает ожидаемое поведение Relay. Фактическое покрытие и ограничения
собраны в [состоянии реализации](../engineering/implementation/README.md).

## Какую проблему решаем

При агентной разработке требования, причины решений и ход работы легко остаются в чате.
Смена сессии теряет понимание цели, непроверенный отчёт выглядит как готовый результат,
а накопленные документы не помогают понять следующий шаг.

Relay должен обеспечивать:

- постоянное описание продукта, его возможностей, сценариев и приложений;
- связь намерения с планом и конкретной работой;
- различимость выполнения, проверки, приёмки, интеграции и поставки;
- восстановление цели, состояния, оснований решений и ближайшего действия;
- компактный обзор с адресным доступом к подробностям.

## Участники и ответственность

**Человек** определяет результат, приоритеты и границы поручения, уточняет намерение
и наблюдает через Web. Он может читать и редактировать сведения; изменения должны
становиться видны агентам.

**Оркестратор** поддерживает понимание продукта, готовит планы и задачи, организует
исполнение и приёмку, сохраняет актуальное состояние и следующий шаг. Новая сессия
может продолжить эту роль. Самостоятельность ограничена поручением пользователя.

**Исполнитель** получает конкретную работу с достаточным контекстом, выполняет её,
фиксирует результаты, вопросы, проверки и точку продолжения.

**Relay** хранит сведения, проверяет правила, связи и версии и предоставляет согласованные
представления через интерфейсы. **Внешняя агентская среда** запускает процессы агентов,
изменяет код и выполняет команды. Запись исполнения или установки не запускает процесс
и не развёртывает приложение сама по себе.

## Основные сценарии

1. **Создать продукт с нуля:** сохранить намерение → описать продукт и ближайшие сценарии →
   спланировать → выполнить и проверить → сохранить результат и дальнейшую работу.
2. **Подключить существующий проект:** исследовать код и источники → описать исходное
   состояние с основаниями и неизвестным → определить изменения → продолжить разработку.
3. **Развивать и сопровождать:** найти затронутое поведение → уточнить изменение или баг →
   выполнить работу → обновить знание о продукте и подтверждения.
4. **Продолжить после паузы:** прочитать цель и точку продолжения → сверить фактическое
   состояние → восстановить контекст конкретной работы → выполнить следующий шаг.

Подробности: [сквозные процессы](workflows/README.md).

## Модель продукта

Проект — изолированная область данных. Workspace объединяет регистрации проектов,
но не смешивает их продукты и задачи.

Внутри проекта раздел **«Продукт»** описывает продукт пользователя: паспорт, возможности
(фичи), сценарии, приложения и их вклады. Документы доступны в общей библиотеке проекта
и связываются с продуктовыми сущностями. Например, пользователь описывает
сервис аренды. Это отдельная [предметная сущность](entities/product/README.md), а не весь Relay.

Задачи на отдельных досках описывают изменение продукта; документы сохраняют требования,
правила и основания решений, связи дают адресный контекст. [Планы работ](applications/web/PLANS.md)
организуют существующие задачи по этапам; самостоятельные [релизы](applications/web/RELEASES.md)
выбирают планы и фиксируют статус, дату и автора выпуска через общие операции Core.
Этапы хранятся внутри плана; состав релиза и его готовность читаются из актуальных планов.
Обзор и отдельный раздел инфраструктуры также в разработке. Общая история Web удалена.
Прежняя модель
жизненного цикла и числовая доска удалены.
Текущее покрытие отмечено в [реализации](../engineering/implementation/README.md).

Продуктовый линк хранится в данных своего функционала. После продуктового действия
бекенд явно вызывает движок Core для установки, изменения или разрыва отдельно
сохраняемой связи. Эти связи нужны для контекста и цепочек, а не вместо продуктовых
правил. Контекст читает граф. Разделение обязательно при разработке каждого сценария:
[линки, связи и контекст](../development/LINKS-AND-CONTEXT.md).

## Приложения Relay

| Приложение                                      | Роль                                                                       |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| [CLI](applications/cli/README.md)               | Терминальные действия человека и структурированный интерфейс автоматизации |
| [Server](applications/server/README.md)         | Общая точка доступа к проектам, REST, события и поставка Web               |
| [Web](applications/web/README.md)               | Наблюдение, навигация, чтение и редактирование памяти проекта              |

Web и MCP используют Server. CLI может работать через Server или напрямую с одним
локальным проектом. Бизнес-правила общие; технические подробности — в
[архитектуре](../engineering/ARCHITECTURE.md).

## Принципы качества

- Один владелец факта; повторные представления используют связи.
- Полное содержание доступно как Markdown, краткий обзор не заменяет подробности.
- Пустые данные, ошибка, неизвестная запись и неполная выборка различаются.
- Параллельные изменения не должны молча терять ввод и подтверждения.
- Завершённая задача, готовый контракт и проверенная поставка означают разные вещи.
- История объясняет состояние; старая проверка не становится свежей после чтения.
