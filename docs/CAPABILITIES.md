# Возможности Relay

Каталог описывает **статически подтверждённые возможности и их подключение в текущем
дереве исходного кода**. Это не отчёт об исполнении пользовательских сценариев, прохождении
тестов или составе выпущенной версии. Он предназначен для людей и агентов, выбирающих
способ работы с проектом. Каталог также отмечает принятые, но пока отсутствующие
возможности: их целевая модель указана отдельно и не означает доступности действия.

## Как читать каталог

- **Есть** — действие реализовано в Core или подключено в указанном интерфейсе, в том числе
  через **общие операции сущностей** (generic). Отсутствие отдельной предметной команды не
  означает отсутствие возможности.
- **Частично** — доступна только часть действия или ограниченный пользовательский путь;
  ограничение указано в последнем столбце.
- **Нет** — соответствующего действия слой или интерфейс не предоставляет.
  Для принятой целевой возможности это пробел реализации, если так указано в границах.
- **—** — действие не применимо к этому слою.

Таблицы по областям составляют **единый реестр покрытия Core / REST / Web / CLI / MCP**.
Web-покрытие отражает пользовательские пути, а не просто наличие метода SDK. Для REST,
CLI и MCP учитываются зарегистрированные обработчики и их подключение к Backend.
Читаемый вид сущности не обязательно поддерживает создание или изменение через общие
операции. Диагностические рёбра графа не заменяют предметные операции над связями задач.

Точки входа под таблицами — ориентир, а не полный справочник API. CLI-команды подразумевают
префикс `npx @oim-dev/relay-cli`; REST-пути — `/api/v1`, а для выбранного проекта также
`/api/v1/projects/:project`. Семейство `entity_<kind>_create` регистрируется по схемам
поддерживаемых видов, а не для любого произвольного `kind`.

Точные команды и аргументы находятся в [справочнике CLI](../apps/cli/docs/CLI.md),
[справочнике MCP](../apps/mcp/docs/MCP.md) и [REST API](../packages/server-runtime/docs/API.md).
Пути человека описаны в [руководстве Web](../apps/web/docs/USAGE.md),
выбор базы и подключения — в [конфигурации](../packages/project-runtime/docs/CONFIGURATION.md).

## История агентской работы

Принятые правила: [ветки, участия и checkpoints](domain/WORK_HISTORY.md).
Маршрут агента: [рабочий цикл](guides/WORKFLOW.md#история-работы-агента-и-субагентов).

Web предоставляет [граф времени проекта](domain/WORK_HISTORY.md#граф-времени-проекта).
Он **не содержит Web-фильтров**, каталога/карточек веток, отдельного списка
открытых намерений или текстовой ленты на основной странице. Графический экран и
адресное модальное чтение подключены к graph-v2. CLI-фильтры
и все прежние CLI/REST-чтения сохраняются; наличие API не означает наличие такого UI.
По принятому правилу completed/cancelled сразу визуально возвращаются к линии родителя
или оси проекта. Это не предметное принятие: отдельного acceptance-ребра нет,
`acceptedSessionIds` и CLI-действия сохраняются независимо от графа. Fork соединяет
линию родителя с созданием ребёнка на времени ребёнка, не с датой старого intent.
Core выделяет новым веткам, участиям и checkpoints восьмисимвольные ID; прежние
длинные адреса и ссылки сохраняются. Формат описан в [контракте истории](domain/WORK_HISTORY.md#ветка-участие-и-точка-работы).

отдельной read-only capability `relay-work-history-graph-v2`; SDK-операции —
`getWorkHistoryGraph` и `getWorkHistoryGraphPoint`. CLI/MCP-графовых команд нет.

проекция не подменяет несовместимый Server пустым графом или локальной
записью. Таблица отражает статическое подключение, не браузерную приёмку или публикацию.
Предметная capability `relay-work-history-v1` и профиль 3 не меняются.

Web-раскладка сохраняет одну вертикальную дорожку для всех точек ветки; родительский
ствол продолжается выше работы потомков. Закрытые непересекающиеся участки могут
переиспользовать колонку. Ответвление выходит прямо из родительской дорожки, а возврат
закрытой ветки заканчивается стрелкой у её внешнего края. Верхняя полоса
незавершённых сессий переводит к месту продолжения, включая точки вне страницы.
Подписи раскрываются при наведении/фокусе; кнопка сброса возвращает исходные позицию
и масштаб 100%. Все маркеры круглые; основной агент обозначен сплошной линией,
субагент — пунктирной. На графе используются иконки событий; аватар оператора
показывается только в подсказке и полном просмотре точки. Техническое устройство визуализации — у
[Web](../apps/web/docs/ARCHITECTURE.md#история-работы); наличие подключённого рендеринга
не является результатом браузерной приёмки, прежние снимки экрана её не заменяют.

## Существенные ограничения

- **Удаление учитывает ссылки всех планов.** Ссылки на удаляемые сущности в `taskIds` или
  `scope` любого плана, включая закрытый, блокируют удаление с
  `PLANNING_REFERENCE_IN_USE`. Закрытый план неизменяем; штатной операции удаления таких
  ссылок из него нет. Наличие удаления вида не означает, что любой его экземпляр можно удалить.
- **Вычисляемый прогресс отличается от сохранённого состояния.** Текущая готовность задачи,
  плана и релиза может отличаться от сохранённых статусов. Совместимые ручные отметки
  контрактов не переопределяют вычисляемую готовность.
- **Компактные формы добавочны.** Прежний JSON без явно выбранной проекции сохраняется;
  сокращённый DTO не доказывает O(limit) чтения или готовности опубликованной версии.
  Compact-чтения работы требуют capability `relay-work-read-models-v1`, сохранение релиза
  по ссылкам — `relay-release-refs-v1`; старый Server нельзя обходить клиентской записью файлов.
- **Условия этапа — текст.** `completionConditions` не являются исполняемой проверкой.
  Пустой этап не блокирует завершение всего плана, если общий состав задач непуст и все
  задачи выполнены.
- **Не вся пагинация закреплена за снимком.** Старые backend-операции `product list` и `product entities` возвращают
  версию состояния, но не принимают её для контроля продолжения: строгие схемы запросов не
  содержат `version`. Согласованность нескольких страниц одним снимком не гарантируется;
  подробнее — в [документе о хранилище](domain/STORAGE.md). Эти команды больше не
  зарегистрированы в CLI: каталоги используют предметные list и search.
  CLI `--cursor` с consistency=snapshot проверяет неизменность текущей версии,
  не открывает исторический снимок; `workspace project list` передаёт исходную версию
  серверной странице, Server проверяет отпечаток всего текущего каталога.
  Полный контракт `meta.page` — в [CLI](../apps/cli/docs/CLI.md#правила-продолжения).
- **Предметная история не равна истории запросов.** Единое хранилище использует формат
  4 и конверт сущности версии 3. Постоянных квитанций результатов и истории содержания нет;
  `requestId` служит только корреляции. Комментарии, алиасы и уведомления имеют собственное
  назначение и не являются историческими ревизиями. История агентской работы
  сохраняет отдельные содержательные намерения и результаты, не каждый вызов инструмента.

Проект адресуется постоянным `projectId`, который не обязан быть UUID. Устройство local/HTTP,
подключение CLI/MCP и ответственность Server описаны в [архитектуре](ARCHITECTURE.md).
Автоматических повторов мутаций в подключении CLI/MCP → Backend → REST нет. После потери
ответа нужно перечитать состояние, а не автоматически отправлять прежнее тело со свежей
ревизией; правила сохранения — в [документе о хранилище](domain/STORAGE.md),
порядок действий при потере ответа — в [руководстве по восстановлению](guides/RECOVERY.md).
