# Линки, связи и контекст: обязательные правила разработки Relay

## Статус и обязательность

Это предметный стандарт линков, сохраняемых связей и контекста. Воркер получает знания
области из своего промпта; применимые разделы этой спецификации читает адресно при
проектировании, изменении или проверке соответствующего сценария.

Стандарт принят пользователем 22 сентября 2026. Он задаёт требуемую модель и правила
новых изменений. Текущая реализация соответствует ему частично: её расхождения перечислены
ниже и в [техническом состоянии](../engineering/implementation/relations.md).
Принятие документа не означает выполненную миграцию или изменение существующего API.

**Главное правило: продуктовые действия решают продуктовые задачи. После выполнения
продуктовой части бекенд явно вызывает функции движка Core, чтобы установить,
изменить или разорвать отдельно сохраняемые связи для контекста.** Агент обязан
рассматривать эту интеграцию при проектировании каждого продуктового сценария Relay.

Линк в продуктовых данных и запись связи в движке — два разных механизма.
Связь не является только вычисляемой при чтении проекцией продуктовых полей.
Именно такая проекционная трактовка в первой редакции документа была ошибкой агента;
пользователь исправил её на примере прикрепления документа к фиче.

## Зарезервированные термины

### Линк

**Линк — продуктовые данные о прикреплении или другом предметном отношении сущностей.**
Он сохраняется у продуктового владельца и используется функционалом продукта:
отображением прикрепления, списками документов, целями задач, зависимостями и другими правилами.

Примеры: документ описывает приложение; материал прикреплён к задаче; задача реализует
сценарий; задача зависит от другой задачи; сценарий принадлежит фиче.
Смысл, направление, допустимые цели, обязательность и последствия определяет владелец.
Слово «линк» здесь не означает произвольный URL или Markdown-ссылку: упоминание сущности
в тексте само по себе не создаёт предметного отношения.

### Связь

**Связь — отдельно сохраняемое отношение между сущностями в движке Core.** Бекенд
продуктового сценария явно вызывает функции движка для её установки, изменения или разрыва.
Связь нужна для общего графа, поиска прямых и обратных отношений и обхода цепочек контекста.

Связь не заменяет продуктовый линк, а линк не заменяет запись связи. Наличие двух записей
здесь намеренно: одна обслуживает продуктовый функционал, другая — механизм движка.
Их согласованность обеспечивает бекенд сценария, а не пользователь или клиент.
Графовые индексы могут быть производными от сохранённых связей; сами связи не сводятся
к индексу продуктовых полей. Обратное чтение одного ребра не требует встречного ребра.

Движок не реализует прикрепление документов, готовность фич или блокировки задач.
Продуктовая логика не должна определять эти результаты по наличию произвольного ребра.

### Контекст

**Контекст — публичный механизм чтения окружения сущности по связям, с объяснением путей
включения и явными границами выборки.** Он помогает понять область, требования, материалы
и работу, найти ответы и исследовать окружение глубже.

Контекст не устанавливает и не разрывает линки или связи. Цепочки вычисляются при чтении,
а не записываются как дополнительные транзитивные линки. Контекст динамический: это
окружение текущего согласованного снимка, а не неизменяемая история требований.

## Разделение ответственности

| Владелец                     | Ответственность                                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Web                          | Предметные формы и действия: прикрепить документ, выбрать цель, назначить родителя                                                    |
| CLI                          | Человеческие команды и машинный контракт тех же предметных действий                                                                   |
| MCP                          | Понятные предметные инструменты для агента                                                                                            |
| REST                         | Доставка предметных операций и запросов контекста в Core                                                                              |
| Бекенд продуктового сценария | Проверка правил и запись продуктовых данных; затем явный вызов функций Core для установки/разрыва связей; согласованность обоих шагов |
| Движок связей Core           | Установка, отдельное хранение и разрыв текущих связей, обратные запросы и обход                                                       |
| Механизм контекста           | Полный обход компоненты, согласованный снимок и бюджет ответа; отдельная ограниченная диагностика                                     |

Бекенд сценария может находиться в прикладном слое Core; это не обязанность HTTP-контроллера.
Продуктовый сервис и движок связей остаются разными механизмами, даже внутри одного пакета.
Локальный CLI вызывает тот же сценарий и соблюдает те же гарантии, что Web/MCP через Server.

Интерфейс проектируется вокруг назначения действия. Пользователь выбирает документ
для задачи, а не технические поля произвольного ребра. Все штатные пути записи используют
общую предметную логику; проверки формы не заменяют проверки Core.

## Продуктовая запись → вызов Core → запись связи

Нормальный сценарий:

1. Участник выбирает предметное действие, например «Прикрепить документ к задаче».
2. Клиент вызывает операцию владельца линка с выбранным проектом и адресами сущностей.
3. Бекенд разрешает адреса и проверяет существование целей, правила и версию;
   requestId служит корреляции, не дедупликации.
4. Выполняется продуктовая часть: сохраняются продуктовые поля, включая линк.
5. Затем бекенд явно вызывает функцию движка Core для установки соответствующей связи.
6. Движок сохраняет связь в своём хранилище. Контекст читает её для построения цепочек.
7. Сценарий сообщает успешное завершение, когда оба шага согласованы.

**Запрещено возлагать на клиент последовательность «сохранить предметную запись,
затем отдельным запросом синхронизировать ребро».** Успешная предметная операция уже
обеспечивает согласованность. Установка связи — явный шаг бекенда после продуктового действия,
а не побочный эффект чтения контекста и не отдельное поручение агенту-пользователю.

Логическая последовательность не требует двух независимых коммитов без защиты.
Реализация обязана определить атомарную публикацию либо долговечное восстановление
составной операции. Отказ между продуктовой записью и записью связи не должен выдаваться
за полный успех. Повтор и восстановление не дублируют ни линк, ни связь. Конкретный механизм
транзакции и сопоставления записей проектируется отдельно; этот стандарт не объявляет его готовым.

### Сквозной пример: документ прикреплён к фиче

```text
UI: выбрать фичу и нажать «Прикрепить»
  → бекенд: выполнить продуктовый сценарий
  → база документа: сохранить продуктовый линк на ID фичи
  → бекенд: вызвать функцию Core для установки связи документа с фичей
  → хранилище движка: сохранить отдельную связь
  → контекст: прочитать связь и раскрыть окружение
```

В продуктовой записи документа остаются поля прикрепления, которыми пользуется UI
и функционал библиотеки. В хранилище движка находится запись связи с адресами документа
и фичи и выбранным типом отношения. Открытие UI не создаёт её; чтение контекста также
не создаёт её. При прикреплении к сценарию меняется целевая сущность, порядок тот же.

Схематически, не названия существующего API:

```text
прикрепитьДокумент(документ, фича):
    сохранитьПродуктовыйЛинк(документ, фича)
    движокCore.установитьСвязь(документ, фича)

открепитьДокумент(документ, фича):
    удалитьПродуктовыйЛинк(документ, фича)
    движокCore.разорватьСоответствующуюСвязь(документ, фича)
```

Это схема шагов внутри согласованной операции, не готовый код обработки отказов.

Постоянная адресация — вид и ID внутри проекта. Ключи разрешаются на внешней границе;
названия, пути файлов и префиксы не являются идентичностью. Переименование не разрывает линки.
Точные адреса и ошибки: [движок сущностей](../reference/ENTITIES.md).

### Как выбрать предметное действие

| Намерение                                        | Продуктовый линк и действие бекенда с движком                                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Продукт принадлежит проекту                      | Сохранить продукт выбранного проекта; затем установить продукт → `part-of` → проект   |
| Фича входит в продукт                            | Сохранить фичу в продуктовом агрегате; затем установить фича → `part-of` → продукт    |
| Сценарий относится к фиче                        | Сохранить принадлежность сценария; затем установить связь с фичей                     |
| Приложение реализует поведение                   | Сохранить приложение и цель реализации; затем установить соответствующие связи        |
| Задача работает над продуктовой целью            | Сохранить `targets` / `productLinks`; затем установить связи с целями                 |
| Декомпозиция работы                              | Назначить родителя задачи; затем установить связь ребёнка с родителем                 |
| Нужен результат другой задачи                    | Сохранить продуктовую зависимость; затем установить связь `depends-on` для контекста  |
| Задачи полезны друг другу без порядка выполнения | Сохранить продуктовый линк; затем установить связь `related`                          |
| Документ описывает сущность                      | Сохранить прикрепление документа; затем установить документ → `documents` → сущность  |
| Сущности нужен материал для чтения               | Сохранить прикрепление документа; затем установить сущность → `references` → документ |

Таблица задаёт требуемый порядок интеграции, а не обещает его текущую реализацию.
Участник не дублирует вызовы движка вручную после успешной продуктовой операции.
На продуктовой доске
задача выбирает фичи/сценарии; на доске приложения — реализации своего приложения;
на инфраструктурной доске целей реализации нет. Действующий контракт — [канбан](../reference/KANBAN.md).

Если для нового отношения ещё нет предметной операции, при разработке сначала определяют
её владельца и контракт. Нельзя молча заменить её универсальным ребром. При использовании
Relay отсутствие нужной операции фиксируют как ограничение, а не обходят выдуманным API.

### Пример цепочки

```text
Задача ──implements──→ Реализация ──implements──→ Сценарий ──part-of──→ Фича
Документ ──documents──→ Сценарий
```

Продуктовые операции сохраняют свои линки и явно устанавливают соответствующие прямые
связи в движке. Контекст обходит сохранённые связи и находит документ из задачи по цепочке.
Вычисляется путь, а не заменяющие запись связи проекции продуктовых полей. Прямой линк задачи
к документу не нужен, если участник не намеревался прикрепить его отдельно.

Выбирай наиболее точную реальную цель. Не добавляй все предки и документы «на всякий случай».
Не создавай искусственную фичу ради инфраструктурной работы или общего исправления приложения.
Область воздействия отличается от цели реализации; её предметный контракт проектируется явно.

## Изменение линков и разрыв связей

1. Прочитай сущность, отношение и его владельца. В переходной реализации учитывай `source`.
2. Измени или сними линк через предметную операцию владельца.
   Её бекенд после продуктового изменения обязан вызвать Core для изменения или разрыва
   соответствующих связей. Одного удаления поля из продуктовой записи недостаточно.
3. При передаче полного массива сохрани остальные элементы; пустой массив означает явное очищение.
4. Используй актуальную ревизию/версию. После конфликта перечитай данные и согласуй изменение;
   не подставляй свежую версию к устаревшему полному содержимому.
5. После потери ответа перечитай текущую запись и отношения, затем реши, нужно ли ещё
   изменение. `requestId` — корреляция, не гарантия дедупликации; безусловный повтор не нужен.
6. Перечитай результат и проверь прямое, обратное и контекстное представления.

При замене цели A на B бекенд сохраняет продуктовую замену, затем снимает связь с A
и устанавливает связь с B. При изменении полного набора он обрабатывает разницу старого
и нового состава, сохраняя незатронутые отношения. Нужно знать, какие записи движка
обслуживают этот сценарий: нельзя удалять все рёбра между двумя сущностями только по совпадению концов.

Снятие линка не удаляет сущности и не затрагивает остальные линки. Документ может остаться
в контексте по другому пути — это не означает, что снятие не сработало.
Завершение задачи не стирает её линки. Каскад удаления сущности и очистка внешних линков
задаются предметным владельцем, а не наличием произвольного пути в графе.
После соответствующих продуктовых действий удаления бекенд вызывает очистку связей Core.
Для удаления используй штатный предпросмотр состава, если он предусмотрен контрактом.
История фиксирует фактические действия; старое содержание нельзя восстанавливать выдуманными событиями.

## Чтение контекста

1. Установи проект и прочитай исходную сущность.
2. Запроси `entity_context` или `graph context` для её ключа/ID.
3. Рассмотри узлы, направления, типы и объясняющие пути, а не только список названий.
4. Проверь `complete: true`: основной контекст возвращает всю достижимую компоненту одним вызовом.
5. При ошибке бюджета увеличь допустимый размер ответа. Основной контекст не ограничивается
   глубиной или первой страницей. Для диагностического `graph list` отдельно действуют
   `nextOffset/version` и `depthLimited/boundary`; их не переносят на основной контракт.
6. Прочитай полные требования и документы адресными предметными операциями, например `entity_get`.

Просмотр контекста любой сущности показывает все сохранённые входящие и исходящие связи
в заданных границах. Документ, приложение, доска или фича не обрывают обход скрытым правилом.
Если сохранён путь через документ к другой области, он виден при достаточной глубине;
это не переносит продуктовую принадлежность или обязательность требований на исходную сущность.
Основной вызов обходит оба направления без ограничения глубины до конца компоненты.
В отдельной диагностической выборке `graph list` профиль `all` используется по умолчанию,
`context` — совместимое имя; там доступны направление, тип, поиск, глубина и страницы.

Краткие карточки не заменяют полные тексты. Пустая выборка, неизвестная сущность, повреждённая
ссылка, смена снимка и превышение бюджета должны различаться. У основной операции успешный
ответ всегда полный. В диагностической выборке `nextOffset` и `depthLimited` независимы;
одна её страница не доказывает полноту окружения.

Контекст объясняет достижимость, а не обязательность или готовность:

- `references` не превращает материал в требование;
- `implements` обозначает намерение реализовать, не приёмку результата;
- наличие отношения проверки не подтверждает успешную проверку;
- блокировки и готовность определяются предметными правилами, не произвольным именем ребра;
- отсутствие документа в выборке не доказывает, что общие правила проекта неприменимы.

### Диаграммы

Диаграмма использует тот же механизм чтения: узлы, рёбра и явную полноту ответа.
Фронтенд не восстанавливает отношения из названий и расположения файлов. Исходная модель —
граф; дерево является проекцией и должно сохранять обозначения повторных узлов, нескольких
родителей и циклов. Визуализация строится по `nodes/edges`; `paths` с одним кратчайшим путём
на узел не заменяет полный состав отношений. Неполный граф должен быть явно обозначен.

## Обязательный контракт новой функциональности

**Для каждого нового или изменяемого продуктового сценария агент обязан определить,
нужно ли после его выполнения устанавливать, менять или разрывать связи Core.**
Не каждое поле требует связи; отсутствие необходимости обоснуй. Это обязательный пункт
проектирования даже тогда, когда пользователь не упоминает граф или контекст.

Перед реализацией проверь и согласуй для сценария:

- пользовательское намерение и предметную операцию;
- владельца и место хранения продуктовых данных и линков;
- отдельно сохраняемые связи движка и их соответствие продуктовым действиям;
- точку явного вызова функций Core после создания, изменения и удаления продуктовых линков;
- вид и ID концов, направление и значение отношения;
- допустимые цели, обязательность, кардинальность, повторы и циклы;
- влияние на готовность, блокировки и область требований либо отсутствие такого влияния;
- создание, замену, снятие, удаление целей, отсутствие истории операций, конкуренцию
  и чтение текущего состояния после потери ответа;
- согласованность двух записей, поведение при отказе между шагами и восстановление;
- идентификацию связей сценария, прямое/обратное чтение и правила контекстного обхода;
- границы списков, продолжение и поведение при большом ответе;
- совместимость существующих данных и необходимость миграции.

Новый функционал не готов, если нужные связи лишь вычисляются из полей при чтении,
если отсутствуют явные вызовы установки/разрыва Core после продуктовых действий
или если клиент должен вручную поддерживать согласованность. Не добавляй отдельное дерево
отношений только для одного экрана. Если задача не меняет этот механизм, фиктивные линки
и формальные правки не нужны.

### Проверяемый результат

Для затронутых отношений проверяй предметное действие и человеческое представление
отдельно от машинного ответа:

- после продуктовой операции сохранены продуктовый линк и отдельная связь движка;
- создание связи происходит без открытия UI, чтения графа или дополнительного запроса клиента;
- сверка после потери ответа обнаруживает уже сохранённые линк и связь; конфликт не затирает чужое изменение;
- отказ между шагами не даёт ложного успеха, восстановление приводит обе записи к согласованному состоянию;
- смена названия/ключа сохраняет отношение;
- снятие убирает продуктовый линк и вызывает разрыв нужной связи, сохраняя сущности и остальные пути;
- удаление выполняет предметный каскад и не оставляет висячих ссылок;
- контекст раскрывает сохранённые пути в заданных границах и не скрывает их по виду сущности;
- циклы завершаются, страницы и границы не выдают усечённый ответ за полный;
- Web, CLI и MCP получают одинаковые предметные последствия через Core.

## Диагностика и переход от текущей реализации

Универсальная запись рёбер допустима как отдельный диагностический или ремонтный механизм,
а не как штатный способ прикрепить документ или назначить цель задачи. Прямое исправление
связи не меняет продуктовый линк и бизнес-последствия. При ремонте проверяй оба состояния;
правка графового индекса не заменяет исправление сохранённой связи.
Документ не разрешает массовое удаление существующих рёбер или ручное редактирование базы.

При переходе 22 сентября 2026 старые базы сохраняют совместимый адаптер, новые используют
`relay-entities`. Устройство и совместимость — в [описании единого хранилища](../engineering/entity-storage.md).

Покрытие:

| Область           | Фактическое состояние и ограничение                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------- |
| `source=domain`   | Удалён из движка и контракта ответа; каталог больше не создаёт рёбра из продуктовых полей                       |
| `source=graph`    | Единственный источник: сохранённые рёбра. В едином формате предметные сервисы явно согласуют свои группы связей |
| Web и CLI/REST    | Универсальная запись обозначена диагностической; единый формат защищает предметные группы от прямого изменения  |
| MCP               | `entity_context` возвращает полный граф одним вызовом; универсальной записи рёбер в инструменте нет             |
| `product_context` | Отдельный подбор продуктовых записей через прежние `fields.links`, не общий обход новых отношений документов    |
| `/context`        | Контекст подключения: проект, автор, конфигурация; не окружение сущности                                        |

Движок теперь читает только сохранённые связи, без прежней политики отсечения видов.
Продуктовый линк без вызова записи Core не появляется в графе: до интеграции сценариев
контекст может быть пустым, кроме корня. Применимые к сценарию контракты сверяются адресно,
даже если до них нет сохранённого пути; отсутствие пути не отменяет их применимость.

В существующем API самостоятельное ребро `depends-on` не заменяет блокирующую зависимость
задачи, а `implements` не заменяет цель для расчёта готовности. Прежние вычисляемые
domain-рёбра больше не возвращаются. Для ремонта сохранённых связей действуют
[контракт графа](../reference/GRAPH.md), версия снимка и текущее состояние; изменение типа
или концов требует remove/add, поскольку update меняет только пояснение.

Этот стандарт отличается как от ошибочной первой редакции о производных проекциях,
так и от прежнего предложения перенести все продуктовые
отношения исключительно в граф: продуктовые линки остаются у своих владельцев, а связи
отдельно записываются в движок вызовами бекенда. Основание —
[техническое решение](../engineering/decisions/product-links-and-core-relations.md).

В едином формате подключены явные вызовы Core из продуктовых сценариев и согласованная
публикация двух записей. Прежние базы переносятся явно с сохранением ID и текущих данных;
автоматическая история удаляется, комментарии сохраняются.
Автоматического импорта на чтении нет; продуктовые поля и сохранённые graph-рёбра остаются.
Согласование уже единой базы после обновления выполняется явно через
`storage reconcile-relations`; точные условия — в [контракте хранения](../reference/STORAGE.md).
