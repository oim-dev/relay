# Правила библиотеки знаний

Библиотеку сопровождает [relay-docs](../../packages/dev-agents/src/docs.md). Его профиль содержит
инструкции исполнителя; эта страница объясняет устройство и качество документов.

## Владельцы информации

- `product` — назначение Relay, ожидаемые возможности, модель и поведение приложений.
- `engineering` — текущее техническое устройство, покрытие и причины решений.
- `reference` — точные действующие команды, API, схемы, конфигурация и ошибки.
- `guides` — практические инструкции использования и эксплуатации.
- `development` — устройство команды и процессы изменения Relay.
- `archive` — прежние спецификации и исходные материалы с объяснением статуса.

Справочники сохраняют стабильные адреса в `reference`: их используют CLI-поставка,
скилл и внешние ссылки. Инженерная навигация связывает их с реализацией.
Корневые страницы `docs` могут оставаться короткими совместимыми точками входа.

## Один владелец факта

Общее правило сущности описывается у сущности. Приложение описывает пользовательское
взаимодействие и ссылается на правило. Справочник определяет синтаксис, руководство
показывает применение. Историческая запись не становится вторым действующим справочником.

README приложения возле кода — инструкция запуска и разработки, а
`product/applications/<имя>` — продуктовый контракт. Бизнес-правила в README возле кода
заменяются ссылками на каноническое описание при смысловом изменении соответствующей области.

Общие правила разработки для всех агентов принадлежат [корневому AGENTS.md](../../AGENTS.md),
полные инструкции ролей — профилям в `packages/dev-agents/src`, включая
[роль оркестратора](../../packages/dev-agents/src/orchestrator.md).
[Руководство команды](AGENT-TEAM.md) поясняет применение, не дублирует профили и не добавляет
обязательное чтение перед поручением. Продуктовый скилл описывает пользователей Relay, не эту команду.

## Статус и достоверность

- Действующая спецификация задаёт ожидаемое поведение. Предложение помечается отдельно
  и не становится требованием без принятого решения.
- Описание реализации указывает область и основания сверки: код, версию, проверки.
  Статическое чтение не равно успешному запуску сценария.
- Историческая проверка относится к указанным версии и окружению. При переносе её дата
  не меняется; непроверенное сегодня остаётся непроверенным.
- Архивный документ получает отметку статуса и ссылку на замену. Его формулировки
  сохраняются как источник, а не действуют параллельно с новой спецификацией.
- При конфликте требований и кода обозначается расхождение. Код не отменяет требования
  автоматически; хронологически последняя заметка также не доказывает решение.

## Структура и обновление

Начинайте с назначения и точки входа, добавляйте статус при необходимости.
Используйте содержательные заголовки, Markdown и относительные ссылки. Путь именуется
по предмету; отдельный файл нужен при самостоятельном сценарии чтения.

Спецификация описывает пользователя, предусловия, нормальный путь, ошибки, ограничения
и наблюдаемые критерии. Для списков указываются границы и продолжение.
Проверяйте возможность выполнить инструкцию, увидеть результат и исправить ошибку.

Канонические документы обновляются при смысловом изменении публичного поведения,
контракта, устройства или процесса. Нет требования редактировать их после каждого
действия, исследования или вызова агента. Если содержание верно, формальное изменение
не нужно. Для общей страницы назначается один писатель; последствия согласуются с владельцами.

## Исторические материалы

Архивные спецификации не подтверждают текущее состояние и не задают маршрут нового поручения.
Устойчивые технические решения описаны в `engineering/decisions`.
Действующие требования и существенные ограничения принадлежат каноническим страницам.

Не переписывайте прежние даты и результаты под новую модель разработки. Единственный
обязательный результат исполнителя — ответ оркестратору с фактическими проверками
и непроверенным. Долговременные документы обновляйте по смысловым изменениям,
не создавая новую хронологию действий под видом README, отчёта или индекса работ.

## Проверка

`pnpm run docs:check` проверяет локальные ссылки и якоря. Адресное форматирование
изменённых документов и `git diff --check` дополняют её. Проверьте человеческий маршрут:
назначение → возможность → приложение → инструкция/справочник → реализация.
История доступна по необходимости. Автоматическая проверка не доказывает истинность
описания, полноту требований или выполнимость инструкции.
