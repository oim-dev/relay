# Выпуск пакетов Relay

Инструкция для сопровождающего: подготовить согласованный комплект CLI, Server и MCP,
проверить его из чистого checkout и опубликовать через GitHub Release либо разрешённый ручной fallback.
Подготовка, Git push и npm publish — разные действия; успешный push не публикует npm-пакеты.

[Документация](../README.md) → Разработка → Релизы

Репозиторий: <https://github.com/oim-dev/relay>.
SSH для клонирования: `git@github.com:oim-dev/relay.git`.

## Выбор способа выпуска

Все три пакета `@oim-dev/relay-cli`, `@oim-dev/relay-server` и `@oim-dev/relay-mcp`
уже опубликованы с версией `0.6.1`. Ближайший план — общий **`0.6.2`** для проверки
нового процесса после merge PR в `main`: стабильная версия, выключенный prerelease flag,
канал `latest`. Это план будущей отдельной публикации, а не факт выпуска или успешного OIDC.
Не используйте существующий выпуск для проверки автоматизации.

Основной путь — [публикация через CI](#публикация-через-ci) при публикации GitHub Release,
после настройки Trusted Publisher для каждого пакета. [Локальная публикация](#локальная-публикация)
остаётся отдельным fallback с локальной npm-авторизацией и явным разрешением на выпуск.
Не запускайте оба пути одновременно. Создание и отправка тега, публикация GitHub Release
и ручная npm-публикация требуют согласованного разрешения, а не следуют из подготовки версии.

## PR, целевая ветка и релизный коммит

Целевая доверенная ветка выпуска — `main`. Она создана на базовом `v0.6.1`
(`ec4a2cc940640739a9415f774a1a811378fb61d6`); это не означает, что новый CI уже доставлен.
Default branch пока остаётся `refactor/application-rebuild`, и эта ветка не удаляется.
При создании PR явно выбирайте base `main`, не полагайтесь на default branch.

Общий порядок для следующих выпусков:

1. В рабочей ветке подготовьте одну согласованную версию CLI, Server и MCP,
   CHANGELOG и документацию; для предстоящего выпуска это `0.6.2`.
2. Отправьте разрешённый PR в `main`, дождитесь успешных CI-проверок сборки и установки
   пакетов и review. Зелёный PR не публикует пакет и не разрешает merge сам по себе.
3. После отдельного разрешения выполните merge в `main`; выберите релизный коммит
   из этой ветки. Проверьте именно его содержимое, workflow и комплект архивов:
   артефакты прежнего PR SHA не заменяют проверку выбранного релизного SHA.
4. После разрешения создайте и отправьте новый `v<version>` на выбранный коммит,
   не перемещая старые теги. Для ближайшего плана это будущий `v0.6.2`.
5. Отдельно разрешённый **Publish release** для этого тега запускает OIDC-публикацию
   проверенного комплекта. Создание PR, merge, tag push и draft Release её не заменяют.

Эта инструкция не выполняет merge или выпуск. Перед каждым следующим релизом снова
согласуйте версию, проверьте registry и готовность инфраструктуры.

### Окружение и чистый checkout

Для сборки используйте Node.js 24 и pnpm 11.18.0 из корневого `packageManager`;
минимум репозитория — Node.js 22.13. Это требования разработки, а не только Node.js 22+
из устанавливаемых пакетов. В CI упаковка выполняется с npm 11.16.0; для ручной упаковки
используйте ту же версию. Нужны Git, доступ к registry для установки зависимостей,
место для сборки и возможность запускать локальные HTTP-процессы на свободных портах.
[Подготовка окружения](../DEVELOPMENT.md#окружение).

Готовьте версию в рабочей ветке, а окончательные проверки и архивы — в отдельном чистом
checkout выбранного релизного коммита, без прежних `dist`, `.artifacts` и локальных изменений.
Если выбранный коммит ещё не отправлен, такой checkout можно получить из локального
репозитория, а не из прежнего состояния ветки в GitHub. Не очищайте чужую рабочую копию
через `reset` или `clean`; используйте отдельный каталог.

Из корня выбранного checkout:

```bash
git status --short
git rev-parse HEAD
node --version
pnpm --version
npm --version
pnpm install --frozen-lockfile
```

Ожидается пустой `git status --short`, согласованный SHA коммита и указанные версии
инструментов. Установка не должна менять lockfile. Если она завершается с ошибкой,
устраните причину у владельца зависимостей, не обходите `--frozen-lockfile`.
Команды ниже выполняются из этого же корня; аргументы `pnpm run` передаются без
дополнительного `--`.

### Перенос ветки без старых тегов

Push выполняется после QA, разрешения на отправку выбранной ветки и проверки отправляемой
истории. Отправляйте рабочую ветку для PR с base `main`; прямой push изменений
в `main` не заменяет PR, CI gate и согласованный merge.
Перед отправкой проверьте рабочую копию, именованную ветку, выбранный коммит и адрес назначения:

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git remote get-url --push --all origin
```

Рабочая копия должна быть чистой; detached HEAD для этого сценария не подходит.
Все адреса push должны вести только в `oim-dev/relay`: `git@github.com:oim-dev/relay.git`
или `https://github.com/oim-dev/relay.git`, без токенов в URL. Просмотрите весь отправляемый
набор коммитов, а не только последний: секреты, локальные конфиги и случайные архивы
не должны попасть в Git. GitHub-доступ и npm-авторизация проверяются независимо.

Перед отправкой убедитесь, что push/PR запускают только проверки, а npm-публикация
доступна только по согласованному [релизному событию](#публикация-через-ci).
Когда потребуется отправить выбранную именованную ветку, отправляйте только её,
без автоматического добавления тегов:

```bash
git push --no-follow-tags origin HEAD
```

После разрешённого push сравните SHA отправленной ветки в GitHub с выбранным локальным
коммитом и проверьте результат CI. Отказ доступа или non-fast-forward — повод остановиться
и согласовать исправление; не обходите его force push. Отправка ветки не отправляет
подготовленные `.tgz` и не заменяет [локальную публикацию](#локальная-публикация).

Не используйте `--tags`, `--follow-tags` или `--mirror` для переноса старых тегов.
Прежний локальный `v0.6.0` указывает на `d3d111d`: там старые имена пакетов и активный
publish-workflow. Изменение workflow в новой ветке **не защищает от отправки старого
тега**: запуск по тегу использует workflow его коммита. Не отправляйте и не ретегируйте
`v0.6.0` для активации нового процесса.

## Единая версия и совместимость

Начиная с `0.6.0`, каждый релиз выпускает **все три npm-пакета с одной версией**,
даже если изменения затронули только один компонент:

| Пакет                   | Манифест                   | Архив                         |
| ----------------------- | -------------------------- | ----------------------------- |
| `@oim-dev/relay-cli`    | `apps/cli/package.json`    | `apps/cli/.artifacts/npm/`    |
| `@oim-dev/relay-server` | `apps/server/package.json` | `apps/server/.artifacts/npm/` |
| `@oim-dev/relay-mcp`    | `apps/mcp/package.json`    | `apps/mcp/.artifacts/npm/`    |

**Совпадение полной версии, включая суффикс RC, обозначает проверенный совместимый комплект.**
CLI, Server и MCP одной версии должны пройти совместную проверку перед публикацией.
Совместимость смешанных версий не гарантируется. Устанавливайте и обновляйте используемые
пакеты вместе, закрепляя одинаковую точную версию вместо независимых диапазонов.

Версия CLI служит опорной при проверке; версии Server и MCP обязаны совпадать с ней.
Команда обновления меняет все три манифеста. Корень `@oim-dev/relay-monorepo` и workspaces
`@relay/*` приватны, сохраняют `0.0.0` и отдельно не публикуются. Код используемых runtime-пакетов
собирается внутрь дистрибутивов. Серверный архив включает Web.

Имя архива — `oim-dev-relay-<component>-<version>.tgz`, где `component` — `cli`, `server`
или `mcp`. Команды `relay-cli`, `relay-server` и `relay-mcp` не переименовываются.
В npm-манифестах всех трёх пакетов `repository.url` — `git+https://github.com/oim-dev/relay.git`.
Только у CLI дополнительно указаны `homepage` — `https://github.com/oim-dev/relay#readme`
и `bugs.url` — `https://github.com/oim-dev/relay/issues`; у Server и MCP этих двух полей нет.
Эти метаданные сами по себе не создают npm provenance.

Единый Git-тег — `v<version>`, например `v0.6.1` или `v0.7.0-rc.1`.
Прежние теги `cli-v…`, `server-v…` и `mcp-v…` остаются историей независимых выпусков.
Отправка тега не является событием npm-публикации нового процесса и не создаёт GitHub Release.
Публикация запускается только при **Publish release**, как описано ниже.

## Подготовка версии

Согласуйте следующую свободную версию, большую текущей, и подставьте её вместо
`<version>` во все команды ниже (без угловых скобок). Это обозначение, а не выбранная
новая версия. Совпадение номера во всех манифестах ещё не доказывает готовность выпуска.

До изменения манифестов проверьте версии и каналы **всех трёх** пакетов в целевом registry:

```bash
npm view @oim-dev/relay-cli versions dist-tags --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-server versions dist-tags --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-mcp versions dist-tags --json --registry https://registry.npmjs.org
```

Для ещё не созданного пакета ожидаем `E404`; это не подтверждение права его создать.
Ошибки авторизации, сети и registry нельзя считать отсутствием версии. Для нового выпуска
выбранная версия должна быть свободна во всём комплекте; исключение —
[повтор той же неполной публикации](#повтор-после-неполной-публикации).
Отдельно убедитесь, что новый Git-тег свободен локально и в целевом репозитории.
Проверка доступности номера и строки тега не создаёт тег и не разрешает публикацию.
Проверьте, что выбранный канал можно перевести на эту версию: обычная публикация
обновит `latest`, предварительная — `next`.

Если манифесты ещё не обновлены до выбранной версии:

```bash
pnpm run release:version <version>
```

Команда проверяет SemVer без build metadata (`+…`) и одновременно обновляет три
npm-манифеста, сохраняя остальные поля. Она не выбирает свободную версию и не проверяет
увеличение номера.
Git-коммит и тег создаются отдельно. В `pnpm-lock.yaml` workspace-зависимости заданы
через `link:`, поэтому смена собственных версий пакетов не изменяет lockfile.

Добавьте раздел с выбранной версией в каждый `apps/{cli,server,mcp}/CHANGELOG.md`.
Если компонент не менялся, укажите совместный выпуск с остальными пакетами.
Описание должно относиться к текущему содержимому; не выдавайте прежние записи
о `@gromlab/*` и старом CI за проверку нового выпуска.

```bash
pnpm run release:check v<version>
pnpm run release:notes v<version>
pnpm run agents:check
pnpm run skills:check
pnpm run build
pnpm run check
pnpm run package:check
```

`release:check` отклоняет разные версии, несовпадение строки `v<version>` с манифестами,
неполный состав выпуска и публичный workspace, который не включён в процесс публикации.
Он **не проверяет**, существует ли Git-тег и на какой коммит он указывает. Проверка входит
в `build`, `check` и `package:check` и выполняется до публикации. `release:notes` читает
CHANGELOG всех трёх приложений и выводит описание; формирование текста не означает выпуск.

Как в полном CI на Node.js 24, `agents:check` и `skills:check` выполняются **до сборки**, чтобы обнаружить drift
сохранённых результатов генераторов, а не скрыть его пересборкой. При расхождении остановитесь
и передайте исправление владельцу генерации. `check` включает `release:test`, форматирование,
проверки документации и генераторов, lint, типизацию и тесты workspaces. Успех только
`release:check` или `build` не заменяет весь набор проверок.

`scripts/package.mjs` упаковывает скомпилированный JavaScript и манифест с внешними
production-зависимостями; они устанавливаются из registry, а не копируются как `node_modules`.
Все три архива содержат `package.json`, `dist/`, `README.md` и `CHANGELOG.md`.
README и CHANGELOG берутся из соответствующего приложения. Дополнительно Server включает
готовый Web в `dist/web`, а CLI — `docs/CLI.md`, `docs/EXTENDING.md`, `docs/RELEASING.md`
и `docs/TERMINAL.md` из `apps/cli/docs`. Корневая библиотека `docs` не копируется:
страницы CLI в архиве направляют читателя к каноническим документам в GitHub.

Состав документации задаёт `files` манифеста каждого приложения. Проверяйте перечень файлов
и доступность ссылок в `.tgz`, а не только запись в `package.json` или содержимое staging.
Внешние ссылки README и CLI docs для будущего комплекта ведут на существующую ветку
`main` в GitHub и не требуют соседнего checkout. Это изменяемая документация ветки,
которая может отличаться от установленной версии, а не ссылки на конкретный релизный тег.
Новые разделы процесса CI появятся в `main` только после merge соответствующего PR;
наличие базовой страницы в `main` не подтверждает наличие нового содержания.
`scripts/smoke-relay.mjs` независимо устанавливает все три архива и проверяет:

- версии установленных пакетов и исполняемых команд;
- состав и байты установленной документации относительно исходных файлов приложений;
- CLI напрямую и через local-сервер;
- серверную статику, Swagger и API;
- workspace с двумя базами и одинаковыми номерами задач;
- MCP, выбор проекта и отказ после остановки общего сервера.

Для отдельной диагностики сборки существуют `package:check:cli`, `package:check:server`
и `package:check:mcp`. Полную установочную проверку выполняет `package:check`.

Для повторной установочной проверки **готовых** архивов используйте `pnpm run package:smoke`
из корня checkout того же коммита. Это прямой запуск `node scripts/smoke-relay.mjs`:
он устанавливает архивы из `apps/{cli,server,mcp}/.artifacts/npm/` в независимые окружения,
но не собирает и не перепаковывает приложения и не требует установки зависимостей
монорепозитория. Архивы должны уже существовать; smoke не заменяет quality gates.

После QA зафиксируйте подготовленный выпуск разрешённым коммитом, затем повторите
окончательные проверки в его чистом checkout и снова проверьте `git status --short`.
Архивы должны быть собраны и проверены из этого же содержимого, без последующих изменений.
При любом изменении исходников до публикации комплект нужно собрать и проверить заново.

**Следующий этап — только после отдельного разрешения на тег и npm publish.**
Создайте новый тег для выбранного релизного коммита, не перемещая старые. Аргумент
`v<version>` в проверках выше — строка, а не требование заранее создать Git-тег.
После разрешённого создания тега сравните:

```bash
git rev-parse HEAD
git rev-parse 'v<version>^{commit}'
```

Оба значения должны совпадать с выбранным коммитом выпуска. Успешный `release:check`
не заменяет эту проверку связи тега, коммита и исходников.

## Публикация через CI

Контракт `.github/workflows/release.yml` — `release.types: [published]`: публикация
GitHub Release запускает проверки комплекта и публикацию проверенных `.tgz` в npm.
Создание draft, отправка тега и push ветки не являются триггерами npm-публикации.
Push/PR выполняют проверки сборки и установки пакетов без credentials, OIDC и publish.
Общие проверки используют reusable workflow `ci.yml`, но publishing job находится
непосредственно в `release.yml` и использует `environment: npm`.

Для издателя нужны GitHub-hosted runner, Node.js 24, npm 11.16.0 и права
`contents: read`, `id-token: write`; последнее право выдаётся **только publishing job**.
Цель — `https://registry.npmjs.org`, доступ `public`. Stable SemVer требует выключенного
GitHub prerelease flag и получает `latest`; SemVer с предварительным суффиксом требует
включённого flag и получает `next`. Несогласованность должна останавливать выпуск,
а не молча выбирать канал. GitHub Release создаёт сопровождающий, не publish job.

### Проверки и передача одного комплекта

`ci.yml` запускается на push веток, PR и `workflow_call`. Его последовательность:

1. `check` на Node.js 24 проверяет сохранённые agents/skills до build, затем выполняет
   полный `check`. На Node.js 22 выполняются build, `release:test` и тесты runtime
   без тестов tooling-пакетов `@relay/dev-agents` и `@relay/relay-skill`.
2. `package` после обеих проверок на Node.js 24 выполняет `package:check` и сохраняет
   один артефакт `npm-packages`: **ровно три `.tgz` и `manifest.json`**. Ведомость
   содержит schema, SHA коммита, тег, имена, версии, имена файлов и SHA-512 integrity.
3. `installed-node22` скачивает этот же комплект по `artifact_id`, проверяет и
   восстанавливает его, затем запускает `pnpm run package:smoke` на Node.js 22.
   Здесь нет build, repack или установки зависимостей монорепозитория.

В `release.yml` сначала `metadata` проверяет событие, версии, описания выпуска,
соответствие checkout коммиту тега и согласованность prerelease flag с SemVer.
Затем `ci` вызывает весь reusable CI; `publish` ждёт его успешного завершения,
включая `installed-node22`, и получает именно его `artifact_id`.
Пустой или некорректный ID останавливает загрузку; `download-artifact` версии 8.0.1
использует `digest-mismatch: error`, а не продолжает при несовпадении digest.

Publisher не устанавливает зависимости монорепозитория, не собирает и не упаковывает
пакеты заново. Он повторно проверяет событие и комплект. В CI переменная
`RELAY_RELEASE_BUNDLE` указывает на скачанный каталог `.artifacts/npm-packages`:
при `GITHUB_ACTIONS=true` команда `release:publish` требует её и перед записью
проверяет ведомость, внутренние манифесты, repository, commit/tag и SHA-512,
затем восстанавливает те же байты в пути приложений. Локально эта переменная
не переключает источник публикации: ручной fallback читает архивы приложений.

Для диагностики сохранённого комплекта из checkout того же коммита доступны команды
ниже. Замените `<bundle-dir>` путём к каталогу; `RELEASE_TAG`, если задан, должен
совпадать с тегом ведомости (иначе тег выводится из общей версии манифестов).

```bash
node scripts/release/bundle.mjs verify "<bundle-dir>"
node scripts/release/bundle.mjs restore "<bundle-dir>"
pnpm run package:smoke
```

`verify` только проверяет комплект; `restore` сначала проверяет весь комплект, затем
копирует архивы в `apps/{cli,server,mcp}/.artifacts/npm/`, заменяя одноимённые файлы.
Используйте отдельный checkout, не каталог чужой работы. Команда
`node scripts/release/bundle.mjs create "<bundle-dir>"` создаёт ведомость и копирует
готовые архивы в пустой каталог; она **не выполняет QA** и не нужна для retry
уже сохранённого комплекта. Артефакт CI хранится 14 дней: для отложенного повтора
сохраните исходный комплект вместе с ведомостью до истечения этого срока.

### Настройка npm Trusted Publisher

В Settings → Trusted publishing **каждого** из трёх npm-пакетов добавьте publisher:

| Поле                 | Значение                                             |
| -------------------- | ---------------------------------------------------- |
| Publisher            | `GitHub Actions`                                     |
| Label                | `relay-release` (необязательная метка)               |
| Organization or user | `oim-dev`                                            |
| Repository           | `relay`                                              |
| Workflow filename    | `release.yml` — только имя, без `.github/workflows/` |
| Environment name     | `npm`                                                |
| Allow npm publish    | **Включено** для прямой публикации                   |

Это инструкция для владельца доступа, а не свидетельство, что настройки уже применены.
Значения доверия должны совпадать точно, включая регистр. npm не проверяет корректность
конфигурации при сохранении: ошибка может обнаружиться только при публикации.
`npm stage publish` всегда разрешён новой конфигурацией, но означает загрузку в staging
с последующим ручным approve и 2FA, а не прямой выпуск. Если оставить `Allow npm publish`
выключенным, описанный прямой publish не разрешён; менять процесс на staging не нужно.

В манифесте **каждого готового архива** проверьте `repository.url`:
`git+https://github.com/oim-dev/relay.git`. npm требует соответствия GitHub-репозиторию.
Для public repository и public package OIDC автоматически добавляет provenance;
отдельный `--provenance` не обязателен по контракту npm; текущая publish-обёртка
дополнительно передаёт его в GitHub Actions. Отключать provenance не следует.
Private repository не исключает OIDC, но не поддерживает такую provenance;
self-hosted runner для npm Trusted Publishing не поддерживается.

Не добавляйте `NPM_TOKEN`, `NODE_AUTH_TOKEN`, `npm login` или auth-токен в `.npmrc`
publishing job. npm сам обнаруживает OIDC; оставшаяся token-auth создаёт ненужный
fallback на долгоживущие credentials. Конфигурация registry без секрета допустима.
Не снижайте 2FA: режим npm **Require two-factor authentication and disallow tokens**
совместим с Trusted Publishing. Изменения политики доступа и отзыв прежних токенов
согласуются отдельно, без чтения или вывода их значений.

### Защита GitHub environment

Заранее создайте environment **`npm`** в `oim-dev/relay`. В **Deployment branches and tags**
выберите **Selected branches and tags**, добавьте правило типа **Tag** с шаблоном `v*`
и не добавляйте правила для branches. Шаблон не проверяет SemVer и доверенность коммита:
дополнительно защищайте создание и перемещение release-тегов через rulesets и проверяйте
происхождение релизного коммита. Само имя environment не создаёт этих ограничений.

По возможностям плана и составу команды настройте required reviewers и запрет admin bypass.
При наличии независимого сопровождающего включите prevent self-review; не создавайте
невыполнимое требование независимого approval для единственного владельца. Ограничение
тегов и 2FA сохраняются независимо от выбранной схемы review.

### Активация и проверка автоматизации

1. Доставьте новый workflow через PR и согласованный merge в `main` и убедитесь, что выбранный релизный
   коммит и его новый тег содержат именно этот workflow. Изменение только ветки не
   обновляет workflow старого тега.
2. Настройте три npm Trusted Publisher и environment `npm`, подготовьте новую
   согласованную версию и пройдите проверки из этой инструкции.
3. После разрешения опубликуйте GitHub Release для нового `v<version>` через
   **Publish release**, согласовав prerelease flag с SemVer. Draft можно подготовить
   заранее, но он не запускает публикацию.
4. Проверьте Actions и [результат в npm](#проверка-результата-в-npm): весь комплект,
   integrity, канал, provenance и запуск опубликованных команд.

Не отправляйте старый `v0.6.0` и не публикуйте GitHub Release для уже выпущенного
`0.6.1` ради теста. Автоматизация предназначена для будущих разрешённых выпусков.
Статические проверки, mock-тесты и локальный smoke **не доказывают OIDC-публикацию**.
`npm whoami` также не проверяет OIDC: обмен credentials происходит при publish.
Live-проверка возможна только при будущей разрешённой публикации после настройки UI;
зелёный CI и наличие артефактов ещё не означают, что версия доступна в registry.
Сообщение владельца о настроенных трёх publishers и environment `npm` без secrets/variables
подтверждает подготовку по его словам, но не выполнение workflow или успешный OIDC-обмен.

Официальные контракты: [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/)
(минимум npm 11.5.1 и Node.js 22.14.0), [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish)
(включая локальные `.tgz`), [staged publishing](https://docs.npmjs.com/staged-publishing/),
[GitHub release event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release)
и [защита environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).
Документированная поддержка tarball не заменяет live-проверку конкретной цепочки
pnpm → npm → `.tgz` → OIDC.

## Локальная публикация

### Авторизация и разрешение выпуска

Публикуйте только после отдельного разрешения, успешных проверок всего комплекта
и сверки его версии, Git-коммита и тега. Проверьте существующую локальную npm-авторизацию:

```bash
npm whoami --registry https://registry.npmjs.org
```

Команда показывает аккаунт, но **не подтверждает права публикации**. В настройках npm
проверьте его право создавать публичные пакеты в `@oim-dev`, а для существующих пакетов —
права записи на каждый из трёх пакетов. Если используется токен, его разрешения,
срок действия и ограничения должны допускать эту запись с учётом политики 2FA организации.
GitHub-права и само наличие `publishConfig.access: public` не дают прав в npm.

Если авторизация уже работает, повторный `npm login` не требуется. При ошибке или
неясных правах остановитесь и согласуйте доступ с владельцем npm-организации до публикации.
Не читайте и не выводите токен, не сохраняйте учётные данные в репозитории, проектном
`.npmrc`, командных примерах или CI. Не отключайте требования 2FA ради прохождения выпуска.

### Публикация проверенных архивов

Запускайте команду из корня того же checkout с сохранёнными проверенными `.tgz`
только после отдельного разрешения на ручную публикацию и исключения параллельного
CI publish. Подставьте согласованную новую версию:

```bash
pnpm run release:publish v<version>
```

Общий вид команды — `pnpm run release:publish v<version>`. Она публикует **три уже готовых
архива** из `apps/{cli,server,mcp}/.artifacts/npm/` последовательно: CLI, Server, MCP.
Сборку, упаковку, Git-тег и GitHub Release команда не создаёт. Перед первой записью
она читает все три архива, проверяет их внутренние манифесты и сверяет существующие
версии и каналы в registry. Только HTTP 404 означает отсутствие версии; сетевые ошибки,
ошибки registry и попытка откатить канал с более новой версии останавливают выпуск.
Команда не повторяет quality/package gates: используйте именно результат успешного
`package:check` этого коммита. После записи она сверяет integrity и канал всего комплекта.
Не запускайте `npm publish` из каталогов приложений или приватных workspaces.

Цель фиксирована: `https://registry.npmjs.org`, доступ `public` для всех трёх scoped-пакетов.
Команда явно передаёт эти значения npm. Обычные версии получают npm dist-tag `latest`,
предварительные — `next`; произвольный канал через аргументы команды не задаётся.
Git-тег `v<version>` и npm dist-tag — разные обозначения.
Без явного аргумента используется `RELEASE_TAG`, а при его отсутствии — `v<version>`
из манифестов. Для ручного выпуска указывайте тег явно. Успешный результат — все три
пакета выбранной версии доступны в npm и соответствуют проверенным архивам.

Запускайте публикацию через `pnpm run`: npm-обёртке нужен `npm_execpath`, который задаёт
pnpm. Проверка метаданных и формирование описания также работают через `node` без установки зависимостей.

### Проверка результата в npm

После завершения запросите именно выбранную версию каждого пакета:

```bash
npm view @oim-dev/relay-cli@<version> version dist.integrity --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-server@<version> version dist.integrity --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-mcp@<version> version dist.integrity --json --registry https://registry.npmjs.org
```

Все три ответа должны содержать одну выбранную версию. Значения `dist.integrity` должны
соответствовать SHA-512 исходных `.tgz` в формате `sha512-<base64>`. Повторите запросы
`versions dist-tags` из [подготовки версии](#подготовка-версии): `latest` либо `next`
должен указывать на выбранную версию у каждого пакета. Затем проверьте запуск трёх
опубликованных команд с точной версией вне монорепозитория; их команды `npx …@<version> --help`
выводит `release:notes`. Это отдельная проверка registry, не результат локального smoke-теста.

Если версия отсутствует, integrity или канал не совпадают, выпуск пока не подтверждён.
Не объявляйте весь комплект доступным по одному успешному пакету или зелёному CI.

### Повтор после неполной публикации

Публикация в npm не атомарна: при сетевом сбое часть пакетов может уже появиться в registry.
Сохраните те же `.tgz` и повторите ту же `pnpm run release:publish v<version>` без пересборки.
Для CI сохраните также исходный артефакт и `manifest.json`: повтор publisher должен
использовать тот же `artifact_id` и те же байты. Не перезапускайте весь pipeline
с новой упаковкой ради повтора частичной публикации. Если точный артефакт больше
недоступен, остановитесь и согласуйте восстановление из сохранённого комплекта;
не подменяйте его вновь собранными архивами. Ручное восстановление выполняйте через
`bundle.mjs verify`/`restore` в checkout исходного коммита, затем — только разрешённый
ручной fallback с теми же байтами. Уже опубликованный `0.6.1` нельзя использовать
для проверки повторов новыми архивами.
Уже опубликованная версия пропускается только при совпадении SHA-512 integrity. Другой
архив с тем же номером или ошибка доступа к registry останавливают выпуск до первой
новой публикации. Для исправленного содержимого нужна новая версия, а не перезапись прежней.
Совпавшие пакеты пропускаются без повторной записи только при совпадении канала;
dist-tags команда автоматически не исправляет. Несовпадение канала требует отдельного согласованного исправления,
а затем повторной проверки всего комплекта. Ошибка в ходе самой записи может оставить
частичный выпуск, даже если предварительное чтение registry было успешным.
Более новая версия в целевом dist-tag блокирует старый выпуск даже при совпадении
его архива. После публикации выполняется повторная сверка integrity и ожидаемого
канала всех трёх пакетов; ошибка этого чтения не доказывает, что запись не состоялась.
CI сериализует publishers группой `relay-npm-publish` без отмены активного job,
но не сериализует локальные процессы. Не запускайте ручной fallback параллельно с CI
или другим ручным выпуском.
