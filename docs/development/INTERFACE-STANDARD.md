# Единые правила интерфейсов и содержания Relay

## Статус и область действия

Это обязательный стандарт для агентов и разработчиков Relay. Он действует в Core,
CLI, MCP, REST, SDK, документации и при проектировании интерфейсов. Знания владельца
содержатся в его промпте; разделы спецификаций читаются адресно по применимости.
Человек и агент работают с одной предметной моделью.
Удобство чтения, понимание действия и восстановление после ошибки — часть результата.

Для сценариев с предметными отношениями применяется
[стандарт линков, связей и контекста](LINKS-AND-CONTEXT.md).
Web, CLI и MCP вызывают предметные действия. Бекенд выполняет продуктовую запись линков,
затем явно вызывает функции движка Core для установки, изменения или разрыва отдельно
сохраняемых связей. Контекст читает граф; продуктовые правила работают со своими данными.
Клиент не выполняет второй запрос синхронизации. Бекенд обеспечивает согласованность шагов;
универсальная запись рёбер из клиента относится к диагностике.

## Язык

Все авторские описания в проекте — на русском: README, справка, описания инструментов
и параметров, сообщения, комментарии к коду, JSDoc, описания схем, тестовых сценариев
и продуктовых материалов. Отсутствие описания публичной команды или аргумента является
нарушением этого стандарта. Технические имена, стандартные протоколы и точные внешние цитаты
сохраняются; сгенерированный код исправляется через источник или генератор.

## Контракт текста

| Назначение          | Представление и поведение                                          |
| ------------------- | ------------------------------------------------------------------ |
| Заголовок, название | Одна строка, без переносов и разметки                              |
| Краткое описание    | Обычный многострочный текст; переносы сохраняются                  |
| Полное описание     | Markdown: разделы, абзацы, списки, ссылки, код и таблицы по смыслу |
| Инструкция          | Markdown с целью, шагами, ограничениями и проверяемым результатом  |
| Документация        | Markdown со структурой, соответствующей виду документа             |

Это относится к задачам, фичам, сценариям, приложениям, их реализациям, правилам,
решениям, пользовательским инструкциям и будущим сущностям. Название поля `text`
не освобождает проектировщика от определения его семантики.

Интерфейс обязан сохранять и показывать тип содержания. Markdown нельзя заменять
однострочным полем, выводить экранированным JSON или молча обрезать. Краткое описание
не заменяет полное. Полное описание не должно быть пересказом заголовка.

## Хранение Markdown

В JSON-базе каждый Markdown-текст хранится массивом строк, включая пустые строки,
отступы, завершающий перевод строки и значимые пробелы:

```json
{
  "description": ["## Цель", "", "Описание результата.", "", "- Проверяемое условие", ""]
}
```

На HTTP/MCP-границе и в CLI допустим ввод одной строки Markdown с переводами строк.
Кодек хранения переводит её в массив и обратно без потерь. Агенту не нужно создавать
промежуточный MD-файл для передачи описания. Самостоятельные ТЗ и документация
репозитория остаются `.md`-файлами; внутри базы их содержание хранится в JSON.

Для изменения формата нужны версия дисковой схемы, совместимое чтение, явная миграция,
проверка прерванного переноса и неизменности ID, ссылок, ревизий и пользовательских комментариев.
Автоматическая история, квитанции и результаты команд не переносятся и не накапливаются.
Техническая миграция не переписывает требования и не подтверждает реализации.

## CLI: интерфейс человека по умолчанию

- Каждая публичная команда проектируется с собственным представлением результата.
  Универсальный обход вложенного объекта допустим для диагностики, не как готовый UI.
- Заголовок сообщает результат, метаданные отделены от содержания. Ошибка объясняет,
  что произошло и какой следующий шаг доступен; введённые данные не теряются.
- Markdown отображается терминальным рендерером. Таблицы строятся библиотекой,
  учитывающей ширину Unicode и ANSI; не склейкой столбцов через пробелы.
- На узком терминале допустим переход к карточкам вместо нечитаемой таблицы.
- Цвет не является единственным носителем смысла. Соблюдаются `--color`, `NO_COLOR`,
  TTY и работа в pipe. Пользовательский текст не исполняет управляющие последовательности.
- Большие списки имеют размер страницы, общее число/признак продолжения и точную команду
  следующей страницы с сохранением фильтров. Контекст можно сузить до сущности.
- Если полный ответ превышает бюджет, вернуть понятную ошибку и способ сузить запрос;
  не выдавать неполный результат за полный и не выгружать огромный граф без предупреждения.
- `--format json` — стабильный структурированный контракт без ANSI, баннеров и пояснений
  вне JSON. Агентам рекомендуется этот режим; человеку — форматированный вывод.

Для каждой команды справка на русском содержит назначение, аргументы и параметры,
пример, ограничения, требования к серверу/ревизии и поведение повтора для записи.

## MCP: наблюдаемые действия

- Имя и описание инструмента объясняют предметное действие, а не внутренний транспорт.
- У каждого публичного параметра есть русское описание, включая поля вложенных объектов.
- Проект, действие, название и целевые ID доступны на верхнем уровне там, где это возможно.
  Не прятать всю пользовательскую операцию в универсальный `command` или `payload`.
- Предметные инструменты используют общую бизнес-логику; отдельные названия не оправдывают
  дублирование проверок, блокировок и правил изменения данных.
- Ответ записи даёт квитанцию: действие, сущность, ID, ревизия и requestId корреляции.
  Это ответ клиенту, не постоянная запись. requestId не гарантирует дедупликацию;
  после потери ответа сначала читается текущее состояние.
  Человекочитаемое сообщение и структурированный ответ описывают один результат.
- Списки ограничены и сообщают продолжение. Большой контекст читается адресно.
- Строку вызова рисует MCP-клиент: фактическую видимость проверять в целевом клиенте,
  не обещать её только на основании серверной схемы.

## Качество продуктового содержания

Следуй [стандарту продуктовых материалов](../reference/PRODUCT-CONTENT.md).
Markdown — способ выразить структуру, не набор декоративных заголовков.
Не выдумывай решения для заполнения шаблона. Неизвестное фиксируй вопросом.
Структурная проверка помогает найти слабое описание, но не доказывает полноту требований.

## Протокол изменения

1. Сверить применимые требования интерфейса с конкретным контрактом и существующими механизмами.
2. Определить пользователя, цель, владельца, текстовые типы и публичные контракты.
3. Зафиксировать нормальный сценарий, пустое состояние, ошибку, большой ответ и повтор.
4. Спроектировать совместимость, пагинацию и миграцию, если они затронуты.
5. Реализовать интерфейс и документацию совместно, не откладывать UI/UX на потом.
6. Проверить реальные человеческие результаты отдельно от JSON и машинных схем.

Изменение не готово, если оно только сохраняет данные, но их невозможно удобно прочитать,
проверить и исправить штатными инструментами.
