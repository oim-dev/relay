# Исходный аудит роутинга Relay Web

[Техническая библиотека](README.md) → Web → Маршруты

**Исторический срез: 20 сентября 2026 года, HEAD `c1c353f`, до исправлений.**
Действующая [карта маршрутов](../product/applications/web/ROUTING.md) находится в библиотеке Web.
Основание среза — дерево роутера, экраны, построение ссылок и адресные браузерные проверки.
Предложения ниже ещё не являются принятым изменением продуктового контракта.

## Обозначения и вход

- `P` — `/projects/:project`, где канонический `:project` — slug проекта.
- `R` — `P/product`.
- Фича, сценарий, приложение и реализация адресуются ключом или ID; обычный URL использует ключ.
- Документ в текущих экранах открывается по ID. Задача канонизируется к ID и текущему slug доски.
- Имена параметров `featureId`, `featureRef`, `entityId`, `entityRef` в коде различаются,
  хотя нередко обозначают одну роль: входную ссылку, которую ещё требуется разрешить.

Главный источник: [app-router.tsx](../../apps/web/src/app/router/app-router.tsx).
Вход и выбор проекта: [RelayScreen](../../apps/web/src/compositions/screens/relay/relay.screen.tsx).

| Адрес                                    | Назначение и фактическое поведение                                                                             |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `/`                                      | В workspace — выбор проекта; в local — переход в единственный проект                                           |
| `P` и `P/`                               | Обзор проекта, сейчас «В разработке»                                                                           |
| `/projects/:id/…` или `/projects/:key/…` | Переход на slug того же проекта; хвост, query, hash и history state сохраняются                                |
| `/projects/:unknown/…`                   | Состояние «Проект недоступен»                                                                                  |
| URL вне `/projects/…`                    | В workspace — выбор проекта; в local — попытка добавить префикс проекта к пути; это не глобальная страница 404 |
| `P/*` без подходящего маршрута           | «Страница не найдена» внутри каркаса проекта                                                                   |

Переключатель проекта ведёт в `P/`, а не в аналогичный раздел другого проекта.
В local добавление проектного префикса сохраняет query, но не hash/history state.

## Что хранит URL

| Область            | В адресе                                | Вне адреса                                                |
| ------------------ | --------------------------------------- | --------------------------------------------------------- |
| Каталог фич        | `q`, `status`, `app`                    | Раскрытие дерева — личная настройка проекта               |
| Каталог документов | `q`, `kind`, `scope`, `sort`            | Возврат из карточки — `state.returnTo`                    |
| Состав приложения  | `feature`, `scenario` — начальный выбор | Ввод и последующий выбор редактора                        |
| Связи              | `root`                                  | Глубина, профиль обхода, offset/version и открытая форма  |
| Канбан             | `q`, `blocked=1`, `cancelled=1`         | При открытой задаче фон/фильтры читаются из history state |
| Реализация         | Идентификатор записи                    | Режим редактирования — `useState`, URL не меняется        |

## Где прерывается логическая последовательность

### 1. Приложение → реализация: выход из родительской ветки

```text
R/applications/WEB
  → R/implementations/WEB-FI-1
  → «К фиче» → R/features/FEATURE-1
```

Реализация показана как часть состава приложения, но её URL теряет приложение.
На странице реализации ни «Приложения», ни «Возможности» не выделяются в меню:
у самостоятельной ветки `implementations` нет пункта навигации или каталога.
Исходная страница с якорем записывается в `state.returnTo`, однако `ProductEntityScreen`
его не читает: возврат всегда ведёт к общей фиче. Это подтверждено браузером.

Источники: [ссылка из дерева приложения](../../apps/web/src/compositions/screens/product-application/ui/application-features/ui/application-feature/application-feature.tsx),
строки 25–32; [страница реализации](../../apps/web/src/compositions/screens/product-entity/product-entity.screen.tsx),
строки 106–145; [меню](../../apps/web/src/compositions/layouts/project/ui/project-navigation/config/navigation.ts).

Плоский адрес реализации **явно закреплён текущим контрактом Web**, поэтому сам по себе
не нарушает согласованную спецификацию. Но для последовательной навигации это главный
кандидат на пересмотр; игнорирование подготовленного возврата — отдельная нестыковка.

Предложение для обсуждения: канонический путь
`R/applications/:applicationRef/implementations/:implementationRef`, текущий короткий путь —
вход с перенаправлением. К исходной фиче/сценарию вести отдельной перекрёстной ссылкой.
Самостоятельность записи не мешает её Web-странице сохранять контекст приложения.

### 2. Реализация → редактирование: у состояния нет продолжения URL

Остальные редакторы продукта открываются через `/edit`. У реализации кнопка
«Редактировать вклад» меняет только `isEditing`; адрес остаётся прежним.
Нельзя скопировать адрес открытого редактора; reload открывает чтение, а Back
не является выходом из этого режима. Браузер подтвердил неизменность URL при нажатии.

У приложения одновременно есть `/scope` для состава и правки вкладов и отдельная
ветка `/implementations/:ref` с локальным редактором. Это два входа в редактирование
одного вклада с разной адресной моделью, а не два независимых продукта.

Источник: [ProductEntityScreen](../../apps/web/src/compositions/screens/product-entity/product-entity.screen.tsx),
строки 33, 161–167, 210–222. Предложение: последовательное `/edit` внутри выбранного
канонического адреса реализации; `/scope` оставить редактором состава приложения.

### 3. Фича → сценарий → редактор: URL вложен, ветка роутера разорвана

```text
ProjectLayout
├── product/features/:featureRef/scenarios/:entityRef → ProductEntityScreen
├── product/implementations/:entityRef                → ProductEntityScreen
└── product → ProductLayout
    ├── features/:featureId                          → ProductFeatureScreen
    └── features/:featureId/scenarios/:scenarioId/edit → ProductEditorScreen
```

Чтение сценария объявлено соседом `product`, а его редактирование — ребёнком.
Поэтому переход «просмотр → редактирование» подключает другой продуктовый каркас:
`ProductDemoProvider`, `ProductOutlet` и `ScrollRestoration` есть только в `ProductLayout`.
Синтаксическая вложенность URL не означает общей ветки и общего жизненного цикла.
Факт подтверждён деревом роутера; потеря прокрутки отдельно не воспроизводилась.

Дополнительно страница сценария отбрасывает query в ссылках «К фиче» и «Редактировать
сценарий». Фильтры `q/status/app`, пришедшие из каталога, не продолжают цепочку.
Браузером проверены фактические `href` для сценария с `?q=Поиск&status=none`.

Источники: [роутер](../../apps/web/src/app/router/app-router.tsx), строки 24–38, 82–88;
[ProductLayout](../../apps/web/src/compositions/layouts/product/product.layout.tsx), строки 15–20;
[ProductEntityScreen](../../apps/web/src/compositions/screens/product-entity/product-entity.screen.tsx), строки 125, 144.

При унификации нужен общий владелец ветки с осмысленной областью жизни. Необязательно
подключать полный снимок продукта для адресного чтения одной записи.

### 4. Редактор сценария возвращается через прежний якорь

```text
R/features/F/scenarios/S/edit
  → R/features/<ID>#scenario-<ID>
  → R/features/F/scenarios/S
```

Хотя вложенный маршрут уже существует, отмена/возврат и успешное сохранение строят
прежний адрес якоря, который `ProductOutlet` снова перенаправляет. Если редактор открыт
из встроенного описания сценария на странице фичи, возврат уводит на самостоятельную
страницу сценария, а не к месту начала. Это установлено чтением кода; запись формы
в браузере в этом аудите не выполнялась.

Источники: [ProductEditorScreen](../../apps/web/src/compositions/screens/product-editor/product-editor.screen.tsx),
строки 55–61; [DocumentForm](../../apps/web/src/compositions/screens/product-editor/ui/document-form/document-form.tsx),
строки 125–140, 158–161; ProductOutlet, строки 59–69 исходной версии
([текущее расположение](../../apps/web/src/compositions/route-boundaries/product-snapshot/ui/product-outlet/product-outlet.tsx)).

Предложение: современные переходы строят прямой вложенный URL и сохраняют адрес
начала сценария; совместимость с якорями обслуживает только входящие старые ссылки.

### 5. Общий шаблон редактора принимает несуществующие разделы

`R/:collection/:entityId/edit` обслуживает фичи и приложения, но также сопоставляет
`R/anything/x/edit` и `R/implementations/X/edit`. Проверка допустимых коллекций происходит
позже в `ProductEditorScreen`, поэтому получается «Редактор не найден», а не проектная 404.
У маршрутов чтения коллекции явные, у части редакторов — произвольный параметр.

Источники: [роутер](../../apps/web/src/app/router/app-router.tsx), строки 101–104;
[ProductEditorScreen](../../apps/web/src/compositions/screens/product-editor/product-editor.screen.tsx), строки 22–32.
Предложение: явные маршруты для двух поддержанных коллекций.

## Дополнительные подтверждённые нестыковки

### Вход `R` без слеша ломается до перехода на паспорт

`ProductOutlet` ищет `"/product/"`. Для `P/product` получает `-1`, но всё равно вычисляет
`base`, `parts` и делает `Navigate`; индексный переход на паспорт не получает управления.
В изолированном local-проекте браузер получил:

```text
/projects/project-9ymz/product
  → /projects/project-9ymz/projec/s/project-9ymz/product
  → «Страница не найдена»
```

`P/product/` открывает паспорт корректно. В workspace результат первого повреждённого
перехода определяется глобальным выбором проекта; этот режим проверен только по коду.
Источник: ProductOutlet, строки 33–35, 75–82 исходной версии
([текущее расположение](../../apps/web/src/compositions/route-boundaries/product-snapshot/ui/product-outlet/product-outlet.tsx)).

### URL открытой задачи не восстанавливает фильтры доски

При наличии `selected` экран читает query только из `backgroundData.search`, игнорируя
`location.search`. Прямой `P/boards/product/:task?q=Аудит&blocked=1` показывает пустой
поиск и выключенный фильтр. Закрытие без `canGoBack` ведёт на доску без query.
Совместимый `P/tasks/PRODUCT-1?q=Аудит#details` при канонизации теряет query и hash.
Все три результата воспроизведены браузером.

Источники: [ProjectBoardScreen](../../apps/web/src/compositions/screens/project-board/project-board.screen.tsx),
строки 43–51, 68–77, 102–107, 137–142. Обычный переход с доски сохраняет фон в history
state — это работает иначе, чем копирование адреса и вход в новой вкладке.

### Markdown-ссылка перезапускает приложение

`MarkdownLink` использует обычный `<a>` по умолчанию, а `MarkdownLinkProvider` не
подключён потребителем. Внутренний переход из описания фичи на доску загрузил новый
Document, контрольное значение `window` исчезло. Это расходится с контрактом Web
о внутренних Markdown-переходах без перезапуска SPA.

Источник: [контекст MarkdownLink](../../apps/web/src/ui/markdown-link/providers/markdown-link-provider/markdown-link-context.ts),
строки 4–7. Сохранность конкретных черновиков при таком переходе отдельно не проверялась.

### Маршрут работы остаётся без работающего назначения

`R/work/:workId` зарегистрирован, но действующий адаптер всегда возвращает `work: []`.
В отличие от явно помеченных «В разработке» планов эта страница говорит, что работа
не найдена. Браузер подтвердил этот результат для `PRODUCT-1`.
Источники: [ProductWorkScreen](../../apps/web/src/compositions/screens/product-work/product-work.screen.tsx),
строки 22–34; [адаптер](../../apps/web/src/domains/product-demo/helpers/create-product-view.ts), строка 153.

## Какие переходы сами по себе последовательность не нарушают

- `features/F → features/F/scenarios/S → …/edit` — логичная URL-иерархия; проблема выше
  относится к дереву React Router и переносу контекста, а не к форме этого адреса.
- `boards/B → boards/B/T` сохраняет родителя; модальное представление допустимо и
  согласовано. Добавление буквального сегмента `/tasks/` было бы унификацией, не исправлением бага.
- Короткие `scenarios/:ref` и `tasks/:ref` могут служить входными ссылками, если далее
  канонизируются и не теряют контекст. Короткий маршрут сценария проверен в браузере.
- Документ может относиться к нескольким фичам и приложениям: единая библиотека
  `documents/:id` оправданна. Нужно сохранять возврат, а не копировать страницу под каждого родителя.
- Переход «Все связи и контекст» в `P/relations?root=…` — явно обозначенный переход
  в общий инструмент. На странице связей отдельного возврата к источнику сейчас нет.

## Порядок дальнейшего решения

1. Согласовать адрес и контекст реализации приложения, единый принцип `/edit` и возврата.
2. Исправить сломанный вход `product`, игнорирование возврата и потерю фильтров/фрагментов.
3. Согласовать дерево продуктовых маршрутов с выбранной иерархией страниц; убрать
   внутреннюю генерацию прежних якорей и слишком общий маршрут редактора.
4. Решить судьбу `work/:workId`, подключить SPA-переходы Markdown и повторить адресные
   сценарии, Back/Forward, reload и вход по скопированной ссылке.
