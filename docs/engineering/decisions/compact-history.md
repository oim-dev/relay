# Компактная сегментированная история

Принято пользователем 23 сентября 2026.

## Основание

Прежний журнал объединял полные JSON до/после, предметные события, комментарии и квитанции.
Небольшое изменение привязки дублировало весь документ и набор отношений. Один файл на
операцию и отдельные указатели на каждое событие увеличивали и базу, и производные индексы.
Восстановление незавершённой записи уже обеспечивается отдельным временным WAL.

## Решение

Текущие сущности и сохранённые связи остаются источниками состояния. История хранит
предметные события и первоначальные квитанции в ограниченных JSON-сегментах. Автор,
время, действие, затронутые ID и значимые изменения сохраняются. Для Markdown-изменения
фиксируется факт без копий редакций; комментарий сохраняется полностью.

Сегмент ограничен 128 записями и целевым размером 1 МиБ, отдельная крупная запись —
16 МиБ. Каждое действие немедленно публикуется общим WAL. Поток локален рабочей копии;
адрес записи вычисляется из потока и последовательности, дополнительного UUID нет.
Исторические индексы хранят сегменты по сущности/группе. Точный поиск сохраняется для
квитанций и служебных резервов. Между строками и сегментами опубликованные записи не перемещаются.

## Последствия и совместимость

Просмотр прежних Markdown-редакций в новой истории намеренно заменён фактом изменения.
Это уточняет [первоначальное решение о ленте задач](task-activity.md). Отдельного отката
состояния по истории не появляется. Полная диагностика файлов не накапливается по умолчанию.
Старые базы читаются совместимо и переходят явно; миграция сохраняет комментарии,
квитанции, идентичность и предметные факты, удаляя технические снимки.

Цена укрупнения индекса — чтение ограниченного сегмента при выборе отдельных событий.
Совместимые предметные адаптеры ещё могут собирать полные списки прежних событий;
новая физическая схема сама по себе не означает постоянную сложность всех выборок.
