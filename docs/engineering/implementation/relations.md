# Реализация связей сущностей

Сверка планирования 25 сентября 2026. [Продуктовые правила](../../product/RELATIONS.md),
[контракт](../../reference/GRAPH.md).

Причины физической схемы и её ограничения: [решение хранения](../decisions/graph-storage.md).

Начат переход на [единое хранилище](../entity-storage.md). Для базы с `storage.json`
сервис предметного сценария явно вызывает `application/entities/owned-relations` после
записи: задачи, принадлежность сценария/доски, реализации и документы. Оба шага публикуются
общей сессией; связи сохраняются наборами владельца/slot. Целевой формат 3 исключает
общий аудит и сохраняет квитанции внутри владельцев. Датированные проверки ниже
относятся к прежнему формату, не подтверждают новый переход.
Сценарная реализация также сохраняет `part-of` к реализации своей фичи в том же приложении.
Исправление 23 сентября: фича сохраняет `part-of` к `product:passport`, продукт —
к постоянному ID проекта. Корневая связь записывается после init/migrate даже при
незаполненном паспорте и при явном reconcile; новые записи фич согласуют обе ступени.
`EntityEngine.get.references` отражает этих фиксированных продуктовых родителей.
Публичная запись графа отклоняет изменение предметных групп с `RELATION_MANAGED`:
линки изменяются через предметного владельца. Явный `storage reconcile-relations`
согласует существующие группы без изменения ревизий сущностей и независимых рёбер.
Подключены каскады, полный контекст REST/CLI/MCP и явное обслуживание; сквозные проверки
переноса, CRUD, шести каскадов, повторов и восстановления прошли. Дальнейшие разделы
о физической схеме v1/v2 описывают прежний формат.

Планирование после упрощения 25 сентября вызывает `replaceOwnedRelations`:
план → проект, явно выбранная задача → план (`part-of`), план → область (`affects`),
релиз → проект (`part-of`) и релиз → план (`includes`). Группы `planning-scope`,
`planning-membership` и `release-composition` принадлежат своим сервисам и отделены
от `task-links`. Первые две группы принадлежат плану, этапы не являются узлами графа.
После записи плана сервис явно согласует обе группы. Перенос между этапами одного
плана сохраняет ID ребра задачи; перенос в другой план снимает старую и записывает
новую связь. Снятие и восстановление согласуют продуктовые линки и отдельные связи
общей Workspace/WAL-сессией. Контекст читает сохранённые отношения.

## Принятый стандарт и расхождения

22 сентября 2026 принят [обязательный стандарт линков, связей и контекста](../../development/LINKS-AND-CONTEXT.md).
Уточнение пользователя: продуктовые операции сохраняют свои данные и линки, затем бекенд
явно вызывает функции Core для установки, изменения или разрыва отдельно хранимых связей.
Контекст читает граф, продуктовые правила работают со своими данными. Первая редакция
стандарта ошибочно приравнивала связи к производным проекциям; эта трактовка исправлена.

Из движка удалены domain-проекции:
`application/graph/catalog.ts` возвращает только карточки и алиасы; сервис читает рёбра
только из репозитория графа. `source` допускает только graph. Существующие постоянные
рёбра v1/v2 и продуктовые поля сохранены. Автоматический импорт продуктовых линков не выполняется.
Для документов добавлен `application/documents/link-workflow`: после продуктовой
записи он явно вызывает `GraphService.mutate`. `storage/document-links` сохраняет
соответствие линков ID рёбер и намерение составной операции; Workspace восстанавливает
её под общей блокировкой. Прежние линки согласуются при явном сохранении документа.
В прежнем формате остальные сценарии сохраняют старое поведение; в едином формате
их жизненный цикл подключён через owned-relations.
Универсальная запись CLI/REST и форма Web являются диагностическими; Web явно обозначает
это назначение и больше не трактует `source=graph` как признак ручного создания.
Материалы задачи используют полный `graph/context` и адресный `entity_get` вместо `product_context`.
Существующие данные и API этой документационной работой не меняются.

`application/product/queries.ts` реализует отдельный `product_context`: документы подбираются
по прежним `fields.links`, не по новым `fields.relations` или самостоятельным рёбрам.
Скрытая политика `application/graph/context.ts` удалена. Контекст обходит все сохранённые
связи независимо от вида сущности; all — стандарт, context — совместимое имя all.
Без установленной связи продуктовый линк не расширяет контекст.

## Владельцы и покрытие

- `packages/contracts/src/entities/graph.ts` — переносимые адреса, рёбра, пакеты, страницы
  и события; `core/domain/entity-graph.ts` сохраняет совместимый экспорт.
- `application/graph/service.ts` — согласованное чтение единственного хранилища, полный
  обход, CAS и идемпотентная запись. Каталог узлов передаётся адаптером; валидатор пакета
  может проверять итоговый состав сохранённых связей. Вычисляемые рёбра каталог не поставляет.
- `application/graph/catalog.ts` — карточки существующих записей, реализаций, досок,
  задач канбана и алиасы. Прежние числовые задачи и записи жизненного цикла не входят в каталог.
  Карточки одиннадцати основных видов и их алиасы поступают из [движка сущностей](entities.md).
- `storage/graph.ts` — раздельный репозиторий v2; `graph-format.ts` — кодеки и лимиты,
  `graph-transaction.ts` — WAL и групповая синхронизация, `graph-migration.ts` — перенос v1,
  `graph-index.ts` — сегментированный индекс без Markdown и кеш списков смежности.
- Server Runtime предоставляет три REST-операции в local и project-scoped вариантах;
  OpenAPI и общий SDK используются CLI/Web, local CLI вызывает тот же Core.
- CLI `graph` предоставляет чтение, объясняющий контекст, запись пакета и историю.
- Web `domains/relations` владеет адаптером и SWR; экран `project-relations` — выбором,
  формой и отзывом связей. Внутренние `entity-browser` и `relation-explorer` отвечают за
  каталог по 40 и группы отношений на странице по 30. Выбор, режим и глубина живут в URL;
  форма в keepMounted-модальном окне переживает сворачивание. Получает обновления через SSE.
  UI/UX переработан 22 сентября 2026.
- Web `relation-context` — ленивый экран диаграммы внутри «Связей проекта».
  `domains/relations` собирает ограниченные страницы и раскрытые области в одной версии;
  основной полный API контекста этим экраном не меняется. React Flow отображает
  сохранённые `nodes/edges`, ELK Layered считает общую геометрию в отдельном Worker.
  Canvas — вложенный юнит экрана; список и инспектор — его внутренняя композиция.
  Основной режим — дерево кратчайших путей; доменный `getRelationPaths` обеспечивает
  одинаковые направленные пути для дерева и текстового объяснения. Каждый адрес
  показан единожды; дополнительные связи считаются отдельно и читаются в инспекторе
  порциями по восемь. Режим графа показывает все загруженные рёбра, список — по 30.
  ELK получает порты и расстояния от корня; renderer использует рассчитанные маршруты.
  У дерева общие порты ветвей, у графа отдельные порты каждого ID отношения.
  Общая перераскладка сохраняет позицию выбранной карточки; остальные координаты
  могут меняться вместе с линиями. После ручного переноса в режиме графа инцидентные
  линии используют SmoothStep; команда восстановления возвращает совместную раскладку.
  При переходе к списку Canvas остаётся смонтированным для сохранения камеры,
  но изолируется прозрачностью, `inert` и `aria-hidden`.
  Бюджет — 8 страниц по 50, до 400 рёбер и 1201 карточки с учётом endpoints/корня.
  Чтение исходного узла отдельно гарантирует его наличие на любой странице.
  Сведения и ошибки, включая смену версии, не смешивают снимки.
  Действующий интерфейс — в [контракте визуального контекста Web](../../product/applications/web/README.md#визуальный-контекст).

## Ограничения

- Пользовательские базы автоматически не мигрировались, проекции удалены.
  Прежний формат согласует документные линки; общий storage migrate явно переносит базу
  и предметные группы, после чего их поддерживают сервисы единого формата.
  Графовый `depends-on`
  не подменяет продуктовую зависимость канбана и не блокирует завершение.
- Суммарного ограничения 16 МиБ нет: отдельно сохраняются связи, события и квитанции.
  Лимиты отдельной записи, сегмента индекса и пакета — в GRAPH.md. Кеш компактного индекса
  ограничен восемью проектами; холодное чтение загружает индекс, не все пояснения и события.
- Прежний предметный каталог пока собирается из записей своего владельца. Нагрузочный
  замер индекса отношений использует 10 000 узлов в памяти, а не 10 000 файлов продукта.
  Полный граф/поиск и произвольный пользовательский валидатор могут требовать полного обхода.
- Ограниченная диагностика GET /graph сохраняет страницы и кратчайшие пути. Основной
  GET /graph/context возвращает все nodes/edges компоненты и complete=true; полные тексты
  читаются отдельно. У него нет скрытой границы глубины или первой страницы.
- История новых отношений сохраняется. Контекст остаётся динамическим.
  [Релиз](../../reference/RELEASES.md) фиксирует факт выпуска и ссылки на планы;
  тексты и готовность состава читаются актуальными, без архивного снимка.
  Canvas доступен в отдельном визуальном просмотре
  с явными границами; глобальная карта проекта и сохранение раскладок не реализованы.
- MCP `entity_context` читает тот же граф по ключу/ID; произвольная запись рёбер доступна CLI/REST.
- Форма Web сохраняет ввод при ошибке/конфликте и обновлении графа; после закрытия страницы
  отдельного постоянного черновика этой формы нет.

## Основания проверки

Прежние результаты ниже относятся к своим этапам, а не к текущему окружению.
22–23 сентября 2026 при интеграции предметных связей проверены все девять видов,
связывание/снятие, смена цели и родителя, перенос задачи,
сохранность независимых рёбер и ID, отказы и восстановление. Дополнительно проверена
принадлежность фичи продукту и продукта проекту, включая пустой паспорт и старые базы.
Полные прогоны: Core — 137, REST — 34, CLI — 36, MCP — 10 тестов.
Web читает полный граф и адресные тексты,
прошёл браузерные проверки записи, SSE, offline, конфликтов, двух тем и четырёх ширин.

Core-тесты проверяют произвольные виды, циклы, пути, страницы, атомарность отказа,
конкуренцию, повтор, Markdown, историю, изоляцию и повреждённые данные.
REST-тесты проверяют маршруты, конфликт, повтор, OpenAPI и SSE от прямой записи Core.
CLI-сценарий на временном проекте восстанавливает сценарий → реализацию → задачу →
зависимость и документ; человеческий и JSON-ответы проверяются отдельно.

Раздельная схема проверена на базе более 16 МиБ, миграции и нескольких границах прерывания
записи, потере индекса, внешней правке, повторе и восстановлении. Для воспроизведения
нагрузочного сценария: `pnpm run bench:graph 10000 100000`.
