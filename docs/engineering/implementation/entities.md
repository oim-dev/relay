# Реализация движка сущностей

Модель обновлена 25 сентября 2026: план и релиз, вложенные этапы, без снимков. [Продукт](../../product/ENTITIES.md),
[контракт](../../reference/ENTITIES.md), [решение о движке](../decisions/entity-engine.md).

## Владельцы

- `packages/contracts/src/entities.ts` — одиннадцать определений, read models, запросы и действия;
  `entities/*` и `primitives.ts` — единственные переносимые схемы полей и текста.
- `packages/core/src/domain/*` — совместимые пути экспорта схем. Contracts не зависит от Core.
- `application/entities/catalog.ts` — согласованный каталог источников, карточки и адреса.
- `application/entities/resolver.ts` — единое разрешение ключа, алиаса, ID или kind:ID;
  тот же механизм использует граф, включая его расширяемые виды.
- `application/entities/service.ts` — общие выборки, фильтры, версии и конвейер операций;
  `handlers.ts` — регистрация предметных обработчиков одиннадцати видов.
- Сервер `modules/entities` вызывает движок; local/HTTP backend сохраняет одинаковый контракт.
- CLI `commands/entities` и `presentation/entities` — действия и человеческий вывод;
  MCP `entity-tools.ts` выводит аргументы предметных инструментов из общих схем.
- Web `domains/entities` владеет каталогом и SWR; существующий EntityPicker использует его
  вместо обхода графа для поиска. Формат связей Web также проверяется общей схемой contracts.

## Гарантии и границы

Ключ разрешается под общей блокировкой; зарегистрированный обработчик получает ID.
Вложенные операции разделяют владение блокировкой через AsyncLocalStorage; внешний
параллельный запрос получает отдельную блокировку. Запись использует транзакцию владельца.
Ключи сохраняются транзакцией владельца; алиасы не передаются другой записи.
По целевому контракту квитанции и результаты команд не сохраняются.

План и релиз участвуют в общем каталоге, разрешении адресов и чтении.
Общий history API удалён; `planningEvents` запрещены вместе с другой историей операций.
Их изменение принадлежит предметным сервисам планирования/релизов: универсальные
create/update/rename не обходят эти правила. Прикрепления документов и защита удаления
учитывают эти виды. Этапы хранятся внутри плана и имеют только внутренние ID.
Реестр кодеков больше не регистрирует технические виды снимка. `dataVersion` плана
и релиза — 2; вместо миграции пользователь выбрал адресный сброс прежних записей
этих разделов. Это не назначает физическую версию перехода без истории операций;
условия сброса — в [контракте хранения](../../reference/STORAGE.md#планы-и-релизы).
Этапы отсутствуют в графе, каталогах и документных целях.

Виды определены в коде. Добавление поля начинается со схемы; изменение предметного смысла
также требует обработчика, кодека/миграции и приёмки интерфейсов. Реестровая архитектура
не генерирует полноценный пользовательский сценарий из названия поля.

Продуктовые линки остаются у предметных владельцев. В [едином формате](../entity-storage.md)
предметная запись явно согласует отдельные связи Core общей сессией; новые группы
планирования и релизов включены в `storage reconcile-relations` и проверки целостности.
Domain-проекции удалены из [движка связей](relations.md): граф читает только явные записи.
Прежние базы используют совместимый адаптер до явной миграции; новые операции планирования
требуют `relay-entities` v2.
Каталог собирает согласованный снимок источников; общий индекс адресного чтения всех записей
и новые нагрузочные гарантии этим этапом не заявлены. История показывает только сохранённые события.

Результаты проверок Core-сценариев, OpenAPI, HTTP backend, CLI text/JSON, MCP discovery/вызовов
и браузерной приёмки передаются в отчёте исполнителя с фактическими командами и ограничениями.
