# Документы и библиотека знаний

Документ хранит знания, которые должны быть доступны человеку и агенту вне отдельной
задачи. Начните с поиска существующего материала: прикрепление не требует копии текста.
Рекомендации по написанию находятся в [руководстве по содержанию](../guides/CONTENT.md).

В новом проекте библиотека пополняется уже при анализе ТЗ: исходные требования,
пояснения пользователя, правила и материалы реализации сохраняют по мере появления,
одновременно с описанием продукта. Документы прикрепляют к существующим продукту,
фичам, сценариям и реализациям, а после создания задач — и к ним. Это не обязательный
финальный подэтап. Знания — содержание документов и сущностей; контекст лишь помогает
разобраться в связях между ними.

## Содержание и тип

Документ имеет название, краткое описание, полное Markdown-содержание, тип, состояние,
раздел и адресные отношения. Название — одна строка; краткое описание — обычный
многострочный текст, объясняющий, когда читать материал. Для создания задают название,
непустой Markdown и тип документа. Краткое описание может быть пустым, прикрепления
не обязательны; обязательность передачи полей определяется контрактом действия.

Тип задаёт назначение материала, а не его готовность:

| Тип             | Назначение                            |
| --------------- | ------------------------------------- |
| `specification` | Требования и ожидаемое поведение      |
| `description`   | Описание предмета или устройства      |
| `rules`         | Правила и ограничения                 |
| `instruction`   | Последовательность действий           |
| `proposal`      | Предлагаемое, ещё не принятое решение |
| `decision`      | Принятое решение                      |
| `research`      | Исследование, наблюдения и выводы     |

## Состояние и организация

Состояния документа: `draft`, `active`, `archived`. Закрепление `pinned` независимо
от типа и состояния и относится к общему проекту, а не только к текущему читателю.
Архивирование сохраняет запись и прямой адрес, но обозначает неактуальность материала.

Сохранённый `draft` доступен участникам проекта. Он не равен локальному черновику UI:
несохранённый ввод вкладки ещё не является общей записью Relay.
Принятие предложения — явное изменение `proposal` в `decision` и состояния в `active`.
Прикрепление к задаче или завершение задачи не принимает предложение автоматически.

Раздел задаётся через `sectionId`; перечень разделов принадлежит
`project.documentSections`. Допускается до 100 разделов; их можно создавать,
переименовывать, упорядочивать и удалять. После удаления раздела его документы
отображаются с `sectionId: null`, а не удаляются.
Тип, раздел и предметные прикрепления решают разные задачи и не подменяют друг друга.

## Прикрепление к сущностям

Документ поддерживает отношения `relations` с целью `target: { kind, id }`,
типом `references` или `documents` и необязательным Markdown-пояснением `description`.
Целью может быть любой из [одиннадцати основных видов](PROJECTS.md) выбранного проекта.
Этапы, критерии и комментарии не являются самостоятельными целями прикрепления.

- `references` — сущность ссылается на документ как на материал для чтения.
- `documents` — документ описывает сущность.
- Пояснение отвечает на вопрос, зачем читать материал для выбранной сущности.
- Выбор родителя не выбирает детей. Пустой набор не означает «для всего проекта».
- Несколько прикреплений ведут к одной записи, а не к разным копиям документа.

Допускается до 100 отношений документа. Дубли пары цель + тип запрещены, как и ссылка
документа на себя. Новое отношение требует существующей активной цели выбранного проекта.

Прикрепление — предметная пользовательская операция. Core сохраняет продуктовые
данные и отдельно записывает соответствующие рёбра в общей транзакции.
Клиент не должен делать второй диагностический запрос записи в граф.
Открепление снимает линк и соответствующую связь, но сохраняет сам документ.

Есть две совместимые формы прикрепления: `links`/`targets` задают продуктовые области
с отношением `documents`, а `relations` — адресные `references`/`documents` ко всем
одиннадцати видам. Выбирайте поле по контракту действия; эти данные не являются
произвольными диагностическими рёбрами. Не предполагайте скрытую конвертацию или очистку
другого поля. Работайте через владельца документа и перечитывайте результат и [контекст](CONTEXT.md).
Markdown-URL в тексте сам по себе не создаёт прикрепления.

## Чтение и изменение

Каталог и поиск дают выборку, не заменяющую полный текст. Проверяйте продолжение списка,
а перед изменением читайте запись и её ревизию. При конфликте сохраните свой ввод,
перечитайте актуальный документ и согласуйте изменение, а не затирайте чужую запись.
После потери ответа сначала проверьте текущее содержание и отношения: `requestId`
не является квитанцией повторного запроса. Общие правила — в [хранении](STORAGE.md).

Прикрепление не меняет [готовность](PROGRESS.md) и не делает текст обязательным требованием
само по себе. Для действия используйте предметный смысл документа, его тип и состояние.
