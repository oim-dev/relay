# Продукт: хранение и операции

Продукт — независимая модель знаний внутри выбранной области Relay. Приложения продукта
(фронтенд, бэкенд и внутренние инструменты) не являются регистрациями из `projects_list`.
Задачи досок сохраняют `productLinks` по ID фич, сценариев и реализаций.
[План](PLANNING.md) отдельно хранит область воздействия `scope` и вложенные этапы
с явно выбранными задачами. [Релиз](RELEASES.md) ссылается на планы по `planIds`;
копии продукта, требований и материалов в нём не создаются.

## JSON-хранилище

Новые базы используют общие коллекции `entities/products`, `features`, `scenarios`,
`applications`, `implementations`, `documents` и технические `scopes`. Квитанции,
события и результаты команд не сохраняются. Все ссылки остаются ID;
подробности — [единое хранилище](STORAGE.md).
Описание вложенных каталогов и дисковых версий ниже относится к прежнему формату
как источнику миграции. Его гарантии сохранения истории и повторов заменены запретом
истории операций; это не руководство для новой записи.

### Ключи и отдельные реализации

Новый код пишет дисковую версию 3. Фичи/сценарии сохраняют файлы по ID, приложение
хранится в `applications/<applicationId>/application.json`. Реализации расположены
в `applications/<applicationId>/{features,scenarios}/<implementationId>.json`;
`scope.json` содержит ссылки, прежние события и квитанции состава, без копий Markdown.
Совместимое чтение старых v1/v2 сохраняется. Первое чтение через продуктовый сервис
закрепляет недостающие ключи; явный `product migrate` завершает перенос остальных записей.

Ключи FEATURE-N, SCENARIO-N, PREFIX-FI-N/PREFIX-SI-N хранятся отдельно от ID.
Изменяющий запрос нормализует входные ссылки в ID. Неоднозначный ключ даёт
`AMBIGUOUS_PRODUCT_KEY`, кандидаты доступны по ID. Новый ключ записи передаётся
верхнеуровневым `key` при update. Ранее использованный ключ записи резервируется.

Составная запись публикует намерение в `.transactions/pending.json`; восстановление
выполняется под общей блокировкой до чтения, с проверкой исходного/итогового содержимого.
Внешняя несовместимая правка останавливает восстановление вместо перезаписи.
`.indexes/catalog.json` — восстанавливаемый компактный индекс; изменение исходных
файлов инвалидирует его по файловой подписи. Эти файлы не являются продуктовым содержанием.

Новые операции: `GET /entities` — компактная страница с q/kind/application/refs/active,
offset/limit (1–100), total/nextOffset; `GET /entity?ref=…` — адресное чтение;
`POST /implementations` — обновление отдельной реализации по ref и её ifRevision.
Операции записи принимают requestId; прежняя замена состава остаётся совместимой.
Описание старого формата ниже относится к прежним v1/v2, не к новой записи.
Переход по [контракту хранения](STORAGE.md) выполняет `storage migrate`: весь автоматический
аудит и квитанции удаляются. Физическая версия базы — 4, оболочки — 3. Исторические гарантии
отдельных миграций продукта ниже не означают сохранение истории после перехода.

Необязательный `implementationTarget=feature|scenario` в `GET /entities` оставляет
только реализации: с `scenarioId=null` для фич или непустым `scenarioId` для сценариев.
Он сочетается с `application`, `active`, `q`, `kind` и применяется до `total`/пагинации.
Без фильтра поведение каталога прежнее; Web использует его для двух разделов выбора
целей карточки на доске приложения.

Записи находятся в `product` рядом с `.relay/config.json`. Паспорт — `passport.json`.
Остальные записи — `<kind>_<128-bit-id>.json` в каталогах `features`, `scenarios`,
`applications`, `scopes`, `documents`. Название сущности не влияет на путь или ID.

Дисковая схема `version: 2`: Markdown-поля `description`, `body` и описания контрактов
хранятся массивами строк, без отдельных MD-файлов. Краткое описание `summary` остаётся
обычной многострочной строкой. Пустые строки, отступы, завершающий перенос, CRLF и значимые
пробелы сохраняются. Поля записи: `productId`, `id`, `revision`, `fields`, даты/авторы,
события и журнал идемпотентных запросов. Внешний API сохраняет прежние строковые Markdown
и версию DTO 1: дисковая версия не меняет публичную модель.

Старый плоский формат v1 читается совместимо. Новые записи создаются в каталогах;
обновление старой записи до миграции сохраняет её путь, используя новый кодек.
Явная миграция: `relay-cli --local --config .relay/config.json product migrate`.
Перед миграцией сохраните резервную копию `product` и остановите старые клиенты,
не понимающие v2. Перенос идёт под общей блокировкой, не меняет текст, ID, ревизии,
историю, квитанции или готовность. Прерванный перенос возобновляется той же командой.
Дубли ID и неверная принадлежность каталогу отклоняются. После перехода откат к старому
коду требует восстановления резервной копии, а не только смены версии программы.

Обычная операция атомарно публикует один JSON. Создание приложения с доской использует
[восстанавливаемую составную запись](BOARDS.md). Весь состав приложения — один агрегат `scope`.
Ревизии записей независимы; `version` снимка — отпечаток всего продукта, включая внешние
изменения. Чтение и запись защищены существующей блокировкой области Relay.

## Контракты и готовность

Приложение обязательно содержит `slug`: уникальный в проекте адрес его доски, от 1 до 64
символов, строчные латинские буквы, цифры и разделяющие дефисы. Адреса `product`,
`infrastructure`, `new` зарезервированы. Slug задаётся при создании и неизменяем;
переименование приложения сохраняет адрес доски. Подробности: [доски](BOARDS.md).
Поле `prefix` задаёт неизменяемый уникальный префикс задач (`WEB`, `API`); без значения
при создании он получается из slug. Новые генерируемые ID записей и контрактов —
8 символов; прежние длинные ID сохраняются и продолжают читаться.
Приложения без slug требуют обновления демонстрационных данных; совместимость с ними
и автоматическая миграция досок в текущем этапе не предусмотрены.

Контракт содержит `featureId`, `scenarioId` (null для общего вклада), `title`,
`description`, `status`. Ядро назначает `id`, `active` и `basis`. `basis` — отпечаток
Markdown общих требований и собственного описания реализации. Снятый контракт сохраняется
неактивным; повторное включение сохраняет его ID. Новый активный сценарный контракт требует
общего контракта своей фичи. Выбор фичи не выбирает сценарии автоматически.

Статус реализации сценария в `state.records` (контракты состава), `entities`, `entity` и общем
каталоге сущностей вычисляется по явным `productLinks` задач вида `implementation`:
пустой набор — `none`; непустой набор фактически выполненных задач — `done`; иначе — `partial`.
Выполнение требует `done`, критериев и всех обязательств по цепочке: [прогресс](PROGRESS.md).
`cancelled` не выполняет обязательство. Сохранённые `status` и `basis` читаются совместимо,
но не переопределяют этот результат. Чтение не меняет дисковую запись и её ревизию.

Реализация фичи FI агрегирует собственные задачи (если есть) и активные SI с теми же
applicationId и featureId. Каждый выбранный SI должен быть done. Без собственных задач
FI может завершиться по всем готовым SI; пустой SI удерживает начатую FI в partial.
Снятые сценарные реализации исключаются из состава FI.

Проектная фича/сценарий агрегирует состояния всех своих активных имплементаций приложений.
Прямые productLinks вида feature/scenario добавляют ветку только при наличии задач.
Если все ветки done — требование done; если хотя бы одна начата — partial; иначе none.
Активная имплементация без задач во всём своём составе имеет none и удерживает начатый состав в partial.
Отсутствие прямых задач не блокирует каскад. Снятые реализации не учитываются.
Тип и ID образуют адрес цели: совпадение ID разных видов не смешивает задачи.
Проектная фича также агрегирует все свои проектные сценарии, в том числе пока не
выбранные приложениями. Полный порядок: задачи → SI → FI приложения; SI → проектный
сценарий; FI и проектные сценарии → проектная фича. Любая незавершённая обязательная
часть исключает done, а работа хотя бы в одной ветке даёт partial.

`readiness.status` отражает каскад. `participants` — число активных
реализаций приложений этой цели, `completed` — число готовых среди них, не число задач.
`stale` сохранён для совместимости и равен 0. Изменение Markdown не сбрасывает статус:
новый объём выражается задачей или возвратом существующей задачи из done.

Версия каталога учитывает динамические статусы. `state.version` остаётся версией
продуктовых записей для CAS описаний: перемещение задачи не конфликтует с правкой текста.

## Связи документов

```json
[
  { "kind": "product" },
  { "kind": "feature", "id": "feature_<id>" },
  { "kind": "scenario", "id": "scenario_<id>" },
  { "kind": "application", "id": "application_<id>" },
  { "kind": "implementation", "applicationId": "application_<id>", "id": "contract_<id>" }
]
```

Ссылки независимы. Цели проверяются в текущем продукте; реализации не создаются через
документы. Пустой набор допустим. Существующая ссылка на снятый контракт сохраняется,
новые ссылки требуют активной реализации. Типы документов: `specification`, `description`,
`rules`, `decision`. Логи, отчёты и события хранения не входят в библиотеку.

## REST

Префикс: `/api/v1/projects/:project/product`; в local также `/api/v1/product`.

| Метод и путь    | Назначение                                                          |
| --------------- | ------------------------------------------------------------------- |
| `GET /state`    | Полный согласованный снимок для редакторов, без внутренних журналов |
| `GET /overview` | Карта записей без полных Markdown и объяснения готовности           |
| `GET /records`  | `kind`, `q`, `id`, `offset`, `limit` (1–100), `total`, `nextOffset` |
| `GET /context`  | Необязательные `id`, `applicationId`; записи с причинами включения  |
| `POST /records` | Создание/изменение записи или точечное изменение контракта          |

Запись принимает `action: create | update`, `fields`, `requestId`, необязательный `actor`.
Обновление требует `id` и `ifRevision`; для `scope` нужен также `ifVersion`.
Точечный `fields.kind: contract` принимает `applicationId`, `contractId`, `status`,
необязательные `title`, `description`; состав находится по его связи с приложением.
Он требует `action: update`, ревизию состава и версию продукта.
Операция сохраняет прежние метаданные совместимо, но не переопределяет готовность по задачам.

Ответ записи: `{ok:true,data:{id,revision}}`. `requestId` служит корреляции,
не гарантирует дедупликацию или исходный ответ. После потери ответа прочитайте текущее
содержание и отношения. Конфликт ревизии — `REVISION_CONFLICT` (409),
неизвестная обновляемая запись — `PRODUCT_RECORD_NOT_FOUND` (404), неверная связь —
`INVALID_REFERENCE`. HTTP сохраняет общий лимит тела 1 МиБ; JSON-запись ограничена 16 МиБ.

## CLI: Markdown напрямую

Содержание пишется по [стандарту продуктовых материалов](PRODUCT-CONTENT.md).
Текстовый CLI предназначен человеку: списки оформлены таблицами (на узком экране —
карточками), полные описания рендерятся как Markdown, контекст объясняет включение записей.
`product list` показывает продолжение со смещением и фильтрами. Обзор отображает первые
30 записей с явным указанием ограничения; JSON-обзор сохраняет полный машинный контракт.
Полный `state`/`context` ограничен бюджетом ответа: выбирайте `--id`/`--application`,
читайте записи через `list` или увеличивайте `--max-bytes`.
`product lint` сообщает структурные предупреждения, `product validate` — целостность.

```bash
relay-cli product passport create --actor agent --request-id passport-1 \
  --name 'Сервис аренды' --summary 'Аренда вещей' \
  --description $'## Назначение\n\nПомочь людям арендовать вещи.\n'

relay-cli product feature create --actor agent --request-id feature-1 \
  --name 'Каталог' --summary 'Поиск вещей' \
  --description $'## Поведение\n\nПользователь находит доступные вещи.'

relay-cli product document create --actor agent --request-id document-1 \
  --name 'Правила аренды' --document-kind rules \
  --body $'## Правила\n\nСрок аренды задаётся в сутках.' \
  --links '[{"kind":"product"}]'
```

Можно передать всю операцию через `product save --json '<JSON>'`. Параметры `--description`
и `--body` заменяют текстовые поля внутри переданного JSON. Для состава используется
`product scope replace <applicationId> --json '<массив контрактов>' --if-revision N --if-version VERSION`.
Совместимая запись прежней отметки контракта — `product contract update <id> --application <id>
--status done --if-revision N --if-version VERSION`; она не меняет готовность по задачам.

`--request-id` служит корреляции; после потери ответа сначала перечитайте текущее состояние.
Без него CLI генерирует ключ одной операции и возвращает его в успешном ответе.

## MCP и контекст

Чтение: `product_overview`, `product_list`, `product_context`, `product_lint`.
Запись: `product_passport_save`, `product_feature_save`, `product_scenario_save`,
`product_application_save`, `product_document_save`, `product_scope_replace`,
`product_contract_update`. Значимые поля доступны на верхнем уровне, у аргументов
есть русские описания. Универсальный `product_save` оставлен для совместимости.
В workspace обязателен `project`; запись требует `actor` и `requestId`.
Markdown передаётся строкой. Предметные записи возвращают человекочитаемую квитанцию
в `content` и машинный ответ в `structuredContent`. Действуют `maxBytes` и ошибки бюджета.

Контекст включает паспорт, выбранную фичу/сценарий, приложения, релевантные контракты
и документы с `reasons`. Документ присутствует один раз, даже если подходит по нескольким
связям. Обход не расширяется на соседние фичи только потому, что общий документ связан с ними.
`product_list` позволяет дочитывать записи порциями. Полное состояние и контекст предназначены
для ограниченного графа; глобальная карта возвращается без тел Markdown через overview.

## Web

Подтверждённые данные общие для всех вкладок, CLI и MCP. SSE и периодическая сверка
обновляют состояние после API и local CLI. Черновики по-прежнему локальны вкладке,
сохраняют исходную версию и не затираются при внешних изменениях.
Служебная панель мока и ручной статус общего сценария убраны. Библиотека использует
настоящие цели; фича, приложение и паспорт показывают обратные списки документов.

Текущий UI использует полный снимок и защищает редакторы версией всего продукта: изменение
другой записи может потребовать явного подтверждения сохранённого ввода. CLI/API для обычной
записи могут использовать только её ревизию. Старые демонстрационные фикстуры не являются
постоянными данными и не импортируются автоматически.
