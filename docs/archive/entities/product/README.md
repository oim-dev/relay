# Сущность «Продукт» и её веб-раздел

> Архив спецификации прототипа. Все формулировки «сейчас» ниже относятся к прежнему этапу.
> Действующие требования: [сущность «Продукт»](../../../product/entities/product/README.md).

> Постоянная реализация: [операции продукта](../../../reference/PRODUCT.md).
> Правила хранения уточнены: исключительно JSON, Markdown массивами строк на диске;
> внешний API принимает Markdown-строку. Обязательны [правила содержания](../../../reference/PRODUCT-CONTENT.md).
> Общая готовность автоматическая по контрактам приложений. Интеграция с работой
> отложена. Описания режима мока ниже сохраняют историю проектирования UI.

[Продуктовое видение Relay](../../README.md) → Сущность «Продукт»

**Редакция от 18 сентября 2026 года. Основание: реализованный UI на моковых данных.**

Этот раздел — точка входа для агента, который будет вводить продуктовую модель в ядро Relay
и подключать существующий интерфейс к постоянным данным. Он описывает предметный смысл,
страницы, действия, состояния и условия приёмки без необходимости восстанавливать прежний диалог.

«Продукт» здесь — продукт, который разрабатывают в выбранном проекте Relay. Например,
в демонстрационных данных это сервис аренды «Напрокат». Сам Relay и его общее видение
описаны в [родительском документе](../../README.md).

### Статусы требований

- **Поведение UI** — правило, уже выраженное в прототипе; его нужно сохранить при замене источника
  данных. Оно описывается в разделах страниц и общих правилах.
- **Требование перехода** — необходимое свойство реальной модели: постоянное хранение,
  общие операции для Web и агентов, проверка ссылок, конкуренции и согласованность представлений.
  Оно ещё не означает наличия такой реализации.
- **Открытое решение** — вопрос, который интерфейс не решает. Он зарегистрирован отдельно;
  предположение агента не должно становиться незаметным изменением продуктового контракта.

Наблюдаемое ограничение или упрощение мока не становится требованием к серверу. В частности,
имена моковых ID, целый `ProductSnapshot`, `sessionStorage` и тестовый переключатель состояний
не задают формат постоянного хранения или API.

## Границы готового прототипа

| Область                             | Что уже делает UI                                                    | Что предстоит подключить                                           |
| ----------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Паспорт, фичи, сценарии, приложения | Чтение, создание и редактирование локальных записей                  | Постоянную модель и общие операции                                 |
| Вклады приложений                   | Сохраняет выбранный состав, отдельные заголовки, Markdown и статусы  | Реальные отношения, атомарную запись, версионирование              |
| Готовность                          | Статус сценария задаётся вручную; фича вычисляется по всем сценариям | Согласованное основание готовности по приложениям и подтверждениям |
| Документы                           | Библиотеку, чтение и редактирование; выбор независимых моковых меток | Реальные типизированные связи и обратные выборки                   |
| Работа                              | Просмотр демонстрационных планов, этапов и задач                     | Связи с существующими объектами жизненного цикла Relay             |
| Устойчивость ввода                  | Черновики, явную отмену, ошибки и выбор версии                       | Те же сценарии при настоящих сетевых сбоях и параллельной работе   |

В этой спецификации не вводятся произвольные подфичи, отдельный каталог сценариев,
множественные продукты внутри одного проекта или новые экраны удаления/архивирования.
Вопросы жизненного цикла и совместимости перечислены в [открытых решениях](OPEN_QUESTIONS.md).
