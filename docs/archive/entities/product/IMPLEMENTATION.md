## Результат этапа

Существующие пользовательские сценарии работают с постоянной моделью выбранного проекта.
Изменения, выполненные человеком в Web и агентом через инструменты Relay, относятся к одним
записям, проходят одни правила и становятся видны в связанных представлениях.

Задача шире замены `sessionStorage` на HTTP: необходимы предметные записи, отношения,
операции, совместимость с действующим жизненным циклом и обновление контекста для агентов.
Конкретные URL API и имена CLI/MCP-команд ниже не выдумываются: их следует определить
после [открытых решений](OPEN_QUESTIONS.md) и закрепить в существующих справочниках.

## Предметные операции, необходимые страницам

| Сценарий          | Чтение                                                             | Изменение и ожидаемый эффект                                                |
| ----------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| Паспорт           | Назначение, карта фич и приложений, текущий план                   | Сохранить содержание без потери остальных продуктовых записей               |
| Каталог фич       | Фичи и сценарии, общий статус, участие приложений, полные счётчики | Создать фичу; отдельно изменять её описание                                 |
| Фича              | Полное описание, сценарии, вклады приложений, связанная работа     | Создать/изменить сценарий с проверкой его родителя                          |
| Приложения        | Общие сведения, число выбранных фич и сценариев                    | Создать/изменить приложение без неявного выбора состава                     |
| Состав приложения | Актуальный каталог, подтверждённые вклады, версия                  | Атомарно заменить выбранный состав и данные вкладов только этого приложения |
| Библиотека        | Список, поиск по содержимому и областям, фильтры, счётчики         | Создать/изменить документ и его выбранные связи                             |
| Выбор областей    | Существующие продуктовые цели и реализации с контекстом            | Выбрать ссылки в форме; применить при сохранении документа                  |
| Работа            | Настоящие планы, этапы, задачи, результаты и продуктовые связи     | Изменения через владельцев жизненного цикла, а не отдельный моковый CRUD    |
| Агентский обзор   | Компактный паспорт, возможности, приложения, связи и состояние     | Те же предметные изменения, что доступны человеку                           |

Фильтры в серверной реализации должны иметь ту же семантику, что в спецификациях страниц.
Пагинация может менять способ загрузки, но не смысл: готовность считается по полному составу,
счётчики не равны случайно загруженной странице, поиск сценария возвращает родительский контекст.

## Общий контракт записи

Каждая операция получает проектную область, данные действия, автора и необходимую прочитанную
версию. Сервер повторно проверяет принадлежность и существование всех целей. Клиентская форма
не является единственным местом проверки.

Потребитель должен различать:

- успех с подтверждённой записью/ID и актуальной версией;
- некорректные поля или состав;
- отсутствие редактируемой записи либо цели связи;
- конфликт версии;
- временную недоступность записи/чтения и неожиданный сбой.

При конфликте нельзя выдавать успешный результат или выполнять безусловную повторную запись.
При потере ответа на создание повтор не должен порождать дубликат: проектировать это вместе
с существующим механизмом `requestId`, не полагаясь только на блокировку кнопки в браузере.

Сохранение состава приложения — единое действие. Часть выбранных вкладов не может успешно
сохраниться, если другая часть не прошла проверку. Снятые элементы исключаются из текущего
состава только после успеха; правила их исторической идентичности и ссылок решаются в D-04/D-05.

## Согласованность представлений

После подтверждения операции обновляются все затронутые представления:

| Изменение            | Что требуется обновить                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------ |
| Паспорт              | Паспорт, общий обзор и контекст для агента                                                 |
| Фича / сценарий      | Каталог, страница фичи, карта готовности, исходные контракты в приложениях, подписи связей |
| Приложение           | Каталог приложений, карточка, вклад в списке приложений фичи, варианты фильтров и связи    |
| Состав / вклад       | Дерево приложения, счётчики, обратный список у фичи, доступные реализации для документов   |
| Документ / его связи | Чтение, библиотека, сортировка по обновлению, счётчики областей и обратные выборки         |
| Настоящая работа     | Блоки связанной работы, текущий цикл и соответствующие страницы жизненного цикла           |

Автоматический пересчёт общей готовности по вкладам добавляется в эту матрицу только после D-02.
Изменение текста исходной фичи обновляет чтение общего контракта, но не переписывает Markdown
вкладов приложений.

Внешние изменения передаются через существующий проектный механизм SSE с перечитыванием REST.
После переподключения нужна сверка состояния. Кеши и события разделяются по проектам; поздний
ответ предыдущего проекта не подменяет данные текущего. Изменённая форма сохраняет исходную
ревизию до явного разрешения конфликта.

## Владельцы в веб-приложении

Архитектурные правила приложения находятся в
[профиле frontend](../../../../packages/dev-agents/src/frontend.md).

- `app/router` подключает существующие публичные экраны и маршруты.
- `compositions/layouts/project` владеет общей навигацией; продуктовый каркас подключает
  область выбранного проекта и вложенные страницы.
- Экраны `compositions/screens/product-*` и их формы владеют представлением, вводом,
  навигацией и показом исходов.
- Предметные типы, интерпретация ответов, операции, серверный кеш и его обновление принадлежат
  доменному владельцу продукта. Конкретную границу с `domains/lifecycle` следует определить
  после модели ядра; UI не должен становиться адаптером transport DTO.
- Транспорт использует существующий `infra/tasks-api` и общий SDK. Браузерное хранение
  остаётся механизмом локальных черновиков, не источником подтверждённого продукта.
- Markdown, тема и универсальные состояния продолжают использовать существующий слой `ui`.

Межюнитные импорты идут через фасеты, вложенные формы доступны своим владельцам.
Не создавать второй REST-клиент, копию серверных данных в произвольном store или встречные
зависимости между доменом продукта и жизненным циклом. Новые границы проверяются по Unit Architecture.

## Последовательность реализации

1. **Согласовать модель.** Закрыть D-01, D-03 и необходимые части D-04/D-05; определить этап
   готовности по D-02. Записать точные контракты и правила миграции, сохранив поведение UI.
2. **Реализовать Core.** Схемы, постоянное хранение, предметные операции, атомарность, ссылки,
   авторство и ревизии. Проверить их на временных local/workspace-хранилищах.
3. **Опубликовать интерфейсы.** Contracts → REST/OpenAPI → генерация SDK; подключить операции
   CLI/MCP и согласованный компактный обзор. Проверить эквивалентность результатов.
4. **Подключить чтение Web.** Паспорт, дерево фич, сценарии, приложения и документы получают
   реальные записи. Пустой проект действительно пуст; демонстрационные данные не подмешиваются.
5. **Подключить редакторы.** Сохранить валидацию, черновики и возвраты; проверить настоящие
   конфликты, пропавшие цели и повтор после сетевого сбоя.
6. **Связать проекции.** Реальные вклады, типизированные связи документов и настоящая работа;
   синхронизировать обратные списки, счётчики и контекст для агентов. Новое размещение обратных
   списков документов согласовать по D-05.
7. **Завершить переход.** Удалить служебные моки из рабочего потока, обновить справочники,
   продуктовый скилл и пройти [сквозную приёмку](ACCEPTANCE.md).

## Совместимость и перенос

- Действующий паспорт, требования, знания, планы и задачи — реальные пользовательские данные.
  Их нужно сохранить при развитии модели, даже если соответствующий старый пункт меню скрыт.
- Переходы мока v1 → v2 → v3 в `demo-session.ts` не являются миграциями постоянной базы Relay.
  `epoch` и `bucket` не переносятся в бизнес-контракт.
- Примеры «Напрокат» пригодны как отдельная тестовая фикстура. Новый настоящий проект
  не должен автоматически получать эти фичи, приложения и документы.
- Перенос пользовательских локальных правок прототипа не задан как автоматический импорт.
  Если он нужен, оформить отдельную явную операцию с сопоставлением ID и проверкой ссылок;
  `demo-*` не конвертировать по названию.
- Постоянные адреса и старые потребители должны иметь согласованный путь миграции.
  Наличие нового экрана не разрешает молча удалить старую запись или команду.
