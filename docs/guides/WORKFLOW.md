# От требования к результату и продолжению

Этот маршрут ведёт от пустой базы и ТЗ пользователя через знания, задачи и планы
к выпуску. Сначала [инициализируйте проект и подключите интерфейсы](GETTING_STARTED.md),
выберите область local или workspace. Заполненный продукт для начала не требуется.
Если проект уже ведётся, прочитайте сохранённые знания и уточняйте их, не создавая копий.

Четыре этапа ниже — основной порядок работы, не ограничения Core. Можно создать
задачу до заполнения паспорта, выполнять её без плана и без отдельного запуска плана,
а также заранее сохранить плановый релиз. Эти операции не заменяют сбор знаний.

В Web используйте разделы продукта, документов, досок, планов и релизов.
Для агента ниже приведены CLI-действия; соответствующие возможности MCP выбирайте
через discovery и [каталог возможностей](../CAPABILITIES.md), а не угадывайте имена.
Примеры CLI выполняются из корня local-проекта с настройками по умолчанию: CLI через
directCore и Web через Server используют одну базу. Необязательный HTTP-вариант показан
в [первом запуске](GETTING_STARTED.md). В workspace выбирайте `--project <имя>`;
если реестр находится вне пути поиска, укажите `--config /путь/relay.workspace.json`.

## 1. Соберите и сохраните знания

Пользователь передаёт ТЗ. Агент анализирует его, уточняет намерение, пользователей,
границы, ограничения и неизвестное. Не подменяйте неясное требование выдуманным решением:
задайте вопрос и сохраните пояснение пользователя. Это самый сложный и долгий,
но самый важный этап. Качество дальнейших задач и планов зависит от полноты и ясности
исходных знаний. Не торопитесь переходить к работе и не выдумывайте отсутствующие
требования. Это принцип работы с пользователем, а не дополнительные блокировки Core.

В Web:

1. Откройте паспорт продукта и заполните назначение, пользователей и границы.
2. В разделе фич создайте выделенные возможности, опишите требования; внутри каждой
   фичи создайте нужные сценарии с предусловиями, нормальным путём, ошибками
   и наблюдаемым результатом.
3. Спроектируйте необходимые приложения, например frontend и backend. В разделе
   приложений создайте их и опишите назначение. Slug и префикс доски выбирайте
   внимательно: после создания они неизменяемы.
4. Откройте состав каждого приложения, явно выберите фичи (FI) и нужные сценарии (SI).
   SI требует FI той же фичи в том же приложении. Заполните собственные обязательства
   реализаций: какой вклад в общее поведение обеспечивает именно это приложение.
   Сохраните состав и перечитайте его и тексты реализаций.

На протяжении этих действий пополняйте библиотеку: сохраняйте исходное ТЗ, пояснения
пользователя, правила и материалы реализации сразу по мере анализа. Прикрепляйте
документы к уже существующим продукту, фичам, сценариям и реализациям; к задачам
их можно будет прикрепить после создания задач. Это часть сбора знаний, а не финальный
шаг после заполнения всех карточек. Практика работы с документами описана ниже.

CLI-чтения помогают агенту проверить сохранённые знания:

```bash
npx @oim-dev/relay-cli product overview
npx @oim-dev/relay-cli product get passport
npx @oim-dev/relay-cli product list --kind feature
```

Краткий список нужен для выбора; полное содержание выбранной записи читайте через
`product get <ключ-или-ID>`. Опишите пользователя, предусловия, нормальный путь,
ошибки и наблюдаемый результат в продуктовых требованиях. Общая фича задаёт поведение,
сценарий — конкретный путь, реализация в приложении — вклад этого приложения.
Не создавайте фиктивное приложение или фичу только ради группировки задач.

Результат шага: участники понимают, **что должно работать**, и могут указать
существующие записи требований. Это ещё не утверждение, что поведение реализовано.
Правила содержания: [продукт](../domain/PRODUCT.md).

### Сохраняйте документы по мере анализа

| Содержание                                                  | Где хранить                                                 |
| ----------------------------------------------------------- | ----------------------------------------------------------- |
| Ожидаемое поведение и ограничения                           | Паспорт, фича, сценарий, реализация приложения              |
| Самостоятельная инструкция, решение, исследование           | Документ библиотеки                                         |
| Цель конкретной работы и условия её завершения              | Описание и критерии задачи                                  |
| Зачем начинать изменение, его границы и ожидаемый результат | Поля плана                                                  |
| Фактические проверки, ограничения и следующий шаг           | Сообщение задачи; существенный итог — также результат плана |
| Содержание выпуска                                          | Описание релиза и выбранные планы                           |

В Web откройте «Документы» → «Создать документ», выберите тип, заполните содержание
и свяжите документ с относящимися к нему сущностями. После сохранения откройте документ
заново и проверьте текст и связи. Длинная инструкция не должна существовать только
в краткой карточке или в переписке агента.

Заголовок — одна строка без Markdown, краткое описание — обычный многострочный текст,
полное описание и инструкция — Markdown. CLI/MCP принимают Markdown строкой;
не превращайте его вручную в массив строк внутреннего хранилища.
Правила: [документы](../domain/DOCUMENTS.md), [хранение](../domain/STORAGE.md).
Как сформулировать требования, критерии и фактический результат так, чтобы их поняли
без исходного чата, — в руководстве [«Полезное содержание»](CONTENT.md).

## 2. Создайте задачи на основании знаний

На продуктовой доске создайте общие и крупные задачи, на досках приложений — собственную
работу приложений. Используйте обычные родительские задачи и подзадачи для декомпозиции:
отдельного типа epic нет. В Web нажмите «Создать задачу», укажите цель и проверяемые
критерии; в списке подзадач родителя задайте нужное родительство. Прикрепите к созданным
задачам документы-основания. Инфраструктурную доску в этом базовом процессе пока
не используем, хотя она уже доступна.

Задача может указывать, какую бизнес-область затрагивает. Текущие продуктовые цели —
не просто тематические метки: задача включается в расчёт готовности выбранной цели.
На продуктовой доске выбирают общую фичу или сценарий, на доске приложения — FI/SI
этого приложения. Пустой набор допустим, например для каркаса или футера, которому
не требуется отдельная фича. Для CLI при необходимости сначала найдите реальную цель:

```bash
npx @oim-dev/relay-cli product entities --kind feature
```

Подставьте ID выбранной фичи вместо `FEATURE_ID`:

```bash
npx @oim-dev/relay-cli --actor agent task create --board product --title "Проверить сохранение формы" --description "Реализовать сохранение и проверить повторное открытие формы." --feature FEATURE_ID --criteria '[{"title":"После повторного открытия сохранённые значения видны"}]'
```

Если продуктовой цели нет и она не нужна, опустите `--feature`, не создавайте
фиктивную запись. Для конкретного сценария или реализации используются соответственно
`--scenario` или `--implementation`; для реализации замените `--board product`
на доску её приложения. Перечитайте задачу через `task get <ключ>`.
Проверьте, что цель связи правильная, а не просто имеет похожее название.

Зависимость двух задач задаётся отдельным предметным действием через CLI или MCP;
Web пока не предоставляет запись `depends-on`/`related`. Пример ниже требует
двух существующих задач; `REVISION` — ревизия первой задачи из свежего чтения:

```bash
npx @oim-dev/relay-cli --actor agent task link PRODUCT-2 --target PRODUCT-1 --relation depends-on --if-revision REVISION
npx @oim-dev/relay-cli task links PRODUCT-2
```

Теперь у `PRODUCT-2` наблюдаемая зависимость от `PRODUCT-1`. Упоминание ключа в тексте
само по себе её не создаёт. Не используйте зависимость вместо тематической связи
`related` или родительства `parent`.

Продуктовый линк — данные предметной записи, связь Core — отдельно сохраняемое
отношение, контекст — чтение графа. Клиент вызывает одно предметное действие;
бекенд согласует запись и отношения. Видимая проекция при чтении не заменяет
сохранение связи. Подробнее: [задачи](../domain/TASKS.md), [контекст](../domain/CONTEXT.md).

## 3. Спланируйте, выполните и проверьте работу

На основании знаний и созданных задач соберите один или несколько планов. План может
быть любого размера, от одной задачи, не только для крупной работы. Пользователь
и агент выбирают декомпозицию, этапы и состав. Возможность выполнять задачу без плана
и без его запуска сохраняется; ниже показан основной путь с планированием.

В Web откройте «Планы», создайте план с названием и целью; изложите в цели границы
и ожидаемый результат. Добавьте этапы и выберите существующие задачи для каждого этапа.
План не копирует задачи; зависимости и подзадачи
не становятся его составом автоматически. Проверьте сохранённый состав:

```bash
npx @oim-dev/relay-cli plan list
npx @oim-dev/relay-cli plan get PLN-1
npx @oim-dev/relay-cli plan stages PLN-1
```

Замените `PLN-1` на ключ созданного плана. Для чтения задач конкретного этапа используйте
`plan tasks <ключ-плана> <ID-этапа>` с ID из ответа. Если запись недоступна для включения,
проверьте её текущее участие и ограничения, а не создавайте дубликат.
Результат: план с ясной целью и явным составом. [Правила планирования](../domain/PLANNING.md).

### Выполните работу и отдельно проверьте результат

Перечитайте задачу, требования и блокеры. После фактического начала переместите задачу
в `in-progress` в Web или через `task move <ключ> --column in-progress --if-revision <ревизия>`
с явно заданным `--actor`. После сохранения убедитесь, что колонка изменилась.

Выполните работу вне Relay. Запустите необходимые тесты, проверьте пользовательский
путь или внешний результат. В сообщении задачи укажите, что именно проверено,
каким способом, что получилось и что осталось непроверенным. Ссылки на исходный код,
вывод теста или внешний артефакт должны позволять проверить утверждение.

Только затем отмечайте выполненные критерии, передавайте работу на проверку и
переносите её в `done`, когда условия соблюдены. Незавершённые критерии и блокеры
нельзя обходить формальной сменой статуса. Если условия не выполнены, сохраните
причину и следующий шаг, не называйте работу завершённой.

`done` — состояние задачи, не запуск тестов. Готовность реализации вычисляется по
текущему составу работ и обязательствам. Изменение только текста требований само по себе
не снимает готовность. Фактическое соответствие новым требованиям проверяют участники;
необходимую доработку выражают новой или переоткрытой задачей, связанной с реализацией.
[Как читать прогресс](../domain/PROGRESS.md).

Если работа объединена планом, **завершите план отдельным действием с итогом**.
Даже когда все задачи в `done`, план автоматически не переходит в `completed`.
Перечитайте план и его состав, убедитесь в выполнении условий завершения, затем
в Web выберите действие завершения и опишите фактический результат, проверки
и ограничения. Для CLI сначала выполните `plan get <ключ-плана>`, затем:

```bash
npx @oim-dev/relay-cli --actor agent plan complete PLN-1 --if-revision REVISION --result "ИТОГ"
npx @oim-dev/relay-cli plan get PLN-1
```

Замените `PLN-1` своим ключом, `REVISION` — актуальной ревизией из чтения,
а `ИТОГ` — содержательным итогом выполненной работы. Ожидаемый результат повторного
чтения: состояние `completed` и сохранённый итог. Если завершение отклонено,
проверьте состав, критерии, подзадачи и зависимости; не обходите ошибку сменой статуса.
Для фиксации выпуска нужны завершённые (`completed`) планы, а не только задачи в `done`.

## 4. Сформируйте релиз из выполненных планов

После выполнения планов выберите вошедшие в выпуск планы. Принятая целевая модель —
**релиз приложения** из проделанных работ. В текущей реализации доступна только
проектная запись релиза с `planIds`: поля `applicationId`, назначения приложения
и фильтрации планов по принадлежности релиза приложению нет. Описание выпуска может
пояснять приложение, но не создаёт структурированной принадлежности.

Доступное действие в Web: откройте «Релизы» → «Создать релиз», задайте название,
обозначение версии, описание и выберите планы целиком. Проверьте предпросмотр готовности
и состав: сохранение релиза не запускает и не завершает планы. Текущие операции также
позволяют заранее включить незавершённые планы в `planned`-релиз; это не основной
порядок данного руководства, но и не запрещённое действие.

Когда условия выпуска выполнены, используйте явную фиксацию выпуска в форме релиза.
Если она недоступна, откройте включённые планы и устраните показанные причины.
После сохранения перечитайте релиз:

```bash
npx @oim-dev/relay-cli release list
npx @oim-dev/relay-cli release get REL-1
```

Используйте фактический ключ вместо `REL-1`. Наблюдаемый результат — сохранённый
релиз с состоянием и составом. Relay не выполняет вместо вас CI/CD, публикацию
пакета или развёртывание: их успех подтверждается отдельно и отражается в содержании.
[Правила релизов](../domain/RELEASES.md).

### Оставьте знания и результат для продолжения

Оставьте следующему участнику выбранный проект, ID/ключ задачи, продуктовую цель,
существенные документы, результат проверки и ближайшее действие. При новой сессии
агент заново читает записи и отношения, а не полагается на прежний чат или старую ревизию.
Полное содержание открывается отдельно от списка; дочитайте все нужные страницы.

Если ответ записи потерян, обнаружен конфликт или состояние не совпало с ожидаемым,
переходите к [восстановлению](RECOVERY.md). Новое требование сначала сохраняйте
у его предметного владельца, затем уточняйте связанную работу.
