# Восстановление без потери данных

Руководство помогает выяснить состояние Relay после ошибки и выбрать безопасное
продолжение. Сначала определите проект, адрес сервера, действие и наблюдаемую ошибку.
Не исправляйте проблему удалением базы, `reset` или массовой очисткой.

## Ответ записи потерян

Таймаут или разрыв соединения не доказывает, что запись не выполнена.
`requestId` в MCP и `--request-id` в CLI служат корреляции, **не идемпотентности**:
дедупликации и сохранённого результата для повтора нет.

1. Сохраните исходные аргументы, идентификатор запроса и известный ID записи.
2. В том же проекте перечитайте запись. После создания найдите её по содержанию,
   автору и другим доступным признакам; одинакового заголовка недостаточно.
   После отправки сообщения прочитайте сообщения задачи.
3. Проверьте не только текст, но и статус, состав и отношения, которые меняли.
4. Если результат уже достигнут, продолжайте без повторной записи. Если состояние
   однозначно показывает, что действие не выполнено, согласуйте новое действие.
   При неоднозначности остановитесь и передайте её человеку.

Результат шага — установленное текущее состояние или явно названная неопределённость.
Повтор создания может породить дубликат; повтор изменения со старой ревизией может
дать конфликт. Ни новый, ни прежний `requestId` не делает повтор безопасным автоматически.

## Конфликт ревизии или порядка

Перечитайте запись целиком и сравните её с исходным намерением. Сохраните свой черновик
отдельно, согласуйте чужие изменения, затем подготовьте новую запись с актуальной
ревизией. Не подставляйте свежий `ifRevision` в старое тело без смыслового сравнения.
При конфликте порядка перечитайте также нужную колонку и её версию.

После сохранения заново откройте запись: должны сохраниться и согласованные изменения
другого участника, и ваш результат. Если конфликт повторяется, договоритесь об одном
писателе для этой записи, а не пытайтесь перезаписать её быстрее.

## Список выглядит неполным или страницы изменились

Список — страница карточек, не вся база и не полный Markdown. В CLI используйте
`--limit`/`--cursor`: копируйте предложенную nextCommand целиком, сохраняя фильтры,
ref, проект, конфиг и транспорт. В JSON публичный курсор находится в meta.page.nextCursor.
Wrapper восстанавливает limit и фильтры, поэтому nextCommand может не повторять их
флагами. Сырой data.nextCursor ленты оставлен для совместимости DTO и напрямую
не принимается CLI; не используйте его вместо курсора из meta.page.
Публичные offset и параметры версии страницы не используются; `--version` — версия CLI.
В MCP смотрите схему конкретного инструмента и метаданные продолжения ответа;
не переносите имена аргументов CLI механически.

Для CLI snapshot guard проверяет неизменность текущих данных и не предоставляет
исторического снимка; реестр workspace проверяет отпечаток текущего каталога на клиенте.
Если версия устарела, начните чтение с первой страницы. Не объединяйте страницы разных
версий как полный результат. При live-продолжении учитывайте возможные
параллельные изменения и перепроверьте важные записи по ID. Полный текст читайте
отдельным действием получения записи. Результат — прочитанный нужный диапазон и
явно известные границы, а не вывод «ничего нет» по первой пустой странице.

`--max-bytes` в CLI удалён: размер вывода CLI не ограничивает полное описание get.
Лимиты ввода, Core и транспорта сохраняются. Если ограничение вернул нижний слой,
уменьшите выборку или прочитайте записи адресно по контракту операции, не выдавая
усечённый ответ за полный контекст. Ошибка после записи не доказывает отсутствие изменения.

## Не тот проект или нет подключения

- Сверьте текущий каталог, явный `--config`, `RELAY_CONFIG`, `--server-url` и
  `RELAY_SERVER_URL`. Явные параметры имеют приоритет; поиск конфигурации идёт вверх.
- В local используется `.relay/config.json` одного проекта. В workspace используется
  `relay.workspace.json`, а проект выбирается отдельно: `--project` в CLI,
  `project` в MCP, выбор проекта в Web. Ключ задачи уникален только внутри проекта.
- В MCP вызовите `projects_list({})` и проверьте режим и имена. Relay Server должен
  работать отдельно; HTTP MCP по адресу `/mcp` не является REST API сервера.
- При занятом порте не завершайте чужой процесс: выберите свободный порт сервера
  и укажите полученный URL во всех клиентах. У MCP свой порт.

Проверка для конкретного local-проекта `alpha` из каталога, содержащего `alpha`:

```bash
npx @oim-dev/relay-cli config get \
  --local \
  --config ./alpha/.relay/config.json
```

Проверка того же проекта через workspace-сервер:

```bash
npx @oim-dev/relay-cli config get \
  --config ./relay.workspace.json \
  --server-url http://127.0.0.1:4700 \
  --project alpha
```

Результат — подтверждённые настройки нужной базы. Затем прочитайте известную задачу
в этой области и сопоставьте её ID между клиентами. Не выполняйте `init` в случайном
каталоге для устранения ошибки подключения. [Правила проектов](../domain/PROJECTS.md).

## Устаревшие индексы и нарушения целостности

После внешнего изменения файлов, Git-слияния или потери индекса чтение может сообщить
об устаревших индексах. Обычное открытие не обязано их перестраивать. До обслуживания
сохраните резервную копию и остановите записи клиентов в выбранный проект.

Все команды ниже адресуют **один local-проект `alpha`** по его собственному конфигу
из родительского каталога. Даже если обычно он доступен через workspace, обслуживание
производится локально, не по URL общего сервера и не для всего реестра сразу.
Замените путь на проверенный путь своей базы.

```bash
npx @oim-dev/relay-cli storage reindex \
  --local \
  --config ./alpha/.relay/config.json
npx @oim-dev/relay-cli doctor check \
  --local \
  --config ./alpha/.relay/config.json
```

Ожидаемый результат: `reindex` сообщает восстановление производных индексов,
`doctor check` — корректность хранилища либо конкретные нарушения. Перестроение индекса
не исправляет ошибочные предметные тексты, потерянные сущности или неправильные связи.
Если проверка не проходит, сохраните диагностику и исправляйте конкретную причину
по [правилам хранения](../domain/STORAGE.md), не удаляя данные ради зелёной проверки.
После успеха перечитайте затронутые сущности и отношения через обычный клиент.

## Явная миграция и резервная копия

После обновления Relay обычное чтение может ответить `STORAGE_MIGRATION_REQUIRED`,
Web — показать эту причину, а Server — ответить 409. Данные при этом не потеряны: новая
версия просто не работает со старым форматом без явного переноса. Перенос выполняет одна
команда сразу из любой поддерживаемой версии, промежуточные версии Relay не нужны.
Правила совместимости и сохранности — в [контракте хранения](../domain/STORAGE.md#совместимость-версий-и-миграция).

Команды ниже адресуют **local-базу `alpha`** по её собственному конфигу, даже если она
зарегистрирована в workspace; для проекта реестра используйте
`--local --config ./relay.workspace.json --project alpha`. Каждая база переносится отдельно.
В HTTP-режиме команды обслуживания отвечают `LOCAL_REQUIRED` и ничего не меняют.

1. **Остановите клиентов.** Завершите Server, MCP, Web-сессии записи и другие процессы
   Relay, работающие с этой базой. Поведение старых процессов нельзя сделать совместимым
   задним числом, а занятая база даёт `STORAGE_BUSY`.
2. **Проверьте состояние** без изменения файлов:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage status
   ```

   `current` — переносить нечего; `migration-required` — переходите к плану.
   `recovery-required`, `unsupported` и `invalid` завершаются ненулевым кодом с причиной
   и блокерами: путём или ID записи и следующим действием. Не правьте номера версий
   и не удаляйте файлы ради зелёного статуса.

3. **Проверьте план** — настоящий перенос в памяти, база и резервная копия не создаются:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage migrate --dry-run
   ```

   Прочитайте шаги, изменения файлов и отношений, удаляемые по правилу категории,
   предупреждения и требуемое место. Сохраните `planFingerprint` (в JSON —
   `data.planFingerprint` при `--format json`).

4. **Выполните перенос** с каталогом резервной копии вне базы и вне Git-рабочей копии:

   ```bash
   npx @oim-dev/relay-cli --local --config ./alpha/.relay/config.json storage migrate \
     --backup-dir /backups/relay-alpha --if-plan PLAN_FINGERPRINT
   ```

   Команда сама строит свежий план под замком; с `--if-plan` любое изменение базы
   или поставки после шага 3 останавливает её до изменений (`STORAGE_PLAN_STALE` —
   повторите шаг 3). Второго подтверждения нет. Резервная копия создаётся в новом
   подкаталоге `relay-backup-…`; его путь — `backup.path` результата. Копия проверяется
   до изменения базы и автоматически не удаляется.

5. **Проверьте результат:** повторный `storage status` должен показать `current`.
   Затем выполните `doctor check`, перечитайте важные записи, комментарии, планы и связи
   через обычный клиент и лишь после этого запускайте Server и другие клиенты.

   ```bash
   npx @oim-dev/relay-cli doctor check --local --config ./alpha/.relay/config.json
   ```

Повтор `storage migrate` после успеха ничего не меняет и копию не создаёт. Если ответ
команды потерян, выполните `storage status`: он покажет фактическое состояние.

### Сбой и продолжение

Перенос публикуется одной восстанавливаемой транзакцией. Сбой до её начала оставляет
базу в исходном состоянии: повторите шаги 2–4. Если процесс прервался во время
публикации, обычные клиенты отвечают `STORAGE_RECOVERY_REQUIRED` и не открывают
частично перенесённую базу. Повторите `storage migrate` с тем же `--config`: перенос
продолжится из записанной транзакции с исходной резервной копией, `--backup-dir`
не нужен. Не удаляйте `transactions/pending.json` и каталог копии.

- `STORAGE_BACKUP_MISSING` — копия по пути из незавершённой транзакции пропала или
  изменилась. Верните её на место и повторите команду; продолжения без копии нет.
- `STORAGE_RECOVERY_CONFLICT` — файл базы изменён посторонним процессом после прерывания.
  Транзакция и копия сохранены; восстановите названный путь и повторите, не перезаписывая
  чужое содержимое.
- Если до миграции осталась незавершённая обычная операция, перенос требует
  `--backup-dir`: копия сохраняется вместе с ней, операция завершается, план строится
  заново. Переданный `--if-plan` в этом случае устаревает — запустите без него.

### Восстановление из резервной копии

Откат завершённого переноса — работа с копией в **отдельном** каталоге. Автоматического
восстановления поверх действующей базы и обратной миграции нет; не копируйте старые
файлы поверх перенесённой базы.

1. Откройте `RESTORE.md` в каталоге копии и сверьте `backup-manifest.json`: `complete: true`,
   список файлов с размерами и SHA-256.
2. Создайте пустой каталог, например `/restore/alpha/.relay`, и скопируйте в него содержимое
   `files/config-root/` с сохранением путей; пустые каталоги перечислены в `directories`.
   Для legacy-базы с отдельным каталогом данных разверните `files/storage-root/` рядом
   и укажите его в `storageDir` развёрнутой конфигурации.
3. Сверьте SHA-256 каждого развёрнутого файла со списком `files`.
4. Откройте каталог версией Relay, совместимой с исходным форматом, и проверьте его командой
   чтения этой версии, например
   `npx @oim-dev/relay-cli@<версия> --local --config /restore/alpha/.relay/config.json task list`
   (ранние сборки публиковались как `@gromlab/relay-cli`), затем прочитайте важные записи.
   `doctor check` и `storage status` используйте только в версиях, где они есть.

Развёрнутая копия совпадает с базой до переноса; её можно снова перенести текущей
версией по шагам выше. Удаляйте копию вручную, когда она больше не нужна.

Если проблема не решена, передайте владельцу проекта код ошибки, область, версию
клиента, действие и результат чтения. Не выдавайте успешный `doctor check` за проверку
пользовательского сценария: после восстановления вернитесь к нужному шагу
[рабочего цикла](WORKFLOW.md).
