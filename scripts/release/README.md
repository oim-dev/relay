# Совместный выпуск Relay

Канонический процесс сборки, проверки и публикации самого Relay: CLI, Server и MCP.
Это инженерная поставка npm-пакетов, а не [проектные записи релизов](../../docs/domain/RELEASES.md)
в пользовательской памяти Relay. Подготовка окружения — в [инструкции разработки](../README.md).
Коммиты, push и публикация выполняются только по отдельному запросу согласно
[общим правилам репозитория](../../AGENTS.md); подготовка архивов этих действий не выполняет.

## Состав и источник версии

| Пакет                   | Манифест                                 | Каталог готового архива       |
| ----------------------- | ---------------------------------------- | ----------------------------- |
| `@oim-dev/relay-cli`    | [CLI](../../apps/cli/package.json)       | `apps/cli/.artifacts/npm/`    |
| `@oim-dev/relay-server` | [Server](../../apps/server/package.json) | `apps/server/.artifacts/npm/` |
| `@oim-dev/relay-mcp`    | [MCP](../../apps/mcp/package.json)       | `apps/mcp/.artifacts/npm/`    |

Все три пакета выпускаются с одной полной версией, включая prerelease-суффикс,
даже если изменился только один компонент. Текущая версия определяется манифестами,
а не номером в этой инструкции:

```bash
pnpm run release:check
```

Опорной служит версия CLI; Server и MCP должны совпадать с ней. Общий Git-тег —
`v<version>`, имя архива — `oim-dev-relay-<component>-<version>.tgz`.
Стабильная версия публикуется в `latest`, предварительная — в `next`.
Смешанные версии не считаются проверенным совместимым комплектом.
Корень и workspaces `@relay/*` приватны и отдельно не публикуются.

Основной путь — событие GitHub **release.published** и npm Trusted Publishing через
OIDC. Ручная публикация с локальной авторизацией — отдельный путь, не обязательный первый
этап каждого выпуска. Настройки доступа npm/GitHub не подтверждаются наличием workflow.

## Подготовка версии и окружения

Все команды ниже запускаются из корня Relay. `<version>`, `<commit>` и `<bundle-dir>`
— заменяемые значения, не выбранные версия, коммит или каталог. Аргументы `pnpm run`
передаются без дополнительного `--`.

1. Выберите новую версию и канал, проверьте доступность номера у всех трёх пакетов:

   ```bash
   npm view @oim-dev/relay-cli versions dist-tags --json --registry https://registry.npmjs.org
   npm view @oim-dev/relay-server versions dist-tags --json --registry https://registry.npmjs.org
   npm view @oim-dev/relay-mcp versions dist-tags --json --registry https://registry.npmjs.org
   ```

   Только отсутствие пакета/версии (`404`) означает отсутствие; ошибка сети или доступа
   не означает свободный номер. Проверьте также, что новый Git-тег свободен и целевой
   dist-tag не указывает на более новую версию. Частично опубликованный комплект
   восстанавливается по [правилам повтора](#повтор-и-диагностика), а не как новый выпуск.

2. Если версия ещё не подготовлена, обновите три манифеста:

   ```bash
   pnpm run release:version <version>
   ```

   Команда принимает SemVer без build metadata (`+…`), но не проверяет свободу номера
   или его увеличение. Она не создаёт коммит или тег. Добавьте непустой раздел
   `## <version>` в каждый `apps/{cli,server,mcp}/CHANGELOG.md`; для неизменённого
   компонента опишите совместный выпуск.

3. Для самостоятельной локальной приёмки используйте отдельный чистый checkout
   выбранного релизного коммита, без прежних `dist` и `.artifacts`. Это отдельный путь
   проверки, а не обязательный повтор QA перед каждым CI-выпуском. Например, после
   подготовки коммита можно создать отдельный worktree:

   ```bash
   git worktree add --detach ../relay-release <commit>
   ```

   Перейдите в его корень. Не очищайте чужую рабочую копию через reset/clean.
   Используйте Node.js 24, pnpm из `packageManager` и npm 11.16.0, как в CI упаковки:

   ```bash
   git status --short
   git rev-parse HEAD
   node --version
   pnpm --version
   npm --version
   pnpm exec npm --version
   pnpm install --frozen-lockfile
   ```

   Ожидаются выбранный SHA и отсутствие локальных изменений. Нужны доступ к registry,
   Git, `tar`, место для сборки и свободные локальные порты для smoke.
   При несовпадении npm подготовьте нужную версию в выделенном окружении;
   `pnpm exec npm --version` проверяет именно npm, который использует обёртка публикации.

## Проверка и упаковка

Ниже — полный самостоятельный локальный preflight. Он нужен, когда проверенный
комплект готовят локально; это не последовательность job релизного CI.
После него возможна [самостоятельная локальная публикация](#проверенный-bundle-и-ручной-fallback)
без свидетельства PR и учётных данных GitHub, с авторизацией npm и проверками publisher.
[Выпуск через GitHub Release](#публикация-через-github-release) использует уже
полученное свидетельство QA из PR и не повторяет общий набор тестов.

```bash
pnpm run release:check v<version>
pnpm run release:notes v<version>
pnpm run agents:check
pnpm run skills:check
pnpm run build
pnpm run check
pnpm run package:check
git status --short
```

`release:check` проверяет состав публичных пакетов, версии и соответствие строки тега.
Он **не проверяет существование Git-тега или его привязку к коммиту**.
`release:notes` читает три CHANGELOG и выводит объединённое описание, но не создаёт
GitHub Release. Обе команды работают и напрямую через `node scripts/release/relay.mjs`
с действиями `check`/`notes`, без установки зависимостей.

Проверки сохранённых agents/skills выполняются до сборки, чтобы не скрыть drift.
Их содержание и восстановление описаны у [dev-agents](../../packages/dev-agents/README.md)
и [relay-skill](../../packages/relay-skill/README.md). `check` включает release-тесты,
форматирование, проверки генераторов и документации, lint, типизацию и тесты workspaces.

[Упаковщик](../package.mjs) читает скомпилированный JS из `dist`, сохраняя результаты
компиляции, в том числе серверные metadata декораторов. Используемые приватные runtime
пакеты включаются в bundle; внешние production-зависимости остаются в манифесте.
В поставке не должно быть `workspace:`, `file:`, `link:`, scripts и devDependencies.
Server включает Web в `dist/web`; CLI/MCP не включают серверный runtime.

Staging создаётся в `apps/<component>/.artifacts/package`, проверенный архив —
в `apps/<component>/.artifacts/npm`. Состав документации берётся из `files` манифестов
приложений; проверяются файлы и байты готовой поставки. CLI-документы обслуживаются
у [CLI](../../apps/cli/README.md), а не копируются вручную в staging.
Прямой prepack приложения останавливается с указанием штатной упаковки.

`package:check:cli`, `package:check:server`, `package:check:mcp` строят и упаковывают
отдельный компонент. Полный `package:check` дополнительно запускает
[smoke-relay.mjs](../smoke-relay.mjs): независимые npm-установки трёх архивов,
версии и bin-команды, документацию, CLI local/HTTP, Web/Swagger/API, workspace A/B,
MCP и отказ клиента после остановки Server. Проверка использует изолированные данные,
не пользовательский Playground.

Повтор установки уже готовых архивов без сборки:

```bash
pnpm run package:smoke
```

Эта команда не требует установки зависимостей монорепозитория, но требует готовых
архивов и окружения для их независимой установки. Она не заменяет остальные проверки.
Smoke — необходимая проверка нового npm-артефакта, а не обещание дешёвого или мгновенного
шага: независимые установки и запуск приложений требуют времени и ресурсов.
Любое изменение исходников после QA требует нового проверенного комплекта.

## Публикация через GitHub Release

Точные механизмы: [ci.yml](../../.github/workflows/ci.yml),
[release.yml](../../.github/workflows/release.yml), [event.mjs](event.mjs),
[фазы CI и упаковки](../ci.mjs), [допуск PR](verified-pr.mjs),
[чтение GitHub API и свидетельства](github-read.mjs),
[доказательство линейного rebase](rebase-proof.mjs),
[bundle.mjs](bundle.mjs), [publish.mjs](publish.mjs).

Проверки новой ревизии выполняются [в PR](../README.md#ci-для-новой-ревизии-pr),
а обычный push или merge не запускает общий набор тестов. Отправка тега и создание
draft Release не запускают npm publish. Сопровождающий создаёт GitHub Release отдельно
для нового `v<version>` на точном результате PR, слитого в `main`.
До публикации Release проверьте:

```bash
git rev-parse HEAD
git rev-parse 'v<version>^{commit}'
```

SHA должны совпасть с выбранным релизным коммитом. Просмотрите workflow именно этого
коммита. Флаг GitHub prerelease должен быть выключен для stable и включён для prerelease.

### Допуск проверенного PR

Релизный CI не вызывает reusable CI и не запускает общий набор проверок повторно.
Вместо этого до сборки он проверяет происхождение результата QA. Свидетельство PR
обязательно для CI-выпуска и продолжения его проверенного комплекта без полного
локального QA; к самостоятельному локальному выпуску после полного preflight это
требование не относится.

Обозначения: `S` — окончательный коммит тега, `H` — final head слитого PR,
`B` — base, на которой выполнялась проверка, `M` — проверенный synthetic merge
с родителями `B` и `H`. Для CI-допуска одновременно должны выполняться условия:

1. `S` — точный результат слияния единственного подходящего PR в `main`, а не произвольный коммит
   из истории ветки и не direct push.
2. Для `H` найден актуальный run активного `.github/workflows/ci.yml` того же
   репозитория. Текущая попытка run, итоговый `PR / Все проверки` и все обязательные
   фазы успешны. Более поздний неуспешный, отменённый или незавершённый run нельзя
   заменить прежним зелёным результатом.
3. Свидетельство **pr-verification** получено из этого же репозитория, точного run
   и попытки его успешного gate. Проверяются ID, digest и содержание артефакта,
   связь с PR, `H`, `B` и `M`. Чужое, отсутствующее, удалённое или просроченное
   свидетельство не подходит; кеш и имя артефакта не доказывают QA.
4. GitHub API подтверждает точных родителей `M` — `[B, H]` — и равенство
   `tree(M) == tree(S)`. История `S` соответствует одной из
   [поддерживаемых топологий](#поддерживаемые-топологии).
5. Хеш `ci.yml` проверенного run совпадает с файлом в релизном checkout. Совпадают
   также `packageManager` и SHA-256 lockfile; свидетельство указывает Node.js 24
   и runner `ubuntu-24.04`.

Механизм допуска связывает PR, результат конкретного workflow/run/attempt, дерево
и артефакт. Совпадение имени, пути, workflow ID, хеша workflow и корректный JSON сами
по себе не доказывают, что код workflow/helpers выполняет заявленные проверки.
Если разрешена замена этого кода заглушками, самопроверка не защищает от такой подмены
и не делает workflow «утверждённым». Доверие к коду должно обеспечиваться независимо —
внешним ревью и [защитой репозитория](#требования-к-защите-main), а не одним helper.

Допуск выполняется до pack и повторяется в publisher непосредственно перед записью,
в том числе при повторе только publisher. Прежнего успешного metadata недостаточно:
более новая попытка PR-проверки или недоступное свидетельство могут закрыть выпуск.
При отказе допуска workflow останавливается, а не подменяет свидетельство запуском тестов
в release или ручным редактированием свидетельства.

#### Поддерживаемые топологии

SHA `M` и `S` могут различаться, но их итоговое дерево обязано совпадать.
[Проверка допуска](verified-pr.mjs) различает три результата:

- **`merge`**: у `S` ровно два родителя, в порядке `[B, H]`.
- **`single-parent`**: у `S` один родитель, равный `B`. Squash и однокоммитный rebase
  структурно неразличимы; helper не угадывает способ слияния по сообщению коммита.
- **`linear-rebase`**: многокоммитный случай. Полный состав исходных коммитов PR
  образует одну линейную цепочку до `H`, а результирующая цепочка той же длины начинается
  от `B` и заканчивается `S`. Для каждой пары коммитов совпадают автор (имя, email и момент авторства),
  сообщение и точные изменения путей: состояния до/после по mode, type и SHA объектов,
  включая blob SHA. Проверка не опирается на сходство текста патча или один patch-id.

Для многокоммитного rebase `B` — родитель **первого** коммита результирующей цепочки,
а не обязательно `parent1(S)`. [Доказательство rebase](rebase-proof.mjs) проверяет
полноту списков и линейность обеих цепочек, не исполняя код PR и не переписывая Git.
Такой rebase блокируется при неполной истории, другой базе, пропущенных/объединённых
коммитах, несовпадающих изменениях или итоговом дереве.

Многокоммитный rebase с изменением blobs при переносе патча на новый контекст
**не поддерживается** этим доказательством и блокируется, даже если GitHub разрешает
такой способ слияния. Для него нужно отдельное доказательство повторного применения
изменений (replay), которого этот механизм не реализует. Используйте доказуемый
merge/squash либо отдельно согласуйте расширение доказательства; общий набор тестов
в release не служит fallback. Доступность merge, squash или rebase в настройках
GitHub сама по себе не подтверждает поддержку всех вариантов их истории.

#### Свидетельство и повторные попытки

Артефакт **pr-verification** содержит единственный `verification.json` со `schema: 1`:
репозиторий и PR, `H`/`B`, `M` и его tree, run и попытку gate, путь/SHA/хеш workflow,
Node.js, `packageManager`, хеш lockfile и runner. В `ci.yml` задан срок хранения
90 дней; helper проверяет также фактический срок и доступность артефакта.

Частичный retry может сохранить успешные job более ранних попыток того же run.
Admission читает полную историю и для каждого обязательного job берёт последнее
выполнение: оно должно быть успешным и не новее принятого gate. Более поздний
failure/cancelled/skipped не заменяется прежним success; устаревший gate не принимается.
Это не требование пересобрать всё при каждом retry: исходный ID успешного build
остаётся допустимым в пределах того же run/SHA.

Artifact API не содержит `run_attempt`. Helper связывает конкретный ID и digest
с run, временем выполнения успешного gate и номером попытки в JSON свидетельства.
Пустой список `run.pull_requests` сам по себе не означает чужой run: связь проверяется
по свидетельству и родителям `M`. Если у выбранного run есть API-ассоциации, хотя бы
одна из них должна подтверждать нужные PR, head и репозиторий.

Внутренний интерфейс [verified-pr.mjs](verified-pr.mjs) обслуживает CI:
`create <file>` использует событие, окружение, checkout `M` и `CI_NEEDS`, а `verify`
проверяет checkout `S` через read-only GitHub API с `GH_TOKEN`. При чтении свидетельства
helper не исполняет его содержимое и не восстанавливает сборочные выходы из PR.
Результат содержит `pr`, `run_id`, текущий `run_attempt`, попытку успешного gate
`verification_attempt`, ID свидетельства `artifact_id` (не ID npm-комплекта),
релизный `commit` (`S`), проверенный `tested` (`M`) и `topology`.
Этот интерфейс не добавляет GitHub credentials к самостоятельному локальному preflight.

Если база PR изменилась, актуализируйте его ветку и дождитесь новой проверки
`synchronize` до слияния. `reopened` без изменения ветки не запускает CI и не освежает
свидетельство. Для первого CI-выпуска по этой схеме нужен PR, прошедший новый workflow
с `pr-verification`: прежние зелёные статусы без свидетельства не равнозначны допуску.
Недоступное свидетельство не даёт CI-допуска, в том числе при publisher-only retry.

### Стадии выпуска

Публикация Release запускает видимую последовательность **metadata → pack → smoke → publish**:

1. **metadata**: проверяет `release.published`, репозиторий, отсутствие draft,
   тег, коммит, общие версии, совпадение checkout с коммитом тега и prerelease-флаг.
   Формирует release notes из непустых разделов CHANGELOG и выполняет допуск проверенного PR.
2. **pack**: один раз строит окончательный SHA тега на Node.js 24, упаковывает
   три приложения, создаёт bundle и загружает **npm-packages**. Возвращает точный
   `artifact_id`; не переносит архивы PR путём замены commit в старой ведомости.
3. **smoke**: скачивает этот `artifact_id` с проверкой digest и вызывает
   `bundle.mjs restore`, который проверяет весь комплект до копирования архивов.
   Затем выполняет `package:smoke`. Сборка, повторная упаковка и общий набор тестов
   здесь не запускаются.
4. **publish**: только после успешного smoke скачивает тот же `artifact_id`,
   повторно проверяет актуальный PR-допуск, событие и весь bundle, затем публикует
   ровно те же smoke-проверенные байты. Зависимости монорепозитория не устанавливаются;
   тесты, сборка, упаковка и smoke здесь не повторяются.

Артефакт **npm-packages** содержит ровно три `.tgz` и `manifest.json`.
Это комплект для публикации, не свидетельство `pr-verification` из PR.
Ведомость содержит schema, окончательный commit SHA, тег, имена/версии пакетов,
имена файлов и SHA-512 integrity. Пустой ID запрещает загрузку; несовпадение digest
при скачивании останавливает job. Внутренняя проверка повторно сверяет ведомость,
байты и метаданные архивов. В `release.yml` задан срок хранения npm-артефакта 14 дней;
для отложенного retry сохраните весь исходный smoke-проверенный комплект с ведомостью
и сведениями о его происхождении до истечения срока.

Publisher находится непосредственно в `release.yml`, использует environment `npm`.
Общие права workflow — `contents: read`; только publisher получает `id-token: write`.
Metadata и publisher дополнительно получают `actions: read` и `pull-requests: read`
для проверки допуска через `GH_TOKEN`, которому передаётся токен текущего workflow.
`contents: write`, npm-токены и создание GitHub Release внутри publisher не нужны.
Цель публикации фиксирована: `https://registry.npmjs.org`, доступ `public`.
В GitHub Actions обёртка передаёт `--provenance`.

### Требования к защите main

В настройках репозитория необходимо обеспечить:

- Изменение `main` через PR, без direct push и обхода обязательных проверок.
- Обязательный required check **`PR / Все проверки`** для актуальной ревизии PR.
  Успех отдельной стадии не заменяет итоговый gate.
- Актуальность base перед слиянием: изменения целевой ветки требуют обновить PR
  и получить новую проверку `synchronize`.
- Внешнее ревью и защиту изменений workflow/helpers от подмены или обхода проверок.
  Проверка связности свидетельства не заменяет это ревью: одноимённый зелёный check
  из недоверенного кода не должен давать право на CI-выпуск.

Это требования к rulesets/branch protection, а не утверждение, что они уже включены.
Наличие workflow само по себе не делает `PR / Все проверки` обязательным и не требует
актуальной base перед слиянием. Проверьте удалённые настройки, права обхода и правила
ревью отдельно: наличие YAML и этой инструкции не подтверждает их действие.

### Настройка доверия

Для каждого npm-пакета проверьте Trusted Publisher:

| Поле                 | Значение                       |
| -------------------- | ------------------------------ |
| Publisher            | GitHub Actions                 |
| Organization or user | `oim-dev`                      |
| Repository           | `relay`                        |
| Workflow filename    | `release.yml`                  |
| Environment name     | `npm`                          |
| Allow npm publish    | Включено для прямой публикации |

В GitHub должен существовать environment `npm`; фактические ограничения тегов
и reviewer-настройки проверяются в настройках репозитория, а не выводятся из его имени.
В каждом архиве `repository.url` должен быть `git+https://github.com/oim-dev/relay.git`.
Не добавляйте токены или `npm login` в publishing job: npm использует OIDC.
Не отключайте 2FA ради выпуска. Права npm и GitHub независимы.

Официальные требования и ограничения: [npm Trusted Publishing](https://docs.npmjs.com/trusted-publishers/),
[npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish),
[GitHub release event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release).
Успешные локальные тесты и `npm whoami` не проверяют OIDC-обмен.

## Проверенный bundle и ручной fallback

Для ручной публикации различайте два основания QA:

- **Самостоятельный локальный выпуск:** выполните весь
  [локальный preflight](#проверка-и-упаковка) для выбранного чистого коммита и его
  комплекта. Свидетельство PR и учётные данные GitHub не требуются. Нужны авторизация
  npm и все проверки архивов, registry, integrity и каналов, выполняемые publisher.
- **Продолжение CI-выпуска без полного локального QA:** используйте его исходный
  проверенный комплект и свидетельство PR. Ручной fallback меняет способ публикации,
  а не обходит отказ CI-допуска; он не разрешает подменять байты, сведения о происхождении
  артефакта или доказательства CI/OIDC provenance.

Одни `verify`/`restore` и smoke не заменяют полный локальный preflight и не дают
CI-допуска. Полная локальная проверка также не создаёт свидетельство PR и не доказывает
CI/OIDC provenance: не приписывайте самостоятельному выпуску происхождение из CI.

Для проверки сохранённого комплекта используйте checkout того же коммита:

```bash
node scripts/release/bundle.mjs verify "<bundle-dir>"
node scripts/release/bundle.mjs restore "<bundle-dir>"
pnpm run package:smoke
```

`verify` не пишет файлы. `restore` сначала проверяет весь комплект и только затем
копирует те же байты в каталоги архивов приложений, заменяя одноимённые файлы.
Используйте выделенный checkout. Если задан `RELEASE_TAG`, он должен соответствовать
ведомости; иначе тег определяется из манифестов. Проверка SHA в ведомости не доказывает
чистоту исходного checkout или выполнение QA сама по себе.

Для сохранения локально проверенных архивов можно выполнить:

```bash
node scripts/release/bundle.mjs create "<bundle-dir>"
```

Каталог должен быть пустым. `create` копирует архивы и создаёт ведомость, но **не
выполняет QA и не устанавливает достоверность происхождения**. Для retry сохранённого
CI-артефакта создавать новую ведомость не нужно. Нельзя переписать commit в bundle
из PR, чтобы выдать его за комплект окончательного SHA тега.

При любой ручной публикации исключите параллельный CI/локальный publisher и проверьте
существующую авторизацию без чтения токена:

```bash
npm whoami --registry https://registry.npmjs.org
```

Аккаунт должен иметь право записи на каждый пакет; `whoami` этого не доказывает.
Не сохраняйте credentials в репозитории и не выводите значения токенов.
После подготовки и проверки исходных архивов команда публикации:

```bash
pnpm run release:publish v<version>
```

Она последовательно публикует CLI, Server и MCP из `apps/*/.artifacts/npm`, без сборки,
создания тега или GitHub Release. Используйте `pnpm run`: npm-обёртке нужен заданный
менеджером `npm_execpath`. Локально `RELAY_RELEASE_BUNDLE` **не переключает источник**
архивов — предварительно выполните `restore`. В CI эта переменная обязательна,
а `release:publish` сам проверяет и восстанавливает bundle перед публикацией.

До первой записи проверяются все архивы и registry. Уже существующая версия
пропускается лишь при совпадении integrity и канала. После публикации повторно
сверяются integrity и dist-tags всего комплекта. Quality gates сама команда не повторяет.
Не заменяйте этот процесс `npm publish` из каталогов приложений или workspaces.

## Подтверждение результата

После публикации проверьте именно выбранную версию:

```bash
npm view @oim-dev/relay-cli@<version> version dist.integrity --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-server@<version> version dist.integrity --json --registry https://registry.npmjs.org
npm view @oim-dev/relay-mcp@<version> version dist.integrity --json --registry https://registry.npmjs.org
```

`dist.integrity` должен совпасть с SHA-512 исходного архива в формате
`sha512-<base64>`, а `latest`/`next` — с выбранной версией у всех пакетов.
Каналы проверяются командами `npm view … versions dist-tags` из подготовки.
Для OIDC-выпуска проверьте также provenance в npm и его связь с ожидаемым workflow
и коммитом; совпадение repository URL не заменяет provenance.

Обычные пользовательские точки входа вне checkout:

```bash
npx @oim-dev/relay-cli --help
npx @oim-dev/relay-server --help
npx @oim-dev/relay-mcp --help
```

Эти команды без версии проверяют текущий стандартный канал, а не обязательно
конкретный prerelease. Для приёмки выбранного выпуска установите именно его три
архива из registry в изолированное окружение и сверьте установленные версии.
Пользовательская эксплуатация описана у приложений; этот документ не заменяет её.
Зелёный CI, готовый артефакт или один опубликованный пакет не подтверждают весь выпуск.

## Повтор и диагностика

- **Не пройден допуск PR для CI-выпуска.** Сверьте результат слитого PR с коммитом тега,
  окончательный head, успешный run/attempt ожидаемого `ci.yml`, его `pr-verification`,
  проверенную base и дерево слияния. Истёкшее или чужое свидетельство, другой head/base/tree,
  direct push, неуспешный или отменённый workflow блокируют CI-выпуск. Не запускайте общий набор тестов
  в release как fallback и не подменяйте свидетельство; до слияния обновите ветку PR
  и получите актуальную проверку. Старого зелёного статуса без свидетельства недостаточно.
- **Частичная публикация или неясный сетевой сбой.** npm-публикация не атомарна.
  Сначала прочитайте состояние registry, сохраните исходные `.tgz` и ведомость.
  В CI повторяйте только необходимый job **publish** с тем же `artifact_id` и байтами,
  не весь workflow и не pack. Publisher заново проверяет PR-допуск: более поздний
  неуспешный run/attempt или просроченное свидетельство остановят повтор даже после
  успешного metadata. Это не запускает тесты, build, pack или smoke заново.
  Если точный артефакт недоступен, восстановите сохранённый
  исходный smoke-проверенный bundle через `verify`/`restore` и используйте ручной
  fallback только при подтверждённом происхождении. Без исходного комплекта повтор
  останавливается. При повторе самостоятельной локальной публикации также используйте
  сохранённые проверенные архивы, не пересборку. Не запускайте публикации параллельно:
  группа CI `relay-npm-publish` не блокирует локальные процессы.
- **Integrity не совпала.** Остановитесь до новых записей. Повторно скачайте точный
  артефакт и проверьте его digest и ведомость; не редактируйте хеши ради прохождения
  проверки. Другие байты с уже опубликованным номером требуют новой версии.
- **Неизвестно происхождение архивов.** Имя файла, совпадение версии и свежая ведомость
  не доказывают QA. До первой публикации подготовьте комплект из выбранного чистого
  коммита и пройдите проверки. После частичной публикации не подменяйте утраченный
  комплект пересборкой: сначала установите происхождение сохранённых байтов и состояние
  registry; если это невозможно, остановите повтор и подготовьте новый выпуск.
- **Канал отличается или новее.** Скрипт не исправляет dist-tags автоматически
  и не откатывает канал. Выясните состояние выпуска; изменение канала — отдельная
  операция registry, после которой нужна повторная сверка всех пакетов.
- **Ошибка чтения registry после записи.** Она не доказывает отсутствие публикации.
  Не выбирайте новую версию и не пересобирайте архивы только из-за потерянного ответа.
- **Нет npm artifact ID, истёк срок или неверный commit/tag.** Не скачивайте все
  артефакты по имени и не меняйте SHA в ведомости. Найдите исходный комплект и checkout
  его коммита. Восстановление не должно подменять источник артефакта; оно также
  не восстанавливает утраченное свидетельство `pr-verification`.
- **OIDC/provenance не подтверждены.** Сверьте publisher каждого пакета, workflow,
  environment, права job, npm и repository в архиве. Не добавляйте токен как скрытый
  обход и не объявляйте происхождение подтверждённым только по успешной загрузке.
- **Падает упаковка или smoke.** Для локальной диагностики используйте адресный
  `package:check:*`. Установочную проверку готового bundle повторяйте через
  `verify`/`restore` и `package:smoke`, без пересборки. При исправлении исходников нужен
  новый комплект: для CI повторите проверку PR, для самостоятельного локального пути —
  полный preflight. Не публикуйте непроверенные архивы.
