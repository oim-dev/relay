# Справочник Relay CLI

CLI — основной интерфейс агента к памяти проекта. Агент и человек читают один
текстовый результат. Этот справочник описывает
зарегистрированные команды, ввод, ответы и ограничения, а не состав опубликованной
версии. Синтаксис установленного пакета уточняйте через `npx @oim-dev/relay-cli --help`.

Предметные правила принадлежат [domain](https://github.com/oim-dev/relay/blob/main/docs/domain/README.md),
покрытие — [матрице возможностей](https://github.com/oim-dev/relay/blob/main/docs/CAPABILITIES.md).
См. также [стиль вызовов](COMMAND_STYLE.md), [терминальное представление](TERMINAL.md)
и [разработку CLI](EXTENDING.md).

## Git-синхронизация

Если явная/локальная конфигурация не найдена, CLI подключает worktree ветки
`relay-data` в `~/.relay/{repo-name}-{hash}`. Он разделяет Git-хранилище и origin
исходного проекта, но имеет собственный индекс. `RELAY_HOME` задаёт корень первой установки.
Существующая ветка восстанавливается автоматически; если её нет, CLI предлагает init.
`init` создаёт orphan-ветку с базой, не меняя HEAD, индекс и рабочие файлы кода.
Origin и первый коммит кода не обязательны: после добавления или смены origin
синхронизируется та же база. Чужая база на новом origin не перезаписывается.
Явный `init --config ./data/config.json` сохраняет файловую инициализацию.
Подробности — [конфигурация](../../../packages/project-runtime/docs/CONFIGURATION.md#внешняя-git-база).

Отправка после записи выполняется короткоживущим worker без Server: debounce 2 секунды,
maxWait 15 секунд. Успех предметной команды означает локальное сохранение; origin
подтверждается отдельно. `SYNC_CONFLICT` запрещает обычные чтения и записи до решения.

### sync migrate

`npx @oim-dev/relay-cli sync migrate --from-config <path>` выполняется из исходного
Git-проекта и переносит прежнюю файловую или самостоятельную Git-базу в worktree.
Параметр выбирает исходный config. Сохраняются projectId, данные и существующая Git-история;
исходная база остаётся резервной копией. На время перехода остановите её писателей,
затем переключите Server на показанный config. Обычный CLI использует worktree;
явный `--config` по-прежнему позволяет выбрать сохранённую исходную копию.
Перенос не заменяет существующий worktree другой базы или чужую ветку origin.

### sync status

`npx @oim-dev/relay-cli sync status` показывает идентичность, каталог, последнюю
удалённую версию и проверку, очередь отправки, ошибку и ID конфликта. Без origin
сообщает о локальном режиме, не обещая удалённого сохранения. Работает при
блокировке. Отсутствие очереди не означает, что origin не изменился после проверки.

### sync now

`npx @oim-dev/relay-cli sync now` получает origin, проверяет объединение и отправляет
подготовленный снимок без ожидания debounce. Поздние локальные записи остаются в очереди.
Предметные команды не повторяются, force-push не используется.

### sync conflicts

`npx @oim-dev/relay-cli sync conflicts` показывает ID, причину, пути и полные версии
B/L/R конфликтующих файлов. Это диагностика дискового JSON, включая Markdown-кодек;
`$integrity` означает предметное нарушение и раскрывает снимки целиком.

### sync resolve

`npx @oim-dev/relay-cli sync resolve --if-conflict <id> --decisions-file <path|->`
принимает JSON-объект решений по относительным путям. Для каждого конфликтующего файла
задайте `{"take":"local"}`, `{"take":"remote"}` или `{"value":<полная JSON-запись>}`.
Остальные однозначные изменения обеих сторон сохраняются. `-` читает stdin; неизвестные
пути и неполный набор решений отклоняются. Исключение новой записи задаётся `value:null`;
у существовавшей в общей базе сущности должен сохраняться файл живой записи или надгробия.
Подготовленный набор проходит полную проверку Core, включая связи и резервы адресов.

`npx @oim-dev/relay-cli sync resolve --if-conflict <id> --take <local|remote>` явно
выбирает **полный снимок базы**, включая неконфликтующие изменения. Сначала изучите
материалы. ID берётся из текущего конфликта; изменение origin отклоняет прежнее решение
и обновляет материалы. Выбор проходит проверку Core и публикацию, затем снимается
блокировка. Неизвестная/устаревшая версия не исправляется автоматически. `--take` и
`--decisions-file` взаимоисключающие.

В текущем Git-проекте `sync` определяет базу автоматически: без настроенного HTTP
`--local` и `--config` не нужны, в том числе в подсказке `sync conflicts` после блокировки.
Явно переданные параметры подключения сохраняются в подсказках.
Семейство sync требует локальный доступ: настроенный HTTP URL без `--local` и выбор
через `--project` отклоняются. При настроенном HTTP нужен только `--local`;
прямой `--config` выбирает другую базу, например зарегистрированную в workspace.
Существующий обычный локальный конфиг не переключается молча на другую внешнюю базу.

## Вызов и подключение

```bash
npx skills add oim-dev/relay
npx @oim-dev/relay-cli init
npx @oim-dev/relay-cli project get
npx @oim-dev/relay-cli board list
```

Установка скилла подготавливает агентский сценарий, но не является runtime-зависимостью
CLI. Полный маршрут — [первый запуск](https://github.com/oim-dev/relay/blob/main/docs/guides/GETTING_STARTED.md).

Синтаксис: `npx @oim-dev/relay-cli [глобальные параметры] [проект] <команда> [аргументы]`.
`<...>` — обязательное значение, `[...]` — необязательное, `<refs...>` — несколько
отдельных аргументов. Примеры рассчитаны на shell с POSIX-кавычками; значения ключей,
ID, ревизий и версий заменяйте фактически прочитанными. Группа без подкоманды
показывает help. Help и версия не открывают проект и не требуют данных.
`-h` и `--help` равнозначны на каждом уровне. Обязательные флаги в справке отмечены
«обязательно»; условные требования (например, текст или файл) объяснены у действия.

| Глобальный параметр  | Значение                                                        |
| -------------------- | --------------------------------------------------------------- |
| `-h, --help`         | Справка выбранной команды                                       |
| `-V, --version`      | Версия CLI, не версия данных                                    |
| `--config <path>`    | Путь к `.relay/config.json` или `relay.workspace.json`          |
| `--project <name>`   | Проект; альтернатива позиционному префиксу, не вместе с ним     |
| `--server-url <url>` | Явное HTTP-подключение                                          |
| `--local`            | Прямой Core; не fallback после HTTP-ошибки и не режим workspace |
| `--actor <id>`       | Автор предметной записи; приоритет над `RELAY_ACTOR`            |
| `--format <format>`  | `text` по умолчанию; `json` — только служебный режим ниже       |

**Формат работы агента — только читаемый текст.** Все предметные команды поддерживают
`--format json` исключительно для отладки CLI или передачи данных в скрипты.
Агенту запрещено переключаться на JSON при обычной работе через CLI, в том числе
ради удобства собственного разбора: пользователь должен видеть читаемые команды
и результаты. В runtime-справке этот режим объясняется один раз, в корневом `--help`;
он скрыт из повторяемых списков параметров и отсутствует в примерах действий.
Машинные поля ниже описывают технический контракт для отладки и скриптов, а не
рекомендуемый способ агентской работы. Help и версия всегда остаются текстовыми.

`output.format` и `output.maxBytes` из конфигурации не управляют CLI. Параметры
`--color` и `--max-bytes` удалены. Текст бесцветный, без ANSI-оформления,
независимо от TTY, NO_COLOR и FORCE_COLOR; ширина и структура Markdown сохраняются.
Подробнее — [TERMINAL](TERMINAL.md).

Конфиг: `--config` → `RELAY_CONFIG` → поиск вверх от cwd. В одном каталоге workspace
имеет приоритет над `.relay/config.json`. URL: `--server-url` → `RELAY_SERVER_URL` →
настройки сервера. Без URL обычный локальный проект использует Core. Явный URL
допускает работу без локального конфига. Workspace требует сервер и явный проект
для предметных команд; команды реестра, наоборот, не принимают выбор одного проекта.

```bash
npx @oim-dev/relay-cli frontend task list
npx @oim-dev/relay-cli task get PRODUCT-1 \
  --server-url http://127.0.0.1:4700 \
  --project frontend
npx @oim-dev/relay-cli config get \
  --local \
  --config /work/project/.relay/config.json
```

HTTP-ошибка не разрешает переключаться на локальные данные. Подробности подключения —
[project-runtime](https://github.com/oim-dev/relay/blob/main/packages/project-runtime/docs/CONFIGURATION.md).

## Ввод, запись и восстановление

Перед изменением прочитайте `get` и ревизию. Update изменяет только переданные поля;
пропуск, пустая строка, false и явная очистка различаются. Набор целей или состава
при передаче заменяется целиком, если команда не названа add/remove. Название —
одна строка, summary — обычный многострочный текст, description/body/goal/result — Markdown.

Полное содержание структурируйте разделами, списками и шагами, достаточно подробно
для исполнения и проверки без исходного чата. Аннотация или заголовок с общей фразой
не заменяют требования. Для фичи раскройте поведение и правила, для сценария — путь,
условия и ошибки, для FI/SI — обязательства конкретного приложения, для задачи —
конкретную работу, границы и проверку. Неизвестное уточняйте, не выдумывайте требования.
Перед первым заполнением прочитайте [правила содержания и примеры](https://github.com/oim-dev/relay/blob/main/docs/guides/CONTENT.md).
После записи перечитайте полный текст через `get` и оцените его достаточность.
CLI принимает и черновые записи: успешная запись не подтверждает полноту требований.
Примеры help учебные; их правила и адреса заменяются данными своего проекта.

**Текстовая пара T(field)** в описаниях ниже означает два конкретных флага:
`--field <text>` и `--field-file <path>`. Путь `-` читает stdin. Например,
T(description) — `--description`/`--description-file`, T(expected-result) —
`--expected-result`/`--expected-result-file`. Это не универсальный флаг `--field`.
Пары существуют только у явно перечисленных полей. Нельзя передать оба источника
одного поля или читать stdin для двух полей. Файл читается как UTF-8; ввод проверяется
до мутации. Лимит чтения общего текстового ввода — 128 МиБ; предметные и транспортные
лимиты могут быть меньше. Пустые строки и значимые отступы не нормализуются.

| Обозначение              | Зарегистрированная пара флагов                                          |
| ------------------------ | ----------------------------------------------------------------------- |
| T(name)                  | `--name <text>`, `--name-file <path>` — только project update           |
| T(summary)               | `--summary <text>`, `--summary-file <path>`                             |
| T(description)           | `--description <text>`, `--description-file <path>`                     |
| T(body)                  | `--body <text>`, `--body-file <path>`                                   |
| T(goal)                  | `--goal <text>`, `--goal-file <path>`                                   |
| T(rationale)             | `--rationale <text>`, `--rationale-file <path>`                         |
| T(boundaries)            | `--boundaries <text>`, `--boundaries-file <path>`                       |
| T(expected-result)       | `--expected-result <text>`, `--expected-result-file <path>`             |
| T(result)                | `--result <text>`, `--result-file <path>`                               |
| T(outcome)               | `--outcome <text>`, `--outcome-file <path>`                             |
| T(completion-conditions) | `--completion-conditions <text>`, `--completion-conditions-file <path>` |
| T(reason)                | `--reason <text>`, `--reason-file <path>`                               |

```bash
npx @oim-dev/relay-cli document create \
  --actor agent \
  --name 'Правила проверки' \
  --document-kind rules \
  --body '## Проверка

1. Открыть карточку.
2. Сравнить сохранённое содержание.'
npx @oim-dev/relay-cli document get DOC-1
npx @oim-dev/relay-cli document update DOC-1 \
  --actor agent \
  --if-revision 1 \
  --body-file ./rules.md
npx @oim-dev/relay-cli task update PRODUCT-1 \
  --actor agent \
  --if-revision 2 \
  --description-file - < ./task.md
```

Числа ревизий здесь иллюстративны. После записи перечитайте полное содержание
и отношения в том же проекте. Не считайте квитанцию проверкой внешнего результата.

**Запись R** ниже означает обязательный `--if-revision <n>` и необязательный
`--request-id <id>`, а также автора через глобальный `--actor`/`RELAY_ACTOR`.
Ревизия относится к изменяемому владельцу: у критериев — задача, у этапов — план,
у разделов — проект, у participation — состав приложения. **Создание C** требует
автора и допускает `--request-id`, но не требует ревизию. У диагностического графа
вместо ревизии требуется `--if-version <version>`.
Ревизия — целое число: task/criterion/plan/release требуют минимум 1;
project и каталог продуктовых сущностей допускают 0 (например, незаполненный паспорт
или ещё не созданный состав приложения). Это не разрешение угадывать ревизию.

`requestId` — только корреляция, по умолчанию UUID; не ключ дедупликации и не
сохранённая квитанция. Скрытых повторов нет. При потере ответа сначала перечитайте
запись/обсуждение/связи. При конфликте согласуйте изменения, не подставляйте свежую
ревизию к старому телу. Правила — [сохранение](https://github.com/oim-dev/relay/blob/main/docs/domain/STORAGE.md).

## Ответы, ошибки и страницы

Команда возвращает карточку, страницу, квитанцию, прогресс или ошибку. Штатные
результаты и ошибки идут в stdout; stderr штатного вызова чист. Успех — exit 0,
ошибка — ненулевой код, синтаксическая ошибка обычно 2. Help и версия всегда текстовые.
Закрытый получателем pipe (`EPIPE`) — штатный exit 0. В text пользовательские
управляющие последовательности обезвреживаются; это не побайтовая копия поля.
JSON не содержит терминального оформления и сохраняет предметные поля.

Параметры, примеры и переходы к связанным командам находятся в `--help` команды
и её группы. Обычный text не повторяет меню действий, get первой строки или совет
перечитать запись. Условные подсказки остаются для продолжения неполной выборки,
восстановления после ошибки и подтверждения предпросмотра по его версии. Ключи,
ревизии, run.id, счётчики и признаки неполноты сохраняются. Пользовательский Markdown,
включая поле checkpoint.nextStep, не считается служебной подсказкой.

Пример формы пустой страницы, не полный DTO конкретного backend:

```json
{
  "ok": true,
  "data": { "items": [] },
  "meta": {
    "page": {
      "count": 0,
      "total": 0,
      "limit": 20,
      "nextCursor": null,
      "nextCommand": null,
      "consistency": "snapshot"
    }
  }
}
```

Ошибка имеет форму:

```json
{
  "ok": false,
  "error": { "code": "ACTOR_REQUIRED", "message": "Для записи укажите --actor или RELAY_ACTOR" }
}
```

У квитанции сущности `data` содержит адрес/ключ, ревизию, действие и requestId;
квитанции других семейств сохраняют DTO своей операции. Их нельзя получить позже
командой истории. Явно выбранный проект передаётся в `meta.project`.

### Правила продолжения

**Страница P** ниже означает `--limit <count>` (1–100) и `--cursor <cursor>`.
Размер берётся из `output.defaultLimit`, в том числе для ленты комментариев;
реестр workspace по умолчанию использует 20. Публичных offset/параметров версии страницы нет.
Глобальный `--version` показывает версию пакета, а не продолжает список.

`Result.page` выводится единым footer в text и как `meta.page` в JSON:
`count`, `total?`, `limit`, `nextCursor`, `nextCommand`, `consistency`.
Отсутствующий total не равен нулю. `null` в nextCursor/nextCommand означает конец.
Пустая страница с курсором имеет продолжение. Копируйте nextCommand целиком:
она сохраняет конфиг, проект, сервер/local, команду, ref и фильтры; жёстких переносов нет.
Курсор непрозрачен и не переносится на другой запрос или подключение.
Публичный CLI-курсор берите только из `meta.page.nextCursor`. Он хранит параметры
продолжения, включая фильтры и limit, и привязан к контексту и ref. Поэтому
`meta.page.nextCommand` может не повторять `--limit` и фильтры: wrapper восстанавливает
их при продолжении. Сохранять выборку не означает повторять все флаги вручную.

`snapshot` для offset-backend — **проверка неизменности текущего состояния**, не
доступ к сохранённому историческому снимку. Исходная версия не заменяется свежей;
конфликт требует начать чтение заново без курсора. `live` означает, что данные
могут меняться между страницами; наличие cursor не создаёт гарантии snapshot.
Для workspace Server проверяет отпечаток заново прочитанного полного каталога,
но передаёт только страницу; исторический снимок не хранится.
У ленты комментариев `meta.page.nextCursor` — wrapper,
который хранит исходный native token backend вместе с фильтрами, limit и контекстом/ref.
`data.nextCursor` сохранён как сырой backend token для совместимости DTO и **не
принимается CLI напрямую**. Не передавайте его в `--cursor`.

В progress один limit применяется к каждому вложенному списку, count/total — сумма
элементов списков, а не число уникальных сущностей. У inspect graph list limit
отдельно ограничивает узлы и рёбра; `meta.paginationUnit` — `nodes-and-edges`,
`meta.limitPerCollection` уточняет размер. Итоги готовности относятся ко всему составу.

CLI не обрезает ответ по байтовому бюджету. Это не отменяет лимиты Core/HTTP/MCP
или ввода. Полный текст `get` не усекается; большие коллекции читаются отдельными
списками. Полный графовый context возвращает компоненту с `complete:true` либо ошибку.

| Ситуация                                                | Действие                                                                     |
| ------------------------------------------------------- | ---------------------------------------------------------------------------- |
| CONFIG_NOT_FOUND / PROJECT_REQUIRED / REGISTRY_REQUIRED | Проверить конфиг, режим и проект, не создавать новую базу вместо неизвестной |
| ACTOR_REQUIRED                                          | Указать автора записи                                                        |
| INVALID_ARGUMENT / CONFLICTING_OPTIONS / INVALID_JSON   | Исправить параметры и источники ввода по help команды                        |
| INVALID_CURSOR / VERSION_CONFLICT / SNAPSHOT_CONFLICT   | Проверить контекст; начать список заново, не смешивая страницы               |
| Конфликт ревизии                                        | Перечитать запись и согласовать изменение                                    |
| NOT_FOUND                                               | Проверить проект и адрес через inspect resolve                               |
| LOCAL_REQUIRED / WORKSPACE_REQUIRES_SERVER              | Выбрать допустимое подключение, не обходить HTTP локальными файлами          |
| Ошибка размера нижнего слоя                             | Уменьшить выборку либо читать адресно; CLI-флага увеличения бюджета нет      |

Если конфиг не найден, проверьте cwd, `--config`/`RELAY_CONFIG` либо подключитесь
через `--server-url`; для workspace выберите проект. Отсутствующий явный путь
конфигурации (`NOT_FOUND`) требует исправить путь, а не искать ключ сущности.
Для remote-only уберите неверный явный путь. `init` предназначен только для
заведомо нового проекта, не для восстановления неизвестной существующей базы.

Для `GRAPH_CHANGED` CLI предлагает исполнимое `inspect graph list` с тем же
подключением; это чтение, не повтор мутации со свежей версией. При
`STORAGE_INDEX_STALE`/`STORAGE_INDEX_CORRUPT` требуется явный локальный
`storage reindex` после остановки писателей и резерва. Неверный JSON записи и ошибки
схемы требуют сначала восстановить содержимое; reindex его не исправляет.
`RELATION_MANAGED` и `MANAGED_RELATIONS_MISMATCH` направляют к предметному владельцу
(если Core вернул адрес) и отдельному явному `storage reconcile-relations`.
Через HTTP обслуживание не выполняется: оператор выбирает реальную конфигурацию
проекта на стороне Server. Клиентские подсказки чтения сохраняют сервер и проект,
не выдумывают локальный путь и не переключаются на local.

## История агентской работы

`session` — ветка поручения, `run` — отдельное участие агента, `checkpoint` —
неизменяемое намерение или материал его исполнения. Это не журнал команд, не снимки
кода и не online-мониторинг. Незавершённые состояния: pending/open/paused; закрытые:
completed/cancelled. Предметные правила — [история работы](https://github.com/oim-dev/relay/blob/main/docs/domain/WORK_HISTORY.md).

Новые ключи `S-token`, `RUN-token`, `CP-token` содержат случайный идентификатор, не
общий счётчик. В примерах заменяйте token и run-id фактически прочитанными значениями.
В text ключи сохраняются целиком на одной физической строке, отдельно от переносимого
названия; это относится также к дереву, хронологии, контексту и квитанциям.
Также принимаются ID и `work-session:ID` / `work-checkpoint:ID`. `--run <id>` всегда
принимает **run.id**, не публичный RUN-ключ. `--if-revision` относится к **ветке**,
включая fork и операции над checkpoint. CLI не перечитывает её перед мутацией.

Все мутации требуют автора и допускают `--request-id` (C/R выше). Только start
не требует ревизии; остальные требуют положительную исходную ревизию ветки.
JSON мутации: `{session, run, checkpoint, childSession}`. У fork `session` —
обновлённый родитель; ребёнок находится в `childSession`. Run в ответе может быть
завершённым: текущее владение проверяйте по `session.currentRunId`. Скрытых повторов нет.
При конфликте `checkpoint open` подсказка читает владеющую ветку, а не checkpoint
с адресом S-token. Неизвестная ветка ведёт к `session list`, неизвестная точка — к
`session history --kind checkpoint`; эти подсказки только читают и сохраняют подключение.

**Подключение участия** у start/attach/resume/takeover: `--client <name>`,
`--source-session-id <id>`, T(reason), `--user-name <name>`, `--user-email <email>`.
Агент `--actor` и человек, от имени которого он действует, сохраняются отдельно.
Приоритет: явная пара user → пара `RELAY_USER_NAME`/`RELAY_USER_EMAIL` → effective
`git config user.name/user.email` в исходном cwd CLI. Если задан один компонент
explicit/env, второй остаётся null; источники пары не смешиваются. Вне репозитория
глобальный Git user не используется. Attach без explicit/env оставляет Core
наследование пользователя участия, создавшего ребёнка; Git user его не подменяет.

Git-ветка и HEAD снимаются с рабочей копии **клиента**, в том числе при HTTP.
Detached HEAD: branch=null; unborn: commit=null. Недоступность Git не блокирует участие,
Git config не изменяется. Метаданные снимаются только при новом участии, не при чтениях,
help или каждой записи. Это заявленная атрибуция, не аутентификация. Передавайте
субагенту пользовательский контекст родителя вместе с проектом и pending-веткой,
но не родительский run для записи.

**Содержание checkpoint** у open/save/complete/cancel: обязательны `--title <text>`
и непустой T(body). Допустимы T(summary), T(done), T(remaining), T(next-step),
T(checks), `--references <refs...>`. Дополнительные текстовые пары:
`--done`/`--done-file`, `--remaining`/`--remaining-file`,
`--next-step`/`--next-step-file`, `--checks`/`--checks-file`.
Title/summary — краткие; body/done/remaining/nextStep/checks — полноценный Markdown.
Пустые строки, отступы и код сохраняются. Summary не создаётся из обрезанного body.
Ссылки сохраняют подписи целей, не снимки содержания.

### session list

`npx @oim-dev/relay-cli session list` — страница P обзорных веток.
Фильтры: `--unfinished [true|false]` (при флаге без значения true), `--status <status>`,
`--parent <reference>` (прямые дети; `null` — корни), `--actor-filter <actor>`
(автор хотя бы одного участия), `--q <text>` (ключ, название, поручение).
Фильтры применяются совместно; глобальный `--actor` не фильтр. Порядок — updatedAt
по убыванию, затем ID. Полные `projectTotals` относятся ко всему проекту независимо
от фильтров, `total` — к выборке. У каждой ветки — counts, последнее участие и принятие.
Полное поручение и итог читайте через get.

### session get

`npx @oim-dev/relay-cli session get S-token` — полные поручение и итог, состояние,
ревизия, currentRun, последнее участие даже после закрытия и полные счётчики ветки.
Завершённый ребёнок с acceptance=null явно ожидает принятия родителем. Ветки и
участия считаются отдельно; одинаковое имя или модель не означает одного агента.
Различия intents/context/tree/history и способы перехода объясняет `session get --help`.

### session tree

`npx @oim-dev/relay-cli session tree S-token` — страница P поддерева, включая корень.
Глубина относительна выбранному корню; фактический родитель вне страницы/поддерева
показан явно. Totals всего поддерева: ветки, незавершённые ветки, участия, точки,
открытые намерения. Обзоры узлов содержат counts/latestRun/acceptance без N+1-чтений.

### session intents

`npx @oim-dev/relay-cli session intents S-token` — страница P всех открытых намерений,
включая старые, без выгрузки всей истории. `--include-children [true|false]` включает
всех потомков; по умолчанию только сама ветка. Text показывает полный заголовок,
сохранённую summary и переход к checkpoint get, не подменяет body аннотацией.
JSON сохраняет полные точки выбранной страницы. Порядок — от старых к новым.

### session history

`npx @oim-dev/relay-cli session history [reference]` — страница P хронологии;
без ref — весь проект. `--include-children [true|false]` включает потомков,
`--order <asc|desc>` выбирает направление (по умолчанию desc), `--kind <kind>` — тип:
session-created/session-forked/session-closed/run-started/run-ended/checkpoint.
Text — обзор событий с автором/run, где они даны DTO, временем с часовым поясом,
веткой и адресом checkpoint. Неизвестный автор не угадывается. JSON сохраняет полные
записи страницы. Lifecycle выводится сервером из сохранённых записей; карточка ветки
в событии — текущая, не историческая ревизия. Полные материалы ветки — через context.
В text сведения об одном участии раскрываются один раз на страницу, события ссылаются
на его run.id. Номер события и время сохраняются; даты не повторяются в карточке участия,
если соответствующее начало или окончание уже показано в хронологии.

### session context

`npx @oim-dev/relay-cli session context S-token` — полная карточка и страница P полных
последних материалов самой ветки, без потомков, desc. Text явно обозначает область
и число событий страницы/истории. Продолжение — через context с тем же ref/cursor,
не через history; для всех незакрытых намерений используйте intents.
Поручение и итог выбранной ветки выводятся один раз в карточке, события создания
и закрытия ссылаются на неё. Совпадающий материал завершения её участия ссылается
на тот же итог. Причина подключения находится у начала участия, материал окончания —
у окончания; если соответствующее событие вне страницы, полученный материал остаётся
в сведениях об участии. Markdown разных checkpoints не объединяется, даже если совпадает.
Каждая страница остаётся самостоятельной: содержит полную карточку ветки. JSON сохраняет
прежний полный состав, включая вложенные карточки lifecycle-событий.

### session start

Создание C: обязательный `--title <text>`, T(description), параметры подключения участия.
Создаёт open-корень и первый run атомарно; возвращает `run.id` для дальнейшего `--run`.

```bash
npx @oim-dev/relay-cli session start \
  --title 'Проверить контракт API' \
  --description '## Поручение

Проверить успешные ответы и ошибки изменения данных.

## Проверка

Сопоставить сохранённое состояние с ответами API.' \
  --actor agent
```

### session fork

`npx @oim-dev/relay-cli session fork CP-token` — R, обязательные `--run`, `--title`,
допустим T(description). Ref — **открытый intent**, не session. Ревизия и run
принадлежат его родительской ветке. Создаёт pending-ребёнка без run до запуска
субагента; передайте childSession исполнителю для attach. Дополнительного чтения
для преобразования session ref в intent нет.

### session attach

`npx @oim-dev/relay-cli session attach S-token` — R pending-ребёнка и параметры
подключения. Создаёт первый run ребёнка. Родительский `--run` не принимается.
Без explicit/env пользователя Core наследует атрибуцию создателя поручения.

### session pause

`npx @oim-dev/relay-cli session pause S-token` — R, обязательные `--run` и непустой
T(reason). Завершает участие с paused и приостанавливает ветку; intent остаются открытыми.

### session resume

`npx @oim-dev/relay-cli session resume S-token` — R paused-ветки и параметры
подключения. Создаёт новый run с predecessorRunId; используйте новый `run.id`.

### session takeover

`npx @oim-dev/relay-cli session takeover S-token` — R open-ветки и параметры
подключения; непустой T(reason) обязателен. Прежний run заканчивается с transferred,
новый становится текущим. Старый run не вправе писать даже со свежей ревизией.
Дети автоматически не передаются; внешние процессы не останавливаются.

### session complete

`npx @oim-dev/relay-cli session complete S-token` — R, обязательные `--run` и непустой
T(result). Core проверяет закрытие собственных intent/детей и явное принятие результатов.
Перечитайте get: квитанция не подтверждает фактического внешнего выполнения.

### session cancel

`npx @oim-dev/relay-cli session cancel S-token` — R и обязательный непустой T(result)
как причина отмены. Для open обязателен `--run`; у pending/paused текущего run нет.
Отмена не принимает результаты детей автоматически; открытые intent/дети блокируют её.

### checkpoint get

`npx @oim-dev/relay-cli checkpoint get CP-token` — полная неизменяемая точка любого
типа: все Markdown-поля, автор/run, время, ветка, исходный intent, принятие детей
и подписи ссылок. Состояние intent определяется последующими точками, не изменением
этой записи. Адрес ветки остаётся в карточке; её чтение и хронология объяснены в help.

### checkpoint open

`npx @oim-dev/relay-cli checkpoint open S-token` — R ветки, обязательный `--run`
и содержание checkpoint. Открывает новый intent; его адрес используется для fork/save/complete/cancel.

### checkpoint save

`npx @oim-dev/relay-cli checkpoint save CP-token` — R владеющей ветки, `--run` и
содержание checkpoint. Ref — исходный intent, не последняя progress-точка. Добавляет
progress без закрытия. `--accept <ids...>` явно принимает результаты завершённых
прямых детей этого intent: постоянные **session.id**, не S-ключи. Отсутствующий/пустой
набор ничего не принимает; ранее сохранённое принятие остаётся в истории.

### checkpoint complete

`npx @oim-dev/relay-cli checkpoint complete CP-token` — входы как у save, включая
`--accept <ids...>`. Создаёт result и закрывает intent. Завершение ребёнка само по себе
не принятие: сначала прочитайте его полный результат и сохраните принятие явно.

### checkpoint cancel

`npx @oim-dev/relay-cli checkpoint cancel CP-token` — входы как у save, включая
`--accept <ids...>`. Создаёт cancel с полным материалом причины, исходный intent
не переписывается. Незавершённые дети и непринятые завершённые результаты блокируют закрытие.

## Проект и workspace

### init

`npx @oim-dev/relay-cli init [--storage <path>]` — создать локальные конфиг и хранилище.
`--storage` по умолчанию `tasks` — совместимая привязка конфигурации, не отдельная
база задач. `--config` задаёт место конфигурации. Существующие данные не заменяются.
В Git-проекте без найденного/явного конфига создаётся внешний worktree ветки `relay-data`;
при наличии origin база публикуется. Существующая ветка подключается. Этот режим описан в
[Git-синхронизации](#git-синхронизация). Остальные правила ниже относятся к файловому init.
При URL из `--server-url`, `RELAY_SERVER_URL` или `server.url` найденного local/workspace
конфига требуется `--local`: без него `LOCAL_ONLY` до создания файлов. Сам init
не обращается к серверу. Один лишь `server.port` не включает этот guard. Автор не нужен.
Ответ JSON сохраняет `configPath`, `storageDir`; text показывает созданные пути.
Проверка через `config get` и подготовка паспорта описаны в `init --help`.
Затем по необходимости прочитайте `board list`.

В файловом режиме без явного config и выбора регистрации создаётся **новый локальный проект в cwd**,
даже внутри другого проекта или workspace; родительская база не заменяется.
`--project KEY` (или префикс) с workspace выбирает локальный путь этой регистрации.
Init не добавляет регистрацию автоматически. Подсказки workspace сохраняют
`--local --config` фактически созданной базы, а не открывают её через реестр/сервер.

Имя **нового файла** конфигурации содержит только `[A-Za-z0-9_.-]+`, кроме `.` и `..`,
служебных имён хранения (например, `storage.json`) и `relay.workspace.json`.
Расширение `.json` необязательно. Unicode, пробелы и кавычки в **каталоге** разрешены;
путь передавайте одним аргументом. Недопустимое имя даёт `INVALID_ARGUMENT` до
создания каталогов. Это ограничение нового init, не запрет чтения существующего
Unicode-конфига по явному пути.

Повторный `init` даёт `ALREADY_INITIALIZED` и ничего не заменяет. В JSON `details`
сохраняет `configPath`, `dataRoot`, причину `config`/`storage`/`pending`/`incomplete`
и относительные `paths`. При существующем конфиге text предлагает его `config get`.
При маркере хранения, незавершённой записи или остатках неполной базы показываются
обнаруженные пути и адресный `storage status`, не повтор init или автоматический перенос.
Init не выполняет recovery WAL. Если конфиг и маркеры утрачены, диагностика тоже
может отказать: сохраните копию остатков и восстановите отсутствующие файлы из
проверенной копии, а не создавайте поверх них новый проект.
Выбор источника для init читает только метаданные конфигурации, без открытия базы
и проектных проекций: WAL не исполняется даже при существующем config до отказа
`LOCAL_ONLY` или `ALREADY_INITIALIZED`. Обычное чтение проекта сохраняет штатный recovery.

### project get

`npx @oim-dev/relay-cli project get` — карточка единственного PROJECT с именем,
slug, публичным ключом, ID и ревизией. Собственных флагов и позиционного ref нет,
в том числе после смены ключа. Это не список регистраций workspace.
Text показывает число разделов; `document section list` читает полный каталог
с порядком страницами. JSON сохраняет всю карточку и массив разделов.
Документы, прикреплённые к проекту, читаются через `document list --target PROJECT`,
полный контекст отношений — через `inspect graph context PROJECT`. Старый ключ
PROJECT после переименования остаётся алиасом.

### project update

```bash
npx @oim-dev/relay-cli project update \
  --actor human \
  --name 'Мой проект' \
  --if-revision 1
```

Обязательны автор, `--if-revision` из `project get` и хотя бы одно изменение:
T(name) (`--name` либо `--name-file`) и/или `--slug <slug>`.
Slug — адресный идентификатор, не текстовое содержание: 2–64 строчные латинские
буквы/цифры с одиночными дефисами между частями; `--slug-file` не предусмотрен.
Имя нормализуется контрактом проекта (краевые пробелы убираются), slug не обрезается.

```bash
npx @oim-dev/relay-cli project update \
  --actor human \
  --slug my-project \
  --if-revision 1
```

Без `--slug` сохраняется прежний путь изменения только имени: ответ — квитанция
сущности `EntitySaved`, допустим `--request-id`. С `--slug` ответ JSON `data` —
настройки `ProjectSettings`: `name`, `slug`, `revision`, `documentSections` при
наличии, не квитанция сущности. `--request-id` в этом режиме отклоняется:
операция настроек его не принимает. Если имя не передано, CLI один раз читает
настройки и сохраняет прежнее имя, но отправляет исходную пользовательскую ревизию,
не свежую из чтения. Переданное имя и slug сохраняются одной операцией.
Разделы, публичный ключ, ID и регистрация workspace сохраняются; прежний slug
не становится алиасом. Description не поддерживается. Проверьте `project get`;
после конфликта или потери ответа запись автоматически не повторяется.
Совпадающая полная пара имени и slug возвращает текущие настройки без новой записи,
даже если передана старая ревизия; это существующий no-op Core, не повтор мутации.
Если HTTP-подключение было выбрано старым slug, для следующего чтения используйте
постоянный ID базы. Для проверки после потери ответа также используйте ID
из исходного `project get` либо неизменный ключ регистрации workspace.

### project rename

```bash
npx @oim-dev/relay-cli project rename PROJECT-TEAM \
  --actor human \
  --if-revision 1
```

Запись R. `<key>` — новый публичный ключ, не имя и не slug. ID, имя, slug,

коллизия отклоняется. Ответ — `EntitySaved`. Перечитайте singleton через

### config get

`npx @oim-dev/relay-cli config get` — чтение конфигурации без собственных флагов.
JSON `data` — полный Config без изменения его полей: `data.mode=local` описывает
проектный конфиг, а не транспорт клиента. `meta.configPath` и `meta.storagePath` —
фактические пути проекта (при HTTP — на сервере).

`meta.connection` описывает фактически установленное подключение:

- `transport`: `local` или `http`;
- `serverUrl` и `serverUrlSource`: только при HTTP, нормализованный origin и его
  источник `flag` (`--server-url`), `env` (`RELAY_SERVER_URL`) или `config`
  (`server.url`, для workspace также адрес из `server.port`);
- `serverUrlConfigField`: только для URL из конфига, `server.url` или `server.port`;
- `projectId`: подтверждённый Backend ID, если доступен; не ключ регистрации;
- `clientConfig`: только при наличии клиентского конфига — абсолютный `path`,
  `mode: local|workspace` и `source: flag|env|discovered` для `--config`,
  `RELAY_CONFIG` или поиска вверх от cwd. Это не серверный реестр.

Выбор URL выполняется до локального селектора: одинаковые HTTP origin и `--project`
действуют одинаково для флага, env и конфига, включая cwd другого local-проекта.
Повреждённый найденный конфиг не игнорируется; `--local` не разрешён для workspace,
а ошибка HTTP не включает local fallback.
Подключение и подсказки используют один разрешённый источник; конфиг не перечитывается
повторно ради представления. Чтение не создаёт legacy-каталоги; актуальная PROJECT-проекция,
проверка совместимости и штатное восстановление обычного WAL Core сохраняются.
Совместимые статусы не меняют фиксированные колонки досок. Это не редактор настроек.
Выдача всегда полная, включая все совместимые статусы; отдельного краткого view нет.

### workspace project init

`npx @oim-dev/relay-cli workspace project init` — создать локальный пустой
relay.workspace.json; `--config`/RELAY_CONFIG выбирает путь. Не требует автора,
не принимает `--project` и проектный префикс. Ответ — результат создания реестра.

### workspace project list

`npx @oim-dev/relay-cli workspace project list` — страница P зарегистрированных
проектов. Подключение задают `--server-url`, `RELAY_SERVER_URL` или конфигурация;
локальная копия серверного реестра не обязательна. Читается workspace- или local-сервер,
без `--local` и выбранного проекта.
CLI получает только серверную страницу; Server проверяет отпечаток всего каталога,
включая регистрации, доступность, идентичность и отображаемые сведения.
Изменение между страницами даёт `VERSION_CONFLICT` (exit 4): начните list без cursor.
`meta.paginationSource` — `server-catalog-fingerprint`. JSON `data` сохраняет прежнюю
форму `mode`, серверный `configPath`, `defaultProject`, `projects` текущей страницы;
total и продолжение находятся в `meta.page`. Клиентский `meta.configPath` есть только
при фактическом наличии клиентского конфига, в remote-only он не выдумывается.
Cursor сохраняет исходную версию, limit и подключение; неизвестные фильтры курсора
отклоняются. Проверка доступности всё ещё охватывает полный каталог: это не
исторический снимок, не универсальная проверка local-проекта и не O(limit) чтения баз.

Перед страницей выполняется лёгкий discovery `/server/capabilities` без открытия баз.
Нужна `relay-project-catalog-v1`; отсутствие capability или 404 discovery даёт
`SERVER_INCOMPATIBLE` (exit 5) до запроса страницы. Обновите и перезапустите Server:
скрытого чтения полного каталога или local fallback нет. Собственной опции projection
у list нет.
Text различает режим Server, его реестр/конфиг и конфиг клиента, показывает defaultProject,
доступность и причины отказа. У недоступной регистрации ID не подтверждает идентичность
базы. Для выбранной доступной строки перейдите в `config get --project <ключ>` с тем же
сервером. Пустой каталог не требует `init` новой базы на клиенте.

```bash
npx @oim-dev/relay-cli workspace project list \
  --server-url http://127.0.0.1:4700
```

### workspace project add

`npx @oim-dev/relay-cli workspace project add alpha ./alpha` — зарегистрировать
инициализированный проект через workspace-сервер. `<name>` — имя регистрации, `[path]` —
путь на стороне Server относительно **серверного** workspace-конфига.
`--project-config <path>` — конфиг относительно path, а без path — серверного реестра;
`--replace` явно разрешает замену регистрации. Автор и ревизия не нужны.
Подключение — как у list, без обязательного клиентского реестра. Не создаёт и не
переносит данные. Ответ — квитанция регистрации; проверьте list.

`--projection <mode>` принимает full/compact. По умолчанию text использует компактный
маршрут, JSON — прежний полный `ServerContextResponse`. Явный compact выбирает
`data: {action: "register", key, configPath, entry}` без соседних регистраций;
entry содержит сохранённые path/config и **не подтверждает доступность базы**.
Явный full в любом формате выбирает прежний маршрут с полным каталогом в ответе,
а не меняет автоматически режим после ошибки. Compact требует `relay-project-catalog-v1`
из discovery до мутации. Затем перечитайте list и проверьте подключение к выбранному проекту.

### workspace project remove

`npx @oim-dev/relay-cli workspace project remove alpha` — удалить только регистрацию
через workspace-сервер. Данные остаются; автор и ревизия не нужны.
`--projection <mode>` принимает full/compact с теми же defaults, что add:
text — compact, JSON — прежний полный ответ. Compact возвращает
`data: {action: "unregister", key, configPath, removed}`; true означает удаление
этой операцией, false — регистрация уже отсутствовала. Full сохраняет старый маршрут.
Capability проверяется до компактной мутации; автоматического переключения на full нет.
Как add/list, не принимает выбор отдельного проекта или `--local`; подключение можно
задать URL без клиентского реестра. Неверный успешный ответ сервера даёт
`INVALID_SERVER_RESPONSE`, а не пустой каталог. После него или потери ответа на
add/remove сначала перечитайте list: запись могла завершиться, скрытого повтора нет.

## Обзор проекта

### overview

```bash
npx @oim-dev/relay-cli overview
npx @oim-dev/relay-cli overview \
  --view full \
  --limit 20
npx @oim-dev/relay-cli overview \
  --metric review-obligations-met
npx @oim-dev/relay-cli overview \
  --metric blocker-impact \
  --limit 10
npx @oim-dev/relay-cli overview \
  --metric blocker-affected \
  --blocker PRODUCT-1
```

Самостоятельный обзор выбранного проекта одним согласованным чтением — первая команда
при знакомстве с проектом. Смысл показателей и версий — в
[контракте продукта](../../../docs/domain/PRODUCT.md#обзор-состояния-продукта).
Команда только читает; она не предлагает начать или завершить задачу.

В workspace требуется явный выбор одного проекта. Оба вызова равнозначны:

```bash
npx @oim-dev/relay-cli overview \
  --project frontend
npx @oim-dev/relay-cli frontend overview
```

`--config` и `--server-url` задаются по общим правилам подключения. Обзор не объединяет
базы workspace. Для проекта с именем, совпадающим с корневой командой, используйте
`--project`, например `overview --project overview`.
Прежний путь `product overview` перенесён на верхний уровень; после обновления
начните чтение заново: курсоры привязаны к пути команды.

По умолчанию text — компактная сводка: показатели и копируемая версия среза,
без повторных карточек подборок. `--view compact` выбирает её явно.
Блок сессий показывает последнюю сессию и до трёх незавершённых с явным общим числом.
Если последняя сессия незавершена, она показана первой с меткой «последняя», без повторной
карточки. Завершённая последняя сессия не скрывает старые открытые ветки. У дочерних
сессий виден ключ родителя. При неполной подборке одна команда `session list --unfinished`
ведёт к полному списку текущих сессий с тем же подключением. При отсутствии незавершённых
остаётся последняя сессия; при пустой истории — одна строка «Сессии: записей пока нет».
`--view full` раскрывает первую страницу полного обзора с блоками по порядку:

1. Проект, продукт, время среза и паспорт. Если summary пуста, показывается начало
   описания; отсутствие паспорта обозначается явно. Создание описано в `product create --help`.
2. «Сводка»: задачи по шести колонкам, фактически выполненные, готовые к началу,
   заблокированные, критерии приёмки и доски. Показатели пересекаются и не складываются.
3. Последняя сессия и до пяти незавершённых, с типом, временем и номером последнего события.
   Полные материалы читаются через `session context/get`; состояние не означает online.
4. «Требует внимания»: задачи в работе, на проверке и заблокированные с причинами.
5. «Показатели работы» — компактные блоки без диаграмм:
   - очередь проверки: «на проверке N = обязательства выполнены A + остались
     обязательства B». «Обязательства выполнены: можно рассмотреть завершение» — это не
     внешняя проверка результата; у второй группы строка «Осталось» называет критерии,
     зависимости и подзадачи с ключами блокеров;
   - «Прямые блокеры»: «блокирует N незавершённых задач напрямую» и затронутые задачи
     со связью (зависимость, подзадача или обе). Не критический путь и не приоритет;
   - «Вне открытых планов»: работа in-progress и review вне состава планов draft/active,
     с разбиением по колонкам. Это сигнал для пересмотра планирования, а не ошибка;
   - незавершённая работа (не cancelled и фактически не выполнена, включая done с
     открытыми обязательствами) с числом задач с прямыми блокерами и разбивкой по доскам.
     Число карточек — не загрузка людей.
6. «Планы» и «Релизы»: собственный статус отдельно от фактической готовности состава;
   затем «Состав выполнен, план открыт» (завершение плана дополнительно требует итог
   и ревизию), «Запланированные релизы с готовым составом» и «Готовые завершённые
   планы вне релизов». Обзор статусы не меняет.
7. «Продуктовые знания» (фичи, сценарии, приложения, реализации FI/SI), доски, документы.
8. Страница «Карта продукта» — записи `items` и общий footer страницы.

Подборки содержат не более 5 элементов и подписаны «все N» либо «показано N из M»;
в последнем случае ниже выводится «Полный список (ещё K)» с командой полного чтения,
например `task list --readiness blocked` или `overview --metric unplanned-work`.
Если у блокера больше пяти затронутых задач, под ним выводится команда
`--metric blocker-affected --blocker <ID>`.
Продолжение в text показывает только следующую страницу карты, без повторения сводки.
Подсказки сохраняют `--local`/`--config` либо
`--server-url`/`--project` текущего вызова.

JSON без view или с `--view compact|full` сохраняет прежний полный DTO независимо
от плотности text. `data` содержит `productId`, `version`, `items` текущей страницы,
`readiness` только для записей этой страницы, `readinessCounts` по всему продукту,
`total`, `nextOffset`, `snapshotVersion`, `generatedAt`, полный `snapshot` и `commands`
— исполняемые команды дальнейшего чтения, сохраняющие явно выбранный формат.
Показатели работы находятся в `snapshot.operator` с полными счётчиками, ID, основаниями
включения (`reasons`, `relations`) и подборками до 5 элементов. В `commands` есть
предметные переходы и группы `metrics` — команда полного чтения каждой метрики,
кроме `blocker-affected`, — и `blockerAffected` — команда состава затронутых задач
для каждого блокера подборки, по его постоянному ID. Дополнительные команды ведут
к полному представлению, карте, состоянию и предметному контексту.
`snapshot.sessions` одинаков в compact/full JSON: `total`, `latest` и `unfinished`
с полным total и до пяти записями; карточки содержат `id`, `key`, `title`, `status`,
`parent` и `lastEvent`. `commands.unfinishedSessions` читает все незавершённые ветки.
`--limit` ограничивает карту, а не подборку сессий. Изменение истории работы также
инвалидирует `snapshotVersion`, включая продолжения карты и метрик.

`--view map` — отдельная серверная страница карты без общего обзора, в том числе
компактный DTO JSON: `productId`, `version`, `snapshotVersion`, `items`, `total`,
`nextOffset`. У каждого элемента `subject` — публичный адрес, ключ и название;
технический scope ведёт к составу приложения. Эта опция не меняет прежний JSON по
умолчанию и не обещает O(limit) чтения Core. Команды адресного чтения этой проекции
находятся в `meta.commands`; они не добавляются в предметный DTO страницы.

P (`--limit`/`--cursor`) без `--metric` листает только карту `items`; итоги среза
от него не зависят. Первая компактная text-сводка не имеет footer карты:
карту читает `overview --view map`. В full и JSON footer относится к карте.
Продолжение действительно, пока не изменился `snapshotVersion`: изменение задачи, плана,
релиза, документа или продукта после первой страницы даёт `VERSION_CONFLICT` —
начните `overview` заново без `--cursor` и `--snapshot` (exit 4).
`--snapshot <snapshotVersion>` привязывает первое чтение к ранее показанному срезу;
text показывает его один раз полем `Срез`; передавайте значение в `--snapshot` при
чтении карты или метрики того же среза. Без него первая страница читает
текущее состояние; пустой snapshot отклоняется. Поле `version` — версия продуктового
состава для `application participation replace`, а не проверка продолжения.
При подключении к Server прежней версии, не возвращающему срез, команда завершается
`SERVER_INCOMPATIBLE`: обновите и перезапустите Relay Server той же версии, что и CLI.

#### Детализация `--metric`

`--metric <метрика>` выводит полный постраничный список одного показателя той же
классификацией, что и `snapshot.operator`:

| Метрика                   | Список                                                        |
| ------------------------- | ------------------------------------------------------------- |
| `review-obligations-met`  | Review, обязательства выполнены: можно рассмотреть завершение |
| `review-obligations-open` | Review, остались обязательства, с `reasons`                   |
| `blocker-impact`          | Прямые блокеры незавершённой работы                           |
| `blocker-affected`        | Задачи, которые блокер `--blocker` задерживает напрямую       |
| `unplanned-work`          | In-progress и review вне открытых планов                      |
| `board-work`              | Доски по незавершённой работе, включая пустые                 |
| `open-plans-complete`     | Состав выполнен, план открыт                                  |
| `ready-releases`          | Запланированные релизы с готовым составом                     |
| `plans-outside-releases`  | Готовые завершённые планы вне релизов                         |

`--blocker <ID или ключ>` обязателен только для `blocker-affected` и запрещён для
остальных метрик, а без `--metric` — тоже ошибка. `--view` вместе с `--metric` запрещён.
`--snapshot` принимает отпечаток обзора для первого запроса метрики. P: `--limit` 1–100 (по умолчанию
из настроек вывода) и `--cursor`; `total` не зависит от размера страницы. Курсор
связывает команду, метрику, блокер, размер страницы, проект и подключение; для
продолжения достаточно `--cursor` или готового `meta.page.nextCommand`. Курсор
local не принимается HTTP и наоборот. Изменение задачи, плана, релиза, доски,
документа или продукта между страницами даёт `VERSION_CONFLICT` (exit 4) —
перечитайте обзор и начните детализацию без `--cursor`.

Text: карточка с подписью метрики, `Всего`, `На странице`, версией среза и временем,
пояснение смысла, элементы и общий footer продолжения. У `blocker-affected` показаны
блокер, его колонка и доска, а у каждой задачи — связь с блокером.

JSON: `data` — страница `metric`, `blocker` (адрес блокера у `blocker-affected`, иначе
`null`), `snapshotVersion`, `generatedAt`, `total`, `items` в порядке метрики, внутренний
`nextCursor` Backend и `commands`: `overview`, у `blocker-impact` — `affected` по ID
блокера, у `blocker-affected` — `blocker` (`task get`). Для продолжения используйте
`meta.page.nextCursor`/`nextCommand`, а не `data.nextCursor`.

Ошибки: неизвестная метрика — `UNKNOWN_METRIC`, неверное сочетание `--blocker` —
`INVALID_ARGUMENT`, повреждённый или чужой курсор — `INVALID_CURSOR` (exit 2);
несуществующий блокер — `NOT_FOUND` (exit 3); Server без
`relay-overview-metrics-v1` — `SERVER_INCOMPATIBLE` (exit 5) до запроса детализации.

## Продукт и каталоги

**Каталог L** для feature/scenario/application/implementation/document означает P
и `--q <text>`, `--sort <field>` (`key`, `title`, `updated`). Фильтры применяются
до пагинации. Ответ — краткие items с показателями страницы, не полные тексты.
Область q — как у [search](#search), включая полное содержание. `updated` использует
собственную дату записи, у FI/SI — дату реализации, не состава; неизвестные даты идут
последними. При равенстве используется постоянный адрес. Старое продолжение общего
каталога до guard `entities-v2` требует начать заново; документный `documents-v1` сохранён.

**Содержание N** для product/feature/application: `--name <text>`, T(summary),
T(description). Create требует name и непустое description; summary по умолчанию
пустое. Update — только переданные поля, минимум одно; `--clear-summary` очищает
summary и несовместим с его текстовым источником. Создание C, изменение R.
Имена не имеют неявного `--name-file`, кроме отдельно описанного project update.

**Прогресс G**: страница P полного ответа предметного прогресса, со сводкой,
причинами и страницами составляющих. Это чтение, не установка готовности.
**Переименование K**: запись R нового читаемого ключа, не названия; ID и прежние
алиасы сохраняются. Возвращает квитанцию сущности; коллизия отклоняется.

У продуктовых get optional `metadata` сохраняет автора/дату создания и изменения
той же записи. Это не история; отсутствующие сведения не угадываются по файлу или
автору вызова. HTTP-новинки validate/lint/map/participation требуют
`relay-product-queries-v1`; compact-чтения работы — `relay-work-read-models-v1`,
сохранение релиза по refs — `relay-release-refs-v1`. При `SERVER_INCOMPATIBLE`
обновите и перезапустите Server согласованной версии; local fallback не выполняется.

### application participation replace

```bash
npx @oim-dev/relay-cli application participation replace WEB \
  --actor agent \
  --implementations WEB-FI-1 WEB-SI-1 \
  --if-revision 2 \
  --if-version VERSION
```

R плюс обязательный `--if-version <version>`. Ровно один вариант:
`--implementations <refs...>` — весь активный набор существующих реализаций данного
приложения; `--clear` — снять всё участие; T(composition) — JSON полного нового состава.
У существующего вклада тексты и адреса сохраняются;
исключённые реализации не удаляются. SI требует FI. Core проверяет исходные revision
и version и атомарно меняет состав.
Скрытого повтора нет. Ответ — квитанция состава.
Новый состав допускает одновременно прежние и новые вклады:

```json
[
  { "kind": "existing", "ref": "WEB-FI-1" },
  {
    "kind": "target",
    "target": "SCENARIO-1",
    "title": "Поиск в Web",
    "description": "## Обязательства\n\nПоказать результаты поиска и объяснить пустую выдачу."
  }
]
```

Сохраните этот массив через `--composition <json>` либо `--composition-file <path|->`;
это не конверт запроса. До 10 000 элементов; `[]` снимает всё участие. `existing`
принимает и снятый вклад, сохраняя ручную отметку; `target` создаёт только новую пару,
необязательный `status` — none/partial/done (default none), не готовность. Уже существующая
пара требует existing. Родительский FI должен быть в том же выборе, в том числе новым.
Весь ввод читается до единственной мутации. JSON нового composition-режима содержит
`application`, `scopeId`, `revision`, `version`, `selected`, `requestId`;
optional `key` — только сохранённое поле исходной предметной квитанции, не публичный
адрес scope и не ключ приложения. Старые варианты сохраняют прежнюю квитанцию
`id`, optional `key`, `revision`, `requestId`; отсутствующий key не заполняется
ключом приложения. Все варианты передают выбор одной операции Core.
При конфликте перечитайте состав и
согласуйте полный выбор. После успеха проверьте список и полные новые тексты.

## Документы и разделы

Содержание документа D: `--name <text>`, T(summary), T(body),
`--document-kind <kind>` (specification/description/rules/instruction/proposal/decision/research),
`--document-status <state>` (draft/active/archived), `--section-id <id>`,
`--clear-section`, `--pinned <value>` (строго true/false), `--targets <refs...>`,
`--clear-targets`, `--relations <json>`, `--relations-file <path>`, `--clear-relations`.
Section-id конфликтует с clear-section,
targets — с clear-targets. Targets заменяет прежние продуктовые области, clear-relations
очищает только современные адресные отношения. Две формы не очищают друг друга.

Relations — полный JSON-массив современных отношений, не добавление к прежнему набору:

```json
[
  {
    "target": { "kind": "feature", "id": "постоянный-ID-фичи" },
    "type": "documents",
    "description": "## Основание\n\nЗачем читать документ для этой цели."
  }
]
```

Замените ID фактическим постоянным ID из `inspect resolve FEATURE-1`; читаемый ключ
не является ID этого поля. Type — `documents` или `references`, description —
необязательное Markdown-пояснение: при отсутствии CLI передаёт пустую строку.
Явные `null` и нестроковые значения недопустимы. `--relations-file ./relations.json` читает UTF-8,
`--relations-file -` — stdin; inline-альтернатива — `--relations '<JSON-массив>'`.
Эти источники и `--clear-relations` несовместимы. `[]` явно очищает современные отношения.
Все источники summary/body/relations проверяются вместе: во всей команде допустим
один stdin. Ввод полностью читается до записи. Содержание и отношения сохраняются
одной атомарной операцией Core; неверный набор или конфликт ревизии не сохраняет
часть изменения. CLI не выполняет серию link. Предметные ограничения — в
[контракте документов](https://github.com/oim-dev/relay/blob/main/docs/domain/DOCUMENTS.md).

### document list

`npx @oim-dev/relay-cli document list` — L; дополнительно `--status <state>`,
`--target <ref>`, `--section <id>` (none — без раздела), `--document-kind <kind>`,
`--pinned <value>`, `--archived <value>` (true/false). Ответ — краткие документы:
сохранённая аннотация (длинная помечена как фрагмент), при поиске — предоставленный
фрагмент содержания, при `--sort updated` — время изменения. Полный документ читает
`document get <ключ>`, описанная в help списка. JSON сохраняет полные поля списка.
Версия списка — непрозрачный guard текущего состояния, не исторический снимок.
При `ENTITIES_CHANGED`, в том числе для курсора прежнего алгоритма версий, начните
чтение без `--cursor`; CLI не подставляет новую версию автоматически.

### document get

`npx @oim-dev/relay-cli document get DOC-1` — полные summary/body, метаданные, время
изменения и ревизия, без собственных флагов. В text — точное число прикреплений
(современных и прежних) и уникальных целей вместо всей коллекции пояснений;
`document links` раскрывает её страницами. JSON полного EntityDetail,
включая relations/links/references, не сокращается. Не заменяйте get превью списка.
`document delete-preview` читает полный каскад удаления без изменения данных;
маршрут указан в help карточки.
При наличии `metadata` text показывает автора последнего изменения и его дату.
JSON сохраняет весь блок `createdAt`, `createdBy`, `updatedAt`, `updatedBy` текущей записи,
не историю. Блок необязателен для совместимости: старый ответ без него не дополняется
выдуманным автором или датой создания. Предоставленная `document.updatedAt` по-прежнему
показывается, если metadata отсутствует. Второго чтения ради авторов CLI не делает.

### document create

```bash
npx @oim-dev/relay-cli document create \
  --actor agent \
  --name 'Решение' \
  --body-file ./decision.md \
  --document-kind decision
```

C и D; name и непустое body обязательны. Summary по умолчанию пустое,
document-kind — description. Ответ — квитанция; проверьте document get.
Для атомарного создания с современными прикреплениями добавьте к этому вызову
`--relations-file ./relations.json` (формат — D выше).

### document update

```bash
npx @oim-dev/relay-cli document update DOC-1 \
  --actor agent \
  --document-status active \
  --pinned true \
  --if-revision 1
```

R и D, минимум одно поле. Дополнительно `--clear-summary`, несовместимый
с T(summary). Непереданные поля сохраняются; смена proposal на decision сама
по себе не доказывает внешнюю приёмку.

Текст и полный современный набор можно заменить вместе:

```bash
npx @oim-dev/relay-cli document update DOC-1 \
  --actor agent \
  --body-file ./decision.md \
  --relations-file ./relations.json \
  --if-revision 1
```

Передайте прочитанную ревизию. Если relations не указан, набор не меняется;
непереданные legacy targets также сохраняются. Для одной цели без полной замены
остаются `document link/unlink`.

### document rename

```bash
npx @oim-dev/relay-cli document rename DOC-1 RULES-1 \
  --actor agent \
  --if-revision 1
```

K по `<ref> <key>`, не изменение названия документа.

### document delete-preview

`npx @oim-dev/relay-cli document delete-preview DOC-1` — полный предпросмотр без записи
и без обязательного автора. `<ref>` — ключ, алиас или постоянный адрес документа.
Удаляется только документ; прикреплённые сущности и другие документы сохраняются,
затронутые ссылки снимаются по
[контракту удаления](https://github.com/oim-dev/relay/blob/main/docs/domain/STORAGE.md#удаление-с-полным-предпросмотром).
Архивирование, открепление и удаление раздела не заменяют удаление документа.

JSON `data` — полный `EntityDeletionPreview`: `target`, непрозрачная `version`,
`deleted[]`, `detached[]`, `relations` (число отзываемых связей, не их подробности).
Text показывает адреса, названия, виды и ревизии всех удаляемых и сохраняемых записей
со снятием ссылок. До 1000 записей в каждом массиве; превышение — ошибка, не усечение.
Страниц, `--limit` и `--cursor` нет. С автором подсказка предлагает явное подтверждение
по этой версии; без автора — справку и указание задать `--actor` или `RELAY_ACTOR`.

### document delete

```bash
npx @oim-dev/relay-cli document delete DOC-1 \
  --actor human \
  --if-version VERSION
```

Замените VERSION исходной версией **из изученного полного delete-preview** этого документа,
не ревизией его карточки. Автор обязателен. Необязательный `--request-id <id>` — только
корреляция, по умолчанию UUID; он не обеспечивает дедупликацию. Команда не запускает
неявный предпросмотр, не подставляет свежую версию и не повторяет запрос.
После изменения состояния требуется заново изучить полный предпросмотр и согласовать
решение. Общие ограничения планов проверяет Core, не CLI. Публичный `plan.scope`
не принимает вид document; планы со ссылками на сохраняемые цели не превращают
эти цели в каскад документа и не блокируют его удаление.

JSON `data` — `EntityDeleted`: `action`, `ref`, `requestId`, числа `deleted`, `detached`,
`relations`. Проверьте оставшиеся материалы и их прикрепления через `document list`,
а не вызывайте get удалённой записи. После потери ответа сначала перечитайте состояние
и снятые ссылки, не повторяйте POST вслепую. Восстановления нет; ключ и алиасы удалённого
документа остаются зарезервированы.

### document links

`npx @oim-dev/relay-cli document links DOC-1` — P прикреплений. Современные
relations и прежние links помечены раздельно; пояснения показываются полностью.
Страница получается непосредственно у Backend, без полного get документа и без
отдельных чтений целей. Продолжение защищено ID и ревизией документа; ответ включает
его revision. При `VERSION_CONFLICT` начните чтение без курсора.
Это собственные прикрепления, не все входящие рёбра графа. Есть переход к первой
цели каждого вида на странице (без дублирования двух типов к одной цели) и к
`inspect graph list --root` для остальных направлений. Для другой цели того же вида
замените ключ/ID в примере; product/project читаются без позиционного адреса.
Прежняя цель plan-stage не получает выдуманную команду get по одному ID.
JSON `data` сохраняет поля `ref`, `revision`, `items`, `total`, `nextOffset`, `version`;
заголовок документа и словарь целей страницы используются только для text.

HTTP-команды `document links/link/unlink` и `document section` требуют capability
`relay-document-library-v1`. Без неё сервер отклоняется с `SERVER_INCOMPATIBLE`,
без обхода через полную карточку, прежнюю запись массива или локальные файлы.

### document link

```bash
npx @oim-dev/relay-cli document link DOC-1 \
  --actor agent \
  --target FEATURE-1 \
  --relation references \
  --description 'Основание требования' \
  --if-revision 1
```

R документа; обязателен `--target <ref>`, необязательны `--relation <type>`
(references/documents, по умолчанию documents), T(description), `--clear-description`,
`--legacy`. Совпавшая цель+тип обновляет пояснение, пропущенное пояснение сохраняется.
Clear-description конфликтует с текстом. Legacy меняет прежние links/targets и
не допускает relation/пояснение/clear-description. Остальные связи сохраняются;
Core проверяет исходную ревизию и атомарно меняет одно прикрепление. CLI передаёт одну
предметную запись, без предварительных get/resolve и без отдельной записи графа.
Весь текстовый ввод читается до этой операции. Ответ — квитанция документа.

### document unlink

```bash
npx @oim-dev/relay-cli document unlink DOC-1 \
  --actor agent \
  --target FEATURE-1 \
  --if-revision 2
```

R документа; обязателен `--target <ref>`, допустимы `--relation <type>`
(по умолчанию documents) или `--legacy`, но не вместе. Снимает только выбранное
существующее прикрепление, не удаляет документ. Ответ — квитанция.
Операция передаётся непосредственно владельцу документа с исходной ревизией,
без чтения и сборки полного массива отношений в CLI.

### document section list

`npx @oim-dev/relay-cli document section list` — P разделов в их порядке и revision
проекта. Если массив ещё не задан, используются стандартные разделы. Версия
продолжения привязана к PROJECT; для записи нужна показанная ревизия проекта.
Подсказка открывает документы первого раздела страницы; можно заменить его ID,
а `none` выбирает документы без раздела.
Backend возвращает страницу непосредственно, без предварительного PROJECT get в CLI.
JSON `data` сохраняет `project`, `revision`, `items`, `total`, `nextOffset`, `version`;
предоставленный projectKey используется только для заголовка text.
При `VERSION_CONFLICT` начните список заново без курсора.

### document section create

```bash
npx @oim-dev/relay-cli document section create guides \
  --actor agent \
  --name 'Руководства' \
  --if-revision 1
```

R проекта, обязательная T(name): `--name <text>` или `--name-file <path|->`;
`<id>` — новый постоянный ID раздела. Источники имени несовместимы; весь ввод
считывается до записи, `-` означает stdin. Добавляет раздел в конец.
Core проверяет исходную ревизию и изменяет массив в одной сессии записи;
CLI передаёт одну предметную операцию. Ответ — квитанция PROJECT.

### document section update

```bash

  --actor agent \

```

R проекта и обязательная T(name), как у section create. Меняет имя существующего раздела,
сохраняя ID, порядок и остальные разделы; ответ — квитанция PROJECT.

### document section move


R проекта. Нужен ровно один из `--before <id>` или `--last`. Нельзя ставить

### document section remove

```bash
npx @oim-dev/relay-cli document section remove guides \
  --actor agent \
  --if-revision 4
```

R проекта, других флагов нет. Удаляет существующий раздел, не документы;
они остаются без раздела. Все операции section сохраняют непереданные разделы
под исходной ревизией в Core, без предварительного get и пересборки массива в CLI.
После конфликта или потери ответа автоматического повтора записи нет.

## Доски и задачи

### board list

`npx @oim-dev/relay-cli board list` — P системных досок и досок приложений.
Ответ — свойства каталога в предметном порядке: product, приложения, infrastructure.
Число досок не является числом задач. `board get <ключ>` читает выбранную доску,
`overview --metric board-work` — показатели работы; эти маршруты описаны
в help. Задачи и счётчики автоматически не раскрываются. Для поиска используйте `search --kind board --q Web`.
Системные доски создаёт проект, прикладную — `application create`; имя меняется через
`application update --name`, удаление с каскадом — `application delete-preview/delete`.
Самостоятельных board create/delete нет.

### board get

`npx @oim-dev/relay-cli board get BOARD-PRODUCT` — карточка по ключу, алиасу, slug,
префиксу или ID, канонический ключ и ревизия, без собственных флагов.
Задачи читаются отдельно через `task list --board`. У прикладной доски виден
актуальный ключ приложения из references для `application get`; префикс задач
не используется для угадывания владельца. Маршруты раскрываются в help.
У системной доски поле приложения неприменимо и опущено. JSON не сокращён.

### board rename

```bash
npx @oim-dev/relay-cli board rename BOARD-PRODUCT BOARD-TEAM \
  --actor human \
  --if-revision 1
```

`<ref>` — ключ, алиас или ID доски; `<key>` — новый публичный ключ. Обязательны автор
и `--if-revision <n>` из `board get`; необязательный `--request-id <id>` — корреляция,
не дедупликация. Ответ — квитанция с новым ключом, ревизией и командой чтения.
ID и прежние ключи-алиасы сохраняются. Имя, slug, префикс задач и принадлежность
приложению не меняются. Устаревшая ревизия и коллизия отклоняются; после конфликта
или потери ответа сначала перечитайте доску. Все ключи — `inspect keys <ref>`.

### task list

```bash
npx @oim-dev/relay-cli task list \
  --board product \
  --completion unfinished
```

P.
Фильтры: `--board <ref>` (slug/префикс/ID), `--column <column>`,
`--completion <state>` (unfinished/finished), `--search-in <scope>` (title/all),
`--product-target <ref>`, `--q <text>`, `--readiness <state>` (blocked/ready).
Finished означает done/cancelled, не фактический успех. Ready — готовые к работе
задачи ready без блокеров. Ответ — краткие задачи, не полные Markdown.

### task get

`npx @oim-dev/relay-cli task get PRODUCT-1` — полная задача и ревизия по текущему
или прежнему ключу/ID. Собственных флагов нет; коллекции читайте адресными списками.

### task create

```bash
npx @oim-dev/relay-cli task create \
  --actor agent \
  --board BOARD-PRODUCT \
  --title 'Проверить поиск' \
  --criterion-title 'search=Находит документ' \
  --criterion-summary 'search=По названию' \
  --criterion-description 'search=Введите название и проверьте результат'
```

C; обязателен `--board <ref>`. Допустимы `--title <text>`, T(description),
`--column <column>` (по умолчанию inbox), `--parent <ref>`, `--dependencies <refs...>`,
`--related <refs...>`, `--targets <refs...>`, `--clear-targets` (не вместе с targets).
Название и описание могут быть пустыми. Цели зависят от доски: общие требования
на продуктовой, реализации своего приложения на прикладной, без целей на инфраструктурной.

Критерии задаются повторяемыми `--criterion-title <label=text>`,
`--criterion-summary <label=text>`, `--criterion-description <label=Markdown>`.
Метка состоит из латиницы, цифр, `_`, `-`, не сохраняется; разделитель — первое `=`.
Для каждой метки обязателен title, остальные тексты по умолчанию пусты; повтор
одного поля метки — ошибка. До 100 критериев; задача, критерии и связи создаются
одной предметной операцией. Метки связывают поля независимо от порядка флагов.
Ответ — квитанция задачи; перечитайте get и criterion list.

### task update

```bash
npx @oim-dev/relay-cli task update PRODUCT-1 \
  --actor agent \
  --title 'Уточнить поиск' \
  --if-revision 1
```

R; `--title <text>`, T(description), `--targets <refs...>` или `--clear-targets`.
Переданный набор целей заменяется целиком; пропуск сохраняет его. Колонка,
критерии и связи меняются отдельными командами. Ответ — квитанция задачи.

### task rename

```bash
npx @oim-dev/relay-cli task rename PRODUCT-1 TASK-1 \
  --actor agent \
  --if-revision 1
```

K задачи по `<task> <key>`; не изменение title.

### task move

```bash
npx @oim-dev/relay-cli task move PRODUCT-1 \
  --actor agent \
  --column review \
  --if-revision 1
```

R; обязателен `--column <column>`: inbox/ready/in-progress/review/done/cancelled.
`--board <ref>` меняет доску, `--before <ref>` задаёт следующую задачу (без него конец),
`--if-version <version>` проверяет прочитанную версию порядка. ID сохраняется;
несовместимые цели снимите явно. Core проверяет обязательства при завершении.
Ответ — квитанция; перечитайте task get и нужный список.

### task children

`npx @oim-dev/relay-cli task children PRODUCT-1` — P прямых детей. Фильтр родителя
применяется до пагинации, не локально к уже ограниченной странице.

### task links

`npx @oim-dev/relay-cli task links PRODUCT-1` — P родителя, детей, зависимостей,
блокируемых и обычных связанных задач. Страница не равна всему составу.
Это только отношения между задачами. Материалы и прямое окружение читайте через
`inspect graph list --root PRODUCT-1 --depth 1`, участие в планах — `plan task memberships`.

### task progress

`npx @oim-dev/relay-cli task progress PRODUCT-1` — G: критерии, дети, зависимости
и причины неготовности. Колонка done сама по себе не доказывает выполнение.
Причина незавершённого критерия сохраняет его точный criterionId и ведёт к
`task criterion get <задача> <criterionId>`, а не к первому критерию списка.

### task delete-preview

`npx @oim-dev/relay-cli task delete-preview PRODUCT-1` — полный предпросмотр без автора
и записи. Удаляется задача с критериями и комментариями; дети и другие задачи,
документы сохраняются со снятием затронутых ссылок и родительства. Любой план со ссылкой
на задачу блокирует каскад. Формат и пределы — [предпросмотр](#application-delete-preview).

## Планы и этапы

Состояния плана: draft/active/completed/cancelled. Закрытые планы неизменяемы.
Plan/release rename отсутствуют: Core не поддерживает это действие.
Для этапов `<reference>` — план, `<stage>` — внутренний ID этапа, не отдельный ключ.
Любое изменение этапа защищено R плана. Порядок этапов не запрещает параллельное выполнение.

Содержание плана F: `--title <title>`, T(summary), T(goal), T(rationale),
T(boundaries), T(expected-result), `--scope <references...>`, `--clear-scope`,
`--participants <actors...>`, `--clear-participants`. Scope принимает ключи/kind:ID допустимых предметных
областей; конфликтует с clear-scope. Переданный scope/participants заменяет набор.
Clear-participants явно очищает участников и несовместим с participants; пропуск
обоих при update сохраняет участников. После изменения перечитайте plan get.

### plan list

`npx @oim-dev/relay-cli plan list` — P; `--q <text>`, `--status <status>`.
Ответ — краткие планы со счётчиками, независимыми от размера страницы.
Без проекции JSON сохраняет полные прежние карточки планов. `--projection compact`
явно выбирает серверный обзор без полных Markdown-полей, с summary, состоянием,
датой, числом этапов, counts/ready/nextStage. Полное содержание — plan get.

## Релизы

Релиз — проектная запись с выбранными планами, не релиз приложения: applicationId
и фильтра принадлежности приложению нет. Состав — 1–200 планов целиком.
Выпущенная запись неизменяема. Фиксация выпуска не запускает CI/CD.

Содержание релиза E: `--title <title>`, `--release-version <label>`,
`--plans <references...>`, T(summary), T(description), `--planned-for <date>`
(YYYY-MM-DD; пустая строка очищает), `--status <status>` (planned/cancelled/released).
Release-version — обозначение выпуска, не глобальный --version. При update CLI
сохраняет непереданные поля из чтения, но проверяет именно переданную пользователем
ревизию, не подменяет её. Status released выполняет проверки выпуска, не обходя publish.

### release list

`npx @oim-dev/relay-cli release list` — P; `--q <text>`, `--status <status>`.
Ответ — краткие релизы с текущей готовностью состава.
Q ищет по ключу, названию, обозначению версии, summary и полному description.
`--projection compact` — серверная страница без description и массива planIds,
но с summary, реквизитами выпуска, датами и readiness. По умолчанию сохраняется
прежний полный JSON; значение full для этой команды не предусмотрено. Полное содержание — get.

### release get

`npx @oim-dev/relay-cli release get REL-1` — полное содержание, состояние,
ревизия и актуальная готовность. Собственных флагов нет.

и автора, P; `--plans <references...>` — выбранные планы, максимум 200.
Пустой выбор допустим для предпросмотра, но не означает готовый выпуск.
Ответ — текущая готовность и страницы выбранного состава.
`--projection compact` возвращает обзорные карточки планов без полных Markdown-полей;
без опции сохраняется прежний DTO. Проекция и выбранные планы сохраняются
курсором. Ни один режим не записывает релиз.

`--kind <kind>`, `--refs <refs...>` (выбранные ключи/ID, до 100), `--board <ref>`,
`--application <ref>`, `--feature <ref>`, `--scenario <ref>`, `--target <ref>`,
`--parent <ref>`, `--status <status>`, `--active <value>`, `--section <id>`
(none — без раздела), `--document-kind <kind>`, `--pinned <value>`,
`--archived <value>`, `--sort <field>` (key/title/updated),
`--implementation-target <kind>` (feature — FI, scenario — SI).
Булевы значения — true/false. Виды: project/product/feature/scenario/application/
implementation/board/task/document/work-plan/release. Ответ — карточки, не полные тексты;
полное содержание читайте у владельца, например document get или plan get.

Поиск без учёта регистра: ключи, алиасы, ID, название, summary и контекст; description
продукта, фичи, сценария, приложения, реализации, задачи и релиза; body документа,
goal плана, version релиза. Для FI/SI также ищутся ключи и названия приложения и цели.
Комментарии, критерии, тексты вложенных этапов и прочие неуказанные поля не входят.
Section/document-kind/pinned без kind оставляют документы; active и implementation-target —
только реализации. Неприменимый вид не считается совпадением с пустым полем.
`--archived false` в смешанном поиске исключает архивные документы, не остальные виды.

`updated` сортирует по собственной предметной дате у всех видов с известной датой;
отсутствующие даты идут последними, равенство разрешается постоянным адресом.
JSON `items[].updatedAt` необязателен. `items[].implementation` содержит тип FI/SI и
компактные application/target с ref/key/title. Обновление соседнего вклада не выдаётся
за обновление выбранной реализации. Guard общего каталога — `entities-v2`, документного —
`documents-v1`; старый или изменившийся снимок требует нового чтения без cursor.
Индексный отбор сужает виды/refs, но q читает тела кандидатов: это не полнотекстовый
индекс и не обещание стоимости O(limit). В mixed-поиске маленький limit не ограничивает
чтение тел только выданными записями; повторный запрос снова выполняет отбор.

При непустом q optional `items[].match` содержит одно подтверждённое основание:
`field`, `text`, `truncated`. Text показывает поле совпадения и его значение отдельно
от сохранённой аннотации; текущий ключ и название уже видны в строке и не дублируются.
Фрагмент — до 240 единиц UTF-16 исходного поля, без добавленной подсветки или многоточия;
`truncated: true` помечается «фрагмент», это не усечение полного get.
Старый `document.excerpt` также сохраняется. При отсутствии match причина не угадывается
по поисковому запросу. Для проверки основания откройте полный get; исправляйте исходное
поле записи, не поисковый фрагмент.

Для HTTP расширенный поиск требует `relay-entity-search-v2`: при implementation-target;
при q или sort=updated вне явного kind=document; при active/section без kind.
При `SERVER_INCOMPATIBLE` обновите Server, не подменяйте результат старой
поисковой семантикой или локальным обходом файлов.

### inspect types

`npx @oim-dev/relay-cli inspect types` — P каталога видов, назначения и действий.
Наличие вида в чтении не означает доступность всех операций записи.

### inspect type

`npx @oim-dev/relay-cli inspect type document` — схемы полей, фильтры и действия
вида; `<kind>` обязателен, собственных флагов нет. Отсутствующая схема означает
отсутствие общей операции, не пустой набор обязательных полей.

### inspect resolve

`npx @oim-dev/relay-cli inspect resolve FEATURE-1 [--kind <kind>]` — постоянный
адрес по ключу, алиасу, ID или kind:ID. Kind уточняет ожидаемый вид.

### inspect keys

`npx @oim-dev/relay-cli inspect keys FEATURE-1` — P текущего ключа и алиасов.
Это не история содержимого.

### inspect key-spaces

`npx @oim-dev/relay-cli inspect key-spaces feature` — P пространств нумерации
и шаблонов ключей вида. Не меняет ключи или резервирование.
Text показывает постоянный адрес владельца scope и готовый get без дополнительного
чтения графа. `scope: null` означает общее пространство вида без отдельного владельца.

### inspect graph list

```bash
npx @oim-dev/relay-cli inspect graph list \
  --root PRODUCT-1 \
  --limit 20
```

P графа.
`--root <address>` выбирает корень, без него весь проект; `--type <type>` фильтрует
отношения, `--direction <direction>` — both/outgoing/incoming, `--profile <profile>` —
all/context (context — совместимое имя all), `--depth <n>` — 0–100,
`--q <text>` — поиск сущностей. Узлы/рёбра имеют отдельные страницы общего guard;
конец страниц не отменяет фильтры или глубину. Ответ содержит version для ремонта.
Направление ограничивает обход: обратные рёбра между выбранными узлами сохраняются.
Text сохраняет адреса узлов и ограниченный list от граничного узла с теми же фильтрами
и подключением (для исходной глубины 0 следующий шаг использует 1). Граница глубины
относится ко всей выборке, даже если на текущей странице граничных узлов нет.
Максимальная глубина 100 тоже не гарантирует полной компоненты.

### inspect graph context

`npx @oim-dev/relay-cli inspect graph context PRODUCT-1` — вся достижимая компонента
в обоих направлениях, включая циклы и параллельные отношения. Собственных флагов,
глубины и страниц нет. Успешный ответ complete=true; лимит Core даёт ошибку,
не усечённый успех. Контекст не заменяет полные тексты требований.
Полные тексты читаются предметным get по виду и ключу узла. Для пояснения выберите
начало нужного ребра и вызовите `inspect graph list --root <адрес> --depth 1 --direction outgoing`.
Найдите ID отношения среди результатов, продолжая страницы при
необходимости. Это существующее ограниченное чтение, не отдельный edge get.

## Диагностика и обслуживание

Прямой ремонт графа не устанавливает цели задач, родительство или состав планов.
Используйте предметного владельца; перед ремонтом сохраните резервную копию.
Графовые записи требуют автора, `--if-version <version>` из inspect graph list/context
и допускают `--request-id <id>`. Ответ — квитанция графа с новой версией; перечитайте связи.

### doctor check

`npx @oim-dev/relay-cli doctor check` — проверка схем, каталога, досок, задач
и связей. Нет собственных флагов, автора и автоматического ремонта. Нарушение
целостности — ошибка с exit 5, не пустая база. Успех содержит показатели проверки.
В `VALIDATION_FAILED.details` сохраняется массив причин Core: `code`, `message`,
необязательные `details` и `checks`. Text показывает компактный список причин,
доступные путь/адрес/поле и число проверок; разные повреждённые записи не объединяются.
Полные структурированные детали доступны в JSON. Подсказка обслуживания — отдельное
явное действие, не автоматический ремонт при проверке.

### doctor graph link

```bash
npx @oim-dev/relay-cli doctor graph link \
  --actor agent \
  --from PRODUCT-1 \
  --to DOC-1 \
  --type references \
  --if-version VERSION
```

Запись графа; обязательны `--from <address>`, `--to <address>`, `--type <type>`;
необязательна T(description). Создаёт диагностическое направленное отношение.

### doctor graph update

```bash
npx @oim-dev/relay-cli doctor graph update EDGE_ID \
  --actor agent \
  --description 'Основание' \
  --if-version VERSION
```

Запись графа; `<id>` — ID отношения, обязательна T(description).
Пустая строка явно очищает пояснение, пропуск — ошибка. Концы и тип не меняются.

### doctor graph unlink

```bash
npx @oim-dev/relay-cli doctor graph unlink EDGE_ID \
  --actor agent \
  --if-version VERSION
```

Запись графа, отзыв отношения по ID; другие предметные данные не заменяет.

### doctor graph apply

```bash
npx @oim-dev/relay-cli doctor graph apply \
  --actor agent \
  --json '[{"action":"add","from":"PRODUCT-1","to":"DOC-1","type":"references","description":"Основание"}]' \

```

Запись графа; обязательный `--json <json>` содержит массив до 100 операций,
не конверт запроса. Add: from/to/type/description; update: id/description;
remove: id. Пакет атомарный. Невалидный JSON — INVALID_JSON; json-file не зарегистрирован.

### storage status

```bash
npx @oim-dev/relay-cli --local --config /project/.relay/config.json storage status
```

Диагностика без изменения базы: начинается с минимального чтения конфигурации и
manifest, затем проверяет весь постоянный набор схемами его версий. Предварительное
открытие текущей схемой проекта не требуется; создания базы, recovery, reindex,
миграции и очистки нет (временный замок удаляется). Работает с конфигурацией любого имени и с проектом реестра:
`--local --config relay.workspace.json --project <имя>`. Показывает проект, реальный корень,
раскладку, фактические и целевые версии (физический формат, профиль, версии по владельцам
с количествами действующих записей и надгробий), объём, незавершённую транзакцию,
блокеры и предупреждения с действием. JSON `data` — `storageStatusSchema`
(`@relay/contracts/storage-maintenance`).
В `blockers` и `warnings` не более первых 50 элементов, `blockersTotal` и
`warningsTotal` — полные количества. Продолжения нет; после устранения причин
повторите диагностику. Ограничение диагностического DTO не является байтовым бюджетом CLI.

| status               | exit | Код ошибки                                                    |
| -------------------- | ---- | ------------------------------------------------------------- |
| `current`            | 0    | —                                                             |
| `migration-required` | 0    | —                                                             |
| `recovery-required`  | 4    | STORAGE_RECOVERY_REQUIRED                                     |
| `unsupported`        | 4    | причина первого блокера, например STORAGE_VERSION_UNSUPPORTED |
| `invalid`            | 4/5  | причина первого блокера, например STORAGE_DATA_CORRUPT (5)    |

При ненулевом статусе `error.details` содержит тот же полный отчёт по схеме статуса.
У базы текущего профиля без шагов миграции stale-marker или расхождение файлов с
индексом дают `invalid` и `STORAGE_INDEX_STALE`, не обещание пересборки при no-op.
После остановки писателей и резерва выполните явный storage reindex, затем status
и doctor check. Повреждённое содержание сначала восстановите; reindex его не исправляет.

Подсказки Core (`next` блокеров и ошибок, включая отказ обычной local-команды на базе,
требующей миграции) содержат переносимый вызов
`npx @oim-dev/relay-cli --local --config <config> storage …`. JSON возвращает их без
изменений. Text в local-режиме подставляет фактический путь выбранной конфигурации и
выводит каждую встроенную команду отдельной строкой; в HTTP-режиме база находится у Server,
поэтому плейсхолдер `<config>` сохраняется.

### storage migrate

```bash
npx @oim-dev/relay-cli --local --config /project/.relay/config.json storage migrate --dry-run
npx @oim-dev/relay-cli --local --config /project/.relay/config.json storage migrate \
  --backup-dir /backups/relay-project --if-plan PLAN_FINGERPRINT
```

Перед запуском остановите процессы Relay. `--dry-run` строит и проверяет точный план
изолированно: база не меняется, backup не создаётся, ответ содержит `planFingerprint`
(`storageMigrationPlanSchema`); неприменимый план — ненулевой exit с причиной.
На текущей базе с непригодными индексами dry-run неприменим и migrate отказывает.
При реальном переносе исправимые проблемы индексов — предупреждения: перенос
действительно перестраивает их. No-op не меняет индексы; `checks.indexes: passed`
означает проверку. Нули `changes` пустого плана — отсутствие изменений планом,
не отсутствие отношений или резервов адресов в базе.
Без `--dry-run` команда строит свежий план под замком; `--if-plan <fingerprint>`
останавливает исполнение до изменений при любом расхождении. `--backup-dir <dir>`
обязателен для изменяющего переноса (каталог вне базы; копия создаётся в отдельном
подкаталоге, путь — `backup.path`); при no-op копия не создаётся.
`--dry-run` и `--if-plan` несовместимы (INVALID_ARGUMENT). Второго подтверждения нет.
Относительный `--backup-dir` разрешается от текущего каталога. Если предыдущий перенос
прервался, повторный запуск продолжает его из незавершённой транзакции с исходной копией
без `--backup-dir` (`resumed: true`). Ошибки возвращают машинный код и exit по
таблице кодов обслуживания, например STORAGE_BACKUP_REQUIRED (2), STORAGE_PLAN_STALE (4),
STORAGE_BACKUP_MISSING (5); порядок действий — в
[восстановлении](../../../docs/guides/RECOVERY.md#явная-миграция-и-резервная-копия).
Результат — `storageMigrationResultSchema`: сохраняются `migrated`, `format`, `entities`.
Шаги плана и результата имеют `type`: `physical`, `record`, `snapshot` или `profile`
(`profile.1-to-2` — только метка профиля данных с полной перепроверкой; в text —
«Метка профиля данных 1 → 2»). Счётчики: `counts.checked` — записи с надгробиями, наборы
отношений и keyspaces, прошедшие полную проверку; `counts.changed` — файлы постоянного
набора (без `runtime/`), созданные, изменённые или удалённые публикацией, сумма
`counts.owners[категория].changed`; `counts.removedByRule` — удалённые распознанные
исторические структуры. В плане `changes.files[категория]` — create/update/delete.
ID, ключи, алиасы, тексты, ревизии и комментарии сохраняются, история запросов — нет.
Для pending обычной операции или legacy-WAL нужен **новый** внешний `--backup-dir`,
а не короткий resume миграции; запускайте без `--if-plan`. Путь копии не выбирается
автоматически. Отпечаток `--if-plan` — ровно 64 шестнадцатеричных символа из dry-run;
некорректное значение отклоняется до обслуживания.

### storage reindex

```bash
npx @oim-dev/relay-cli storage reindex \
  --local
```

Перестроение производных
индексов после внешних изменений или потери индекса; без собственных флагов и автора.
Не создаёт недостающие предметные отношения из полей. Ответ — результат

### storage reconcile-relations

```bash
npx @oim-dev/relay-cli storage reconcile-relations \
  --local \
  --actor agent \
  --request-id relations-v1
```

Локальное согласование предметных связей одной транзакцией. Автор обязателен,
`--request-id <id>` необязателен; ревизия параметром не передаётся.
Сохраняет ID неизменённых связей, независимые диагностические рёбра и ревизии сущностей.
Ответ: added/updated/removed и requestId. После потери ответа перечитайте связи.

Все storage-команды выполняются только локально. В HTTP-режиме (`--server-url`,
`RELAY_SERVER_URL`, `server.url` или реестр без `--local`) они возвращают LOCAL_REQUIRED
(exit 2) до любого сетевого запроса и без перехода на локальные файлы. status и migrate
принимают конфигурацию проекта любого имени и проект реестра через `--project`;
reindex и reconcile-relations — файловую рабочую область проекта, не workspace-реестр.
Если для этих двух команд выбраны `--local` и проект workspace, CLI возвращает
`LOCAL_CONFIG_REQUIRED` (exit 2) с `details.configPath` и готовой `details.next`:
та же команда через прямой `--local --config` выбранной базы, без реестрового project.
Это подсказка, не исполнение и не сетевой вызов. Перед явным запуском остановите
писателей и сохраните резерв; подсказка не отправляет обслуживание на Server.
Сначала остановите записи и сохраните резерв, после — выполните doctor check.
Предпросмотр и подтверждение удаления доступны у feature, scenario, application,
implementation, task и document через delete-preview/delete. У проекта, продукта,
самостоятельной доски, плана и релиза таких команд нет.
Команд истории запросов, product save,
старых entities/boards/projects/progress/graph на верхнем уровне нет.
