# Терминальное представление Relay CLI

Этот документ помогает читать человеческий вывод и настраивать его для терминала,
pipe и CI. Агент использует то же читаемое представление, которое видит пользователь.
Точный синтаксис команд определён в [справочнике CLI](CLI.md). Документация описывает
текущее дерево исходников, а не обещает совпадение с ранее опубликованным пакетом.

## Выбор формата

```bash
npx @oim-dev/relay-cli task get PRODUCT-1
npx @oim-dev/relay-cli task list \
  --format text
```

Если формат не передан, используется `text`; настройка format в конфигурации
игнорируется. Pipe сам по себе не переключает формат. JSON включается только явно
через `--format json`.

В text предметные команды показывают карточки, компактные списки и содержание.
Синтаксис, примеры и переходы к связанным командам читаются через `--help` команды
или группы. Обычный результат не повторяет меню действий, пример get для первой
строки, совет перечитать запись или напоминание о help. JSON возвращает машинные поля:
человеческое оформление не меняет DTO, UUID/ID, requestId или details ошибки.
Изменение ширины не меняет данные JSON. Help и версия всегда текстовые.
Команда возвращает карточку, страницу списка, квитанцию действия, прогресс или ошибку.
Квитанция сообщает результат записи, а не заменяет чтение сохранённого содержания.

Квитанция `init` показывает пути созданной конфигурации и хранилища.
Порядок первоначальной настройки описан в `init --help`.
При повторе `ALREADY_INITIALIZED` ведёт к чтению существующего конфига. Для остатков
неполной базы выводятся адресные пути и команда диагностики `storage status`, без
совета повторить init; отсутствие необходимых файлов может остановить и диагностику.

## Текст без цвета и ширина

CLI — прежде всего инструмент агента: текст всегда выводится без цветного ANSI,
параметр `--color` удалён. TTY, `NO_COLOR`, `FORCE_COLOR` и `TERM` не включают
ANSI-оформление. Это относится также к help, ошибкам и подсказкам. JSON остаётся
без ANSI-оформления. Смысл результата передаётся текстом и структурой, а не цветом.

Ширина берётся из `stdout.columns`, при его отсутствии — из `COLUMNS`.
Корректное положительное целое ограничивается диапазоном 24–160; иначе используется
100 колонок. `COLUMNS` не переопределяет фактическую ширину TTY, если она известна.

```bash
COLUMNS=40 npx @oim-dev/relay-cli task list | less
npx @oim-dev/relay-cli task get PRODUCT-1 | less
```

На узкой ширине представление может переходить от таблиц к карточкам. Выравнивание
учитывает Unicode: число байтов, длина JS-строки и экранная ширина не равны.
Заголовки, summary и обычные метаданные могут переноситься; не используйте пробельные
позиции таблицы как API. Полный Markdown и команды в подсказках не получают жёстких
переносов по ширине. Визуальный перенос самим терминалом не меняет строку ответа.
Версия графа, ID отношений и постоянные адреса в графовых метаданных также остаются
одной физической строкой: если значение не помещается, метка выводится отдельно.
Токен можно копировать без склеивания строк; обычные названия продолжают переноситься.

## Карточки, списки и Markdown

Карточка начинается с ключа и названия в естественном регистре: пользовательский
title не превращается в прописные буквы. Затем идут выровненные по меткам значимые
поля: состояние, ревизия, автор или показатели предметного состава. Пустые
необязательные поля и секции пропускаются, а числовой `0` сохраняется. Отсутствующая
обязательная часть может поясняться явно: например, незаданная цель или пустой состав
плана — полезная причина неготовности, а не пустое поле для скрытия.

Список показывает название выборки, применённые фильтры, ключ/ID и название каждой
записи с краткими предметными деталями. Полные описания каждой записи туда не
копируются: найдите ключ и вызовите адресный `get`. Полное описание в `get` не
усекается. Большие вложенные коллекции читаются отдельными списками с продолжением,
а не бесконечной карточкой. Пустая страница обозначается явно, но не означает ошибку
отсутствующей записи или отказ чтения базы.

В `project get` text показывает паспорт и число разделов документов, а не весь
вложенный каталог. Команда `document section list` раскрывает полный порядок
страницами и даёт переход к документам раздела. JSON `project get` сохраняет
весь массив. Квитанция изменения имени показывает нормализованное принятое имя;
при изменении slug выводятся имя, slug и ревизия из результата сохранения настроек.

`board list` сохраняет свойства и порядок каталога. Способы чтения выбранной доски
и показателей `board-work` описаны в help. `board get` не раскрывает задачи автоматически:
состав читается через `task list --board`, приложение-владелец — через `application get`.
Ключ владельца берётся из полученных references, не из префикса задач; у системной доски
неприменимое поле приложения опущено. Пустая страница не получает выдуманный пример.

`delete-preview` у feature, scenario, application, implementation, task и document показывает весь каскад
и все сохраняемые записи со снятием
ссылок, без страниц и усечения. Ключи, виды, ID, ревизии, счётчики и версия остаются
копируемыми непрозрачными значениями даже на узкой ширине. Число отзываемых связей не
превращается в выдуманный список их деталей. Без автора вместо исполнимого удаления
предлагается справка; с автором — явное подтверждение по показанной версии. Квитанция
удаления показывает результат каскада. Проверка оставшихся каталогов и снятых ссылок
описана в help удаления; обычная карточка не предлагает удалить запись.
Архивирование не заменяет удаление.
Снятие участия реализации также не является удалением.

`config get` показывает полный конфиг и действующее подключение: транспорт, источник
URL, способ выбора клиентского конфига и его режим. Если клиентский конфиг или реестр
отличается от конфига проекта, его путь показан отдельно. При HTTP пути проекта явно
помечены как серверные, не как клиентская база или реестр. Совместимые статусы
раскрываются полностью и на узкой ширине; машинные сведения находятся в
[`meta.connection`](CLI.md#config-get), не подменяют поля Config.

Каталог workspace показывает отдельно режим и URL Server, серверный реестр/конфиг,
клиентский конфиг, если отличается, и defaultProject. У недоступной регистрации
показаны причина и серверный путь; её ID не объявляется подтверждённым ID базы.
Выбор проекта для `config get --project` объясняется в help каталога.
Пути доступных проектов остаются в JSON
и адресном config get. Remote-only чтение не требует локальной копии реестра.

Workspace add/remove в text по умолчанию получают адресную компактную квитанцию,
без передачи соседних регистраций. Она показывает изменённый ключ, серверный реестр
и сохранённый entry либо факт removed; доступность проекта после регистрации
проверяется отдельным list. JSON по умолчанию сохраняет прежний полный каталог,
компактный DTO включается только `--projection compact`. Явный `--projection full`
доступен в обоих форматах: это выбор прежнего маршрута, не скрытый fallback.
List и compact-квитанции требуют `relay-project-catalog-v1`; отказ discovery направляет
к обновлению Server до операции, не к чтению локальных файлов.

Продуктовые карточки сохраняют собственные метаданные записи, когда их дал Backend.
У реализации сохранённая ручная отметка подписана отдельно от вычисляемой готовности;
снятое участие не выглядит выполнением. Список FI/SI показывает приложение и цель,
список приложений — сохранённую summary, не подстановку полного description.
Поиск и каталоги используют одну семантику полей и сортировки; полный текст остаётся в get.

При q Core может вернуть `match` — одно подтверждённое поле и его текст. В text это
«Совпадение в …», отдельно от аннотации; при truncated явно указано «фрагмент».
Совпадение в текущем ключе или названии не повторяется отдельной строкой: они уже
видны в заголовке. Пробельные разрывы фрагмента в обзоре схлопываются, управляющие
символы обезвреживаются; JSON сохраняет исходный фрагмент. Ограничение 240 единиц
UTF-16 относится к проекции match, не к полному Markdown записи. Разметка выделения
не добавляется, но исходные Markdown-маркеры могут присутствовать.
Если match не предоставлен, CLI не угадывает совпавшее поле. Прежний документный
excerpt остаётся допустимым самостоятельным основанием; совпавший body не дублируется
одновременно через match и excerpt.

В `document list` и `search --kind document` аннотация берётся только из сохранённого
summary. Для обзора пробельные разрывы схлопываются; свыше 200 графем выводится
«Аннотация (фрагмент)» с многоточием. Пустой summary не заменяется названием или body.
Поисковый excerpt, предоставленный Core при q, также схлопывает пробельные разрывы
и помечается отдельно:
«Совпадение в содержании (фрагмент)». При сортировке updated видна дата изменения.
Это обзор, не полное чтение: `document get` сохраняет полные summary и Markdown body.
Его text показывает точные числа прикреплений и уникальных целей, а адреса и полные
пояснения раскрываются через `document links`, описанную в help. JSON карточки не сокращён.
Если Backend предоставил metadata текущей записи, карточка показывает «Изменил»
и «Изменён» из этого блока; JSON также сохраняет автора и дату создания.
В старом ответе без metadata автор не угадывается, а прежняя предоставленная дата
document.updatedAt остаётся видимой. Это не история и не дополнительное чтение.
`document links` получает только страницу прикреплений, её адресный словарь и заголовок,
а `document section list` — страницу разделов. Небольшая страница больше не требует
полной карточки документа или PROJECT в клиенте; JSON этих страниц не расширен
служебными заголовками. Для HTTP нужен сервер с `relay-document-library-v1`:
несовместимость не исправляется скрытым полным get или локальным fallback.

Квитанция называет выполненное действие, его адрес и значимый результат, например
новую ревизию. Правила проверки сохранённого содержания находятся в help. UUID/ID и requestId не дублируются
в каждой карточке или квитанции ради полноты DTO: в text они нужны только для
адресации действия или диагностики. Например, ID этапа нужен вместе с ключом плана;
requestId остаётся корреляцией, а не гарантией безопасного повтора. Подробности ошибки
в text выбираются по смыслу диагностики; полные машинные поля доступны в JSON.

Полное содержание выводится как буквальный Markdown: заголовки, списки, цитаты,
inline-код, ссылки и fenced code сохраняют свои маркеры. Сохраняются в том числе
повторные пустые строки, начальные и конечные пустые строки непустого поля, отступы
и табуляция. Длинные строки Markdown и кода не переносятся принудительно и не
усекаются. Это не HTML-браузер, не исполнение кода и не лексическая подсветка.

Отображение применяет безопасный текст: пользовательские управляющие
последовательности не должны исполняться терминалом. Не считайте text побайтовой
копией исходного поля: служебные заголовки, разделители и обезвреживание управляющих
символов принадлежат представлению. Это не разрешение нормализовать Markdown.
В обычной работе читайте полный текст карточки; побайтовую
проверку содержимого выполняют отдельно при отладке CLI.

Необходимые служебные действия после содержания отделены линией и заголовком
«Команды CLI — вне содержания». Сам Markdown, включая похожие на команды строки,
не меняется. Это визуальная граница, не защита от подделки и не машинный парсер:
для программного разбора используйте JSON.

В `inspect graph list/context` словарь узлов содержит полные названия один раз;
отношения и пути используют короткие ключи, ID и ревизии. Концы рёбер вне страницы
узлов показаны отдельным адресным словарём, не увеличивающим счётчик страницы.
Стрелки рёбер обозначают сохранённое направление, пути — направление обхода;
петли и параллельные отношения не сворачиваются.

В list пояснение заключено между строками «Начало пояснения ID» и «Конец пояснения ID».
Полный Markdown внутри сохраняет отступы, fences и пустые строки; похожие на footer
или `npx` строки остаются пользовательским содержанием, не командами CLI.
Границы помогают чтению, но не гарантируют защиту от подделки: такой же текст может
находиться в самом пояснении. Для машинного разбора используйте JSON, не поиск `npx`.

## Страницы и полнота

Списки используют `--limit` и `--cursor`. Единственный общий footer из `Result.page`
показывает число выданных элементов, общий размер выборки, если он известен, и конец
либо продолжение; для live отдельно предупреждает о возможном изменении данных
между страницами. Предметные секции не добавляют собственные footer продолжения.
Копируйте предложенную команду целиком: она сохраняет команду, ref, фильтры,
явно выбранные config/project/server/local. В обычном проекте продолжение запускается
из того же каталога проекта без автоматически добавленных `--local`/`--config`.
Не переносите курсор в другой проект,
транспорт, команду или выборку и не редактируйте его вручную.

В JSON тот же `Result.page` становится `meta.page`: `count`, необязательный `total`, `limit`,
`nextCursor`, `nextCommand`, `consistency`. `count` — число элементов этой страницы,
а не всего списка; отсутствие `total` не означает ноль. Продолжение определяется
курсором, а не только наличием элементов: пустая страница может иметь продолжение.
Например, `Показано: 0 из 5 подходящих записей` вместе с `Есть продолжение` требует
следующего запроса, а не вывода о пустом составе. `limit` задаёт размер страницы,
но не доказывает ни общий размер, ни полноту ответа.

- `snapshot`: offset-продолжение сохраняет исходную версию и проверяет неизменность
  текущего состояния. Это guard, не доступ к историческому снимку. При конфликте
  начните чтение с первой страницы; CLI не подменяет версию свежей.
- `live`: данные между страницами могут измениться. Курсор не превращает такой
  backend в снимок; перед записью перечитайте целевую карточку.

Workspace project list получает только серверную страницу. Server проверяет guard
полного текущего каталога, включая доступность и идентичность; при VERSION_CONFLICT
(exit 4) начните без cursor. JSON сохраняет прежнюю форму data, а
`meta.paginationSource` равен `server-catalog-fingerprint`. Исторического снимка нет.
CLI-курсор ленты комментариев сохраняет исходный
native token backend вместе с подключением, ref, фильтрами и размером страницы.
Копируйте meta.page.nextCursor/nextCommand, а не внутренний data.nextCursor:
сырой backend token сохранён для совместимости DTO и напрямую CLI не принимается.
NextCommand может не повторять limit/фильтры — их восстанавливает CLI-wrapper.
У progress и inspect graph list limit действует отдельно на вложенные коллекции,
а count/total суммируют их элементы, не уникальные сущности.

Первая text-сводка `product overview` по умолчанию компактна: показатели и версия среза,
без повторных карточек подборок. `--view full` раскрывает подборки до пяти элементов.
Их заголовок сообщает полное число: «все N» либо «показано N из M» с отдельной
командой полного чтения. Это не страница и не footer продолжения: общий footer
относится только к карте продуктовых записей, а итоги сводки от `--limit` не зависят.
Полный список показателя работы читается режимом `product overview --metric`: у него
собственный footer и native-курсор, восстанавливающий метрику и блокер.
Продолжение text показывает только карту, не повторяет сводку. `--view map` читает
самостоятельную серверную страницу; для чтения карты/метрик того же обзора передайте
поле `Срез` в `--snapshot`. При конфликте начните обзор без snapshot/cursor.
Компактность text не сокращает прежний JSON: только явный view map меняет DTO обзора.

Аналогично `--projection compact` явно выбирает сокращённый DTO у plan list,
release list/plans/preview, application participation list и task dependency list.
Отсутствие опции сохраняет прежний JSON. Курсор связан с проекцией; полные описания
читайте адресно, а не считайте отсутствующее поле compact пустым содержанием записи.

CLI не ограничивает вывод байтовым бюджетом: параметр `--max-bytes` удалён.
Это не отменяет ограничения ввода, Core, HTTP или MCP. Если ошибку размера вернул
Core или транспорт, следуйте контракту этой операции: уменьшите выборку либо
прочитайте отдельные записи, но не считайте частичный результат полным контекстом.

```bash
npx @oim-dev/relay-cli task list \
  --limit 10
npx @oim-dev/relay-cli task list \
  --limit 10 \
  --format json
```

## Планирование и прогресс

В плане сохранённое состояние «Завершён» и текущие показатели выполнения — разные
факты. После повторного открытия задачи состояние плана сохраняется, хотя
`plan progress` может показывать «Не выполнено» и расхождение с завершением.
Аналогично «Выпущен», автор и дата выпуска релиза не исчезают при потере текущей
готовности. Состав читается из актуальных планов, а не исторического снимка выпуска.
Предметные основания — [планы](https://github.com/oim-dev/relay/blob/main/docs/domain/PLANNING.md)
и [релизы](https://github.com/oim-dev/relay/blob/main/docs/domain/RELEASES.md).

`plan stage get` показывает полное содержание этапа: краткое описание, Markdown
результата и условий завершения, ID этапа, ревизию плана и число задач в составе.
Актуальные задачи читайте через `plan stage task list` и проходите
все страницы. JSON карточки сохраняет явные `taskIds`; text не заменяет список задач
перечислением технических ID. Текст условий завершения сам не исполняется как тест.

Прогресс доступен для восьми видов: задачи, реализации, сценария, фичи, приложения,
продукта, плана и релиза. Он разделяет полный предметный итог и видимую часть каждого
вложенного списка, включая причины. Надпись «показано 1 из 3» описывает страницу,
а не долю выполнения. Отсутствие причин на странице не доказывает готовности.
`limit` применяется **к каждому списку отдельно**; общий `count` суммирует видимые
элементы и может превышать `limit`. `total` здесь также сумма размеров списков,
а не уникальных задач. Например, три списка по три элемента дают `count=9` при
`limit=3`. Готовность и уникальные предметные счётчики не пересчитываются по этим
девяти строкам; их смысл задан в [контракте прогресса](https://github.com/oim-dev/relay/blob/main/docs/domain/PROGRESS.md).

Совпавшая адресная причина может показываться рядом с уже видимой составляющей,
без повторной карточки. Сокращается только известный совпавший COMPONENT_INCOMPLETE;
самостоятельные причины, неизвестные тексты, NO_WORK и STATE_DIVERGED сохраняются.
При этом JSON и счётчики отдельных коллекций не меняются: объединённая строка text
не становится одним элементом всех исходных страниц. Причина критерия содержит его
точный ID и адрес задачи; чтение полного критерия объясняется в help прогресса.

Например, у завершённого плана после повторного открытия его задачи можно увидеть
следующие строки (это фрагмент ответа, без списков и команды продолжения):

```text
Уникальные задачи состава: 0/1

Состояние: Завершён
Можно начать: нет
Можно завершить: нет
Расхождение с завершением: есть
```

При `limit=1` тот же ответ может содержать одну задачу, один этап и одну из двух
причин: общий footer — `Показано: 3 из 4 подходящих записей` и `Есть продолжение`.
Это не противоречит лимиту и не означает три уникальные задачи.

## Условные подсказки

Постоянное знание об интерфейсе принадлежит `--help`. Подсказка в результате нужна,
если помогает продолжить конкретную неполную выборку, восстановиться после ошибки
или подтвердить явно запрошенный предпросмотр по его версии. Успешные карточки,
квитанции и полные страницы не получают статическое меню команд. Сведения о числе
элементов, границе глубины, live-выборке, ключах, ревизиях и run.id остаются данными.

Пагинация выводит одну команду продолжения только при наличии cursor, в том числе
на пустой странице с продолжением. Неполные подборки полного обзора и граница
графа могут иметь адресное продолжение по фактической неполноте. Компактный обзор
сохраняет `Срез` отдельным копируемым полем; help объясняет применение `--snapshot`.
Наличие данных о связях само по себе не повод печатать get каждой цели.
Сохранённые Markdown-поля, включая checkpoint.nextStep, не фильтруются как подсказки.

### Копируемые подсказки

Готовая подсказка адресного чтения, исправления ошибки или продолжения — одна
физическая строка с `npx @oim-dev/relay-cli`. В обычном проекте она короткая:
`npx @oim-dev/relay-cli document get DOC-1`. CLI не добавляет `--local` и путь
автоматически найденного конфига: следующую команду выполняют в том же проекте.
Явно переданные `--local`, `--config` и выбор через `RELAY_CONFIG` сохраняются;
значение config становится фактическим абсолютным путём. HTTP-подсказка сохраняет
сервер и выбранный проект. При обслуживании проекта workspace сохраняется прямой
local-доступ к его выбранному конфигу. Значения с пробелами и кавычками экранируются;
перевод строки внутри аргумента не превращается в разрыв команды. Копируйте всю
строку и учитывайте указанную оболочку: ANSI-C quoting `$'…'` для таких аргументов
поддерживается Bash/Zsh, но не каждой POSIX-оболочкой.

Не путайте готовую runtime-подсказку с авторским примером help или документации.
Для авторских примеров [COMMAND_STYLE.md](COMMAND_STYLE.md) задаёт многострочное
оформление именованных опций. Эти правила не требуют разбивать готовую подсказку
или opaque cursor на строки.

Help документного списка объясняет get по ключу, help разделов — фильтр по ID раздела,
help карточки — собственные прикрепления и полную компоненту графа. Эти маршруты
не повторяются в каждой странице или строке отношения.

## Pipe и ошибки

Штатный результат и штатная ошибка идут в stdout; stderr штатного вызова чист.
Ошибка имеет код и понятное сообщение, в text — также визуальную отметку.
Проверяйте код завершения и сообщение результата, а не наличие слова «ошибка» в пользовательском тексте.
Закрытие pipe получателем (`EPIPE`) считается штатным и даёт код 0.

Help группы не требует открытия проекта. Ошибка синтаксиса указывает help команды,
в которой возникла проблема. Потеря ответа после записи не доказывает отсутствие
изменения: сначала перечитайте состояние, не повторяйте вслепую. Скрытых повторов нет.
`CONFLICTING_OPTIONS` требует убрать несовместимые источники ввода и оставить не более
одного stdin; перечитывание ревизии эту ошибку не исправляет. Настоящий конфликт
ревизии требует сравнить сохранённую запись со своим изменением, не подставлять
свежую ревизию автоматически.

Отсутствие конфигурации ведёт к проверке каталога и подключения, а не к поиску
ключа записи. Неверный явно указанный путь нужно исправить (для remote-only —
убрать); `init` допустим только для заведомо нового проекта. При `CONFIG_NOT_FOUND`
предлагается копируемая `npx @oim-dev/relay-cli init --help` — только справка,
не создание поверх неизвестной базы.

`doctor check` показывает причины целостности отдельным адресным списком, а не JSON-массивом:
код, сообщение, доступные путь/адрес/поле и число проверок, обнаруживших причину.
Отсутствующий адрес не угадывается. Полные `details`, включая исходные schema issues
и перечень проверок, сохраняются в JSON.
HTTP-ошибка записи может содержать оболочку `serverDetails`, `requestId`, `url`:
text раскрывает серверную причину тем же адресным представлением, отдельно показывает
ID запроса и URL сервера. JSON сохраняет оболочку без изменений; ID запроса не означает
безопасного повтора записи.

После `GRAPH_CHANGED` предлагается чтение графа с тем же подключением, без повтора записи.
Повреждение индексов ведёт к явному локальному `storage reindex` после остановки писателей
и резерва. Повреждённый JSON или поле схемы сначала нужно восстановить: перестроение
индексов не исправляет содержание. Управляемые отношения изменяются у предметного владельца;
при наличии его адреса подсказка ведёт в `inspect resolve`, отдельно предлагается явное
`storage reconcile-relations`. Для него нужен автор. HTTP/workspace-подсказки оставляют
чтение на том же сервере, но не подставляют серверный путь в локальную команду обслуживания:
оператор выбирает реальную конфигурацию проекта на стороне Server.

Для reindex/reconcile-relations из локально выбранной регистрации workspace отказ
`LOCAL_CONFIG_REQUIRED` показывает одну прямую команду с конфигом этой базы,
а не предлагает перейти на Server. Полный путь и команда остаются копируемыми
на узкой ширине; подсказка сама ничего не выполняет.

В storage status/dry-run одинаковые блокеры объединяются по коду, сообщению,
следующему действию и смысловым атрибутам; все возвращённые пути/ID остаются видимыми.
Предупреждения и блокеры содержат не более первых 50 элементов с полным total,
без cursor. После устранения причин повторите диагностику. Пустой план не затрагивает
отношения и адреса: нули changes — не утверждение об отсутствии графа.
Обычный/legacy-WAL требует нового внешнего backup-dir; прерванная миграция использует
исходную копию. Подсказка с DIR явно является шаблоном, не готовой командой записи.

## Где сопровождается представление

Для разработчика: `src/terminal.ts` вычисляет среду, `src/presentation/` содержит
предметные рендереры. Общий `src/presentation/common.ts` задаёт `cardText`, `listText`
и `receiptText`: единый каркас, но не универсальный обход DTO. Поля и секции выбирает
предметный владелец. `src/presentation/markdown.ts` сохраняет Markdown,
`src/queries/result.ts` сериализует конверт, `src/output.ts` выводит ответ.
Общие сведения `Result.page` должны оформляться централизованно, а не отдельным
footer каждого предметного рендерера.
Готовые команды формируются через `commandInvocation` в `src/command-kit.ts`;
пагинация использует тот же фактический контекст подключения.
Подробности проверки и добавления команды — в [EXTENDING.md](EXTENDING.md).
Пути исходников относятся к checkout, а не обещают наличие TypeScript в npm-архиве.
