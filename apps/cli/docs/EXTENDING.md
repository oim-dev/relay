# Разработка и расширение Relay CLI

Руководство для разработчика команд, ввода и представления CLI. Пользовательский
синтаксис поддерживается в [CLI.md](CLI.md), оформление — в [TERMINAL.md](TERMINAL.md).
Исходники находятся в [репозитории Relay](https://github.com/oim-dev/relay/tree/main/apps/cli),
не в обязательном составе npm-пакета. Все команды разработки ниже выполняются
из корня checkout, если явно не указано иное.

Точные регистрации сверяются в CLI.md с createProgram и source help,
а сигнатуры общих средств — по исходникам. Не объявляйте предметную операцию
доступной только на основании нового имени группы или наличия метода SDK.

## Граница приложения

CLI разбирает аргументы, подключает backend, вызывает предметное действие и
представляет результат. CLI не владеет хранением и предметными инвариантами.
Общие правила находятся в [domain](https://github.com/oim-dev/relay/blob/main/docs/domain/README.md),
границы компонентов — в [архитектуре](https://github.com/oim-dev/relay/blob/main/docs/ARCHITECTURE.md).
Backend прямого Core и HTTP должен давать одинаковый предметный результат.

Новая возможность требует сначала определить пользователя (агент/человек), цель,
вход, наблюдаемый результат и владельца действия. Отделяйте ошибки разбора,
подключения, предметной операции и представления. Изменение text не должно менять
JSON или аргументы. Наличие метода SDK не означает готовности команды.

## Запуск и проверки

Для checkout требуются Node.js 22.13+ и pnpm 11.18.0+ согласно корневому manifest,
а также установленные зависимости workspace. `apps/cli/package.json` содержит
скрипты build/dev/typecheck/test/docs:check/package:check; отдельного lint-скрипта нет.

```bash
pnpm run build:cli
pnpm --filter @oim-dev/relay-cli run typecheck
pnpm run test:cli
pnpm --silent run dev:cli task list --help
```

Собранный вход — `apps/cli/dist/cli/main.js`; пользовательский вызов во всей справке,
примерах и подсказках — `npx @oim-dev/relay-cli`.
Вызов через npx проверяет выбранный им пакет и не доказывает работу текущего checkout.
Для запуска текущих исходников используйте `pnpm --silent run dev:cli <аргументы>`;
это путь ручной проверки изменений, не требующий запуска тестов.
`apps/cli/scripts/dev.mjs` сохраняет каталог вызывающего процесса через `INIT_CWD`:
при сценарии с данными это влияет на поиск конфигурации. `--silent` убирает
служебный вывод pnpm, но не переключает формат CLI; для JSON передавайте `--format json`.

### Собранный CLI и исходники в тестах

Стандартный маршрут — `pnpm run test:cli` из корня. Turbo запускает CLI test после
его build; build зависит от сборок зависимостей workspace. Так тесты используют
актуальный dist, а не случайно оставшийся бинарник. Корректный cache hit допустим;
успех source-прогона не заменяет проверку этой цепочки и собранного CLI.
Пакетный test script запускает `node --import tsx --test --test-concurrency=3 test/command-*.test.ts`:
одновременно выполняется не более трёх тестовых файлов.
Для стандартного прогона не устанавливайте `RELAY_CLI_TEST_SOURCE=1` и уберите
source-настройки загрузчика из окружения.

Тестовый helper `apps/cli/test/helpers/cli.ts` по умолчанию запускает
`apps/cli/dist/cli/main.js`. Прямой `pnpm --filter … exec node --test` обходит
Turbo-зависимости, поэтому перед адресным dist-тестом нужна актуальная сборка:

```bash
pnpm run build:cli
pnpm --filter @oim-dev/relay-cli exec node --import tsx --test test/command-plans.test.ts
```

Для быстрой адресной проверки исходников из корня checkout:

```bash
RELAY_CLI_TEST_SOURCE=1 TSX_TSCONFIG_PATH="$PWD/apps/cli/tsconfig.dev.json" \
  pnpm exec node --conditions=tasks-source --import tsx --test apps/cli/test/command-plans.test.ts
```

Здесь есть два независимых процесса:

- Родительский Node test runner загружает TypeScript-тесты через `--import tsx`,
  выбирает workspace-исходники через `--conditions=tasks-source` и получает абсолютный
  `TSX_TSCONFIG_PATH`. Dev-конфиг нужен также для импортов server-runtime с decorators.
- `RELAY_CLI_TEST_SOURCE=1` переключает `binary` helper на `src/main.ts`.
  `cliNodeArgs` добавляет дочернему CLI `--conditions=tasks-source` и `--import`
  с абсолютным адресом tsx через `import.meta.resolve("tsx")`. `cliEnv` задаёт
  абсолютный путь к `tsconfig.dev.json`. Это важно: cwd ребёнка — временная база,
  где нельзя рассчитывать на разрешение относительного loader или tsconfig.

Один `RELAY_CLI_TEST_SOURCE=1` не настраивает родительский runner. Не подменяйте
source/dist-различие общим утверждением «тесты прошли»: указывайте режим фактического
запуска. Package-тесты и ручной source launcher тоже не заменяют независимую
установку архива через [проверку поставки](RELEASING.md).

### Общие средства тестов

`test/helpers/cli.ts` предоставляет:

- `invokeRaw(cwd, args, options)` — отдельный CLI-процесс и `{code, stdout, stderr}`
  для human/help/ошибок; `invoke` добавляет `--format json` и разбирает `body`.
- `successful(result)` — проверку exit 0, пустого stderr и `ok:true` с возвратом
  конверта; `failed(result, code, exitCode = 2)` — проверку кода ошибки и завершения.
- `RunOptions` — `input`, `env`, `nodeArgs`, `timeoutMs`; таймаут останавливает
  дочерний процесс, а не оставляет его работать после теста.
- `tempDirectory(t)` — временный каталог с очисткой через `t.after`;
  `fixture(t)` — инициализированную через CLI базу, её `root`, JSON-вызов `run`
  и `create` для задачи на продуктовой доске с возвратом постоянного ID.
- `cliEnv` — окружение без унаследованных `RELAY_CONFIG`, `RELAY_SERVER_URL`,
  `INIT_CWD`, с тестовым автором; явные overrides теста имеют приоритет.
  `binary` и `cliNodeArgs` позволяют сохранить тот же режим при специальном запуске.

Общие средства help и HTTP находятся в `test/helpers/help.ts` и
`test/helpers/http.ts`. Используйте изоляцию helper, не рабочую память пользователя;
HTTP-сценарии также должны завершать только собственные серверы и процессы.

## Маршрут команды в коде

| Участок                                  | Ответственность                                                      |
| ---------------------------------------- | -------------------------------------------------------------------- |
| `src/main.ts`, `src/run.ts`              | Запуск, проектный префикс, ошибки Commander, exit code, EPIPE        |
| `src/program.ts`                         | Дерево команд и глобальные параметры                                 |
| `src/command.ts`                         | CommandDefinition, registerCommand, группы и общая справка           |
| `src/context.ts`                         | Runtime, подключение Backend, автор, параметры вывода, печать Result |
| `src/commands/`                          | Предметные адаптеры CLI                                              |
| `src/backend/connect.ts`                 | Выбор подключения через project-runtime                              |
| `src/input.ts`, `src/text-input.ts`      | Общие средства чтения ввода                                          |
| `src/presentation/`                      | Представления конкретных семейств                                    |
| `src/queries/result.ts`, `src/output.ts` | Конверт, сериализация и вывод ответа                                 |
| `src/terminal.ts`                        | Ширина терминала                                                     |

Текущий `CommandContext` содержит `backend`, `workspace` (сведения о проекте),
`runtime`, `output`, `globals`. В нём нет прежнего `context.tasks`; числовая доска
не является текущим входом. Общий Backend и адаптеры находятся в
`packages/project-runtime/src/backend`. Прямой доступ к файловой базе допускается
в явно локальном обслуживании, не как обход отсутствующего HTTP-метода команды.

## Добавление команды

Общий модуль нового интерфейса — `src/command-kit.ts`. Согласованные экспорты:
`textOption`, `readTextFields`, `paging`, `offsetQuery`, `pageResult`.
Используйте их для регистрации текстовых полей, чтения источников, общих параметров
страницы, адаптации offset-backend и формирования `Result.page`. Не копируйте
эту логику в семейства команд. Точные типы принадлежат этому модулю.

Например, в `configure(command)` текстовое поле регистрируется вызовом
`textOption(command, "description", "Полное описание")`, а в обработчике читается
через `await readTextFields(context, input.options, ["description"])`.
Полученный объект содержит только переданные поля; отсутствие description не
нужно заменять пустой строкой при update.

Для offset-backend последовательность следующая: зарегистрировать `paging(command)`,
получить query через `offsetQuery(context, options, command, filters, consistency)`,
вызвать backend и передать его ответ в
`pageResult(context, command, filters, query, data, consistency)` как `Result.page`.
Здесь `command` — массив сегментов команды и позиционных ref, а не строка запуска.
`offsetQuery` восстанавливает пропущенные фильтры из курсора в переданный объект
`filters`: запрос backend формируйте после этого вызова. `data` содержит `items`,
`total`, `nextOffset` и, для снимка, версию. Не применяйте offset-адаптер к backend
с собственным непрозрачным курсором.

Для native backend используйте `nativeQuery`/`nativePageResult`: они сохраняют
исходный token backend внутри CLI-курсора, восстанавливают фильтры и limit.
В JSON внутренний data.nextCursor не заменяет публичный meta.page.nextCursor.
Для реестра без проектного Backend используйте чистые `offsetQueryFor`/`pageResultFor`
с `PaginationContext { identity, defaultLimit, invocation }`: invocation — массив
неэкранированных аргументов, не shell-строка. Отпечаток текущего каталога служит
version для guard; это не серверный исторический снимок.

1. Найдите предметный метод Backend и его контракт. Если операция отсутствует,
   согласуйте её у владельца Core/Backend, не имитируйте последовательностью
   клиентских правок и не добавляйте отдельный запрос синхронизации графа.
2. Определите `CommandDefinition` в соответствующем семействе `src/commands/`.
   Для нового семейства подключите регистрацию в `src/program.ts`.
3. Через `configure` задайте аргументы и параметры. `requiredOption` обозначает
   синтаксически обязательный параметр; предметные условия проверяются схемой/Core.
4. Обработчик получает `context.backend` и `CommandInput`. Возвращает `data` и
   собственный `text` либо функцию рендеринга; для списка — также `page`.
   Общий адаптер печатает один ответ и единый footer страницы.
5. Добавьте справочник, тесты и согласуйте покрытие в общем каталоге возможностей.

Ниже самостоятельный пример формы регистрации существующего действия чтения,
а не предложение добавить вторую копию `task get`:

```ts
registerCommand(group, runtime, {
  name: "get <reference>",
  description: "Прочитать задачу с полным содержанием",
  arguments: { reference: "Ключ или постоянный ID задачи" },
  details: "Полученную ревизию используйте при следующем изменении.",
  examples: [["npx @oim-dev/relay-cli task get PRODUCT-1", "Прочитать задачу"]],
  async run(context, input) {
    const data = await context.backend.boardTasks.get(input.argument());
    return { data, text: (options) => boardTaskText(data, options) };
  },
});
```

`registerCommand` и `commandGroup` импортируются из `src/command.ts`, представление —
из `src/presentation/board-tasks.ts`. `group` и `runtime` передаёт регистрация семейства.
`input.options` содержит локальные опции команды, `context.globals` — глобальные;
`input.argument(index)` читает обязательный позиционный аргумент,
`optionalArgument(index)` — необязательный.

## Справка и совместимость

У каждой команды нужны русские назначение, объяснения позиционных аргументов и
параметров, ограничения и исполнимые примеры. `details` дополняет основной синтаксис,
а не скрывает обязательные поля. Группа без команды показывает help; help работает
без проекта и без открытия данных. Синтаксическая ошибка должна указывать help
того уровня, где она возникла.

Авторские примеры документации и help следуют каноническому пользовательскому
[стилю вызовов Relay CLI](COMMAND_STYLE.md): он задаёт копируемое оформление,
короткие вызовы, кавычки и сохранение текстового ввода. Не дублируйте эти правила
в справочнике каждой команды. Проверяйте shell-синтаксис примеров через `bash -n`
без исполнения операций над базой.
В примерах разработки сохраняйте source launcher `pnpm --silent run dev:cli`.
Готовые runtime-подсказки — другой случай: `commandInvocation` формирует одну
копируемую физическую строку с фактическим контекстом. Не применяйте к ней
многострочное оформление авторских примеров help.

Глобальный `--version` показывает версию CLI. Новые списки используют `--limit`
и `--cursor`, а не публичные offset или параметры версии снимка.
Для существующего аргумента проверяйте совместимость по фактической регистрации.
Не добавляйте обещания истории и безопасного повтора: requestId — только корреляция.

Канонический справочник содержит отдельный заголовок `### полный путь команды`
для каждого реального листа, например `### task get`, а также все параметры.
Общие наборы флагов можно объяснять один раз с явной привязкой к командам.
Документ должен объяснять действие без обязательного чтения исходника или help.

## Ввод и предметная запись

Передавайте Markdown строкой, сохраняя пустые строки и значимые пробелы. Не
преобразовывайте его в массив строк JSON-хранилища: это задача Core. Не навязывайте
временные файлы. Для каждого поддержанного текстового поля регистрируйте пару
`--field <text>` и `--field-file <path|->`: здесь field — имя конкретного поля,
например description, а не универсальный флаг. `-` означает stdin. Одновременная
передача обоих источников одного поля — ошибка; во всём вызове допускается только
один потребитель stdin. Общих неявных `--stdin`/`--file` нет.

При добавлении чтения файла/stdin используйте общий InputReader, проверяйте
конфликт источников, UTF-8, размер и ошибки. Полностью считайте ввод **до** предметной
мутации и её блокировки, чтобы не удерживать запись базы в ожидании stdin.

Update передаёт только предоставленные поля. Не добавляйте значения по умолчанию
из create и не обнуляйте пропущенные тексты/массивы. Отсутствие поля, явная пустая
строка, false и очистка — разные случаи; допустимость определяет предметная схема.
Если backend принимает полное содержание, адаптация должна сохранить непереданные
поля и исходную проверяемую ревизию, а не перезаписать конкурентное изменение.

Для записи получите автора через `author(context)`. Передайте прочитанную ревизию
или версию и requestId по контракту метода. Скрытых повторов запросов нет.
После конфликта нельзя автоматически
подставлять свежую ревизию; после потери ответа нельзя безусловно повторять.
Публикация комментария не требует ревизии задачи, но повтор может дублировать сообщение.
Формат 4 обслуживается `storage migrate`; product/graph migrate в CLI не
зарегистрированы. Команд истории не добавляйте под видом диагностики.

## Представление и транспорт

Не печатайте напрямую из предметного обработчика: верните `Result`, чтобы сохранить
общий конверт и обработку ошибок. Байтового бюджета вывода CLI и `--max-bytes` нет;
лимиты ввода, Core, HTTP и MCP сохраняются. Ошибку нижнего слоя нельзя превращать
в успешное усечение. JSON:
`{ok:true,data,meta?}` / `{ok:false,error:{code,message,details?}}`. Штатные ответы и
ошибки идут в stdout. Help и версия — отдельные текстовые исключения, EPIPE — код 0.

По умолчанию выводится text независимо от config format; JSON выбирается явно
через `--format json`. Для человека нужен предметный рендерер: карточка, страница,
квитанция, прогресс или ошибка, с метаданными, содержанием и следующим шагом.
Универсальный обход DTO не заменяет его. Используйте `cardText`, `listText` и
`receiptText` из `src/presentation/common.ts`: предметный рендерер выбирает поля,
секции и команды, общий слой отвечает за каркас. Заголовок сохраняет ключ и название
в естественном регистре; значимые метаданные выравниваются, пустые необязательные
поля пропускаются, числовой `0` остаётся. Компактный список включает фильтры и
краткие строки, а не полные тела карточек. Квитанция объясняет действие и предлагает
чтение, но не подменяет его. UUID/ID и requestId в text нужны по смыслу адресации
квитанции или диагностики, а не как обязательное дублирование всех машинных полей.
JSON, включая технические адреса, requestId и details ошибки, не меняется ради text.

Используйте существующий безопасный текст и `renderMarkdown`; экранную ширину
измеряйте через `string-width`, не `.length`. Обычные метаданные и summary могут
адаптироваться по ширине. Полный Markdown передавайте без `.trim()`, схлопывания
пустых строк, отступов и табуляции, hardwrap и усечения. Проверка `.trim()` допустима
для решения, показывать ли пустую секцию, но не для изменения её непустого тела.
Сохраняйте literal Markdown, включая fenced code; не исполняйте ANSI пользователя.
Текст всегда без цветного ANSI; не регистрируйте `--color` и не включайте
ANSI-оформление по TTY, NO_COLOR или FORCE_COLOR. Сохраняйте Markdown, отступы,
карточки, таблицы и адаптацию к ширине терминала, но не цветную подсветку блоков.
Подробнее — [терминальное представление](TERMINAL.md).

Полное описание `get` не усекается. Большие вложенные коллекции выносите в отдельные
list, а не обрезайте без продолжения. `Result.page` — единый источник footer text
и JSON `meta.page`: `count`, `total?`, `limit`, `nextCursor`, `nextCommand`,
`consistency`. Предметные рендереры не добавляют второй footer.
Пустота `items` не определяет конец: при `nextCursor` нужно продолжение. Неизвестный
`total` не заменяйте нулём. Полные предметные итоги не вычисляйте по видимой странице.
В progress восьми видов limit действует на каждый вложенный список, а count/total
суммируют элементы этих списков: count может быть больше limit. Для плана/релиза
разделяйте сохранённое completed/released и текущую готовность. Карточка этапа
сохраняет полные тексты и ведёт к отдельному списку актуальных задач.

Курсор привязывается к команде, ref, фильтрам, проекту и транспорту. Offset API
остаётся внутренней деталью адаптера. Для snapshot сохраняйте версию первой страницы:
конфликт требует начать новое чтение, не подставить свежую версию. Это guard текущего
состояния, а не чтение исторического снимка. Live backend
нельзя объявлять снимком только потому, что CLI упаковал offset в cursor.
Для адресных подсказок используйте `commandInvocation(context, tokens)` из command-kit,
а не ручную склейку запуска с `context.globals`. Он сохраняет эффективное подключение,
в том числе выбранное через конфиг или окружение: local с абсолютным config либо
server-url с проектом. Явные actor/format также сохраняются. Пагинация использует
тот же контекст и сохраняет фильтры/ref. Вход helper — неэкранированные аргументы,
выход — строка с `npx @oim-dev/relay-cli` и shell-экранированием. Не экранируйте её
повторно и не пропускайте через wrap даже на узкой ширине. Проверяйте пробелы,
апострофы и переводы строк внутри аргумента; ANSI-C quoting требует Bash/Zsh.

Подключение должно выбираться до открытия локальной базы. HTTP-ошибка не разрешает
fallback на локальные данные. Workspace требует проект и сервер; remote-only с
явным URL не требует конфиг. Явный проект сохраняется в `meta.project`.
Точные правила у [project-runtime](https://github.com/oim-dev/relay/blob/main/packages/project-runtime/docs/CONFIGURATION.md).
REST-контракт принадлежит [server-runtime](https://github.com/oim-dev/relay/blob/main/packages/server-runtime/docs/API.md),
генерируемый SDK не правится как источник контрактов.

## Достаточная проверка изменения

Выберите сценарии по изменению, не заменяйте их одной типизацией:

- help без конфига, группа без подкоманды, неизвестный параметр/команда;
- human и JSON, чистый stderr, ненулевой exit code ошибки, EPIPE;
- пустота, Unicode, полный многострочный Markdown, узкая ширина, ANSI, pipe;
- отсутствие цветного ANSI в text/help/ошибках при TTY и любых NO_COLOR/FORCE_COLOR;
- отклонение удалённого `--color`, сохранение структуры и безопасного текста без цвета;
- полный большой ответ без CLI byte limit, сохранённые ограничения ввода и транспорта;
- stdin/file/inline, конфликт источников, несколько stdin и отсутствие мутации при ошибке ввода;
- update только переданных полей, отдельная проверка пустой строки, false и очистки;
- единый footer и meta.page, пустая страница с продолжением, конец списка;
- страницы со всеми фильтрами, ref, проектом, конфигом и транспортом;
- конфликт снимка без подмены версии, явное live-продолжение;
- копируемая подсказка без жёстких переносов при узкой ширине;
- local/HTTP, ошибка сервера без локального fallback;
- успешная запись и отдельное чтение сохранённых отношений;
- потеря ответа, повтор как новая попытка, конфликт прочитанной ревизии.

### Критерии командного набора тестов

Набор `apps/cli/test/command-*.test.ts` организует проверки по реальным командам и
семействам:

- Предметные сценарии — `command-product`, `command-feature`, `command-scenario`,
  `command-application`, `command-implementation`, `command-documents`,
  `command-boards`, `command-tasks`, `command-task-criteria`, `command-task-comments`,
  `command-plans`, `command-releases`, `command-progress`, `command-search`.
- `command-foundation` — общий ввод, представление, конверт, пагинация и запуск.
- `command-help` и `command-documentation` — справка, регистрации, примеры,
  канонические страницы, ссылки и поставляемые материалы.
- `command-package` — правила упаковки и запуска; не замена установке архива.
- `command-services` — проект, конфигурация, граф, диагностика и обслуживание.
- `command-http` — HTTP/local, workspace, выбор подключения и продолжение страниц.
- `command-recovery` — сбои, конфликты, потеря ответа, повреждения и миграции.

Все перечисленные имена имеют суффикс `.test.ts`. Общие средства запуска и изоляции
находятся в `test/helpers/`. Добавляя команду, дополняйте предметный сценарий и
проверку соответствия runtime-регистраций покрытию; наличие имени команды только
в help не доказывает исполнение операции. Имя файла, новый helper или успешная
сборка сами по себе не подтверждают прохождение набора.

Достаточный сценарий выполняет реальную command operation на изолированной базе,
проверяет квитанцию/ошибку, отдельно читает сохранённое состояние и отношения, затем
сопоставляет human-вывод и JSON. Unit-тест рендерера с вручную собранным DTO полезен,
но не доказывает путь регистрации → ввод → Backend → чтение → вывод. Нужны как
local-, так и HTTP-сценарии, не только mock вместо предметного действия.

Обязательные акценты при изменении представления и пагинации:

- На наборе не менее 300 задач пройти страницы до конца без пропусков и дублей;
  сравнить полный набор адресов с ожидаемым. Повторить с фильтрами и сочетаниями
  фильтров, проверить их применение до пагинации, а не к уже выбранной странице.
- Проверить в text фильтры, ключи и конец/продолжение, в JSON — соответствующий
  `meta.page`; отдельно пустую страницу с курсором, неизвестный total, snapshot
  conflict и live. Полный счётчик не подменяется количеством видимых строк.
- Для всех восьми видов progress проверить состав, причины, независимость итогов
  от страницы и сумму нескольких вложенных списков, превышающую per-list limit.
  Повторное открытие задачи должно менять текущую готовность, но не сохранённые
  completed плана и released релиза. Прочитать полные тексты этапа и его задачи.
- Проверить одинаково доступное полное Markdown-содержание на ширинах 24, 40, 100
  и 160: повторные и краевые пустые строки, отступы, табуляцию, длинный код, Unicode
  и маркер в конце большого текста. Проверить отсутствие ANSI и сохранение нуля.
- Готовую подсказку не только сравнить как текст, но и разобрать/выполнить как команду
  чтения в том же контексте. Проверить конфиг с пробелами, проект, URL из окружения,
  ref и фильтры; запускать checkout, а не случайную опубликованную версию через npx.

Snapshots фиксируют понятный читателю результат. Нормализуйте только заранее
определённый недетерминизм — например, случайные ID, время и временный корень,
сохраняя связи между повторяющимися значениями. Нельзя стирать пробелы, Markdown,
строки, счётчики, фильтры или команды, чтобы snapshot прошёл. Ожидания проверяются
независимо по пользовательскому контракту, а не вычисляются тем же рендерером или
копией его алгоритма. Обновление snapshot требует чтения смыслового diff.

Отдельно сверяйте дерево Commander с заголовками и флагами канонического CLI.md
и help без проекта. Это проверка справки, не замена предметным сценариям.
Успешная сборка не доказывает читаемость терминала или сценарий HTTP.

Для адресной проверки Markdown можно вызвать существующий helper без сборки приложения:

```bash
pnpm exec prettier --check apps/cli/AGENTS.md apps/cli/README.md apps/cli/docs/EXTENDING.md apps/cli/docs/TERMINAL.md
node --input-type=module -e 'import {checkDocumentation} from "./apps/cli/scripts/lib/documentation.mjs"; console.log(await checkDocumentation(process.cwd(), ["apps/cli/AGENTS.md", "apps/cli/README.md", "apps/cli/docs/EXTENDING.md", "apps/cli/docs/TERMINAL.md"]));'
git diff --check -- apps/cli/AGENTS.md apps/cli/README.md apps/cli/docs/EXTENDING.md apps/cli/docs/TERMINAL.md
```

Helper проверяет локальные переходы и якоря, не доступность внешних HTTPS-страниц.
Полный `docs:check` охватывает документацию репозитория и установленный скилл;
его результат не равен адресной проверке выбранных файлов. При изменении CLI.md
добавьте его в адресный список; сверку дерева выполняйте после готовности регистраций.

## Документация и поставка

Поддерживайте точный синтаксис в локальном CLI.md, общую семантику — у владельца
domain, общий реестр покрытия — только в CAPABILITIES. Производные материалы скилла
не являются вторым авторским справочником. Генерация и проверка скилла выполняются
отдельно назначенным владельцем после согласования канонических источников;
Markdown-правка не требует автоматического запуска общей генерации.

README пакета должен быть коротким и понятным на npm. Поставляемые документы входят
в `files: [dist, README.md, CHANGELOG.md, docs]`: соседние docs могут ссылаться друг
на друга относительно, а внешние общие документы — через HTTPS GitHub `main` по
каноническим путям. Не полагайтесь на наличие корневой `docs/` в архиве.

Проверка установленного комплекта — `pnpm run package:check`; это отдельная проверка
поставки, не обязательное действие каждой Markdown-правки. Процесс версий и публикации
не копируется сюда: [руководство поставки](RELEASING.md). Сообщайте фактически выполненные
команды, ограничения и оставшиеся процессы отдельно от прочитанного кода.
