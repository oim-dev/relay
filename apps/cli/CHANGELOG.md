# История изменений

## Не выпущено

- Материалы библиотеки: `document create/update` принимают `--document-format markdown|link`,
  `--url` и повторяемый `--tag` (update — также `--clear-tags`); для ссылки body —
  необязательное пояснение. Формат выбирается `--document-format`, глобальный
  `--format` по-прежнему выбирает text/json.
- `document list` фильтрует по `--document-format`, повторяемому `--tag` (все теги) и
  `--unattached`; карточки показывают формат, адрес и теги. Продолжение списка
  повторяет флаг для каждого элемента массива-фильтра вместо объединения через запятую.
- Новые команды: `document facets`, `document materials <ref>` и `document bulk
move|add-tags|remove-tags|status|pin`. Массовая операция печатает полный поэлементный
  результат и завершается с кодом 1 при хотя бы одном отказе.
- `document link/unlink` без `--legacy` меняют одну связь через Core relateDocument;
  `document link --next-relation` меняет тип связи. Отсутствующая связь в unlink теперь
  `RELATION_NOT_FOUND` (exit 3) вместо `INVALID_ARGUMENT`. Требуется сервер с
  `relay-document-materials-v1`.

### Совместимость

- Новая версия читает документы и карточки индекса прежних версий без миграции:
  формат считается `markdown`, теги — пустыми.
- После того как новая версия записала документ с `documentFormat`/`tags` или карточки
  индекса, прежние CLI, Server и MCP падают с `IO_ERROR` «Unrecognized keys …» при чтении,
  записи и `doctor`. Откат на прежнюю версию не поддерживается — только восстановление
  резервной копии базы, сделанной до обновления.
- Новые клиенты с прежним Server читают данные, но новые поля, фильтры и операции
  документов получают `SERVER_INCOMPATIBLE`. Обновляйте CLI, Server и MCP одной версией.

## 0.9.2

- Расширен `product overview`: согласованный срез проекта с паспортом, задачами,
  блокерами, планами, релизами, знаниями, досками и документами в text и JSON.
  Краткие подборки показывают полные счётчики и команды дальнейшего чтения.
- Добавлен `product overview --metric` для полных постраничных списков: очереди проверки,
  прямых блокеров, работы вне открытых планов, незавершённой работы по доскам и подготовки

  показывает задачи, которые выбранный блокер задерживает напрямую.
- Продолжение обзора проверяет `snapshotVersion` всего среза, а не только версию
  продуктового состава. При изменении данных между страницами возвращается
  `VERSION_CONFLICT`: начните чтение заново без `--cursor`.
- Для HTTP-обзора обновите и перезапустите Relay Server до `0.9.2`: прежний ответ
  без нового среза несовместим. Детализация требует серверной возможности
  `relay-overview-metrics-v1`; при её отсутствии возвращается `SERVER_INCOMPATIBLE`.
- Совместный выпуск с `@oim-dev/relay-server@0.9.2` и `@oim-dev/relay-mcp@0.9.2`.

## 0.9.0

### Несовместимые изменения и переход

- Перестроено дерево CLI: 129 конечных команд с предметными группами верхнего уровня
  `feature`, `scenario`, `application`, `implementation`, `document`, `board`, `task`,
  `plan` и `release`. Вместо общих `entities create/update/get` используйте действия
  соответствующей сущности; поиск доступен через `search`, техническое чтение —
  через `inspect`. Команды `projects` перенесены в `workspace project`.
- Обычные предметные операции принимают именованные флаги вместо JSON-объектов.
  Update изменяет только явно переданные поля. Текст можно передать непосредственно
  или через поддерживаемый парный флаг `--field-file <path|->`; `-` читает stdin.
  Переданный набор целей или состава заменяет весь набор, если действие не названо add/remove.
- Вывод по умолчанию всегда `text`, независимо от `output.format` в конфигурации.
  Для машинного разбора явно указывайте `--format json`. Оболочки успеха
  `{ok, data, meta}` и ошибки `{ok, error}` сохранены; это не гарантия неизменности
  содержимого `data`. Например, ID созданной задачи теперь читается из `data.ref.id`.
- Удалены `--color` и `--max-bytes`; `output.maxBytes` больше не ограничивает CLI.
  Текст не содержит ANSI-оформления даже при TTY или FORCE_COLOR. Ограничения ввода
  и транспорта сохраняются.
- Для постраничного чтения используйте `--limit` и `--cursor`. В JSON продолжение
  берите из `meta.page.nextCursor` или `meta.page.nextCommand`, не из `data.nextCursor`.
  При конфликте версии начните выборку заново: курсор не открывает исторический снимок.

### Читаемый вывод и работа агента

- Переработаны карточки, списки, квитанции записи, прогресс и ошибки: полное описание
  читается через `get`, большие связанные коллекции — отдельными списками.
  Команды продолжения сохраняют проект, подключение и фильтры.
- Справка содержит русские описания аргументов, структурированные пояснения и копируемые
  примеры через npx; она доступна без открытия проекта.
- Добавлено краткое руководство агента. Обновлённый отдельный скилл Relay требует
  сначала прочитать его, а полный справочник и стиль вызовов открывать по необходимости.
  Скилл не является runtime-зависимостью CLI.
- Переработаны командные тесты, включая local/HTTP, ввод, страницы, ошибки и документацию.
  В CI проверки CLI отделены от остальных наборов; установочный smoke адаптирован
  к новым командам, квитанциям создания и метаданным страниц.
- Совместный выпуск с `@oim-dev/relay-server@0.9.0` и `@oim-dev/relay-mcp@0.9.0`.
  Формат хранения относительно 0.8.0 не меняется.

Для перехода обновите команды и обработчики JSON по
[справочнику CLI](https://github.com/oim-dev/relay/blob/main/apps/cli/docs/CLI.md)
и [руководству агента](https://github.com/oim-dev/relay/blob/main/apps/cli/docs/AGENT_GUIDE.md).
Ссылки ведут на main; точный синтаксис установленной версии проверяйте через `--help`.

## 0.7.0

### Несовместимые изменения

- Удалены команды общего автоматического аудита `entities history`, `graph history`
  и `task history`. Чтение и публикация пользовательских сообщений остаются в `task comment`.
- `--request-id` служит только корреляции, а не дедупликации: сохранённый ответ прежней
  команды больше не возвращается. HTTP-записи не повторяются автоматически при сбое.
  После потери ответа перечитайте текущее состояние и связи; перед новой публикацией
  комментария прочитайте обсуждение. Осознанный повтор может создать дубликат даже с тем же ID.
- Результаты операций планирования и релизов описывают текущее состояние, не историю операций.

### Переход базы и совместимость

- `npx @oim-dev/relay-cli --local --config .relay/config.json storage migrate` явно переносит
  поддерживаемые legacy-базы и форматы 1/2/3 в формат хранения 4 (оболочки записей — версия 3).
  Чтение и `storage reindex` не выполняют этот переход автоматически.
- Хранятся текущие данные и пользовательские комментарии, без автоматического аудита,
  `events`/`planningEvents`, `receipts`/`requests` и сохранённых результатов команд.
  Миграция сохраняет ID, алиасы, ревизии, связи и полное содержание комментариев.
- До миграции остановите старые процессы записи, сохраните резервную копию и обновите
  используемые CLI, Server и MCP до согласованного комплекта `0.7.0`. История и квитанции
  удаляются необратимо; откат возможен только восстановлением старой базы из резервной
  копии с соответствующей версией пакетов, не автоматическим понижением формата.
  После переноса выполните `validate` и перечитайте данные.
- CI проверяет комплект на Node.js 24. Поле `engines` пакетов не изменено:
  это изменение CI, а не отмена заявленной поддержки Node.js 22.

## 0.3.0

### HTTP-режим и параллельные агенты

- CLI выбирает HTTP по `--server-url`, `TASKS_SERVER_URL` или `server.url`. Глобальный
  `--local` принудительно включает Core; при сетевой ошибке локальная запись автоматически не включается.
- Единый интерфейс операций с локальным и HTTP-адаптерами. Существующий `@relay/rest-sdk`
  включён в npm-дистрибутив. В HTTP-режиме рабочая копия агента не открывает `.tasks` и `.tasks-runtime`.
- API получает автора каждой мутации отдельно; `claim`, записи и метаданные сохраняют
  `--actor` / `TASKS_ACTOR` конкретного агента. Автор сервера остаётся значением по умолчанию для UI.
- Рабочие команды поддерживают HTTP, включая `overview`, дерево, зависимости, фильтры
  истории, проверку проекта, JSON, текст и курсоры. `init`/`migrate` обслуживают локальные данные.
- `--request-id` у добавления логов и комментариев: дедупликация в Core внутри документа,
  сохранение ключа при перезапуске, повтор через HTTP или `--local`; другой текст или автор дают конфликт.
- Явная `--if-revision` сохраняет проверку версии. Запросы без неё используют текущий
  документ под блокировкой, как в прежнем локальном CLI.
- Проверки десяти Git worktree, потерянного ответа после записи, остановки сервера,
  аварийного `--local` и установленного npm-архива.

### Обзор и веб-доска

- Команда `overview [id]`: прогресс родительских задач, доступная работа, настраиваемые
  статусы проверки и рейтинг блокеров по прямому влиянию и будущей готовности к `claim`.
- Обзор использует один снимок Core, учитывает внешние зависимости дерева и сохраняет

Конфиг версии 1 совместим; секция `server` необязательна.

### Веб-доска и поставка

- CLI публикуется из `apps/cli` в pnpm workspaces/Turbo-монорепозитории; приватные Core, Contracts и Server Runtime включаются в самодостаточный архив вместе с веб-интерфейсом.
- Зависимости монорепозитория управляются pnpm 11.18.0: общий `pnpm-lock.yaml`, внутренние ссылки `workspace:*`, установка в CI с `--frozen-lockfile`. Готовый архив проверяется через npm/npx и публикуется в npm registry.

- Dev-сервер запускается из TypeScript-исходников и сохраняет работоспособность при очистке `dist`; проверка типов работает отдельным watch-процессом.
- CLI и самостоятельная точка входа сервера находятся в `apps/`, общий NestJS runtime, ядро и API-контракты — в `packages/`; тесты находятся внутри приложений и пакетов.
- Реализован NestJS/Fastify API с OpenAPI 3.1 и Swagger: задачи, доска, назначения, комментарии и отчёты напрямую через Core.
- Курсорная пагинация снимков доски и истории, проверка ревизий и единый формат HTTP-ошибок; схемы запросов и документации на основе Zod/Core.
- SSE отслеживает изменения из API/CLI, замену файлов и конфигурации; HTTP/OpenAPI и потоковые интеграционные тесты.
- Команда `server` поднимает общий сервер с React-доской на `/`: готовые HTML, JS, CSS и шрифты включены в npm-пакет в `dist/web`. API и Swagger работают на том же порту; SPA-маршруты изолированы от API и отсутствующих ресурсов.
- `build:server` собирает статику `apps/web` вместе с backend; standalone-сервер раздаёт её из `apps/web/dist` независимо от рабочего каталога.
- Настройка порта: `--port` → `TASKS_PORT` → `server.port` в `tasks.config.json` → `3000`. Значение `0` выбирает свободный порт. `init` создаёт настройку, `config get` показывает её, старые конфиги используют `3000`.

### Хранилище и команды

- Плоское хранилище `.tasks/<id>.json`; миграция прежней структуры, служебные файлы вне каталога задач.
- Сохраняемый порядок карточек и чтение через `list --sort board`.

- Единственный числовой `id` задачи: от 1, следующий равен максимальному существующему плюс один. Файлы и все ссылки используют тот же ID; поле `number` удалено.
- Формат задач v2 и команда `migrate`: перенос UUID-документов со всеми связями и контекстом, сохранение исходников и возобновление после прерывания.
- Рабочий `list`: все незавершённые задачи по группам, включая заблокированные; `--all` включает конечные статусы, явный `--status` выбирает заданный статус.
- Количество задач в `list` ограничено только байтовым бюджетом или явным `--limit`; большие списки имеют продолжение и счётчик «показано N из M». `--all` совместим с `--limit` / `--cursor`.
- ID блокеров рядом со статусом; подсказка истории для пустого рабочего списка.
- Цвет каждого статуса в конфиге через `statuses.<имя>.color`.
- Справка всех команд с объяснениями, аргументами, общими параметрами и примерами; подсказки при ошибках.
- `create "Название"` в дополнение к `--title`; `claim --status` для атомарного назначения и перехода.
- Единый формат регистрации команд, общие источники текстового ввода и руководство расширения CLI.
- Прямое чтение карточки и её связей; один снимок графа на изменение вместо повторного чтения всей базы.
- README со сквозным жизненным циклом задач через `npx`: постановка, зависимости, проверка, доработка, передача работы, завершение и отмена; playground в новом формате.

### Терминал

- Цветные статусы, таблицы, карточки, дерево связей и оформление комментариев и отчётов.
- Подсветка Markdown и распространённых блоков кода; перенос по ширине терминала.
- Управление цветом через `--color auto|always|never`, `NO_COLOR` и `FORCE_COLOR`.
- Текстовые ответы для всех команд и ошибок; JSON-режим без ANSI-последовательностей.
- Байтовая пагинация учитывает полное оформление, включая цветовые коды.
