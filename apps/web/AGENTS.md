# Правила работы с Relay Web

Эти локальные правила обязательны для всех исполнителей, включая QA, при исследовании,
изменении и ревью клиентского кода `apps/web`. Они дополняют [корневой AGENTS.md](../../AGENTS.md).
Если общие инструкции уже переданы средой, повторно читать их не нужно.

## Обязательная подготовка

- Web разрабатывается **строго по React Reference и Unit Architecture**. Для нового
  и изменяемого кода обязательны их применимые правила, а не только стиль соседних файлов.
  Самовольные исключения, ослабление типов и отключение линта вместо исправления причины запрещены.
- До работы с клиентским кодом загрузи `react-reference` и `unit-architecture` инструментом
  skills и полностью прочитай их `SKILL.md`, а также профиль React SPA из React Reference.
  Если загрузчика нет, прочитай установленные файлы; пути ниже указаны от корня репозитория:
  `.agents/skills/react-reference/SKILL.md`, `.agents/skills/unit-architecture/SKILL.md`,
  `.agents/skills/react-reference/reference/application/architecture/project-profile.md`.
- Уже загруженные и прочитанные актуальные источники в текущем контексте повторно не читай.
  По картам skills выбирай относящиеся к задаче разделы, правила кода и инструкции библиотек;
  для исследования читай адресно, а не весь reference. При расширении задачи дополни чтение.
- Установка dev-навыков описана в [DEVELOPMENT](docs/DEVELOPMENT.md#источники-инструкций-и-создание-компонентов).
  Это инструменты разработки, не пользовательский Relay skill. Отсутствие обязательного
  источника или существенная неопределённость блокируют реализацию: сообщи оркестратору
  конкретный недостающий источник или вопрос; не реализуй по памяти.

## Адресные источники и границы

- Начни с [README](README.md). Выбирай по задаче [архитектуру](docs/ARCHITECTURE.md),
  [путь человека и ограничения](docs/USAGE.md), [маршруты](docs/ROUTING.md)
  и [методы разработки](docs/DEVELOPMENT.md).
- Покрытие интерфейсов сверяй с [CAPABILITIES](../../docs/CAPABILITIES.md), предметные
  правила — с нужным документом в [docs/domain](../../docs/domain). Не создавай локальную
  копию матрицы готовности, предметных схем или полного перечня API.
- При REST-интеграции читай [HTTP-контракт](../../packages/server-runtime/docs/API.md)
  и [разработку SDK](../../packages/rest-sdk/docs/DEVELOPMENT.md); загрузи `rest-api-codegen-ru`
  либо прочитай `.agents/skills/rest-api-codegen-ru/SKILL.md`. Внутренности CLI/MCP
  не входят в обязательное чтение без реального стыка задачи.
- До реализации установи ответственность, ближайшего владельца, слой, необходимость
  отдельного юнита, публичный контракт/фасет, потребителей и зависимости. Прочитай нужные
  главы `.agents/skills/unit-architecture/reference/docs`; существующий код не доказывает
  корректность архитектуры. Кратко изложи план и проверяемый пользовательский результат.
- Бизнес-правила принадлежат Core; Web представляет данные Server через доменные адаптеры
  и общий SDK. Не компенсируй отсутствие API предметными расчётами или вторым запросом
  синхронизации из UI. Нужный контракт согласуй через оркестратора; не вводи параллельный
  transport и не правь generated-код вручную.

## Новый TSX и профильные навыки

- Каждый новый прикладной `.tsx` создавай закреплённым генератором через pnpm по текущему
  [README шаблонов](.templates/README.md). До запуска прочитай инструкцию
  `.agents/skills/react-reference/reference/application/components/tsx-generation.md`
  и все файлы выбранного шаблона; проверь отсутствие целевого каталога.
- Не заменяй генерацию ручным созданием или копированием. Не запускай её поверх существующей
  реализации и не используй `--overwrite`. Адаптируй заготовку в том же изменении.
  Правка и перенос существующего TSX не требуют перегенерации; системные исключения
  ограничены чистым запуском и связующей конфигурацией по React Reference, не Providers/guards.
- Другие skills выбирай по реальной задаче: `svg-sprites-ru` — для `@gromlab/svg-sprites`,
  `template-generation` — при наличии для работы над генерацией и шаблонами.
  Их локальные инструкции: `.agents/skills/svg-sprites-ru/SKILL.md` и
  `.agents/skills/template-generation/SKILL.md`. Отсутствие `template-generation` в lock
  не делает его обязательной внешней установкой и не отменяет обязательную TSX-генерацию.

## Проверка и результат

- При изменении кода приложения выполни из корня `pnpm run lint:web`,
  `pnpm run typecheck:web`, `pnpm run build:web`. Отдельно проверь применённые правила skills,
  владельцев, фасеты, вложенность, свёрнутый граф зависимостей и циклы, включая type-only
  и динамические импорты: линт и сборка не доказывают соблюдение всей архитектуры.
- Автотесты фронтенда **не добавлять** — это принятое решение пользователя.
  Не вводи Vitest из общего reference. Выполнение человеческого UX доказывай отдельно
  браузерной приёмкой затронутого пути через **agent-browser**, а не одной типизацией.
- Используй собственные временные данные, сервер и свободные порты, отдельный экземпляр
  headless-браузера с уникальной `--session tasks-web-<суффикс>` и конфигом
  [agent-browser.json](agent-browser.json). Не используй пользовательский профиль,
  `--cdp` или `--auto-connect`; `--headed` допустим только по явному запросу пользователя.
- Методы и команды бери из [DEVELOPMENT](docs/DEVELOPMENT.md#проверки-изменения-приложения)
  и актуального `--help`. После действия получай свежие refs; при SSE ожидай наблюдаемое
  состояние, не `networkidle`. Используй `a11y`, `console`, `errors` и скриншоты;
  автоматический аудит не заменяет визуальную оценку.
- Проверь обе темы и ширины **1440 / 1024 / 768 / 390**, длинный текст, переполнение,
  клавиатуру, touch-доступность, начальный/возвращаемый фокус, Escape и reduced motion.
  По применимости проверь прямой URL, Back/Forward, reload, совместимость, фильтры и возвраты;
  черновики, ошибки чтения/записи, восстановление, конфликты, SSE, поздние ответы и изоляцию
  A → B → A; для списков — продолжение, дубли/пропуски и сохранность прокрутки.
- Закрой только свою сессию и свои процессы, не используй `close --all`. Недоступность
  собственного headless-браузера сообщи как блокер; пользовательские скриншоты пригодны
  для визуальной оценки, но не подтверждают непройденные интерактивные сценарии.
- Для изменённых файлов выполни адресные `prettier --check` и `git diff --check`;
  для документации — проверку ссылок по [DEVELOPMENT](docs/DEVELOPMENT.md#проверки-только-документации).
  Изменение только документации не требует серверов, браузера или проверок исходного кода.
- Постоянный журнал агента не создавай. В ответе оркестратору передай изменения, причины,
  затронутые контракты/документы, команды и фактические результаты, блокеры и следующий шаг.
  Для нового TSX укажи генерацию и пути; для браузера — маршрут, данные, состояние, тему,
  ширину и наблюдения. Отдели статическую сверку от запуска, перечисли непроверенное
  и оставшиеся собственные процессы/ресурсы.
