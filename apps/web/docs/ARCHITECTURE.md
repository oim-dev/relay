# Архитектура Web

Web — браузерная React SPA, представляющая данные Relay Server. Эта страница объясняет
локальных владельцев и путь изменения; общие границы Core, Contracts и runtime-пакетов
заданы в [архитектуре Relay](../../../docs/ARCHITECTURE.md).
Вход в приложение — [README](../README.md), карта адресов — [ROUTING](ROUTING.md).

## Владельцы и Unit Architecture

Корень приложения — `apps/web/src`. Алиасы слоёв определены в
[tsconfig.json](../tsconfig.json); Vite читает их через `resolve.tsconfigPaths`.
Браузерный профиль ESNext/Bundler отделён от NodeNext серверных пакетов.

- `app` — запуск, подключение готовых Providers, дерево URL и метаданные крошек:
  [app.tsx](../src/app/app.tsx), [router](../src/app/router/app-router.tsx).
- `compositions/layouts` — устойчивые каркасы и навигация:
  [project](../src/compositions/layouts/project), [product](../src/compositions/layouts/product).
- `compositions/screens` — законченные экранные пути: выбор проекта, обзор проекта,
  доска с окном задачи, продукт, библиотека, планы, релизы, связи.
- `compositions/route-boundaries` — отдельное поведение ветки:
  [product-snapshot](../src/compositions/route-boundaries/product-snapshot)
  подключает снимок для части продуктовых страниц.
- `compositions/widgets` — самостоятельные области UI:
  [page-breadcrumbs](../src/compositions/widgets/page-breadcrumbs),
  [planning-workspace](../src/compositions/widgets/planning-workspace),
  [entity-documents](../src/compositions/widgets/entity-documents),
  [entity-delete](../src/compositions/widgets/entity-delete).
- `domains` — предметные адаптеры, модели, операции и lifecycle чтения: project,
  workspace, product, product-overview, boards, board-tasks, entities, documents, relations, planning, releases.
- `infra` — технические механизмы HTTP, SWR-конфигурации, SSE, browser storage.
- `ui` — общие визуальные возможности: темы, Markdown, состояния страниц, канбан DnD.
- `shared` — чистые значения и преобразования без сети, storage и браузерного lifecycle.

Полные правила доступны после [подготовки dev-навыков](DEVELOPMENT.md#источники-инструкций-и-создание-компонентов):
Unit Architecture — `.agents/skills/unit-architecture/SKILL.md`, профиль React SPA —
`.agents/skills/react-reference/reference/application/architecture/project-profile.md`
(пути от корня репозитория; локальные копии не входят в чистый checkout).
Профиль закрепляет фасеты `index.ts` для статического API и `lazy.ts` для динамического.
Ленивый экран экспортирует `Component`; фасет не реализует JSX и предметные операции.
Межюнитные импорты идут через фасет и алиас слоя, внутренние — относительные.
Группы `layouts`, `route-boundaries`, `screens`, `widgets` не являются юнитами.

Разрешённые направления: `app` подключает все слои; `compositions` использует
`domains`, `infra`, `ui`, `shared`; `domains` — `infra`, `ui`, `shared`;
`infra` — `ui`, `shared`; `ui` — `shared`. Зависимости одного слоя допустимы без циклов.
Вложенный юнит доступен непосредственному родителю, но не импортирует родителя,
предков или соседних детей. Координация остаётся у родителя.
Provider принадлежит своему механизму, а не месту подключения: например,
`ThemeProvider` остаётся в `ui/themes`, `DataProvider` — в `infra/query-cache`.

`domains/product-demo`, несмотря на имя, — действующий адаптер постоянного продукта
к прежнему UI, не автономный мок. Его использование не означает, что планы и релизы
хранятся в демонстрационном состоянии: они используют собственные домены.

## Тема и цветовые роли

Цвета принадлежат юниту [ui/themes](../src/ui/themes) и устроены в два слоя:

1. Примитивные палитры — только в [theme.config.ts](../src/ui/themes/config/theme.config.ts)
   как палитры Mantine: нейтральные `gray` и `dark`, акцент `ultramarine` (`#3e5bff`
   в светлой теме, оттенок 4 — в тёмной), положительное состояние `jade`, прежняя `teal`.
   Предупреждение, ошибка и информация используют стандартные палитры Mantine `orange`,
   `red`, `blue`; колонка «К выполнению» — `grape`, градиент главной карточки — `cyan`.
   Hex-значения не повторяются в CSS.
2. Семантические роли `--tasks-*` — в [variables.css](../src/ui/themes/styles/variables.css):
   каждая связывает оттенки палитр со светлой и тёмной схемой через `light-dark()`.
   Группы ролей: поверхности (`canvas`, `chrome`, `surface`, `surface-quiet`, `raised`,
   `subtle`, `border`, `border-strong`), уровни экрана-дашборда от дальнего к ближнему
   (`backdrop` — серая область экрана, `stage` — светлая сцена с содержимым, `card` —
   тонированная карточка блока, `tile`, `tile-hover`, `tile-border` — светлый подблок,
   `tile-translucent` — полупрозрачный подблок поверх градиента;
   `card-feature` — градиент главной карточки), текст (`ink`, `muted`, `soft`), инверсная
   поверхность (`inverse-surface`, `inverse`, `inverse-muted`, `inverse-accent`), акцент
   (`accent`, `accent-hover`, `accent-ink`, `accent-subtle`, `accent-contrast`) и
   выделенный показатель (`highlight`, `highlight-hover`, `highlight-ink` — ссылки
   на акцент; `icon-chip-highlight`, `icon-chip-hatch`, `icon-chip-inverse` — подложки
   иконок показателей), состояния `success`/`warning`/`danger`/`info` с парами `-surface` и
   `-border`, `focus-ring` и `selection`, роли диаграмм (`column-*` для шести колонок,
   `column-cancelled-fill` — бледная заливка отменённых, `completed`, `blocked`,
   `chart-track`, `chart-grid`), прогресс (`progress`, `progress-track`), декоративная
   штриховка показателя (`hatch` — нейтральные полупрозрачные полосы, `hatch-surface` —
   основа под ними) и тени (`card-shadow`, `card-hover`, `raised-shadow`). Прежние имена
   сохранены, включая `surface-quiet`, которую сейчас не использует ни один экран;
   `--tasks-warning-ink` — совместимый псевдоним `--tasks-warning`. Роли-градиенты и
   штриховки (`card-feature`, `hatch`) содержат значение `background`, а не цвет.

Акцентные полосы прогресса и величин оформляются одним способом — вариантом
`<Progress variant="accent">` Mantine. Вариант подключён в `theme.config.ts` через
`classNames` и описан в [progress.module.css](../src/ui/themes/styles/progress.module.css):
толщина, скругление, дорожка `progress-track` и заливка `progress`. Экраны не держат
собственных копий этих стилей; остальные `Progress` приложения сохраняют прежний вид.

CSS Modules и свойства компонентов используют только роли `--tasks-*`, без hex/rgb/hsl,
выбора палитры вида `color="orange"` и прямых `--mantine-color-*` по смыслу статуса.
Локальная CSS-переменная компонента допустима как ссылка на роль, например
`--stage-color: var(--tasks-column-done)`. Прозрачность и смешения (`color-mix()`,
alpha) задаются только в теме отдельной ролью в `variables.css`, например
`--tasks-icon-chip-hatch` или `--tasks-tile-translucent`; компонент ссылается на роль.
Геометрия диаграмм задаётся inline: доля высоты столбца — переменной `--share`, длина
полосы — значением `Progress`. Экран «Обзор» соблюдает это
правило полностью; часть старых экранов ещё выбирает палитры Mantine напрямую.

Чтобы добавить цвет, добавьте роль в `variables.css` со значениями для обеих схем,
при необходимости — новую палитру в `theme.config.ts`, проверьте контраст (текст ≥4.5:1,
крупный текст и значимые индикаторы ≥3:1, в том числе на градиентах и штриховках)
и используйте роль в компоненте. Палитра `ultramarine` в CSS используется только
в `--tasks-accent`; производные роли (`accent-hover`, `accent-ink`, `accent-subtle`,
`inverse-accent`, `selection`, `progress`, `progress-track`, `card-feature`, `highlight*`,
`column-in-progress`) смешиваются из него в теме. Колонка «В работе» окрашена акцентом,
как выделенный показатель «В работе»; бейджи статуса старых экранов берут то же имя
палитры из `TASK_COLUMNS`. Смена акцента — правка одной роли `--tasks-accent` или палитры
`ultramarine` без изменения компонентов.
Акцент не является единственным признаком ошибки: ошибки используют `danger`, текст
и значок.

## Путь данных и предметного действия

```text
Композиция → публичный доменный хук / операция → доменный адаптер
          → infra/tasks-api → общий REST SDK → Server → Core
```

[tasks-api](../src/infra/tasks-api/tasks-api.ts) создаёт клиент из общего SDK.
`getProjectApi(projectId)` закрепляет неизменяемый проектный HTTP-контекст:
`/api/v1/projects/:projectId/...`. Относительный base URL подходит и для Vite-прокси,
и для SPA, поставляемой сервером. В компонентах нет необходимости заводить второй transport.
DTO преобразуются у доменного владельца, не в JSX.

HTTP-контракт описан в [Server runtime API](../../../packages/server-runtime/docs/API.md),
генерация — в [разработке REST SDK](../../../packages/rest-sdk/docs/DEVELOPMENT.md).
`packages/rest-sdk/src` принадлежит генератору: исправление контракта выполняют через
источник OpenAPI и генерацию, не ручной правкой клиента под форму Web.

GET для отображения проходит через SWR-хук домена. Общая политика
[DataProvider](../src/infra/query-cache/providers/data-provider/data-provider.tsx)
задаёт дедупликацию чтений, ограниченный повтор чтения после ошибки и обновление при фокусе.
Мутации вызываются явно; доменный lifecycle обновляет затронутые GET-ключи.
Подтверждённые серверные данные не становятся вторым постоянным клиентским store.

Предпросмотр несохранённого состава релиза — отдельный POST, а не GET-кеш.
[useReleasePreview](../src/domains/releases/hooks/releases.hook.ts) связывает результат
с проектом и полным выбором планов, отвергает поздний ответ предыдущего расчёта
и предоставляет явное обновление.

Предметное действие не дополняется вторым запросом Web для синхронизации графа.
Связи сохраняет владелец операции в Core; визуальный контекст не вычисляет отношения
из названий и не заменяет предметный выбор. Правила — в
[контракте связей](../../../docs/domain/CONTEXT.md).

## Проект, маршруты и область жизни

[RelayScreen](../src/compositions/screens/relay/relay.screen.tsx) разрешает проект из URL
и подключает `ProjectScope` с ключом постоянного ID. `useProjectBasePath` строит адреса
со slug, `useProjectId` задаёт область запросов, кеша, подписок и черновиков.
Смена slug не меняет идентичность; глобальный изменяемый active project не нужен.

React Router подключает каркасы и экраны через фасеты. Предметное чтение не перенесено
в `loader/action`. Граница `product-snapshot` нужна паспортным и каталоговым страницам,
но не библиотеке документов, адресному чтению сценария/реализации, планам и релизам.
Их загрузка не требует полного снимка библиотеки или продукта.
Крошки собираются из метаданных `app/router` общим виджетом, а не каждым экраном.

## Черновики, конкуренция и неопределённая запись

Формы используют Mantine `useForm`; черновой ввод редактора отделён от SWR-данных.
[browser-storage](../src/infra/browser-storage) предоставляет механизм `sessionStorage`,
а формат, ключ и исходную ревизию определяет владелец формы. Ключи включают проект
и редактируемую запись; session storage разделяет вкладки. Планы и релизы используют
версированные форматы `server-v2`, которые нельзя молча смешивать со старой моделью.

SSE-обновление не означает разрешения подставить свежую ревизию к старому вводу.
Конфликт требует явного решения; успешная запись или явный отказ очищает черновик.
Отказ browser storage должен быть виден пользователю: сохранность при reload
в этом случае не гарантируется. Черновики отдельных действий имеют свои сроки жизни;
это не универсальный журнал всех нажатий и запросов.

`requestId` — корреляция, не идемпотентность. Нет гарантии безопасного повтора мутации,
постоянного журнала квитанций или API истории операций. После потери ответа сначала
перечитывают состояние, а затем решают, требуется ли новая отправка. Повтор GET
в SWR нельзя трактовать как политику повтора записи. См. [восстановление](../../../docs/guides/RECOVERY.md).

## SSE и постраничное чтение

[workspace-events](../src/infra/workspace-events/events.ts) разделяет один `EventSource`
между подписчиками одного ID проекта. `changed` и восстановление подключения
инициируют REST-перечитывание через доменные подписки; heartbeat не является изменением.
Механизм закрывает поток и таймеры без подписчиков, учитывает StrictMode, закрытие
потока прокси и `pagehide/pageshow` при BFCache. На каждую карточку не нужен свой SSE.

Обзор проекта — пример такой доменной подписки. Экран
[overview](../src/compositions/screens/overview/overview.screen.tsx) получает данные
только из [product-overview](../src/domains/product-overview): адаптер читает
`GET /api/v1/projects/:projectId/product/overview` проектным клиентом `getProjectApi`
и проверяет ответ схемой `productOverviewSchema` из Contracts, маппер готовит модель экрана, хук `useProductOverview` хранит её
под SWR-ключом `["product-overview", projectId]` (`getProductOverviewKey`). Web не пересчитывает показатели:
все числа, подборки и готовность приходят из общего расчёта Core.

Полные наборы сверх подборок экран не вычисляет, а читает существующими фасетами.
Раскрытая группа «Требует внимания» вызывает `useBoardTasks` из
[board-tasks](../src/domains/board-tasks) с тем же фильтром, что и подборка
(`column=in-progress`, `column=review` или `readiness=blocked`, без доски), — это
`GET /board-tasks` по всему проекту порциями по 40 с продолжением и перечитыванием по SSE;
подписи колонок берутся из `TASK_COLUMNS`, ошибка — из `BoardTaskError`. Запрос выполняется
только после раскрытия. Каждую загруженную порцию экран упорядочивает по доскам в порядке
каталога `useBoards`, затем по `rank` и ID; порции выводятся в порядке загрузки, поэтому
продолжение не перемещает уже показанные задачи. Задачи из подборки показываются
её карточкой с адресными причинами, у остальных ключ блокера берётся из уже известных
задач, иначе показывается ID. Каталог досок раскрывается через `useBoards` из
[boards](../src/domains/boards): это тот же SWR-кеш, что у навигации проекта, поэтому
отдельного запроса нет, а продолжение идёт порциями по 50. Счётчики задач есть только
у досок из среза обзора; полный каталог их не содержит. Число загруженных страниц
каталога общее для всех потребителей проекта, и потребители только перечитывают данные.
`useBoards` подписан на `workspace-events`: первый сигнал подписки пропускается, соседние
сигналы объединяются за 100 мс, затем все загруженные страницы перечитываются с первой
(SWR `revalidateAll`), и их число не сбрасывается. Поэтому показанные доски, фокус
и прокрутка сохраняются. Каждая следующая страница читается в версии только что прочитанной
предыдущей, так что после смены версии каталога страницы разных версий не склеиваются
и не дают дублей. При `BOARD_CHANGED` между страницами показывается ошибка
с «Перечитать доски», а показанные данные остаются.

Показатели оператора (`snapshot.operator`: проверка обязательств, прямые блокеры, работа
вне открытых планов, незавершённая работа по доскам, открытые планы с выполненным составом,
подготовка выпуска) маппер переводит в модель `operator` того же обзора; подборки
показываются сразу, без отдельных запросов. Полный состав каждой группы, включая
затронутые задачи одного блокера, читает `useOverviewMetric` того же домена через
`getProductOverviewMetric` сгенерированного SDK (`GET /product/overview/metrics/:metric`,
проектный клиент) и проверяет страницу схемой `productOverviewMetricPageSchema`. Записи
страницы приходят как `OverviewMetricEntry` с видом (задача, затронутая задача, блокер,
доска, план, релиз), поэтому экран выводит подборку и полный список одним компонентом.
Перед первым запросом домен проверяет возможность `relay-overview-metrics-v1` в
`GET /context` (отдельный SWR-ключ на проект); без неё запрос не выполняется,
а ошибка `UNSUPPORTED` объясняет несовместимость версий.

Страницы привязаны к `snapshotVersion` показанного обзора: SWR-ключ страницы —
`["product-overview-metric", projectId, request, snapshotVersion, cursor]`, первая страница
передаёт `version`, следующие — `nextCursor` предыдущей страницы той же версии.
Собственной подписки на поток у списков нет: SSE перечитывает обзор, новая
`snapshotVersion` меняет ключи, и `useSWRInfinite` с `persistSize` читает заново то же
число страниц (не сбрасывая его к первой), а `keepPreviousData` оставляет прежние
записи до прихода новых. Записи с прежним ID не пересоздаются, поэтому раскрытие,
фокус и положение сохраняются; если запись с фокусом исчезла, `MetricFrame` переводит
фокус на запись, вставшую на её место, а в пустом списке — на заголовок показателя.
`VERSION_CONFLICT` (или устаревший курсор) становится ошибкой `SNAPSHOT_CHANGED`: домен
сразу перечитывает обзор по его ключу, и список читается заново по новой версии;
страницы разных состояний не склеиваются. Страница версии неизменна, поэтому
повтор по фокусу, reconnect и при монтировании не нужен; «Перечитать список» повторяет
весь загруженный объём.

Хук подписывается на общий поток `workspace-events` (один `EventSource` на проект,
номер сигнала `sequence` монотонен в пределах страницы). Первый сигнал подписки
отражает уже известное состояние и чтения не вызывает — начальное чтение выполняет SWR.
Каждый следующий `connected` или `changed` запрашивает перечитывание; heartbeat
игнорируется. Уведомления объединяются до 300 мс тишины, но не дольше 1 с от первого в пачке; одновременно
выполняется не более одного чтения, а изменение во время чтения вызывает ещё одно после
его завершения. Состояние актуальности `live`, `refreshing`, `connecting`, `offline`,
`stale`, `storage-error` выводится из сигнала потока и результата перечитываний
с приоритетом: `storage-error` и `offline`, затем `stale` (последнее повторное чтение
не удалось, показаны прежние данные), затем `refreshing` при незавершённом чтении.
Polling нет; replay пропущенных событий нет — после переподключения обзор перечитывается целиком.

Ошибка перечитывания не заменяет показанные данные: они остаются с предупреждением
и «Повторить чтение». Ошибка первого чтения показывает экран ошибки, а `workspace-error`
показывается отдельно как ошибка хранилища. При смене проекта меняется ключ кеша и подписка,
поэтому поздний ответ прежнего проекта не попадает в обзор нового. После HTTP-отказа,
закрывающего `EventSource`, повторное подключение идёт с задержкой 1 → 2 → 4 с (не более 4 с).

У списков сохраняются фильтры, запрошенный объём и предусмотренная API версия продолжения.
[read-api-pages](../src/infra/tasks-api/helpers/read-api-pages.ts) не означает загрузку
всего каталога. Сводная готовность приходит с сервера по полному составу, а не считается
по загруженным карточкам. Гарантии версии различаются между API: старые продуктовые
offset-списки нельзя объявлять единым снимком без поддержки такого продолжения.

## Визуальный контекст

### История работы

[work-history](../src/domains/work-history) владеет проверкой capability
`relay-work-history-graph-v2`, компактными graph-чтениями SDK, runtime-проверкой по Contracts,
ожидаемыми ошибками, SWR и общим `workspace-events`. Ключи graph/point/support включают
capability v2 и ID проекта, поэтому прежний кеш v1 не подставляется после обновления;
query основного холста всегда project-wide, `order=desc`. `useSWRInfinite` последовательно перечитывает
запрошенный объём от первой страницы с её версией. Объединяется только непрерывный
префикс одной версии; загруженные концы исключаются из `boundaryNodes`, рёбра дедуплицируются.
`openEnds` сохраняет все незавершённые ветки независимо от возраста последней точки.
Авторство берётся из `point.runId → runs`, не из `latestRun`; полные материалы читаются
отдельным point-запросом только при открытом модальном окне.

Вложенный `graph-point-modal/ui/branch-points` использует `useGetBranchPoints`
того же домена. Адаптер вызывает существующий SDK `getWorkHistoryGraph` с `ref=ID ветки`,
`includeChildren=false`, `order=desc`, `limit=20`, проверяет ответ
через Contracts и принадлежность каждой записи выбранной ветке. Используется общий
кеш проверки capability `relay-work-history-graph-v2`. Список содержит те же точки,
что и линия графа, включая lifecycle; заголовки и аннотации компактные, полный
материал выбранной записи по-прежнему читает point API. Ключи включают проект, ветку,
смещение и версию; последовательное продолжение и общий SSE не смешивают версии страниц.
Этот список не зависит от загруженных точек графа и не включает дочерние ветки.
Экземпляр `GraphPointModal` закреплён за проектом, а не адресом точки: при переключении
сохраняются DOM модального окна и блокировка фоновой прокрутки. После чтения новой точки
заголовок получает фокус, содержимое возвращается к началу. Список допускает передачу
прокрутки внешнему контейнеру окна при достижении своего края.

[Экран](../src/compositions/screens/work-history/work-history.screen.tsx) координирует
URL-выбор точки, вложенные `history-graph` и `graph-point-modal`. Прежние каталог, фильтры,
дерево и текстовая лента удалены. `history-graph` владеет read-only React Flow, локальной
hover/focus-карточкой и задачей ELK в собственном Worker. Позиции нод и маршруты берутся из
результата `elk.layout`, не из прежнего SVG-роутера. `BaseEdge` рисует `edge.sections`.
Для split/join и sequence используются NORTH → SOUTH. `clipHistoryJunctions` убирает
только концевой участок, совпадающий с родительским стволом, и обрезает горизонтальный
стык по внешнему краю его штриха (`HISTORY_EDGE_WIDTH / 2`). Так выход остаётся прямым,
а стрелка закрытия смотрит горизонтально в родительскую линию, не заходя внутрь неё.
Другие углы скругляются радиусом до 8 px, ограниченным соседними сегментами.
Закрытия `branch-end`/`root-end` используют `ArrowClosed` без обводки. Стрелка рисуется
на отдельном концевом фрагменте исходного маршрута: SVG `marker-end` на всём разрезанном
path ошибочно добавил бы стрелки перед каждым разрывом пересечений.
Внешний круг каждого реального маркера — 40×40, как bbox ELK; внутри отображается
иконка события. `GraphPoint` не рендерит `WorkAuthorAvatar`: аватар оператора есть
только в `point-preview` и `graph-point-modal`. Постоянной полосы подписей нет:
вложенный `point-preview` представляет имя агента и клиента, событие, время и summary,
затем поручение и оператора в локальной hover/focus-подсказке. Он использует уже загруженные
point/run, не делает запросов материалов; аватар относится к оператору, не к агенту.
Маркеры корневой работы и субагентов одинаково круглые. Сплошные линии обозначают
корневую работу, пунктирные — работу субагента. Флаг роли принадлежит
метаданным каждого реального ребра, включая fork/join, и не зависит от границы страницы.
Наведение не меняет непрозрачность остальных веток.

Колонки — входные ограничения interactive phases ELK. Ветка получает одну колонку
для всех своих точек и якорей. Обход в глубину размещает поддерево рядом с родителем
раньше соседних поддеревьев. Занятость проверяет полный видимый интервал; две незавершённые
ветки одного поручения не делят колонку даже без одновременных записей. Закрытые
непересекающиеся участки могут переиспользовать колонку.
Интервал родительского ствола расширяется снизу вверх по дереву до строки над последней
видимой активностью потомков. Прозрачные `extent`-якоря продолжают родительскую линию,
не создавая событий. Reader проверяет вертикальность стволов, разделение parent/child
и горизонтальные стыки с внешним краем родительской дорожки.
`markHistoryCrossings` отмечает разрывы только во внутренних пересечениях независимых
сегментов ELK: приоритет у оси, затем у незавершённой работы, при равенстве — у вертикали.
Эти разрывы меняют только отрисовку, не предметные рёбра и не положение точек.
Цвет зависит от ID ветки, не от слота. При одинаковом `at` каждая точка получает собственную
визуальную подстроку: стабильный причинный порядок использует sequence, загруженные
parent birth, origin intent, parentSequence и child-close-before-parent. Противоречие
даёт явную ошибку, отсутствующие события не создаются; времена, API items и пагинация
не меняются.

Рисуются только типизированные серверные sequence/fork/branch-end/root-start/root-end,
включая пересекающие окно связи. Fork и join используют якорь родительской линии на времени
создания/закрытия ребёнка, не далёкую по времени точку исходного intent. Обе терминальные
ветки (`completed` и `cancelled`) замыкаются визуально; explicit acceptance не управляет
линией возврата и остаётся содержанием checkpoint. Последняя точка из `openEnds`
рисуется на настоящем времени, включая точку вне страницы, с отметкой незавершённости.
Искусственных `head`-нод и пунктирных продолжений до верхнего края нет. Изолированные
старые точки и ось явно выравниваются ELK по центру строки (`alignment=CENTER`).
Технические anchors прозрачны и не выбираются,
но не используют `hidden=true`, иначе React Flow мог бы скрыть связанные рёбра.

Пока новый layout считается, показывается предыдущий согласованный срез вместе с его
счётчиками. Смена проекта, данных и размонтирование завершают Worker; поздний результат
проверяется по поколению и не заменяет текущий. Начальный масштаб читаемый (1), без
автоматического `fitView` длинной истории. SSE и страницы сохраняют zoom и экранную позицию
видимого point через камеру, не через отдельный перенос нод без routes. Верхний внутренний
компонент `unfinished-sessions` получает адреса из того же согласованного snapshot;
нажатие подводит последнюю настоящую точку по вертикали, подсвечивает и фокусирует её,
не меняя горизонтальную позицию и масштаб. Сброс вида
использует общую константу исходной камеры и возвращает zoom 1. Открытие Modal
не запускает layout и не сбрасывает камеру. Приватный `context-canvas` другого экрана
не импортируется: переиспользуются установленные React Flow/ELK, не чужой предметный UI.

Доменный `WorkAuthorAvatar` использует авторский снимок оператора и
[infra/gravatar](../src/infra/gravatar): SHA-256, кеш хешей/отказов в памяти страницы,
без ключа API, Profile API или отправки email в URL. Изображения запрашиваются при
видимости; ошибка не мешает читать граф и оставляет локальный fallback. `RunAttribution`
представляет человека, агента и Git-снимок в модальном окне без дополнительного GET.
`ui/markdown-view` поддерживает необязательный `headingStartLevel`: первый
реальный заголовок Markdown начинает заданный уровень контейнера, вложенность сохраняется
без пропусков уровней. Нормализация работает по remark-дереву, не затрагивает кодовые блоки
и исходную строку. Без этой опции прежнее отображение и `headingOffset` сохраняются.

### Связи сущностей

`domains/relations` владеет данными графа. Вложенный
[context-canvas](../src/compositions/screens/relation-context/ui/context-canvas)
владеет раскладкой, камерой и линиями React Flow; ELK работает в Worker.
Расчёт освобождается при смене и размонтировании, поздний результат не должен заменять текущий.
Диаграмма использует ограниченный `GET /graph`; полный `GET /graph/context` вызывается
в материалах выбранной продуктовой цели задачи. Эти пути не взаимозаменяемы.
Режим дерева не отменяет дополнительных связей и циклов исходного графа.
