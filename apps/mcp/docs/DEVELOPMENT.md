# Разработка Relay MCP

Этот документ описывает владельцев кода, регистрацию и проверку агентского интерфейса.
Пользовательские аргументы и подключение принадлежат [MCP.md](MCP.md), общие границы —
[архитектуре Relay](../../../docs/ARCHITECTURE.md), предметные правила —
[контрактам domain](../../../docs/domain/README.md). Не переносите бизнес-правила
из Core в MCP и не поддерживайте второй пользовательский справочник в профиле агента.

## Маршрут вызова

```text
MCP-клиент → stdio или Streamable HTTP /mcp → tools / projectTool
          → Projects.withBackend → project-runtime HTTP Backend
          → REST SDK → Relay Server / server-runtime → Core
```

MCP — процесс со stdio или HTTP-транспортом, не встроенный Core и не владелец базы.
`src/stdio.ts` подключает те же инструменты к stdin/stdout без слушающего порта.
Discovery не требует доступного API; вызовы используют обычный Projects Backend.
EOF и сигналы закрывают транспорт. Проверки процесса — `test/stdio.test.ts`.
Импорты схем Core/Contracts не дают права открывать хранилище напрямую.
Предметный инструмент использует Backend, а не собственный HTTP-клиент.
Исключение общего маршрута — реестр Server: Projects предоставляет общий server API
из project-runtime для чтения, регистрации и удаления регистрации.
Контракт HTTP находится в [server-runtime API](../../../packages/server-runtime/docs/API.md),
конфигурация — в [project-runtime](../../../packages/project-runtime/docs/CONFIGURATION.md).

## Карта реализации

| Файл                              | Ответственность                                                                                                                                                                                     |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/main.ts`                     | CLI, приоритеты флагов и окружения, сообщение запуска, SIGINT/SIGTERM. Текст идёт в stderr; JSON запуска с URL/PID — в stdout.                                                                      |
| `src/server.ts`                   | Проверка доступности Server перед стартом, loopback HTTP, путь /mcp, проверки Host/Origin, отдельный Server/transport на запрос, ожидание активных операций при остановке.                          |
| `src/projects.ts`                 | Свежий серверный реестр и выбор проекта на каждый вызов, только createHttpBackend. Нет глобального активного проекта и fallback на локальную базу.                                                  |
| `src/tools.ts`                    | Общие define/projectTool, строгие входные схемы, annotations, инструменты задач/продукта/реестра, обработчики tools/list и tools/call.                                                              |
| `src/entity-tools.ts`             | Чтение видов и сущностей, адреса, контекст, перемещение/связи задач; циклы регистрации create/update по картам схем Contracts; фасеты, обратное чтение, массовая квитанция и одна связь материалов. |
| `src/product-tools.ts`            | Предметные save-схемы из вариантов productMutationSchema, scope/contract, текст текущего результата.                                                                                                |
| `src/planning-tools.ts`           | Планирование, этапы, состав, перенос, релизы и их прогресс; явные аргументы поверх Backend.                                                                                                         |
| `src/schema-documentation.ts`     | Рекурсивное дополнение русских описаний JSON Schema, исключение для неизвестного недокументированного поля.                                                                                         |
| `src/output.ts`                   | content/structuredContent, ошибки бюджета и курсорная страница реестра.                                                                                                                             |
| `test/mcp.test.ts`                | Интеграция SDK Client и StreamableHTTPClientTransport с изолированными проектами и Server.                                                                                                          |
| `test/document-materials.test.ts` | Материалы через реальный Server: формат link, теги, фильтры, фасеты, массовая квитанция, одна связь, обратное чтение и `SERVER_INCOMPATIBLE` прежнего Server.                                       |

В `createTools` создаётся локальная Map определений и обработчиков. `define` строит
`z.strictObject(shape)`, преобразует через `z.toJSONSchema(schema,{io:"input"})`,
затем `documentToolSchema` и валидацию ToolSchema SDK. Неизвестное поле без описания
роняет построение **всего** набора, а не один будущий вызов.
Русские описания обязательны для аргументов, вложенных свойств и смысла элементов массивов.
JSON Schema не выражает все refine-проверки текста: пределы UTF-8 и предметные условия
нужно учитывать при сверке с исходной Zod-схемой.

`projectTool` выбирает backend и бюджет, формирует meta, выполняет обработчик и
передаёт Result в checked. Ошибки преобразуются в `{ok:false,error}` с isError;
неизвестное имя инструмента даёт протокольный InvalidParams. Не превращайте сетевой
отказ, неизвестный проект и пустую выборку в один результат.

## Динамические инструменты и совместимость

Создание регистрируется по `entityCreateDataSchemas`: product, feature, scenario,
application, implementation, task, document (7). Изменение — по
`entityUpdateDataSchemas`: те же виды плюс project (8). Это не все 11 читаемых видов:
board, work-plan и release не получают generic create/update автоматически.
Планы и релизы имеют собственные операции; этап остаётся частью плана.

Кроме этих циклов учитывайте динамические plan_start/complete/cancel,
plan_stage_create/update/remove/move, release_plan/cancel/publish,
прогресс пять product-save инструментов и четыре операции каталога материалов
(`entity_document_facets`, `entity_documents_list`, `entity_document_bulk`,
`entity_document_relate`), которые требуют capability `relay-document-materials-v1`. Полный пользовательский индекс
находится только в [MCP.md](MCP.md#индекс-инструментов); проверка должна получать
весь tools/list, а не искать строковые литералы в одном исходнике.

При изменении инструмента сначала определите намерение, явные аргументы и наблюдаемый
результат. Сохраняйте публичные имена и смысл полей. Не прячьте новое действие
в непрозрачный command; product_save — совместимый универсальный путь, не образец
для новых операций. Не добавляйте поля, которых нет в текущем контракте предмета.

Частичные update не должны получать defaults создания: пропуск сохраняет поле,
пустой массив или строка очищают только по контракту владельца. Сверяйте требование
ревизии не только по optional discovery: общая схема create/update может требовать
её условно внутри операции. Один вызов выполняет одно предметное действие;
согласование полей и отношений делает Core за серверной границей.

## Записи и представление ответа

`requestId` — корреляция, не дедупликация. Нет постоянных квитанций, replay-cache,
аудита каждого действия или сохранённых результатов. Текст результата текущего
вызова должен согласовываться с structuredContent, но не обещать прежний ответ при
повторе. После потери ответа пользователь читает текущее состояние и решает,
нужно ли новое действие; MCP не делает автоматических повторов записи.
Все записи имеют idempotentHint:false; публикация комментария — новое сообщение.

checked считает сериализацию полного CallToolResult, а не только data.
maxBytes принимает 1 КиБ–128 МиБ, начальный проектный бюджет берётся через Backend.
Курсорная страница реестра может уменьшить число элементов с корректным продолжением;
полный entity_context никогда не сокращается до успешного частичного графа.
Не вводите в него depth/offset/limit. Протокольная корректность structuredContent
не доказывает, что конкретный клиент показывает полные данные агенту.

## Добавление инструмента

1. Найдите предметный контракт и существующую операцию Backend. Если её нет,
   согласуйте работу у владельцев Core/HTTP, не копируйте правила в MCP.
2. Выберите существующее семейство, создайте строгую схему из Contracts,
   задайте прямые типизированные аргументы и русские описания. Проверьте вложенные
   массивы/варианты, required/optional/default, допустимость null и пустого значения.
3. Используйте общую регистрацию, Projects.withBackend, общую нормализацию ошибок
   и output.ts. Автор и проект принадлежат вызову, не состоянию клиента.
4. Обновите пользовательскую запись и индекс MCP.md. Поведение общего предмета
   меняйте у domain-владельца; покрытие интерфейсов — в единой CAPABILITIES,
   не в новой локальной матрице.
5. Проверьте полный discovery и необходимые сценарии чтения/записи, конфликта,
   неопределённого ответа, страниц, бюджета и изоляции. Для новых действий записи
   важны также создание, замена и снятие связей через то же предметное действие.

Изменения сгенерированного SDK выполняются через серверный OpenAPI и закреплённую
генерацию пакета rest-sdk, не ручной правкой операций в MCP.

## Проверки

Из корня checkout Relay:

```bash
pnpm run build:mcp
pnpm --filter @oim-dev/relay-mcp run typecheck
pnpm run test:mcp
```

Прямому запуску теста нужны сборки зависимостей. Отдельного lint-скрипта пакета нет.
Для проверки поставки используется `pnpm run package:check` из корня;
это отдельная более широкая проверка, а не обязательный запуск при чтении документации.

Проверка только metadata не требует Server, сети и базы: создайте createTools
с заглушкой Projects, соедините его с SDK Client через InMemoryTransport,
вызовите initialize/tools/list и закройте обе стороны. Нельзя вызывать tools/call
с такой заглушкой. Рекурсивно проверяйте descriptions, уникальность имён,
annotations и покрытие всех имён пользовательским индексом. Это проверяет
регистрацию, но **не** HTTP-транспорт, Backend и выполнение предметных операций.

Интеграционные тесты используют только изолированные данные и собственные процессы.
Они проверяют initialize/list/call, JSON Schema, полноту Markdown, страницы,
ошибки бюджета/сети, горячий реестр, разделение проектов и авторов. При изменении
поведения отдельно проверьте целевой MCP-клиент после обновления процесса и
переподключения: строку вызова, доступность полного содержания и понятность результата.
Не объявляйте эту проверку выполненной по одной сборке или in-memory discovery.

Для документационных изменений достаточно адресных prettier, git diff --check
и checkDocumentation из `apps/cli/scripts/lib/documentation.mjs` по своим Markdown.
Проверяйте также новые локальные ссылки, не возвращайте ссылки на прежние справочники.
Каталог apps/mcp/docs не включён в npm files: npm README использует HTTPS-ссылки
на канонические пути main, внутренний справочник — относительные ссылки репозитория.
Перенос тестовых путей и комплектация пользовательского скилла выполняются у их
владельцев; изменение Markdown само по себе не обновляет установленный пакет/скилл.
